# Nebokrai

`Nebokrai` — основной рабочий проект реконструкции серверной части исходной игры в чистый и поддерживаемый код.

Проект не копирует старые попытки целиком и не вводит новую игровую архитектуру без необходимости. Исходные owners, классы, структуры данных, протоколы, порядок действий и игровая семантика сохраняются настолько близко к оригиналу, насколько это подтверждается исходными материалами.

## Структура

`server/` содержит две изолированные реализации. `server/rust/` — активная Rust-реконструкция, а `server/cpp/` — сохранённая C++-реконструкция и дополнительный рабочий источник. У каждой реализации собственные build-файлы и source root; Rust и C++ не смешиваются в одном дереве:

```text
server/
├─ rust/
│  ├─ Cargo.toml
│  ├─ Cargo.lock
│  └─ src/
│     ├─ nets/
│     ├─ public/
│     ├─ setup/
│     ├─ dbaccess/
│     ├─ authserver/
│     ├─ loginserver/
│     ├─ billingserver/
│     ├─ miscserver/
│     ├─ worldserver/
│     ├─ gameserver/
│     ├─ updatesys/
│     ├─ manifest/
│     └─ main.rs
└─ cpp/
   ├─ CMakeLists.txt
   ├─ vcpkg.json
   ├─ apps/
   └─ src/
```

Новые каталоги и абстракции создаются только когда для них появляется реальная ответственность в проекте.

## Источники реконструкции

Источники имеют разные роли и не конкурируют между собой:

- `server/rust/src` — основной рабочий корпус поздней Rust-реконструкции: owner-пути, EXE/PDB, RVA, различия вариантов, подтверждённая семантика, готовый код, сохранённый RAW pseudocode и явно отмеченные недостающие факты;
- `server/cpp/src` и `server/cpp/apps` — более новый C++-проход, в котором уже материализованы связанные владельцы, исправления донора и технические замены библиотеками. Он служит дополнительным источником уже проделанной работы, но не подменяет доказательство контракта;
- `archive/Miracle_server_linux` — широкий C++-каркас предыдущей Linux-попытки: структура файлов, классы, связи, сигнатуры и большой объём уже написанных тел. Он ускоряет перенос формы и объёма, но местами существенно сломан и не считается источником истины сам по себе;
- оригинальные EXE/PDB и точечный анализ в Ghidra — арбитр для конкретных недостающих или спорных фактов. Ghidra не используется для повторного полного reverse owner-а, если нужное знание уже сохранено в поздней реконструкции.

Обычный проход выполняется целым Rust owner-файлом или связанной подсистемой, а не повторным расследованием каждой функции. Текущий C++-проход и старый C++-донор дают практическую реализацию и форму там, где она полезна; сохранённые Rust provenance и RAW определяют уже доказанную семантику. Результат остаётся нормальным современным Rust для Linux с сохранением подтверждённых контрактов оригинала.

В EXE/PDB и Ghidra возвращаемся только когда после совмещения Rust owner-а и C++-источников остаётся конкретное неизвестное, источники расходятся или требуется доказать layout, сигнатуру, вызов либо другую существенную деталь. Уже сохранённые факты повторно не доказываются, а код из донора не считается правильным автоматически только потому, что когда-то запускался.

## Библиотеки

Зрелые библиотеки используются для универсальных инженерных задач, которые не являются особенностью `Nebokrai`: сетевой I/O, логирование, форматирование, конфигурация, стандартное сжатие и хеширование, работа с БД и другие инфраструктурные задачи.

Специфические контракты `Nebokrai` библиотеками не подменяются. Собственный wire-протокол, форматы сообщений, игровые структуры, алгоритмы и другие особенности исходного сервера восстанавливаются явно.

Для БД текущая реконструкция также не исходит из будущей миграции на PostgreSQL или другой backend. Подтверждённый MSSQL/stored-procedure контракт оригинала сохраняется как baseline; Windows ADO и конкретный драйвер могут быть заменены технической Linux-реализацией. Миграция самой модели БД возможна только как отдельное последующее решение и не влияет на восстановление исходного поведения.

Критерий простой: особенность `Nebokrai` восстанавливается; универсальная инженерная задача по возможности передаётся подходящей зрелой библиотеке вместо новой самописной реализации.

Зависимости активной Rust-реконструкции объявлены в `server/rust/Cargo.toml`; за асинхронный runtime и транспорт отвечает Tokio, а MSSQL/TDS реализуется через Tiberius. `server/cpp/vcpkg.json` и `server/cpp/CMakeLists.txt` относятся к сохранённой C++-реконструкции.

## Документация кода

Основная документация реконструкции находится в самих owner-файлах. Верхний комментарий файла фиксирует происхождение, существенные подтверждённые особенности, важные различия вариантов, технические замены и оставшиеся неизвестности.

Отдельные карты, журналы прогресса, отчёты и вспомогательные `.md` не создаются без явной необходимости.
