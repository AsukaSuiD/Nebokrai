# Владение состоянием

Владелец состояния определяет, где операция выполняется и в каком порядке меняет данные. Это помогает выбрать место для нового поведения и не создавать две независимые копии одного игрового решения.

## Обязанности процессов

| Процесс | За что отвечает | Основной код |
| --- | --- | --- |
| Auth | Проверка учётной записи, очередь DB-запросов и результаты авторизации. | [Auth CGame](../../server/rust/src/authserver/src/cgame.rs) |
| Login | Клиент до входа в мир, ожидание Auth/GAS, CD-key, выбор мира и маршрутизация. | [Login CGame](../../server/rust/src/loginserver/loginserver/game.rs) |
| World | Мировой реестр персонажей, страны, организации, метаданные регионов, загрузка и сохранение. | [World CGame](../../server/rust/src/worldserver/worldserver/game.rs) |
| Game | Игроки и объекты региона, соединения игровых клиентов, движение, бой, навыки и NPC. | [Game CGame](../../server/rust/src/gameserver/gameserver/game.rs) |
| Billing | Баланс, покупка, обмен и обработка пополнений. | [Billing CGame](../../server/rust/src/billingserver/billingserver/game.rs) |
| Misc | Комната аукциона и её обмен с World. | [Misc CGame](../../server/rust/src/miscserver/miscserver/game.rs) |

## Почему World и Game разделены

Game должен быстро и последовательно обрабатывать события региона. World связывает персонажа с мировыми данными и БД, которые живут дольше отдельного пребывания в регионе. Поэтому Game изменяет живую фигуру, а World загружает и сохраняет её мировую проекцию.

Для нового поля персонажа это даёт конкретный путь работы: определить владельца значения, проверить его передачу между Game и World, затем чтение и запись в БД. Прямой SQL из игрового обработчика создаёт второй путь сохранения и меняет порядок относительно остальных действий. Причина сохранения этой границы и условия её пересмотра — [ADR-0005](../decisions/0005-world-game-boundary.md).

## Как персонаж попадает в игру

1. Login принимает запрос и выбирает путь проверки/продолжения входа: Auth, GAS, локальную проверку или ветвь уже указанного World. Условия собраны в [службах входа](../server/auth-login-and-services.md). Для отложенной проверки очередь связывает ответ с ожидающим клиентом.
2. World разрешает персонажа и загружает данные через свои DB-модули. В ответ Game получает адресованное сообщение `0x7F901`.
3. Game проверяет клиентский маршрут и ID, читает `GameSave`, создаёт игрока и готовит клиентский снимок.
4. После успешной сборки снимка Game ставит клиенту `0xBF401`, затем запрашивает баланс у Billing через `0xEF201`. Этот запрос не зависит от результата клиентской отправки; постановка не подтверждает доставку.

Точные поля и ветви отказа находятся в [протоколе входа Game](../protocol/game-login.md); переходы online/offline и возврат персонажа — в [жизненном цикле персонажа](../gameplay/player-lifecycle.md). В частности, отсутствие маршрута и дубликат ID не допускают успешного входа, а отрицательные статусы имеют собственные формы ответа.

## Что учитывать при изменениях

Межпроцессное сообщение передаёт данные и связывает этапы операции. Текущая реализация использует [исходное TCP-обрамление](../protocol/transport.md). Возможность иной внутренней доставки рассматривается отдельно: потребуется сохранить адресацию, порядок и поведение при потере соединения.

Очереди обрабатываются в определённых местах [серверного цикла](../server/runtime-ordering.md): Login читает World → Client → Auth, Game — World → Billing → Game-клиентов. Асинхронный результат должен вернуться своему владельцу в предусмотренную очередь.

Поздний отказ не отменяет уже отправленные сообщения и выполненные SQL-операции. Поэтому повтор операции требует понимания пройденных этапов; это особенно существенно для [сохранения](database.md).

Основания исходных маршрутов и их локальные неизвестные приведены в связанных страницах протокола, циклов и персонажа. Полная трасса World ↔ Misc и глобальный порядок между разными TCP-соединениями пока не установлены.
