# Сохранение состояния World

Сохранение отделяет два момента: изменение мира и попытку записать его состояние в БД. Между ними World собирает самостоятельный пакет данных. Game продолжает владеть региональной симуляцией, а DB-поток работает с переданными копиями. Из этого устройства следует, что успешная игровая операция, попадание в пакет и успешный SQL — разные результаты.

Эта страница описывает общий путь и обработку отказов. Состав персонажа — в [жизненном цикле игрока](../gameplay/player-lifecycle.md), маски организаций и параметры территории — в [мировых регионах](../gameplay/regions-and-organizations.md), границы соединений — в [БД](database.md).

## От живого состояния к пакету

У World нет универсального dirty-флага. Полный `CGame::generate_db_data` собирает данные так:

| Данные | Что попадает в пакет |
| --- | --- |
| Персонажи | Новые персонажи по creation-списку; затем копии всех существующих записей player-map. Проверки общего dirty-бита здесь нет. |
| Восстановление и удаление персонажей | ID восстановления и пары ID/время удаления из отдельных списков. |
| Фракции и союзы | Только организации с ненулевой маской изменений. После добавления копии маска живого объекта очищается. |
| Враждующие фракции | Полная копия списка отношений с оставшимся временем. |
| Регионы и страны | Снимки всех существующих объектов соответствующего обхода. |
| Почётные рейтинги | Отдельные копии history/current и календарного времени. |

Перед ними копируются счётчики ID игрока и сообщения организации. Порядок сборки задают `generate_db_data_player_prefix` и `generate_db_data` в [World CGame](../../server/rust/src/worldserver/worldserver/game.rs). Ветка `materialize_save_all_organizations_snapshot` не вызывает сборку персонажей и стран; её имя не означает принудительное сохранение всех организаций: она тоже передаёт `force_all = false`.

Для персонажа есть **две разные копии**. Сначала `clone_map_player` сериализует World `CPlayer` с дочерними данными и декодирует его в новый `CPlayer`. Сериализация попутно обновляет организационные и вычисляемые свойства исходного объекта. Позже, уже в save-потоке, `CPlayer::db_projection` и `PlayerDbProjection::save_snapshot` строят SQL-проекцию этой копии. Поэтому поле, добавленное только в DB-проекцию, может потеряться ещё при первом клонировании.

Накопитель `WorldDbData` содержит разные структуры: карту персонажей по unsigned ID, FIFO копий организаций и списки отдельных операций. `append_db_player` заменяет прежнюю копию того же ID; `append_db_creation_player` удаляет первое совпадение и добавляет новую копию в хвост. Это объединяет обновления только внутри текущего накопителя, а не между всеми уже запущенными сохранениями.

## Когда данные передаются worker-у

При обычном запросе World посылает Game `0x7F803`. Ответы `0x5FA03` обновляют мировые копии; маркер `-1` увеличивает счётчик завершений. После точного равенства числа ответов и подключённых Game запускается полная сборка. Это счётчик, а не множество ответивших серверов: повторный terminal-пакет не отсекается по ID отправителя. Подробности приёма находятся в `on_server_message` и `materialize_completed_save_response_snapshot` в [servermessage.rs](../../server/rust/src/worldserver/appworld/message/servermessage.rs).

Ручное немедленное сохранение и работа без подключённых Game могут собрать уже имеющееся состояние World, не ожидая этой доставки. После успешной сборки обычный путь очищает живые списки создания/восстановления/удаления/offline и удаляет из player-map тех, кто не состоит в login или online. Эта очистка происходит **до SQL**.

`take_save_data_owner` заменяет накопитель новым пустым `WorldDbData`. `take_save_thread_job` добавляет копии общих переменных, справочника предметов, honor ranks и параметров GodsBattle. Worker владеет старым пакетом целиком; изменения следующего прохода поступают в новый. DB I/O не удерживает живой `CGame`. Save-worker-ы и сборка через process save-контекст используют барьер сериализации; это не механизм транзакционного отката и не журнал повторов. Реализация: `WorldSaveThreadJob`, `WorldSaveWorker`, `WorldProcessSaveRuntime` в [game.rs](../../server/rust/src/worldserver/worldserver/game.rs) и [runtime.rs](../../server/rust/src/worldserver/worldserver/runtime.rs).

## Порядок записи

Основное место порядка — `DoSaveDataPhase` и `do_save_data_phases` в [savedb.rs](../../server/rust/src/worldserver/worldserver/savedb.rs). На открытом World-соединении выполняются 17 фаз:

1. Счётчики ID настроек.
2. Общие переменные.
3. Создание персонажей.
4. Восстановление персонажей.
5. Пометка удаления персонажей.
6. Удаление союзов.
7. Удаление фракций.
8. Сохранение фракций.
9. Сохранение союзов.
10. Параметры регионов.
11. Почётные рейтинги.
12. GodsBattle: faction XYD.
13. GodsBattle: принадлежность NPC.
14. Враждующие фракции.
15. Страны.
16. Largess / load details персонажей.
17. Сохранение персонажей.

Это последовательность операций со своими транзакционными границами. Ошибка поздней фазы не отменяет успешные ранние. Даже внутри персонажа отдельное сохранение JJC открывает собственное соединение; rollback основной транзакции его не отменяет. Для Largess настройка `use_old_save_largess_way` выбирает самостоятельный DB-вызов либо вызов с переданным соединением между `BEGIN TRAN` и `COMMIT`.

## Что означает результат

Обычный отрицательный SQL-результат и `Blocked...` ведут к разным действиям. `BlockedProjection`, `BlockedMissingFact` и блокировка публикации журнала останавливают соответствующий путь. Обычный `false` часто записывается в отчёт и допускает продолжение. Поэтому фраза «при ошибке save останавливается» неверна.

| Фаза | Действия после обычного результата |
| --- | --- |
| Создание, восстановление, удаление персонажа; сохранение персонажа | Успешная ветвь пытается сделать `COMMIT`, публикует журнал и удаляет элемент. При неуспехе пытается сделать `ROLLBACK`, если `BEGIN` не сообщил ошибку, и оставляет элемент в **этом пакете**. |
| Сохранение фракции или союза | После `true` и `false` выполняется `COMMIT`, затем копия удаляется. Типизированный блок прерывает этот путь до обычной очистки. |
| Удаление организаций | Выполняются попытки удаления и `COMMIT`; списки очищаются независимо от bool-результатов. |
| Регионы, страны | После попытки записи выполняется `COMMIT`; снимки расходуются независимо от bool-результата. |
| Враждующие фракции | После обычного результата выполняется `COMMIT`, весь переданный список уничтожается. |

Успешная ветвь персонажа определяется возвратом DB-метода, а ошибка самого `COMMIT` сохраняется отдельно как `commit_error`. Она не переводит ветвь `Saved` обратно в `Failed`. Некоторые итоговые сообщения `SUCCESS` содержат исходный размер списка, а не число подтверждённых SQL-записей. Для диагностики нужны конкретные `begin_error`, `save_returned`, `commit_error`, notices DB-модуля и стадия очистки; один итоговый текст недостаточен.

Оставленный элемент не гарантирует повтор на следующем цикле. `WorldSaveWorker::launch` сохраняет `retained_job` только если `save_thread_func` не вернул `Complete`. При обычном завершении пакет уничтожается вместе с оставшимися неуспешными записями. Ошибка открытия DB также проходит штатный финализатор без выполнения фаз. При блокировке пакет удерживается в `retained_jobs`; в некоторых блокирующих ветвях удерживается и guard сериализации. Автоматического возврата таких данных в новый накопитель или повторного запуска этого пакета в текущем worker-е нет. Это конкретное ограничение реализации, а не обещание доставки «хотя бы один раз».

## Повторное использование и добавление поля

По [ADR-0003](../decisions/0003-database-contract.md) и [ADR-0005](../decisions/0005-world-game-boundary.md) долговременная запись остаётся на стороне World/dbaccess. По [ADR-0007](../decisions/0007-reuse-existing-mechanisms.md) при одинаковых требованиях используется существующий механизм. Для нового мирового поля это `WorldDbData` → `WorldSaveThreadJob` → профильная фаза `savedb`, а для игрока дополнительно — уже существующее клонирование и `PlayerDbProjection`. Новый writer из игрового обработчика обойдёт эти границы.

Это правило повторного использования **не утверждает**, что все сегодняшние способы очистки и обработки ошибок оптимальны. Расходование копии после обычного SQL-неуспеха, отсутствие автоматического повтора и отдельное JJC-соединение — текущие свойства конкретных путей. Если новой операции нужна иная гарантия доставки или атомарности, это различие требований нужно явно описать; молча копировать либо менять семантику соседней фазы нельзя. Общая карта выбора — [общие механизмы](shared-mechanisms.md).

Начинайте с владельца значения и требуемого момента сохранения. Проследите одну цепочку целиком:

1. **Изменение.** Установите поле в живом объекте. Для организации отметьте нужную часть маски; новый setter без вызывающего его игрового пути ничего не сохраняет.
2. **Перенос между процессами.** Если значение рождается в Game, включите его в согласованные отправитель и декодер World. Учтите возврат, периодический сбор и повторный вход. Формат менять нужно с обеих сторон.
3. **Отделение копии.** Для игрока проверьте World encode/decode при `clone_map_player`, затем `db_projection`; для организации — выборочную `clone_save_data`. Для региона/страны измените соответствующий снимок.
4. **SQL.** Добавьте чтение и запись в DB-модуль, проверьте создание новой строки отдельно от обновления, тип, signedness, длину и единицы. Член структуры snapshot не означает, что SQL использует его.
5. **Результат и повторный вход.** Установите, когда копия расходуется, что делает `false`, как обрабатывается `COMMIT` и откуда загрузка восстановит значение. Нельзя исправить потерю данных одним восстановлением dirty-бита, не разобрав уже выполненный SQL и независимые соединения.

Для анализа отказа полезно зафиксировать ID объекта, путь сбора, выбранную маску, содержимое копии и первую неуспешную SQL-стадию. Затем отдельно проверить, остался ли объект в живой карте, в текущем накопителе или только в удержанном пакете. Это разные места хранения с разным временем жизни.
