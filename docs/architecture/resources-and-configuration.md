# Конфигурация и игровые ресурсы

У сервера есть настройки самого процесса, игровые таблицы и данные состояния. Они загружаются разными путями. Чтобы изменить значение, сначала нужно определить, где оно читается и как попадает к потребителю.

## Три вида данных

| Вид | Пример | Как используется |
| --- | --- | --- |
| Настройки службы | Адреса БД и серверов, порты, интервалы, `setup.ini` и отдельные дополнительные файлы | Читаются процессом из его runtime-каталога. |
| Игровые определения | Параметры персонажей, навыки, предметы, регионы, тексты | World загружает ресурс, строит таблицу и передаёт нужную проекцию Game. |
| Изменяемое состояние | Персонаж, предметы игрока, параметры мировой организации | Загружается и сохраняется через [модель БД](database.md). |

Поэтому изменение таблицы опыта и изменение опыта конкретного игрока требуют разных путей. Первое меняет определение правил, второе — состояние персонажа.

## От файла до игрового кода

```mermaid
flowchart LR
  data["Файл или пакет ресурсов"] --> read["Чтение байтов"]
  read --> parse["Разбор таблицы в World"]
  parse --> snapshot["Снимок для потребителя"]
  snapshot --> worker["Загрузка персонажей"]
  snapshot --> wire["Сообщение World → Game"]
  wire --> registry["Таблица в Game"]
  registry --> rule["Игровая механика"]
```

Основные ветви загрузки собраны в `CGame::reload` World, доступ к данным — в `WorldProcessResources`. [World reload](../../server/rust/realm/src/app/world_reload.rs) определяет порядок, [world_process_resources.rs](../../server/rust/realm/src/app/world_process_resources.rs) хранит ресурсы и публикует снимки для фоновых потребителей.

В этом пути `publish_player_load_snapshot` обновляет набор таблиц для загрузки персонажа: свойства, коэффициенты, предметы и параметры валюты. Поэтому исправление только живой таблицы World может быть недостаточным для следующей загрузки игрока. Это описание существующего пути передачи данных, а не утверждение о едином устройстве всех настроек сервера.

## Как выбирается пакет или обычный файл

[DefaultClientResourceOwner](../../server/rust/src/public/clientresource.rs) устанавливает корень и хранит активный [ResourceCatalog](../../server/rust/shared/src/resources/catalog.rs) из Shared. Каталог связывает `FilesInfo.ril` с доступными снимками пакетов. Открытие ресурса отделено от жизненного цикла World: библиотеке передаётся заимствованный `ResourceSource` с корнем и необязательным каталогом.

[open_resource](../../server/rust/shared/src/resources/source.rs) выбирает источник:

1. С установленным resource-контекстом путь приводится к ASCII lowercase, `/` заменяется на `\`, добавляется начальный `\`.
2. Если записи в индексе нет либо установлен младший бит `package_type`, файл открывается с диска относительно корня.
3. Иначе данные извлекаются из указанного пакета. Ошибка этой ветви не означает автоматическую повторную попытку чтения одноимённого файла с диска.
4. Результат представлен `CRFile`: единый курсор над памятью или файлом. Метод `read_data` продвигает курсор только при полном успехе; у других методов, например `read_to_stream`, свои условия.

Обрезка входа на первом NUL предшествует выбору ветви. Без установленного контекста открывается непосредственно переданный дисковый путь, без пакетной нормализации. С контекстом нормализация выполняется один раз; один поиск записи даёт и признак источника, и предел распаковки. Публичных обходных `read_packaged`/`read_loose` больше нет: загрузчики используют одну точку открытия.

Это объясняет ситуацию «положил изменённый файл рядом, но значение прежнее»: индекс может направлять чтение в пакет. Кроме того, сам пакет уже загружен в память. Требуется понять профиль reload и обновление resource-контекста.

Если `FilesInfo.ril` не загрузился, новый resource-контекст всё равно установлен, но без индекса; чтение обычных файлов остаётся доступным. Проверка наличия в индексе и фактическое открытие файла поэтому могут давать разные ответы. Для поиска skill-cache отдельно предусмотрен обход `SKILLS`, когда индекс не содержит нужный корень.

`ResourceOpenError` сохраняет отдельные причины: дисковую I/O-ошибку с путём, недоступный пакет, отсутствие записи внутри пакета, отказ декодирования и создания memory-курсора. Пакетные варианты содержат `package_type`. Shared не пишет журнал: серверный владелец добавляет корень и запрошенный путь, затем преобразует отказ в прежнее `None` для загрузчиков. Обычный дисковый `NotFound` остаётся сообщением debug; остальные отказы открытия — warn.

## Каталог и его установка

Граница выбрана по ответственности: чтение форматов не требует состояния World, а момент замены ресурсов зависит от запуска и reload конкретного сервера.

| Участник | Чем владеет и что делает |
| --- | --- |
| `ResourceCatalog`, Shared | Неизменяемый индекс и карта доступных пакетов. `load_directory(root)` читает `.ril`, открывает `.pak` и возвращает каталог вместе с отчётом. Не хранит глобальный корень и не публикует игровые таблицы. |
| `ResourceSource` / `open_resource`, Shared | Заимствует переданные корень и каталог только на время открытия; выбирает источник и возвращает курсор либо причину отказа. |
| `DefaultClientResourceOwner`, сервер | Хранит выбранный корень и установленный каталог, заменяет/освобождает контекст, пишет диагностику и обслуживает существующие загрузчики. Специфический поиск skill-cache остаётся здесь. |
| Владельцы таблиц и reload World | Разбирают полученные байты, применяют изменения и передают нужные представления потребителям. Успех открытия не означает готовность навыков или заданий. |

`load_directory` сохраняет прежний порядок: последний пакет с повторным ID задаёт имя; ID обходятся по возрастанию. Пустое имя пропускается, к непустому добавляется `.pak` в каталоге `Package`. Режим открытия остаётся `r+b`. Отказ индекса возвращает `ResourceLoadError`; отказ отдельного пакета попадает в `ResourcePackageLoad` и не отменяет загрузку остальных. Каталог поэтому может содержать запись файла, пакет которого недоступен. Клоны каталога разделяют снимки `.ril` и каждого `.pak`; сама карта ID клонируется.

Установка сохраняет прежние частичные эффекты: сначала освобождается старый контекст, затем устанавливается новый корень без индекса, после чего выполняется загрузка. Ошибка `.ril` не возвращает старый каталог. При успехе индекса владелец устанавливает полученный каталог и записывает отказы пакетов с ID, путём и причиной, а также числа `loaded`, `skipped`, `failed`. Это происходит и при первоначальной установке, где runtime не использует возвращаемый отчёт. Ошибки чтения каталога skill-cache, его записей и их типов тоже журналируются; доступные файлы продолжают собираться в прежнем порядке.

Происхождение каталога — World `CClientResource`, `public/clientresource.cpp/.h`; выбор источника происходит из `public/rfile.cpp` ([привязки](#происхождение-курсора)). Идентификаторы варианта World сохранены [ниже](#происхождение-чтения-пакета). Это перенос существующей Rust-реализации, без новых свидетельств по бинарнику. Исходный bool-возврат `LoadEx` остаётся `PARTIAL`; подробный Rust-отчёт не реконструирует его. Совместимое `Load package file OK!` по-прежнему вызывается World безусловно и не подтверждает успешную загрузку пакетов.

## Индекс FilesInfo

[FilesInfo](../../server/rust/shared/src/resources/filesinfo.rs) из `nebokrai_shared::resources` хранит версию `.ril`, записи пакетов и дерево метаданных ресурсов. Индекс неизменяем после построения, а клоны разделяют один снимок через `Arc`. `FileInfo` выдаётся по ссылке; отдельное глубокое клонирование поддеревьев не входит в интерфейс. Чтение файлов, связывание package ID и установка контекста разделены между участниками [загрузки каталога](#каталог-и-его-установка).

Текущий parser читает whitespace-токены: версию, записи пакетов, свойства корня и записи дерева. Имена пакетов сохраняют исходные байты, ключи дерева приводятся к ASCII lowercase. Тип записи `0x14` завершает каталог; другие ненулевые типы означают папку. Поля читаются в прежнем порядке, signed-поля сохраняются как биты `u32`. Повторное имя заменяет прежний дочерний узел. `file_count` считает обработанные файловые записи, включая впоследствии заменённые; это не число успешно открытых ресурсов и не признак готовности игры.

Поиск сохраняет прежние особенности пустого сегмента и корня. Для уже нормализованного сегмента используется заимствованный ключ `BTreeMap`, без промежуточного `Vec`; ASCII uppercase преобразуется только при необходимости. `find_file_list` сохраняет порядок ключей дерева и приводит к нижнему ASCII-регистру как корень, так и расширение. Эти операции не читают файловую систему и не выбирают дисковый fallback.

Приведение обоих аргументов подтверждено инструкциями `CFilesInfo::FindFileList` в `Nworldserver.exe`, VA `0x004d2ecb–0x004d2f33`: второй `_strlwr` применяется к расширению после первого `_free`. Продолжение после `_free` было пропущено в прежних границах функции Ghidra, из-за чего Rust и комментарий ошибочно сохраняли регистр расширения. Для ASCII этот факт — `VERIFIED`; поведение исходной локали для не-ASCII байтов здесь не установлено. Идентификатор сборки и совпадение EXE/PDB приведены в [основании сценарной загрузки](../gameplay/scripting.md#основание-загрузки-и-границы-проверки).

Ошибки `UnexpectedEnd`, `InvalidUnsigned`, `InvalidSigned` содержат `offset` — **байтовое смещение от начала `.ril`, начиная с нуля**. Ошибка числа указывает на начало токена, EOF — на конец входных данных с учётом оставшихся пробелов. `ResourceLoadError::FileInfoParse` добавляет путь; обработка отказа описана [в установке каталога](#каталог-и-его-установка). Эти ошибки относятся к Rust-парсеру; возвращаемое значение оригинального `CFilesInfo::Load` остаётся `UNKNOWN`.

## Снимок пакета

`nebokrai_shared::resources::PackageArchive` в [resources/package.rs](../../server/rust/shared/src/resources/package.rs) владеет неизменяемыми байтами `.pak` и разобранным индексом. Они объединены в один `Arc`: клонирование архива разделяет тот же снимок, а замена архивов у владельца ресурсов не меняет уже выданные снимки. Связь с `.ril` и установка контекста описаны [в каталоге](#каталог-и-его-установка); это соответствует [границе Shared resources](realm-and-zone.md#6-общие-компоненты-shared).

`from_bytes` принимает владение прочитанным `Vec` и проверяет заголовки и записи индекса. `extract_compressed` возвращает заимствованные запись и срез с проверкой размера и границ. Срез живёт в пределах заимствования архива; копии сжатого блока и записи индекса перед распаковкой больше нет. `extract_decoded` возвращает собственный буфер результата для `CRFile`: несжатая ветка копирует в него исходные байты, LZO/zlib пишут распакованные данные. Тип сжатия берётся из записи `.pak`, предел распаковки — из связанной записи `.ril`; эти поля не подменяют друг друга.

Внешние форматы и выбор ветвей при выделении сохранены. `AllocationFailed { requested }` обозначает отказ `try_reserve_exact` при подготовке выходного буфера; частичный результат не выдаётся. Это обработка ошибки Rust-аллокации, а не реконструкция старого кода возврата. Произвольный новый предел размера ресурса не вводился.

`PackageReadError` передаётся через `ResourceOpenError::Package` серверному владельцу. Остальные отказы и правила fallback описаны [в выборе источника](#как-выбирается-пакет-или-обычный-файл).

## Курсор ресурса

[CRFile](../../server/rust/shared/src/resources/rfile.rs) из `nebokrai_shared::resources` владеет буфером либо файловым дескриптором, объявленным размером и логической позицией. Курсор создаёт [open_resource](../../server/rust/shared/src/resources/source.rs); в Shared нет зависимости от World или состояния его загрузчиков.

`read_exact` возвращает причину ошибки, а совместимый `read_data` преобразует результат в `bool`. Оба продвигают логическую позицию только после полного чтения; при short read файла переданный выходной срез может быть заполнен частично. Переполнение и выход за объявленный размер отклоняются до чтения. `from_memory` возвращает ошибку для размера больше `u32`, вместо прежнего `expect`.

`into_bytes` потребляет курсор и возвращает **весь ресурс с начала**, независимо от его логической позиции. Для памяти это передача исходного `Vec` без копирования. Для файла — резервирование буфера с проверкой ошибки, позиционирование на начало и чтение ровно объявленного размера. Укороченный после открытия файл даёт ошибку, выросший не расширяет результат. `DefaultClientResourceOwner::read_resource` использует этот путь на новом курсоре: прежняя повторная аллокация и копирование распакованного ресурса удалены. Ошибка открытия/чтения по-прежнему даёт потребителю `None`; I/O-ошибки записываются с путём. Отсутствие необязательного файла отмечается на уровне debug.

`read_to_stream` — отдельный совместимый путь, его семантика при переносе сохранена: память публикует C-строку до первого NUL и сдвигает логическую позицию с wrapping; файловая ветвь использует текущую позицию дескриптора и возвращает `false` даже после успешной вставки. Новый `into_bytes` не используется вместо этого метода.

Общая [нормализация пути](../../server/rust/shared/src/resources/path.rs) вызывается на границе `open_resource`; байты вне ASCII не перекодируются. Особый алгоритм `ResourceCatalog::is_file_exist` сохранён отдельно: при отсутствии начального `\` он дописывает его в конец. Это проверка индекса для прежних вызывающих функций, а не проверка доступности файла или замена открытия.

Дисковые пути дополнительно проходят `resolve_resource_path` по [ADR-0012](../decisions/0012-resource-path-case.md): существующее точное имя имеет приоритет, иначе каждый компонент разрешается без учёта ASCII-регистра. Неоднозначность даёт ошибку. Это применяется к обычным ресурсам, `FilesInfo.ril`, открытию `.pak` и поиску корня skill-cache, включая различие `SKILLS`/`skills`. Ключи пакетов и выбор источника от этого не меняются; режим `r+b` открытия пакета сохранён.

### Происхождение курсора

## Форматы, байты и кодировки

Файлы с расширением `.ini` не обязательно используют стандартный формат секций и ключей. Некоторые парсеры читают позиционные записи. Нельзя заменить их универсальной INI-библиотекой без сопоставления конкретной грамматики.

[GlobeSetupSnapshot](../../server/rust/shared/src/resources/globesetup.rs) хранит общий блок размером `0x1114` байт. Типизированные методы читают известные поля из него; единое представление сохраняет связь игровых значений с передаваемыми байтами. Смысл неизвестных диапазонов не следует из их положения.

В текущем парсере `load_globe_setup` ожидает 549 записей, `load_game_setup` — 47 или 48. Первый строит новый кандидат, второй накладывает значения на копию существующего блока; замена активного блока происходит после успешного разбора. Это локальная гарантия парсера, а не общей операции reload.

Пакеты используют собственный индекс; данные могут быть несжатыми, LZO или zlib. [extract_decoded](../../server/rust/shared/src/resources/package.rs) выбирает ветвь по `compress_type`. Не следует путать эту компрессию ресурсов с сетевым [RLE](../protocol/transport.md).

Строковые таблицы хранят байты; их разбор и передача описаны [ниже](#таблица-текстов). [Подготовка runtime](../../deploy/hybrid/prepare-runtime.ps1) редактирует свои INI в Windows-1251; это не объявляет единую кодировку всех форматов сервера.

## Шаблоны персонажа

[CPlayerList](../../server/rust/shared/src/resources/playerlist.rs) содержит исходные характеристики персонажа, таблицу опыта, три набора улучшений и список стартовой экипировки. World/Realm выбирает файлы, разрешает текст уведомления через свою таблицу строк и передаёт Game снимок без стартовой экипировки; Game/Zone хранит отдельную копию определений для создания и развития живого игрока. Стартовая экипировка используется World при создании персонажа и не входит в снимок Game. Shared отвечает за грамматику и общий wire-формат, а не за выдачу предметов или начисление уровня.

`VERIFIED` для идентифицированных World `Nworldserver.exe`/`WorldServer.pdb` и Game `gameserver.exe`/`GameServer.pdb`: World `CPlayerList::AddToByteArray` от VA `0x0042C4D0` начинает снимок с количества и 0x58-байтных записей свойств, затем пишет количество/значения опыта и три таблицы улучшений в порядке Fighter → Hunter → Taoist. Game `DecordFromByteArray` VA `0x004C76B0–0x004C7C07` очищает карту свойств и вектор опыта **до** чтения первого count, но не очищает таблицы улучшений: полученные уровни заменяют соответствующие записи, отсутствующие сохраняются. Первые два count интерпретируются как знаковые для условия прохода, записи улучшений читаются по отдельным count; у строки уведомления NUL-граница. Rust при обрыве возвращает ошибку и оставляет применённый префикс, но безопасность такого отказа не является исходным результатом повреждённого буфера. Текстовые загрузчики и редкие некорректные значения требуют отдельной проверки перед утверждением полного совпадения.

Неиспользуемые методы прямого чтения файлов удалены при переносе. Текущий [World reload](../../server/rust/src/worldserver/worldserver/game.rs) уже читает их через ресурсный контекст и задаёт порядок нескольких файлов и частичных результатов; Shared не должен обходить этот выбор. Правила применения опыта и улучшений описаны на [странице развития](../gameplay/death-and-progression.md).

## Таблица эмоций

[Общий `CEmotion`](../../server/rust/shared/src/resources/emotion.rs) хранит формат `data/Emotions.ini` и передачу World → Game. Он находится в Shared, потому что Realm читает и сериализует таблицу, а Zone принимает ту же таблицу и использует её для проверки эмоции игрока. Экземпляры остаются разными: выбор ресурса, отправка selector `0x15` и время публикации принадлежат World/Realm; Game/Zone применяет полученный снимок. [Поиск маркера](../../server/rust/shared/src/resources/marker.rs) вынесен вместе с общим разбором токенов; старые потребители `public/readwrite.rs` временно используют его через прежнее имя.

`VERIFIED` для идентифицированных World `Nworldserver.exe`/`WorldServer.pdb` и Game `gameserver.exe`/`GameServer.pdb`: World `CEmotion::LoadSetup` VA `0x004A0CA0–0x004A0D99` ищет `*`, читает signed ID и значение, записывает их в map без предварительной очистки; отсутствие файла возвращает отказ, а открытый файл возвращает успех после обхода. `Serialize` VA `0x004A03F0–0x004A0476` дописывает число записей и пары ID/значение по порядку map через 32-битный `_AddToByteArray`. Game `Unserialize` VA `0x004D80C0–0x004D8115` читает count и пары, заменяя совпавшие ID без очистки; `IsEmotionRepeated` VA `0x004D7870–0x004D789E` возвращает значение либо ноль. Rust сохраняет уже применённые полные записи при обрыве входа; отрицательный count и нехватка байтов отклоняются на безопасной границе вместо небезопасного чтения оригинала. Неполный текстовый record также останавливает Rust с ошибкой, сохранив разобранный префикс; исходное поведение при таком повреждении не заявляется эквивалентным.

## Таблица HitLevel

[CHitLevelSetup](../../server/rust/shared/src/resources/hitlevel.rs) хранит определения из `data/hitlevel.ini` и их передачу World → Game. Формат находится в Shared, поскольку World/Realm готовит таблицу, а Game/Zone получает её и использует значения при обновлении серии убийств игрока. Владелец World выбирает источник, сообщает об отсутствии файла и отправляет selector `0x14`; Game хранит отдельный экземпляр. При изменении серии Game теперь читает общий срез записей без копирования всего каталога на каждый вызов.

`VERIFIED` для пары World `Nworldserver.exe`/`WorldServer.pdb` и Game `gameserver.exe`/`GameServer.pdb`: `LoadHitLevelSetup` World VA `0x004979C0–0x00497B2A` очищает прежний вектор **до** открытия файла, ищет `*` и читает три последовательных `unsigned long`; открытый пустой файл заканчивается успехом. `AddToByteArray` VA `0x00497550–0x004975AB` дописывает 32-битный счётчик и для каждой записи 12 исходных байт. `DecordFromByteArray` Game VA `0x004C5CB0–0x004C5D2D` очищает свой вектор до счётчика, копирует по 12 байт на положительный count и при нулевом или отрицательном count не добавляет записей. Поля в Rust называются `level`, `hit`, `experience`; использование `hit` и `experience` при [серии убийств](../gameplay/death-and-progression.md) остаётся игровой операцией Zone. На обрыве и неверном числовом токене Rust оставляет только полностью разобранные записи и возвращает ошибку; результат исходного загрузчика на повреждённом файле этим не утверждается.

## Таблица текстов


[StringTable](../../server/rust/shared/src/resources/stringtable.rs) хранит байтовые пары в `BTreeMap`, а [MyStringTable](../../server/rust/shared/src/resources/stringtable_wire.rs) содержит эту таблицу и кодирует/декодирует её передачу. Оба типа находятся в `nebokrai_shared::resources`: формат и представление нужны обеим ролям. Это не глобальная таблица — World и Game держат собственные экземпляры. Shared не выбирает файл, не очищает таблицу по событию reload, не рассылает сообщения и не пишет журнал.

Текстовый `load_bytes` пропускает ASCII whitespace и комментарии от `;` в начале записи до `\n`. ID собирается из ASCII букв/цифр; затем parser ищет открывающую кавычку, пропуская промежуточные байты. Значение читается до следующей прямой кавычки, без escape-обработки. Запись с пустым ID не добавляется. Существующая грамматика при выделении сохранена, включая поиск кавычки за границей строки; это не строгий INI-парсер. Повторный ID заменяет значение. Очистки перед чтением и отката уже применённых записей при ошибке нет.

`load_bytes` возвращает `Result<(), StringTableParseError>`. Ошибка содержит ID, `record_offset` начала записи и `offset` места отказа — байтовые смещения от начала входа, начиная с нуля. Обе существующие ветви отказа достигают конца входа, поэтому `offset == source.len()`: `MissingValue` означает отсутствие байтов после найденной открывающей кавычки либо отсутствие самой кавычки; `MissingClosingQuote` — отсутствие закрывающей. Начало записи сохраняется отдельно, чтобы найти ошибку и при пустом ID. Ошибочная пара не вставляется; ранее вставленные/заменённые пары остаются.

Прежний `last_error` сохраняет текст для существующих сообщений загрузчика. Успешное чтение и `free` не очищают его; результат текущей загрузки определяется `Result`, а не наличием старого текста. World при отказе пишет путь, оба смещения, вид ошибки, ID и размер оставшейся таблицы, затем формирует прежний `FAILED`-отчёт. Размер таблицы может включать записи предыдущего языкового файла и не означает число записей, прочитанных до текущей ошибки.

Текущее представление передачи: little-endian `i32` количества, затем пары NUL-terminated байтовых строк в порядке ключей `BTreeMap`. Encoder дописывает в переданный буфер и отклоняет количество, не помещающееся в `i32`, до записи. Decoder принимает неположительное количество без чтения пар, возвращает число использованных байтов и не требует исчерпания всего входа. Он вставляет пару только после чтения обоих её полей; дубликат заменяет значение. При обрыве возвращаются поле, индекс пары, смещение относительно переданного payload и число доступных байтов; уже применённый префикс остаётся. Диагностические счётчики возвращаются вызывающему владельцу и не входят в сообщение.

Порядок очистки задают серверные владельцы:

| Путь | Порядок и частичный результат |
| --- | --- |
| World `update_string_table` | Очищает таблицу и буфер передачи, читает `data/Language.lag`, затем настроенный языковой пакет. Переданный аргумент `requested_package` сохраняется в отчёте, но не выбирает файл. После успеха кодирует и рассылает `0x7F807`; поздний отказ не восстанавливает прежнюю таблицу. |
| Game `create_string_table` | Очищает таблицу **перед** вызовом декодера. После успеха пишет журнал и продвигает внешний курсор на `consumed`. При отказе курсор не продвигается, но декодированные пары уже остаются в очищенной таблице. |
| Сам `MyStringTable::from_byte_array` | Не очищает таблицу. Это свойство кодека, а не обещание сохранения старых записей при получении сообщения в Game. |

Привязки перенесены из прежних Rust-файлов: `public/stringtable.cpp/.h`, `public/mystringtable.cpp` с объявлением в `public/stringtable.h`. Для текстового пути World сохранены RVA конструктора `0x0004E570`, разбора `0x0004E5E0`, файловой перегрузки `0x0004EA30`, очистки `0x0004E020`, поиска `0x0004D8F0`; для Game `MyStringTable::fromByteArray` — `0x0002A910`. ## Начальная конфигурация Game и reload

World отправляет каталоги и настройки последовательностью конфигурационных сообщений. Основной контейнер — `0x7F801` с селектором: например, предметы `0x00`, игроки `0x01`, монстры `0x02`, навыки `0x06`, Globe `0x07`, задания `0x16`. Отправку собирают [World servermessage](../../server/rust/src/worldserver/appworld/message/servermessage.rs) и World `CGame`; [Game servermessage](../../server/rust/src/gameserver/appserver/message/servermessage.rs) выбирает соответствующий декодер.

Reload имеет независимые параметры перечитывания resource-контекста и отправки обновлений Game. У каждого профиля собственный порядок и собственная реакция на отсутствующие файлы.

Например, профиль Globe загружает `globesetup.ini`, разрешает тексты стран, накладывает `gamesetup.ini`, читает `AuctionList.ini` и обновляет router. Отправка селектора `7` зависит от успеха нужных загрузок и флага рассылки; снимок для загрузки персонажей обновляется отдельно. Поздний отказ не отменяет все предыдущие стадии.

Порядок reload строк, очистка при получении в Game и частичные эффекты описаны [в таблице текстов](#таблица-текстов).

## Как добавить параметр или найти неприменившееся изменение

Для существующего пакетного ресурса используйте `DefaultClientResourceOwner` и `CRFile`, чтобы сохранить выбор источника и распаковку. Для совместимого поиска маркеров уже есть `readwrite::read_to`, для декодирования `setup.dat` — `tools::ini_decode`; ссылки и границы собраны в [общих механизмах](shared-mechanisms.md). Грамматика конкретной таблицы остаётся у её парсера. Ни двоичный блок Globe, ни частичное применение строковой таблицы не объявляются универсальным форматом новой конфигурации.

Проследите источник → parser → активную таблицу → снимок/сообщение → потребителя. Для нового параметра проверьте размер и тип, обязательность/default, поведение ошибки и обновление всех нужных представлений. Если поле участвует в wire, согласуйте запись World и чтение Game.

Для существующего значения полезно последовательно проверить: нужный runtime-каталог, выбор package/обычного файла, завершение парсера, условия рассылки, селектор Game и место чтения значения механикой. Это позволяет искать конкретную потерянную стадию, не повторяя полный анализ всех ресурсов.
