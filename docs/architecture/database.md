# Данные и владение БД

Исходная модель сервера опирается на MSSQL и хранимые процедуры. Активная реконструкция сохраняет этот контракт; Linux-код заменяет Windows ADO/COM на Tiberius, но не объявляет миграцию схемы. Граница описана в [`README.md`](../../README.md) и закреплена в конкретных владельцах [`dbaccess/`](../../server/rust/src/dbaccess/mod.rs).

## Кто обращается к данным

| Область | Владелец в коде | Ответственность |
| --- | --- | --- |
| Учётная запись и Auth | [`dbaccess/authdb`](../../server/rust/src/dbaccess/authdb/) | Проверки, результаты авторизации и операции, которые исходный AuthServer отправлял DB worker-ам. |
| Login/CD-key | [`dbaccess/logindb`](../../server/rust/src/dbaccess/logindb/) | CD-key, локальный пароль, ограничения IP, matrix-card и сопутствующие операции входа. |
| Оплата | [`dbaccess/dbbilling`](../../server/rust/src/dbaccess/dbbilling/) | Счёт, покупка, обмен и очередь пополнений BillingServer. |
| Мир и персонаж | [`dbaccess/worlddb`](../../server/rust/src/dbaccess/worlddb/) | Игроки, предметы, регионы, страны, организации и иные сохраняемые мировые данные. |

[`WorldServer`](../../server/rust/src/worldserver/worldserver/game.rs) собирает состояние и запускает работу с БД; [`savedb.rs`](../../server/rust/src/worldserver/worldserver/savedb.rs) распределяет snapshots между конкретными DB owners. Живая симуляция региона остаётся у [`GameServer`](../../server/rust/src/gameserver/gameserver/game.rs); запись персонажа не превращается в прямой SQL-вызов из его игрового `CGame`. Это сохраняет границу сообщений World ↔ Game и один владелец мирового сохранения.

## Контракты важнее драйвера

Замена ADO/COM на Tiberius допустима там, где это только способ выполнить тот же запрос. Значимыми остаются имя процедуры, параметры и их типы, порядок вызовов, отдельные соединения, результат ошибки и уже выполненные действия. Например, [`CRsCDKey`](../../server/rust/src/dbaccess/logindb/rscdkey.rs) сохраняет отдельные соединения и исходную нетранзакционную последовательность проверки и изменения ban. [`CRsPlayer`](../../server/rust/src/dbaccess/worlddb/rsplayer.rs) сохраняет порядок полей и частичных эффектов игрока. [`savedb.rs`](../../server/rust/src/worldserver/worldserver/savedb.rs) не превращает все мировые операции в одну общую транзакцию: поздний отказ не отменяет автоматически успешный префикс.

Важный пробел: найденные резервные копии LoginDB и Account не содержат исходной `userinfo`. Контракт некоторых запросов подтверждён EXE/PDB, но точная схема этой таблицы неизвестна — это прямо указано у [`CRsCDKey`](../../server/rust/src/dbaccess/logindb/rscdkey.rs). [Локальный скрипт стенда](../../deploy/hybrid/database-init.sh) создаёт представление с нужной Login-проекцией поверх BillingDB, чтобы иметь рабочую локальную форму данных. Представление является **технической подстановкой стенда**, а не доказательством исходной схемы или поведения всех ветвей входа.

## Локальные материалы

Для гибридного стенда нужны пять `.bak` в локальном `runtime/Database`; каталог исключён из Git. [`database-init.sh`](../../deploy/hybrid/database-init.sh) восстанавливает базу только если её ещё нет в постоянном томе. Поэтому конфигурация контейнеров и фактическая версия БД могут различаться после замены backup. Состав стенда и ограничения запуска описаны в [операционном документе](../operations/hybrid-runtime.md), а статус проверки живых сценариев — в [аудите готовности](../status/audit.md).

## Владелец операции и снимок состояния

«Владелец» означает место, где определяется порядок действий и побочных эффектов, а не единственное физическое SQL-соединение. DB worker может выполнить запрос асинхронно, но не должен менять очередность доменных стадий. World формирует снимки изменяемого состояния до передачи DB-owner-у; при остановке save barrier завершается прежде, чем освобождаются нужные worker-у игровые владельцы. Статус этой схемы `VERIFIED` по точным World EXE/PDB и верхним контрактам [`game.rs`](../../server/rust/src/worldserver/worldserver/game.rs) / [`savedb.rs`](../../server/rust/src/worldserver/worldserver/savedb.rs). Успешный runtime-проход текущего Nebokrai ещё не проверен.

## Порядок мирового сохранения

`DoSaveData` проходит 17 фаз в следующем порядке: IDs настроек → общие переменные → новые персонажи → восстановленные персонажи → удалённые персонажи → удалённые союзы → удалённые фракции → сохранение фракций → сохранение союзов → регионы → honor ranks → GodsBattle faction XYD → GodsBattle NPC factions → враждующие фракции → страны → Largess/load details → сохраняемые персонажи. Это `VERIFIED` для исходного оркестратора `worldserver/savedb.cpp/.h` (точная World EXE/PDB) и [`DoSaveDataPhase`](../../server/rust/src/worldserver/worldserver/savedb.rs). Фазы не являются произвольными группами запросов: поздняя стадия может использовать ID/состояние предшествующей, а отказ сохраняет уже выполненный префикс.

Внутри owner-а локальная транзакция может существовать для **своей** операции (`BEGIN TRAN`/`COMMIT`/`ROLLBACK` есть в `savedb.rs`). Это не делает весь `DoSaveData` одной атомарной транзакцией. Судьба элемента очереди при ошибке зависит от того, извлечён ли он до SQL-запроса: уже pop-нутый не возникает обратно автоматически, а оставленный до успеха может достаться следующему проходу. Статус `VERIFIED` для достигнутых очередей; позицию pop конкретной фазы следует читать в её owner-е. Ошибки представлены фазовыми `Blocked...` результатами, а повторение всего сохранения с начала без анализа выполненного префикса может удвоить эффект.

## Границы отдельных баз

Login/CD-key использует отдельное соединение на операцию. Для `CDKeyBan` подтверждён нетранзакционный порядок `SELECT WITH(NOLOCK) → UPDATE/INSERT`. При гонке он не эквивалентен атомарному UPSERT; техническая замена может параметризовать SQL, но не молча менять duplicate/ban-семантику. `IPIsAllowed` и `IPIsForbidded` при SQL-ошибке оба возвращают `false`: allow-проверка закрывается, forbid-проверка не запрещает. `IsBetweenIP` имеет исходную странность: `true` соответствует как найденному диапазону, так и EOF успешно прочитанного result set. Эти исходы `VERIFIED` в [`rscdkey.rs`](../../server/rust/src/dbaccess/logindb/rscdkey.rs) по Login EXE/PDB; нельзя заменять их предположением о «разумном» поведении.

Billing обслуживает баланс, покупку и обмен через [`rsplayeraccount.rs`](../../server/rust/src/dbaccess/dbbilling/rsplayeraccount.rs); ожидающие пополнения выбираются из `TBL_NeedUpdate` по `ID` максимум по 50 и затем удаляются как обработанный набор в [`rsplayerfillmgr.rs`](../../server/rust/src/dbaccess/dbbilling/rsplayerfillmgr.rs). Основной и cash-log SQL endpoint-ы конфигурируются отдельно. Статус этих конкретных операций `VERIFIED` по Billing EXE/PDB и DB owners; атомарность полного цикла «покупка → уведомление клиента» здесь `UNKNOWN` без полной трассы.

`CRsPlayer` сохраняет фиксированный порядок equipment-полей `HELM, BODY, GLOV, BOOT, WEAPON, BACK, HEADGEAR, FROCK, WING, MANTEAU, FAIRY` и исходную 32-битную арифметику. Его `GetPlayerDeletionDate` различает `0` и catch-result `-1`; caller считает `-1` ненулевым timestamp. Статус `VERIFIED` по World EXE/PDB и [`rsplayer.rs`](../../server/rust/src/dbaccess/worlddb/rsplayer.rs). Полная таблица полей игрока, единиц и миграций остаётся `PARTIAL`.
