# Данные и доступ к БД

Сервер использует существующую MSSQL-модель: таблицы, процедуры и бинарные поля участвуют в игровой логике. Tiberius заменяет подключение через Windows ADO/COM; он не переносит автоматически модель на новую схему. Поэтому при изменении запросов важны типы параметров, порядок действий, отдельные соединения и частичные результаты. Причина этого выбора и его последствия закреплены в [ADR о БД](../decisions/0003-database-contract.md).

## Где проходит граница

Game меняет живое состояние региона. World принимает его проекции, ведёт мировые объекты и передаёт отделённые данные DB-потоку. Это позволяет выполнять SQL без доступа worker-а к живому игроку. Полный механизм «изменение → снимок → очередь → SQL → очистка или удержание» описан в [сохранении World](persistence.md); там же находятся порядок фаз и маршрут добавления поля.

Доступ к БД разделён по служебным задачам:

| Задача | Точка входа | Особенность |
| --- | --- | --- |
| Авторизация учётной записи | [authdb](../../server/rust/src/dbaccess/authdb/) | DB-операции Auth и их результаты для входа. |
| CD-key и ограничения Login | [CRsCDKey](../../server/rust/src/dbaccess/logindb/rscdkey.rs) | Самостоятельные операции проверки account, IP, ban, локального пароля и matrix-card. |
| Баланс и оплата | [rsplayeraccount](../../server/rust/src/dbaccess/dbbilling/rsplayeraccount.rs) | Операции счёта, покупки и обмена; основной и cash-log endpoints задаются отдельно. |
| Персонажи и мировой прогресс | [worlddb](../../server/rust/src/dbaccess/worlddb/) | Игрок, предметы, регионы, страны, организации, рейтинги и специальные мировые системы. |

Внутри World `savedb` определяет последовательность и время жизни пакета, а конкретный DB-модуль знает запросы своей операции. Trait вроде `RsPlayerOwner` описывает этот вызов, реализация `TiberiusRsPlayer` исполняет его. Само слово owner не означает одно физическое соединение для всех действий. По [ADR-0007](../decisions/0007-reuse-existing-mechanisms.md) новое обращение с теми же требованиями использует подходящий DB-модуль и существующую передачу снимка; отдельное соединение или writer не создаётся только ради новой функции. Существующие исключения ниже описывают текущий код и не задают универсальную схему доступа.

## Персонаж хранится в нескольких проекциях

`TiberiusRsPlayer::save_player` пишет последовательно базовую строку, способности, задания и предметы. Состав задаёт `PlayerSaveSnapshot`: `base`, `abilities`, `quest`, `goods`. Вложенные ID должны относиться к одному персонажу. Базовая строка содержит в том числе имя, уровень, профессию, пол, страну, внешний вид, регион и проекцию экипировки; ability-часть включает игровые значения и составные данные. Детали преобразования находятся в [PlayerDbProjection](../../server/rust/src/worldserver/appworld/player.rs) и [rsplayer.rs](../../server/rust/src/dbaccess/worlddb/rsplayer.rs), жизненный цикл — [отдельно](../gameplay/player-lifecycle.md).

Порядок полей экипировки фиксирован: `HELM, BODY, GLOV, BOOT, WEAPON, BACK, HEADGEAR, FROCK, WING, MANTEAU, FAIRY`. Имена передаются в DB через Windows-1251 и видимый префикс до NUL. Нельзя автоматически заменить эти представления сериализацией произвольной Rust-структуры.

Загрузка не является простым обратным вызовом save: `load_player` читает ability, задания, предметы, затем JJC и применяет их к создаваемому `CPlayer`. Базовая таблица также обслуживает учёт персонажей и их краткие данные. Новое значение, записанное только в `CSL_PLAYER_BASE`, не становится от этого частью полной загрузки персонажа.

Отдельные строки могут иметь разные правила отсутствия. При сохранении player base/ability отсутствие строки даёт неуспех. [Регион](../../server/rust/src/dbaccess/worlddb/rsregion.rs) сначала ищет `RegionID` и выбирает UPDATE либо INSERT. [Страна](../../server/rust/src/dbaccess/worlddb/dbcountry.rs), напротив, при отсутствии строки в `CSL_Countrys` возвращает `true` без INSERT. Следовательно, «save вернул true» нельзя использовать как универсальную проверку существования данных.

## Транзакция ограничена соединением

`DoSaveData` не является общей транзакцией мира. Более того, сохранение abilities вызывает `RsJjcSysOwner::save_jjc_data`, а [TiberiusRsJjcSys](../../server/rust/src/dbaccess/worlddb/rsjjcsys.rs) открывает собственное соединение. Если следующий save заданий или предметов завершится неуспешно, rollback caller-соединения не отменяет уже выполненную запись JJC.

Такая же внимательность нужна при замене последовательности запросов одной процедурой: это может изменить блокировки, дубликаты и уже выполненный префикс. Например, `CRsCDKey::CDKeyBan` использует `SELECT WITH(NOLOCK)` перед UPDATE/INSERT без общей транзакции. Это не атомарный UPSERT. `IPIsAllowed` и `IPIsForbidded` при SQL-ошибке оба возвращают `false`; `IsBetweenIP` возвращает `true` и при найденном диапазоне, и при EOF успешно прочитанного результата. Эти правила задаёт текущий [rscdkey.rs](../../server/rust/src/dbaccess/logindb/rscdkey.rs); заменять их «обычной» политикой проверки нельзя незаметно для вызывающего кода.

Для удаления персонажа `GetPlayerDeletionDate` различает `0` и результат catch `-1`; вызывающий код может трактовать `-1` как ненулевое время. Для Billing очередь пополнений [rsplayerfillmgr](../../server/rust/src/dbaccess/dbbilling/rsplayerfillmgr.rs) читает `TBL_NeedUpdate` по `ID` максимум по 50 записей и затем удаляет обработанный набор. Атомарность полного пути «изменение счёта → уведомление клиента» остаётся отдельным вопросом; её не доказывает успех одного запроса.

## Схема и локальный стенд

Точный DDL исходной `userinfo` остаётся `UNKNOWN`: найденные резервные копии LoginDB и Account её не содержат. [database-init.sh](../../deploy/hybrid/database-init.sh) создаёт для локального стенда представление с Login-проекцией поверх BillingDB. Это техническая подстановка, а не восстановленная исходная таблица; ограничения указаны также в `rscdkey.rs`.

Пять резервных копий `.bak` для стенда хранятся в локальном `runtime/Database` вне Git. Скрипт восстанавливает базу только при её отсутствии в постоянном томе. Поэтому замена файла backup не означает обновление уже существующей БД. Подготовка описана в [эксплуатации](../operations/hybrid-runtime.md), фактические результаты проверок — в [состоянии проекта](../status/audit.md).

При поиске ошибки начните с конкретного DB-метода и его caller-а. Проверьте, какое соединение передано, что означает bool/typed-result, проверяется ли число строк и кто завершает транзакцию. Верхний комментарий файла помогает найти происхождение восстановленного правила; фактическую запись определяют используемый SQL и привязка параметров.
