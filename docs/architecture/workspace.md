# Устройство рабочего пространства

[`README.md`](../../README.md) задаёт устойчивое назначение проекта. Здесь описано, куда идти за конкретной частью и почему материалы разделены. [Модель владения](state-ownership.md) фиксирует, кто вправе менять живое, глобальное и сохраняемое состояние.

| Путь | Назначение | Почему отдельно |
| --- | --- | --- |
| [`server/rust/`](../../server/rust/) | Активная реконструкция серверных процессов под Linux; зависимости и бинарные входы заданы в [`Cargo.toml`](../../server/rust/Cargo.toml). | Поведение игры восстанавливается в одном Rust module graph, без зависимости от старого C++ runtime. |
| [`server/cpp/`](../../server/cpp/) | Более новый C++-проход со своими [`CMakeLists.txt`](../../server/cpp/CMakeLists.txt) и [`vcpkg.json`](../../server/cpp/vcpkg.json). | Служит рабочим техническим источником и самостоятельной реализацией; наличие тела функции здесь само по себе не доказывает точное поведение оригинала. |
| [`deploy/hybrid/`](../../deploy/hybrid/) | Рецепт локального смешанного стенда: часть служб на Rust, GameServer через Wine. | Способ запуска не определяет полноту активной реконструкции и не превращает старый EXE в исходный код. |
| `runtime/` | Локальные конфигурации, ресурсы, резервные копии БД и бинарники для стенда. | Каталог исключён из Git в [`.gitignore`](../../.gitignore); его содержимое зависит от машины и не должно попадать в репозиторий. |
| `.exe/`, `ghidra/` | Локальные оригинальные EXE/PDB и данные анализа. | Это исходные свидетельства, а не часть поставляемого кода; оба пути также исключены из Git. |
| `server/references/`, `related/Luvinia/` | Локальные неизменяемые снимки оригинала, прежних реализаций и родственной игры. | Их [разные доказательные роли](../reconstruction/sources.md) не смешиваются с активным кодом и не отправляются в Git. |

## Внутри Rust-сервера

[`src/lib.rs`](../../server/rust/src/lib.rs) собирает общий граф модулей. [`src/bin/`](../../server/rust/src/bin/) содержит тонкие бинарные входы; их логика находится в [`src/process/`](../../server/rust/src/process/). Остальной код организован по владельцам исходных серверов:

- `authserver/`, `loginserver/`, `billingserver/`, `miscserver/`, `worldserver/`, `gameserver/` — поведение отдельных серверных областей;
- `dbaccess/` — владельцы операций с БД, сгруппированные по историческим сервисам;
- `nets/` и `transport/` — сетевые владельцы и транспортные правила;
- `setup/` — чтение исходных настроек и таблиц;
- `public/` — общие структуры и контракты сообщений.

Размер каталога или число перенесённых файлов **не** равны готовности процесса: часть owners содержит только доказанные фрагменты, а запуск зависит от того, связаны ли они в полный жизненный цикл. Папки `updatesys/` и `manifest/` присутствуют в дереве, но [`lib.rs`](../../server/rust/src/lib.rs) их не подключает; `manifest/` содержит служебные TOML-файлы, а `updatesys/` — сохранённые owner-файлы без отдельного бинарного входа.

## Где искать подтверждение

Для конкретного поведения сначала читайте тематический документ: [владение состоянием](state-ownership.md), [порядок циклов](../server/runtime-ordering.md), [протокол](../protocol/transport.md) или [игровую модель](../gameplay/simulation.md). Если там стоит `PARTIAL`/`UNKNOWN`, открывайте верхний комментарий нужного Rust owner-файла, затем сверяйте C++-проход и первичные материалы по [правилам реконструкции](../reconstruction/evidence-and-contracts.md). Для состава процессов смотрите [модель процессов](../server/process-model.md); для локального стенда — [гибридный runtime](../operations/hybrid-runtime.md).
