# Клиентский wire-runtime: evidence локального клиента

Эта страница — доказательная база машинного разбора локального игрового клиента. Она фиксирует идентификаторы сборки, опорные точки разбора и пределы выводов; поведенческие контракты остаются на своих страницах ([заголовок](../protocol/message-header.md), [игровой вход](../protocol/game-login.md), [каталог исходящих команд](../protocol/client-outgoing-catalog.md)). Роль клиента как внешней границы совместимости определена в [значениях и совместимости](../architecture/values-and-compatibility.md#клиент-как-внешняя-граница-совместимости) и здесь не дублируется.

Все адреса — VA при ImageBase `0x00400000`.

| Диспетч входящих game-сообщений, ветвь `0xBF402` | сравнение `0x54A0D1` → `0x54AD3D` | где клиент принимает validate-кадр дрейфа |
| Обработчик `0xBF402` | `0x54AD3D..0x54ADA2` | три `GetLong` (`0x43B440`), запись пар в app-поля, флаг готовности |
| Глобальное состояние drift-пар | app+`0x167C` (накопитель), `0x1680`, `0x1684`, `0x1688`; флаг `0x1678` | состояние, которое штампует отправку |

| Обработчик `0xBF403` | `0x54B020..0x54B039` | вызывает сброс и десериализатор последовательности |
| Сброс последовательности | `0x43D730` | обнуление статики, индекс `-1` — зеркало серверного ctor |
| Десериализатор последовательности | `0x43DA60`; статика `0x6F9180/84/88`, vector `0x6F9190/94/98` | (индекс, count, элементы) — зеркало серверного `CSequenceString::Serialize` |

Серверная пара игры (`gameserver.exe`, точная сборка по существующему манифесту): отправитель `0xBF402` — `0x49F63F..0x49F6C7` (три `AddLong`: `player_id`, `timeGetTime()`, `time()`); отправитель `0xBF403` — `0x49F6CC..0x49F8F3` (payload ровно `CSequenceString::Serialize`, без ведущих слов); `CSequenceString::Serialize` — `0x42A3D0`.

## Установленный контракт и его пределы

1. **Отдельного ответа-опкода на validate-кадры нет.** Клиент отвечает словами `+0x08`/`+0x0C` заголовка исходящих game-сообщений; `+0x08` — накопленная оценка серверного uptime, `+0x0C` — очередной элемент последовательности. Статус: `VERIFIED_DISASSEMBLY`.
2. **Серверной проверки штампов в парной сборке нет.** По `gameserver.exe` прямые обращения к картам `CGame+0x198`/`+0x1A4` найдены только в сопровождении (создание/уничтожение карты, `Append…`, удаление записей, clear); ветка чтения/сравнения входящих слов в достигнутом разборе не найдена. Статус: `VERIFIED_DISASSEMBLY` для отсутствия в достигнутом охвате; охват реестра обращений высокий, но **не byte-exhaustive** — косвенные пути через указатель на карту отдельным доказательством не исчерпаны.
3. Семантика `+0x08`/`+0x0C` установлена только для направления клиент → Game. Auth/Billing/Misc/World направления здесь не разбирались; их смысл остаётся `UNKNOWN`.

## Ведущая строка `0x8F801` = account

Цепочка, поднявшая статус с `INFERRED`:

- Отправитель `0x8F801` клиента (VA выше) пишет перед `i32` аргументом C-строку `std::string` глобального app по `+0x80`.
- Та же строка по `+0x80` пишется первым полем обоих отправителей `0x2FD09` (инлайн SSO-чтение в одном сайте, accessor `0x4040D0` — в другом).
- Парный приёмник: оригинальный `LoginServer/loginserver.exe` (sha256 по `_loginserver_export_manifest.toml`), case `0x2FD09` по VA `0x48038E` читает первое поле payload через `GetStr(buf, 0x14)` и передаёт его дальше как account; текущий Rust `on_valid_code_answer` читает то же поле с тем же пределом `0x14`.

Статус цепочки: `VERIFIED_DISASSEMBLY`.

## Границы метода

- **Клиентский `0xBF403` (`PARTIAL`)**: его обработчик перед вызовом десериализатора выполняет один `GetLong` (`0x54B022`), чей результат далее не используется. Фактическая запись vector стартует словом позже начала payload, тогда как сервер пишет (индекс, count, элементы) без ведущего слова. Либо ветвь исторически не доходила до исполнения при выключенной настройке, либо это исходный дефект разбора. Для текущего сервера безразлично: входящие штампы всё равно не читаются; решения для Rust отсюда не следует.
- **Инвентарь исходящих типов** строится сканированием call-site конструктора `0x43AAF0`. Числа (≈368 прямых кандидатов `E8`, ≈133 уникальных типа у разведки) зависят от экстрактора типа: наивный поиск ближайшего `push imm32` в окне ~12 байт даёт ложные попадания в середине чужих инструкций (например, якобы-сайт `0x8F702` в `0x401632`) и пропускает сайты с длинной прослойкой между push и call (например, реальный сайт `0x8F801` в `0x414C8B`). Это нижняя граница оценки, не потолок; матрица покрытия — [на странице каталога](../protocol/client-outgoing-catalog.md).
- Ghidra-проект `runtime/ghidra-client/` существует как рабочий контур; здесь результаты воспроизводимы inline-дампами capstone без внешних инструментов.
