# Протоколы Nebokrai

Читать в таком порядке: [внутренний заголовок и сериализация](message-header.md) → [направленные TCP-кадры, CRC и RLE](transport.md) → [жизненный цикл соединения и очередей](connection-lifecycle.md) → [каталог достигнутых сообщений](opcode-catalog.md). Подробные пакеты: [клиентский вход `0x2FD01`/`0x2FD0B`](login-auth.md), [игровой вход `0xBF401`](game-login.md) и [команды игрока в GameServer](game-actions.md).

Документируемая единица — **контракт направления и сообщения**, а не исходный файл. Разные направления могут использовать одинаковый `CMessage`, но разные внешние префиксы, правила проверки и реакции на ошибку. Номер opcode без отправителя, получателя и состояния соединения недостаточен для определения смысла.

`VERIFIED` здесь означает прямое свидетельство указанного правила в оригинальном EXE/PDB либо явное runtime-наблюдение, если оно названо. Оно само по себе не означает, что Rust-сервер собран, передал этот пакет или принят исходным клиентом. `PARTIAL` указывает точно установленную часть и оставшийся пробел; `INFERRED` — вывод из косвенных данных; `UNKNOWN` — факт не установлен. Общие [правила фиксации доказательств](../reconstruction/evidence-and-contracts.md) распространяются на каждую страницу.

Когда установлен новый пакет, добавить его в [каталог](opcode-catalog.md), а сложный payload описать отдельной страницей: направление, событие, предусловия, полный порядок полей и типов, вариативные ветви, побочные эффекты и их порядок, ошибка/отмена, исходное свидетельство с EXE/PDB/RVA или capture, текущая реализация, неизвестные поля и степень проверки клиентом. Неизвестный диапазон нельзя заполнять по аналогии с соседним opcode.
