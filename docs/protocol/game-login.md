# Игровой вход: сообщение `0xBF401`

`0xBF401` отправляет **GameServer клиенту конкретного игрока** при завершении входа, а также в короткой ветви отказа. WorldServer передаёт GameServer результат `0x7F901`, после которого GameServer строит этот клиентский ответ.

## Свидетельства и область действия

Основной вариант — `GameServer/gameserver.exe` + `GameServer/GameServer.pdb`, исходный owner `gameserver/gameserver.cpp`, вызов `CGame::OnLogMessage` по записанному в [игровом owner-е](../../server/rust/src/gameserver/gameserver/game.rs) адресу **VA `0x0049F140`**. Его **RVA `0x0009F140` вычислен** из указанного VA при базе образа `0x00400000`, а не записан в owner-е отдельно. Парный сериализатор игрока — `CPlayer::AddToByteArray_ForClient` по [сохранённым метаданным и выводам разбора](../../server/rust/src/gameserver/appserver/player.rs) **VA `0x0044A480`, RVA `0x0004A480`**, исходный `appserver/player.cpp:941`. База сериализации `CMoveShape::AddToByteArray_ForClient` отмечена как VA `0x004CDD30` в [её owner-е](../../server/rust/src/gameserver/appserver/moveshape.rs). Размеры базовых операций `CBaseMessage` и заголовок описаны [отдельно](message-header.md).

Порядок внешних блоков ниже опирается на сохранённую семантику owner-ов; поля региона дополнительно сверены непосредственно с указанным EXE и совпадающим по GUID и age PDB. [Rust-сборка сообщения](../../server/rust/src/gameserver/gameserver/game.rs) использует эти источники полей. Размер player snapshot и C-строк зависит от данных, поэтому **общей таблицы абсолютных offset-ов payload нет**. Полная побайтовая сверка всех вложенных контейнеров с исходным клиентом не проведена; статус всей спецификации — `PARTIAL`.

## Условия отправки

Перед основным `0xBF401` Game может отправить `0xBF402`, затем `0xBF403`. В оригинальном `OnLogMessage` ненулевая настройка по смещению `CGame+0x134` вызывает вставку отметки по player ID и отправку `0xBF402` (`0x0049F63F–0x0049F6C7`). Его payload — три 32-битных слова: `player_id`, результат `timeGetTime()`, результат `time(NULL)` в этом порядке; вставка предшествует построению сообщения. Затем ненулевая настройка `CGame+0x138` и непустой статический реестр разрешают `0xBF403` (`0x0049F6CC–0x0049F6F9`). В Rust [Zone sessions](../../server/rust/zone/src/sessions/validation.rs) хранит реестр и состояние по игрокам, а `CGame` сохраняет настройки, общий RNG и отправку. Проверка ответа клиента и смысл отметки в текущем Rust ещё не восстановлены.

**Форма внутреннего payload `0xBF403` — VERIFIED для указанной пары GameServer EXE/PDB:** `u32` начальный индекс (`0xFFFFFFFF` при пустом реестре), `u32` число элементов, затем каждый элемент как `u32`, все в little-endian. `CSequenceString::Serialize` (`0x0042A3D0–0x0042A473`) выбирает индекс через один `rand % count` только при непустом реестре, записывает индекс до count и обходит значения по порядку. `Initialize` (`0x0042A6D0–0x0042A755`) вызывает `srand(timeGetTime())`, затем ровно `count` вызовов `rand`, заменяет ноль единицей и дописывает значения к уже существующим. Конструктор (`0x0042A390`) задаёт индекс `-1` и ложный флаг пригодности. Rust получает значения RNG через callback; его собственная обработка нехватки памяти и недопустимой длины — безопасная граница, а не установленный исходный результат. Последующая проверка ответа клиента в этот контракт не входит.

`CGame::AppendSequenceMap` (`0x00409340–0x004093C7`) при повторном ID удаляет прежнюю запись и возвращает отказ, не расходуя RNG. `AppendValidateTime` (`0x004093D0–0x004093F9`) делает `map::insert`, поэтому прежнее значение при повторном ключе не заменяется. [Zone `LoginValidationState`](../../server/rust/zone/src/sessions/validation.rs) сохраняет оба порядка. Эти операции относятся к состоянию входа; формат `0xBF403` выше остаётся отдельным контрактом.

[Диспетчер `logmessage`](../../server/rust/src/gameserver/appserver/message/logmessage.rs) принимает `0x7F901` от WorldServer. Положительный status служит ID игрока; требуется действующий client-route. Далее декодируется GameSave, проверяются ID и отсутствие дубликата, подбирается регион, создаётся player snapshot. После успешной сборки snapshot [GameServer](../../server/rust/src/gameserver/gameserver/game.rs) формирует полный `0xBF401` и вызывает `send_to_player`. Перед этим выполняются login-script и выбор начального навыка. Затем ставится запрос баланса Billing `0xEF201` — без проверки результата `send_to_player`. Это порядок постановки, а не подтверждение доставки клиенту; поля баланса описаны в [каталоге opcode](opcode-catalog.md). Неустановленные реакции исходного кода на остальные состояния входа — `UNKNOWN`.

До формирования клиентского снимка оригинальный `CGame::OnLogMessage` также завершает начальную подготовку координат. `VERIFIED` для matching GameServer EXE/PDB: после общей коррекции позиции он вызывает virtual region `SetEnterPosXY` по VA `0x0049FBAF`. Для достигнутых concrete owner-ов это [`CServerCityRegion::SetEnterPosXY`](../../server/rust/src/gameserver/appserver/servercityregion.rs) RVA `0x001CEE80` и [`CServerCountryRegion::SetEnterPosXY`](../../server/rust/src/gameserver/appserver/servercountryregion.rs) RVA `0x001CA9F0`. City применяет этот путь только при city state `3` или `2`, Country — при state `3`; обе ветви выбирают подтверждённую return-point того же региона, получают случайную позицию в её диапазоне и вызывают player `SetPos`. Rust `complete_world_player_login` теперь выполняет эти concrete City/Country ветви до привязки shape к региону. Пространственный `AddObject`, `AutoStart` и `OnEnterRegion(false)` по-прежнему отложены до клиентского подтверждения `0x8F801`. Это статически восстановленный и собранный путь; повторный клиентский вход после его подключения ещё не является runtime-доказательством.

При status `0` или `-1`, а также при ряде ошибок дальнейшего входа [ветвь отказа](../../server/rust/src/gameserver/appserver/message/logmessage.rs) создаёт тот же тип `0xBF401`, записывает **один 32-битный ноль** и отправляет его игроку. Этот короткий вариант нельзя декодировать как полный login snapshot. Status `-2` игнорируется и сам по себе `0xBF401` не создаёт. Для ветвей отказа имеется реализованный Rust-маршрут и owner-контракт; точный оригинальный byte capture для них здесь не представлен (`PARTIAL`).

## Порядок данных полного варианта

После [16-байтового внутреннего заголовка](message-header.md), в котором `MsgType = 0x000BF401`, идёт следующая последовательность. Числа `long` здесь 32-битные little-endian; `byte` занимает один байт, `float` — четыре байта IEEE-754 little-endian. Отправка одному игроку проходит через [Game `CMessage::send_to_player`](../../server/rust/src/nets/netserver/message.rs), который обрамляет RLE-представление внутреннего сообщения отдельной 32-битной длиной транспортного кадра. Таблица описывает **внутренний payload до RLE**.

| № | Часть payload | Размер и условие | Статус и свидетельство |
| ---: | --- | --- | --- |
| 1 | ID игрока | `long`, 4 байта | `VERIFIED`: `CGame::OnLogMessage` VA `0x0049F140`; `initial.add_long(expected_player_id)` в [Game owner-е](../../server/rust/src/gameserver/gameserver/game.rs). |
| 2 | Разреженная проекция `tagSetup` и соседних настроек | Переменный размер из-за двух C-строк; точный порядок источников ниже | `VERIFIED` для указанного порядка в [GlobeSetup owner-е](../../server/rust/src/setup/globesetup.rs). Назначение каждого сырого байта внутри диапазонов не выводится из этой страницы (`UNKNOWN`). |
| 3 | `CPlayer::AddToByteArray_ForClient(true)` | Переменный блок, без отдельной длины перед ним в `0xBF401` | `PARTIAL`: оригинальный serializer RVA `0x0004A480`, реализованный [player snapshot](../../server/rust/src/gameserver/appserver/player.rs). Отдельные доказанные поля описаны ниже; весь вложенный layout здесь не заявлен. |
| 4 | Имя региона | Исходные байты C-строки до первого NUL, затем `0x00` | `VERIFIED`: оригинал копирует строку без перекодирования; Rust берёт `region.region.get_name()`. [Точные источники ниже](#поля-региона-после-player-snapshot). |
| 5–8 | `region_type`, `war_region_type`, `resource_id`, `exp_scale` | Три `long`, затем биты `float`; по 4 байта | Источники и порядок записи оригинала — [ниже](#поля-региона-после-player-snapshot). Размеры карты в этот блок не входят. |
| 9 | Признак первого входа | `byte`, 1 байт: `0` или `1` | `VERIFIED`: `add_byte(u8::from(first_login))`; флаг получают при первом `mark_login_script_started`. |
| 10 | Дублирующие регионы | Только если первый вход и существует setup-owner; знаковый 32-битный счётчик, затем по два 32-битных ID на запись | `VERIFIED` для этой условной формы в [CDupliRegionSetup](../../server/rust/src/public/dupliregionsetup.rs); обязательность присутствия owner-а при любом запуске не утверждается. |
| 11 | Расширение `tagSetup` | `AddEx`: 32-битная длина `0x400`, затем ровно `0x400` байт из setup offset `0xD08..0x1108` | `VERIFIED` для вызова и длины: [Game owner](../../server/rust/src/gameserver/gameserver/game.rs), [GlobeSetup](../../server/rust/src/setup/globesetup.rs), [базовый `AddEx`](../../server/rust/src/nets/basemessage.rs). Семантика всех 1024 байт здесь не заявлена. |

## Поля региона после player snapshot

Клиенту передаётся ID ресурса карты отдельно от ID игрового региона: несколько регионов могут использовать один набор ресурсов. Множитель опыта также приходит из описания региона. Для этих полей используются существующие [accessor-ы `CRegion`](../../server/rust/src/gameserver/appserver/region.rs), чтобы сохранить данные, уже полученные от World, без повторного чтения конфигурации.

`VERIFIED` для источников и порядка записи указанного оригинального GameServer: `CGame::OnLogMessage` собирает следующий хвост. Все адреса — VA при базе образа `0x00400000`; `region` обозначает найденный объект региона.

| Поле | Источник оригинала | Запись в BF401 |
| --- | --- | --- |
| Имя | Байты `std::string` региона: выбор буфера по `0x0049FBB8–0x0049FBC6`, копирование по `0x0049FBCA` | `AddString` по `0x0049FDC6` |
| `region_type` | Результат виртуального вызова `region.vtable+0xB8` по `0x0049FACB` | `AddLong` по `0x0049FDD8` |
| `war_region_type` | `region+0x210`, чтение по `0x0049FAD1` | `AddLong` по `0x0049FDEA` |
| `resource_id` | `region+0x64`, чтение по `0x0049FAD7` | `AddLong` по `0x0049FDFC` |
| Биты `exp_scale` | `region+0x68`, чтение по `0x0049FAE0` | `AddLong` по `0x0049FE0E` |

Совпадающий с EXE PDB определяет `region+0x64` как `m_lResourceID` (`long`), `+0x68` как `m_fExpScale` (`float`), а ширину и высоту — как отдельные поля `+0x6C/+0x70`. Декодер оригинала `CRegion::DecordFromByteArray` записывает эти четыре значения по VA `0x004F10A1`, `0x004F10AD`, `0x004F10B9`, `0x004F10C5`. Конструктор по `0x004F0DFB` задаёт масштабу биты `0x3F800000`, то есть `1.0f32`.

Текущая цепочка Rust: [World читает `ResourceID` и `expScale` из `regionlist.ini`](../../server/rust/src/worldserver/worldserver/game.rs), назначает их через `configure_region_owner`, затем [World `CRegion`](../../server/rust/src/worldserver/appworld/region.rs) пишет их перед размерами карты. [Game `CRegion`](../../server/rust/src/gameserver/appserver/region.rs) раздельно читает `resource_id`, `exp_scale_bits`, ширину и высоту. BF401 берёт первые два через `resource_id()` и `exp_scale_bits()`. Численное преобразование `exp_scale() as i32` потеряло бы представление float: `1.0` превратилось бы в байты целого `1`. Преобразование `exp_scale_bits() as i32` сохраняет все 32 бита для существующего `add_long`, как в оригинале.

Имя передаётся через `get_name().to_vec()`: промежуточная строка `CServerRegion.name` декодирована для работы Rust и её `as_bytes()` дал бы UTF-8 вместо исходных байтов. BF401 не вводит перекодирование; конкретная кодировка входных ресурсов остаётся отдельным свойством данных. ID ресурса также нельзя заменять шириной: например, описание региона `13001` задаёт ресурс `11001` и масштаб `1`, тогда как его `.rgn` содержит размеры `512 × 512`.

## Проекция `tagSetup` перед блоком игрока

[GlobeSetup](../../server/rust/src/setup/globesetup.rs) пишет исходные байты **в указанном порядке**, а не сплошной `tagSetup`. Таблица фиксирует только доказанное копирование и размер, не придумывая названия каждому полю исходной структуры.

| Порядок | Источник | Что записывается |
| ---: | --- | --- |
| 1–6 | `0x000..0x084`, `0x424..0x428`, `0x3F0..0x3F2`, `0x3F2..0x3F4`, `0x4F4..0x4F6`, `0x2EC..0x2F8` | Последовательно `0x84`, 4, 2, 2, 2 и 12 сырых байт. |
| 7–10 | `0x7B0..0x7F0`, `0x7F0..0x7F8`, `0x768..0x7A8`, `0x7A8..0x7B0` | C-строка из 64-байтного поля до первого NUL (либо всё поле) плюс завершающий NUL; 8 сырых байт; вторая такая строка; ещё 8 сырых байт. |
| 11–14 | Два `contribute_combat_levels`, `tagSetup[0x905]`, `tagSetup[0xCD1]` | По одному младшему байту каждого combat level, затем два одиночных байта setup. |
| 15–16 | `tagSetup[0x514..0x518]`, `tagSetup[0x518..0x51C]` | По четыре байта ширины и высоты area без перестановки. |

Этот порядок имеет статус `VERIFIED` по сохранённому owner-контракту и непосредственной записи Rust. Поля, для которых исходные имена/назначения здесь не приведены, остаются семантически `UNKNOWN`; нельзя считать их свободным padding.

## Порядок вложенного снимка игрока

Этот блок не содержит своей длины: клиентский `CPlayer` decoder VA `0x004509B0` последовательно продвигает общий курсор `0xBF401`. Поэтому ошибка размера любого вложенного поля меняет смысл всего остатка сообщения. Ниже — порядок и размеры блоков, сопоставленные с [полным Rust-сериализатором](../../server/rust/src/gameserver/appserver/player.rs); имена переменных обозначают текущие поля Rust. `CString` включает завершающий NUL, GUID занимает байт маркера и при ненулевом маркере ещё 16 байт.

| ---: | --- | --- |

| 2 | Базовые и боевые свойства | `0x194` сырых байта, account `CString`, title `CString`, `0x9C` сырых байта, опыт уровня `u32`. |

## Флаги перед заданиями

В полном блоке игрока после четырёх валют и организационных данных идут `contend_state` и `city_war_died_state` — **по одному байту каждый**, затем данные заданий. Название оригинального поля `m_lCityWarDiedState` не определяет его ширину: это булев флаг, а не 32-битное время состояния. [Rust-сериализатор](../../server/rust/src/gameserver/appserver/player.rs) использует `write_u8` в полном и коротком вариантах.

`VERIFIED`: оригинальный GameServer по VA `0x0044A973–0x0044A988` читает оба поля как byte и вызывает один и тот же `_AddToByteArray` (`0x0047AF60`). Получатель в локальном `Miracle game.exe`, `CPlayer` decoder VA `0x004509B0`, читает их по VA `0x00451966–0x00451989`, увеличивая курсор на один байт перед каждым чтением. Использованный клиент идентифицирован в [результатах диагностики](../status/audit.md#сдвиг-пакета-входа-перед-заданиями). Расширение второго флага до `i32` сдвигает все последующие переменные блоки на три байта; номер предмета или счётчик из такого разбора нельзя трактовать как данные инвентаря.

## `country_identity` внутри блока игрока

Полный player snapshot сначала пишет [снимок `CMoveShape`](../../server/rust/src/gameserver/appserver/moveshape.rs), затем 0x194 байта базовых свойств и переменные строки, навыки, друзей, контейнеры, валюты, организации и задания. Ближе к концу, **после quest snapshot**, идут: `country` (`byte`), `contribution` (`long`), **`country_identity` (`byte`)**, `loan_time_limit` (`DWORD`). Затем следуют контейнеры боевой феи/CiQing и завершающие поля. Поэтому абсолютный offset `country_identity` от начала `0xBF401` без разбора всех предшествующих переменных частей неизвестен.

Ширина `country_identity` — **ровно один байт**, статус `VERIFIED`: в локальном RAW оригинального `CPlayer::AddToByteArray_ForClient` (RVA `0x0004A480`) результат `get_country_identity` имеет тип `uchar uVar3` и передаётся `_AddToByteArray`; в [Rust player owner-е](../../server/rust/src/gameserver/appserver/player.rs) параметр `u8` записывается `write_u8(country_identity)`. В [Game owner-е](../../server/rust/src/gameserver/gameserver/game.rs) поиск identity также возвращает `u8` через [country owner](../../server/rust/src/gameserver/appserver/country/country.rs). Четырёхбайтовые ID игроков внутри состояния страны и соседний `contribution` не расширяют это wire-поле до `long`.

## Записи контейнеров и предметов

`append_old_client_volume` обслуживает семь контейнеров одним форматом: аукционные полученные товары, пакет, выставленные товары, фея, боевая фея, составление CiQing и CiQing. После счётчика `i32` каждая запись содержит `is_equipment: u8`, `amount: u16`, `position: u8`, затем полный `CGoods::SerializeForOldClient`. Последний байт — младший байт результата `QueryGoodsPosition`, а не направление предмета. Обход сохраняет порядок хранения предметов; ячейка передаётся отдельным полем и не задаёт порядок записей.

`VERIFIED`: общий `CPacketListener` с vtable `0x0064DB74` используется исходным `CPlayer` для этих обходов; callback VA `0x0042D35A–0x0042D3BF` получает позицию и пишет три поля префикса. Клиент читает их, например, по VA `0x00451A73–0x00451A90` для боевой феи. Ветка выставленных товаров по VA `0x004514D0–0x004514D9` пропускает первые три байта и использует четвёртый; отдельного формата отправителя для неё нет. Пустой контейнер занимает только четыре байта счётчика.

Внутренняя запись предмета использует общий [CGoods-сериализатор](../../server/rust/src/gameserver/appserver/goods/cgoods.rs). Число свойств DaKong определяется отсутствием **типа свойства** в каталоге, а не пустотой его значений (`QueryNoInSelfPropertyType`, VA `0x004CB7C0`; `QueryAttrbuteInGoodsList`, VA `0x004CB550`). Полный вход передаёт сериализатору тот же setup-флаг DaKong, что и обычные обновления предмета. Оригинальный `SerializeForOldClient` читает этот флаг через `CDaKongXiangQian::GetKey` перед хвостом дополнительных свойств; локальная константа `true` этого условия не заменяет.

## Предел проверки

Направление, внешний порядок блоков, перечисленные размеры, флаги перед заданиями, `country_identity` и префиксы контейнерных записей имеют конкретные статические свидетельства. Смысл каждого байта непрозрачных setup/base-property/combat диапазонов и работа редких условных ветвей с клиентом этим не подтверждены. Наблюдённые результаты входа хранятся в состоянии проекта; отсутствие расхождения при чтении кода не заменяет запуск клиента.
