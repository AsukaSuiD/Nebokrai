# Жизненный цикл соединения и доставка сообщений

Эта страница задаёт ограничения, адресацию и реакции на ошибки **от принятия TCP-соединения до передачи сообщения обработчику**. Модель владения, очередей и расширения изложена в [сетевом runtime](../server/network-runtime.md); [формат кадра](transport.md) и [внутренний заголовок](message-header.md) заданы отдельно. Свидетельства исходных контрактов находятся в комментариях указанных Rust-файлов; локальные неизвестные отмечены рядом с правилом.

## Владелец и зачем сохранять порядок

Принятое соединение принадлежит `CServer`, а конкретный `netlogin`, `netserver` и другой компонент выбирает парсер, метаданные и реакцию на ошибку. Доменный `CGame` получает готовое сообщение из FIFO. Общий код — [servers.rs](../../server/rust/src/nets/servers.rs) и [serverclient.rs](../../server/rust/src/nets/serverclient.rs); конкретные клиентские парсеры — [Game](../../server/rust/src/nets/netserver/myserverclient.rs) и [Login](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs).

Изменения реестров через `CSocketCommands<ServerSocketCommand>` сохраняют последовательность исходного `CServer::DoNetThreadFunc`: RVA Auth `0x00011C80`, Billing `0x0000BC90`, Login `0x00069AE0`, Game `0x000180C0`, World `0x00027740`, зафиксированные в [servers.rs](../../server/rust/src/nets/servers.rs). Для этих ветвей порядок `VERIFIED`; конкурентное поведение остальных исходных производителей команд — `PARTIAL`. Причины замены платформенной инфраструктуры описаны в [ADR о границе семантики](../decisions/0002-semantic-boundary.md).

## Входящее соединение

1. `Host` создаёт и привязывает IPv4 TCP socket, затем начинает слушать. Исходный default backlog равен `INT_MAX`; конфигурация отдельных служб может менять пределы позднее. В Rust используются `TcpSocket::bind` и `listen`, поскольку автоматический `SO_REUSEADDR` у удобного Unix `TcpListener::bind` менял бы поведение привязки. [Транспортный адаптер](../../server/rust/src/transport/mod.rs), [общий сервер](../../server/rust/src/nets/servers.rs). **`VERIFIED` для исходного порядка bind/listen; совместимость всех Linux socket options `PARTIAL`.**
2. Перед принятием проверяется число клиентов (исходный default `100`), затем при включённых настройках allow-list по canonical IPv4 и порту и временный forbid-list. Порт `0` в разрешающей записи означает сравнение только IP. Принятому соединению выдаётся process-local socket ID, создаётся `CServerClient` и ставится команда `ADD`; это ещё не доменная авторизация игрока. [Admission owner](../../server/rust/src/nets/servers.rs). **`VERIFIED` по исходным EXE/PDB.**
3. После применения `ADD` реестр содержит socket ID и, когда компонент его назначит, map identity. У Login идентификатор может быть строкой, у Game — числовым ID игрока. Эти значения являются **внутрипроцессными адресатами очереди отправки**, а не полями общего wire-заголовка. [Общий сервер](../../server/rust/src/nets/servers.rs), [Game send owner](../../server/rust/src/nets/netserver/message.rs). **`VERIFIED` для названных направлений.**
4. Для принятого соединения исходный блок чтения равен `0x2000` байт; для исходящего `CClient` — `0x2800`. TCP-фрагмент добавляется в накопитель, из которого последовательно извлекаются все полные кадры, а неполный суффикс остаётся до следующего чтения. Один `recv` не равен одному игровому сообщению. [Server client](../../server/rust/src/nets/serverclient.rs), [outbound client](../../server/rust/src/nets/clients.rs), [transport](../../server/rust/src/transport/mod.rs). **`VERIFIED` для порядка и размеров блоков.**
5. Внешняя длина и CRC проверяются в конкретном направлении; затем создаётся `CMessage`, нормализуется его внутреннее слово длины, присваиваются доступные socket/map/IP/identity metadata и только потом сообщение публикуется в FIFO. Для [Login клиентского пути](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs) допустимы входные opcode `0x2FD01..=0x3FBFF`, для [Game](../../server/rust/src/nets/netserver/myserverclient.rs) — `0x8F701..=0x9F5FF`. Это **фильтр диапазона**, не список реализованных сообщений. **`VERIFIED` для этих двух receive owners.**

`process_command_snapshot` атомарно забирает очередь, применяет команды по порядку, затем запускает максимум одну новую send-операцию на соединение за проход с учётом лимита уже начатых операций. Байты нескольких команд отправки этому соединению могут войти в **один** batch. После send-прохода публикуется timeout-`QUIT` для следующего снимка, затем обрабатываются close-флаги. Немедленное закрытие при постановке `QUIT` изменило бы этот порядок. [Порядок snapshot](../../server/rust/src/nets/servers.rs). `VERIFIED` для пяти исходных вариантов; точное совпадение времени планировщика Windows и Tokio — `UNKNOWN`.

Контроль нового соединения снимается при первом `Receive`, **до** проверки кадра. Это ожидание первого TCP-фрагмента, а не полного сообщения или успешного логина. Default 8000 ms и точная граница срабатывания приведены в [таймерах](../server/runtime-ordering.md).

## Назначение и потеря адресата

`assign_map_id` / `assign_map_name` меняют контекст клиента и индекс identity → socket. Текущий код не удаляет прежний индекс при повторном назначении. `DeleteBySocketId` удаляет запись клиента, но также не очищает все связанные индексы; `QuitByMapId` / `QuitByMapName` удаляют именно запрошенный индекс перед установкой close-флага. Поэтому socket map и identity map нельзя считать одной автоматически согласованной коллекцией. При отладке адресации нужно проверить обе и доменную очистку после `OnClose`.

Числовой поиск отсутствующей identity возвращает `0`; строковый `get_socket_id_by_map_name` возвращает **`1`**. Это сохранённая особенность текущей реализации и исходного контракта, а не рекомендуемое значение «не найдено»: send/quit по отсутствующему имени может обратиться к socket `1`, если он существует. Отправка по отсутствующему socket ID тихо пропускается. Producer `ServerCommandHandle` возвращает `1` при постановке непустой команды, не проверяя будущего адресата. Следовательно, по его результату нельзя подтвердить ни существование клиента, ни доставку.

## Отправка и частичный результат

Для принятого `CServerClient` команды отправки складывают байты в накопитель. При превышении разрешённого предела (общий default `0xC800`, служба может настроить другое значение) `add_send_data` возвращает `LimitExceeded`, а `CServer::buffer_send_command` **сразу удаляет клиента с `OnClose`**. При адресной отправке счётчик клиентов уменьшается до callback, при broadcast — после callback. Это отличается от отложенного `QUIT`.

Уже установленный close-флаг даёт `IgnoredWhileClosing`: новые данные не добавляются, но это не ошибка. `begin_send` снимает весь накопитель в отдельный batch до выполнения асинхронной записи. Если completion сообщает меньше запрошенного, хвост **не повторяется**: `ServerSendCompletion::dropped_tail_bytes` показывает разницу, а успешная операция публикует `SENDEND`. В том числе успешный `Ok(0)` на этом принятом пути означает потерю всего batch. Следующий batch может уже содержать другие сообщения; гарантии восстановления TCP-кадра после частичной записи здесь нет. `write_all` изменил бы сохранённую семантику. [ServerSendBatch и CServerClient](../../server/rust/src/nets/serverclient.rs), [адаптер одной записи](../../server/rust/src/transport/mod.rs). `VERIFIED` для исходных обработанных completion; timing readiness/completion — `PARTIAL`.

У исходящего межсерверного `ClientSendQueue` priority-команда ставится в начало очереди, обычная — в конец. Несколько ещё не снятых priority-команд идут в обратном порядке их добавления. `try_flush` снимает очередь и пытается дописать каждую команду полностью, сохраняя offset. При `WouldBlock`, `Ok(0)`, ненулевых неподдержанных flags или постоянной I/O-ошибке неполный хвост **вместе с остальными снятыми командами** возвращается перед командами, поступившими во время flush, включая новые priority. `WouldBlock` возвращается как обычный `FlushOutcome`; другие названные исходы — `ClientSendError`. Это сохранение очереди текущего объекта, а не гарантия повторной доставки после его замены при reconnect. [ClientSendQueue::try_flush](../../server/rust/src/nets/clients.rs); исходные `SendToServer` RVA Login `0x0006B0F0`, Misc `0x000113F0`, Game `0x000191D0`, World `0x00028960`. Порядок очереди — `VERIFIED`; прочие исходные sender call sites — `PARTIAL`.

## Закрытие и ошибки

На принятой стороне применение `QUIT` выставляет close-флаг. Shutdown будит read-задачу; она публикует `DeleteBySocketId`, после которого выполняются `OnClose` и удаление. EOF или ошибка чтения сразу публикуют `DeleteBySocketId`. Удаление вследствие переполнения send-накопителя, описанное выше, происходит непосредственно в снимке и не ждёт этого пути.

Порядок send и quit **внутри** снимка важен: send-команда после close-флага игнорируется; накопленные до него байты ещё могут образовать batch. Для нового batch закрывающегося клиента `ServerIoAction::Send` делает попытку записи до shutdown. Дальнейший `Drop` зависит от оставшихся `Arc<TcpStream>`. На ошибке Linux write публикуется delete; исходные немедленный отказ `WSASend` и ошибка pending IOCP имели разные позиции удаления, а этот адаптер их не различает (`PARTIAL`). [ServerIoAction::run](../../server/rust/src/nets/servers.rs), [shutdown_tcp](../../server/rust/src/transport/mod.rs).

Компонентные последствия закрытия не взаимозаменяемы. Клиент Login при непустом CD-key публикует synthetic `0x10001` с NUL-terminated ключом; клиент Game при ненулевом map ID публикует synthetic `0x6FA01` с map ID и пустой C-строкой. Login, принимающий WorldServer, публикует `0xFF01` с map ID. Эти сообщения являются **локальными событиями после закрытия**, их нельзя автоматически объявить wire-пакетами. [Login client](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs), [Game client](../../server/rust/src/nets/netserver/myserverclient.rs), [Login World](../../server/rust/src/nets/netlogin/mynetserverclient_world.rs). **`VERIFIED` по соответствующим EXE/PDB.**

У клиентских Login/Game входов превышение настроенного размера, неверный length/content CRC и opcode вне диапазона дают ошибку снимка, запрет IP и постановку `QUIT` **в следующий снимок**. Это не прерывает оставшиеся команды текущего снимка. Отдельный `ClientNetworkNotice::OneMessageSizeExceeded` создаётся для превышения размера; наличие типизированной ошибки для остальных случаев не означает автоматически отдельной строки журнала. Ошибка создания сообщения очищает накопитель без такого запрета. У Login-входа от WorldServer CRC/create-ошибка также очищает накопитель без IP-ban и `QUIT`. [Login client](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs), [Game client](../../server/rust/src/nets/netserver/myserverclient.rs), [Login World](../../server/rust/src/nets/netlogin/mynetserverclient_world.rs), [применение действия](../../server/rust/src/nets/servers.rs). `VERIFIED` для указанных исходных ветвей.

Auth, Billing и World на принятой межсерверной стороне также возвращают `ComponentReceiveErrorAction::None` из своих callbacks при ошибке парсера. Это не отменяет отдельную общую защиту по скорости receive, если она включена: она может поставить forbid/quit ещё до парсера. У исходящих Login→Auth и Misc→World ошибка I/O/send запускает transport-close, тогда как framing-ошибка обрабатывается отдельно. Место вывода ошибок и ограничения наблюдаемости описаны в [диагностике](../operations/diagnostics.md).

Длина с установленным sign bit, кадр короче внешнего префикса и завершающий RLE-marker без байта значения в исходном x86 пересекали небезопасные границы чтения. Наблюдаемая реакция процесса на такие входы — `UNKNOWN`; Rust детерминированно отклоняет их локальной ошибкой и не воспроизводит undefined behavior. [Входной парсер Login](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs), [Game](../../server/rust/src/nets/netserver/myserverclient.rs), [RLE](../../server/rust/src/nets/basemessage.rs).

## Исходящие соединения между серверами

`CClient` подключается к уже разрешённому IPv4 endpoint. Оригинал ждал успешное `FD_CONNECT` не более **10 секунд** и считал успехом только нулевую socket error; синхронный `gethostbyname` происходил до этого ожидания, поэтому DNS не входит в срок. Rust использует `tokio::time::timeout` вокруг connect, а выбор адреса оставляет конкретному service owner. После успешного connect направление становится доступным для queued sends; явный `Close` и транспортный EOF могут порождать **разные** component events. Например, [Login→Auth](../../server/rust/src/nets/netlogin/mynetclient_auth.rs) публикует `0xCF301` при transport-close, а явный `close` лишь сбрасывает флаг; reconnect публикует типизированное внутрипроцессное событие вместо старого `0xCF302 + pointer`. [Общий `CClient`](../../server/rust/src/nets/clients.rs), RVA `Connect` Login `0x0006BB90`, Misc `0x00011E90`, Game `0x00019CE0`, World `0x000293E0`. **`VERIFIED` для перечисленных путей; политика reconnect всех направлений `PARTIAL`.**

## Границы спецификации

CRC, RLE и границы сведений о шифровании описаны в [обрамлении](transport.md). Неизвестные реакции исходного кода на повреждённый ввод и различия scheduler timing остаются локальными ограничениями перечисленных ветвей.
