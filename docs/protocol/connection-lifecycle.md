# Жизненный цикл соединения и доставка сообщений

Эта страница описывает сетевой контракт **от принятия TCP-соединения до передачи сообщения доменному обработчику**. [Формат кадра](transport.md) и [внутренний заголовок](message-header.md) заданы отдельно. У каждого утверждения ниже свой предел доказанности: исходные `CServer`/`CServerClient` и `CClient` восстановлены по точным EXE/PDB, но работа этой Rust-реализации с исходным клиентом здесь не проверялась. Обозначения `VERIFIED`, `PARTIAL`, `INFERRED`, `UNKNOWN` определены в [правилах свидетельств](../reconstruction/evidence-and-contracts.md).

## Владелец и зачем сохранять порядок

Принятое соединение принадлежит одному экземпляру `CServer`: он хранит listener, реестры socket ID и map ID, временный запрет IPv4 и очередь команд. Конкретный `netlogin`, `netserver` и другой компонент определяет, какой `CMessage` создать, какие метаданные присвоить и как поступить с ошибкой. Доменный `CGame` получает уже готовое сообщение из FIFO; он не должен трактовать границы произвольных TCP-чтений как границы пакетов. Это подтверждено `CServer::DoNetThreadFunc` и `CServerClient::OnReceive` пяти исходных серверов; [общий серверный owner](../../server/rust/src/nets/servers.rs), [состояние соединения](../../server/rust/src/nets/serverclient.rs), [Game receive](../../server/rust/src/nets/netserver/myserverclient.rs) и [Login receive](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs). **Статус: `VERIFIED` для исходных вариантов и статического соответствия достигнутых ветвей; runtime parity `UNKNOWN`.**

Оригинал передавал изменения реестров в один сетевой поток через concurrent `CSocketCommands`; сами `std::map` реестры не имели независимых конкурентных писателей. Rust выражает это `CSocketCommands<ServerSocketCommand>`, `ServerCommandHandle` и `BTreeMap`. Важен единый владелец изменений и порядок команд, а не WinSock, IOCP, STL или форма указателя. Замена ручного выделения памяти на `Vec` и `Arc<TcpStream>` допустима, пока сохраняются байты, ownership и порядок наблюдаемых событий. Основание: исходные `CServer::DoNetThreadFunc` RVA Auth `0x00011C80`, Billing `0x0000BC90`, Login `0x00069AE0`, Game `0x000180C0`, World `0x00027740`, зафиксированные в [owner-е](../../server/rust/src/nets/servers.rs). **Статус: `VERIFIED`; конкурентное поведение всех ещё не достигнутых производителей команд `PARTIAL`.**

## Входящее соединение

1. `Host` создаёт и привязывает IPv4 TCP socket, затем начинает слушать. Исходный default backlog равен `INT_MAX`; конфигурация отдельных служб может менять пределы позднее. В Rust используются `TcpSocket::bind` и `listen`, поскольку автоматический `SO_REUSEADDR` у удобного Unix `TcpListener::bind` менял бы поведение привязки. [Транспортный адаптер](../../server/rust/src/transport/mod.rs), [общий сервер](../../server/rust/src/nets/servers.rs). **`VERIFIED` для исходного порядка bind/listen; совместимость всех Linux socket options `PARTIAL`.**
2. Перед принятием проверяется число клиентов (исходный default `100`), затем при включённых настройках allow-list по canonical IPv4 и порту и временный forbid-list. Порт `0` в разрешающей записи означает сравнение только IP. Принятому соединению выдаётся process-local socket ID, создаётся `CServerClient` и ставится команда `ADD`; это ещё не доменная авторизация игрока. [Admission owner](../../server/rust/src/nets/servers.rs). **`VERIFIED` по исходным EXE/PDB.**
3. После применения `ADD` реестр содержит socket ID и, когда компонент его назначит, map identity. У Login идентификатор может быть строкой, у Game — числовым ID игрока. Эти значения являются **внутрипроцессными адресатами очереди отправки**, а не полями общего wire-заголовка. [Общий сервер](../../server/rust/src/nets/servers.rs), [Game send owner](../../server/rust/src/nets/netserver/message.rs). **`VERIFIED` для названных направлений.**
4. Для принятого соединения исходный блок чтения равен `0x2000` байт; для исходящего `CClient` — `0x2800`. TCP-фрагмент добавляется в накопитель, из которого последовательно извлекаются все полные кадры, а неполный суффикс остаётся до следующего чтения. Один `recv` не равен одному игровому сообщению. [Server client](../../server/rust/src/nets/serverclient.rs), [outbound client](../../server/rust/src/nets/clients.rs), [transport](../../server/rust/src/transport/mod.rs). **`VERIFIED` для порядка и размеров блоков.**
5. Внешняя длина и CRC проверяются в конкретном направлении; затем создаётся `CMessage`, нормализуется его внутреннее слово длины, присваиваются доступные socket/map/IP/identity metadata и только потом сообщение публикуется в FIFO. Для [Login клиентского пути](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs) допустимы входные opcode `0x2FD01..=0x3FBFF`, для [Game](../../server/rust/src/nets/netserver/myserverclient.rs) — `0x8F701..=0x9F5FF`. Это **фильтр диапазона**, не список реализованных сообщений. **`VERIFIED` для этих двух receive owners.**

Исходный `DoNetThreadFunc` атомарно снимал текущую очередь, применял команды по порядку, запускал максимум одну новую send-операцию на соединение за проход, публиковал timeout-`QUIT` **для следующего snapshot** и только затем закрывал соединения с close flag. Поэтому немедленное закрытие при постановке `QUIT`, перестановка таймаута перед уже снятыми командами или выполнение сразу всех queued sends меняет семантику. [Порядок snapshot](../../server/rust/src/nets/servers.rs). **`VERIFIED` для пяти вариантов; точное совпадение времён планировщика Windows и Tokio `UNKNOWN`.**

## Отправка и частичный результат

Для принятого `CServerClient` команды отправки складывают байты в send accumulator. Если сумма превысит разрешённый предел (исходный общий default `0xC800`, у Game и Login другие настроенные значения), добавление может быть отвергнуто. Уже установленный close flag приводит к странному исходному результату: данные не добавляются, но метод сообщает успех; это сохранено как контракт старого владельца. При старте send копируется весь batch, накопитель очищается после принятия операции. Если completion сообщает меньше запрошенных байт, оригинал **не повторяет хвост**: он логирует отличие, освобождает весь batch и публикует `SENDEND`. Rust делает один успешный системный write на batch и явно возвращает количество потерянных байт; `write_all` здесь нарушил бы исходную семантику. [Точное свидетельство и RVA пяти `Send`/worker](../../server/rust/src/nets/serverclient.rs), [адаптер одного write](../../server/rust/src/transport/mod.rs). **`VERIFIED` для исходных обработанных completion; timing readiness/completion `PARTIAL`.**

У исходящего межсерверного `CClient` правило иное: priority-команда ставится в начало очереди, обычная — в конец. Send-loop пытается отправить команду полностью; при временной невозможности owned неполный хвост возвращается **перед** параллельно поступившими командами. Старое поле socket ID на этом пути не влияло на выбор получателя. Rust сохраняет хвост и offset, а Tokio `WouldBlock` заменяет Windows `FD_WRITE`; [исходящий владелец](../../server/rust/src/nets/clients.rs) и его `SendToServer` RVA Login `0x0006B0F0`, Misc `0x000113F0`, Game `0x000191D0`, World `0x00028960`. **`VERIFIED` для очереди и порядка; прочие sender call sites `PARTIAL`.**

## Закрытие и ошибки

На принятой стороне `QUIT` выставляет close flag; shutdown будит читающую задачу, но удаление из реестра, компонентный `OnClose` и окончательный `Drop` происходят позднее на исходной стадии worker `DELETE`. Если send и close оказались в одном snapshot, send начинается до shutdown. [Общий сервер](../../server/rust/src/nets/servers.rs), [transport shutdown](../../server/rust/src/transport/mod.rs). **`VERIFIED` для порядка исходного owner-а; момент завершения асинхронной записи `PARTIAL`.**

Компонентные последствия закрытия не взаимозаменяемы. Клиент Login при непустом CD-key публикует synthetic `0x10001` с NUL-terminated ключом; клиент Game при ненулевом map ID публикует synthetic `0x6FA01` с map ID и пустой C-строкой. Login, принимающий WorldServer, публикует `0xFF01` с map ID. Эти сообщения являются **локальными событиями после закрытия**, их нельзя автоматически объявить wire-пакетами. [Login client](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs), [Game client](../../server/rust/src/nets/netserver/myserverclient.rs), [Login World](../../server/rust/src/nets/netlogin/mynetserverclient_world.rs). **`VERIFIED` по соответствующим EXE/PDB.**

У клиентских Login/Game входов превышение настроенного размера, неверный length/content CRC и opcode вне допустимого диапазона вызывают компонентную диагностику → запрет IP → `QUIT` до следующей команды snapshot. Ошибка создания сообщения с нулевым результатом очищает накопитель без этого запрета. У Login-входа от WorldServer CRC/create-ошибка очищает накопитель, но тот owner не ставит IP-ban и `QUIT`. Единая универсальная политика ошибок была бы неверной. [Login client](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs), [Game client](../../server/rust/src/nets/netserver/myserverclient.rs), [Login World](../../server/rust/src/nets/netlogin/mynetserverclient_world.rs), [применение действия](../../server/rust/src/nets/servers.rs). **`VERIFIED` для достигнутых ветвей.**

Длина с установленным sign bit, кадр короче внешнего префикса и завершающий RLE-marker без байта значения в исходном x86 пересекали небезопасные границы чтения. Наблюдаемая реакция процесса на такие входы — `UNKNOWN`; Rust детерминированно отклоняет их локальной ошибкой и не воспроизводит undefined behavior. [Входной парсер Login](../../server/rust/src/nets/netlogin/mynetserverclient_client.rs), [Game](../../server/rust/src/nets/netserver/myserverclient.rs), [RLE](../../server/rust/src/nets/basemessage.rs).

## Исходящие соединения между серверами

`CClient` подключается к уже разрешённому IPv4 endpoint. Оригинал ждал успешное `FD_CONNECT` не более **10 секунд** и считал успехом только нулевую socket error; синхронный `gethostbyname` происходил до этого ожидания, поэтому DNS не входит в срок. Rust использует `tokio::time::timeout` вокруг connect, а выбор адреса оставляет конкретному service owner. После успешного connect направление становится доступным для queued sends; явный `Close` и транспортный EOF могут порождать **разные** component events. Например, [Login→Auth](../../server/rust/src/nets/netlogin/mynetclient_auth.rs) публикует `0xCF301` при transport-close, а явный `close` лишь сбрасывает флаг; reconnect публикует типизированное внутрипроцессное событие вместо старого `0xCF302 + pointer`. [Общий `CClient`](../../server/rust/src/nets/clients.rs), RVA `Connect` Login `0x0006BB90`, Misc `0x00011E90`, Game `0x00019CE0`, World `0x000293E0`. **`VERIFIED` для перечисленных путей; политика reconnect всех направлений `PARTIAL`.**

## Границы спецификации

Протоколы этих TCP-направлений имеют подтверждённые CRC и RLE в [обрамлении](transport.md). Поиск текущих `nets/` и `transport/` владельцев не обнаружил отдельного шифра/obfuscation в описанных send/receive путях; утверждение «в игре нигде нет encryption» из этого **не следует**. Для перечисленных путей отсутствие дополнительной стадии в достигнутом коде — `PARTIAL`, для остальных путей — `UNKNOWN`. Runtime captures, побайтовая сверка с исходным клиентом, реакция на все повреждённые кадры и точное равенство scheduler timing пока `UNKNOWN`.
