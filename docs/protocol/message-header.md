# Общий заголовок сообщения и базовый буфер

Эта страница описывает только общий внутренний формат `CBaseMessage` — шестнадцать начальных байт и методы чтения/записи его продолжения. Источник — восстановленный владелец [`nets/basemessage.rs`](../../server/rust/src/nets/basemessage.rs) с указанными там исходными `nets/basemessage.h/.cpp`, EXE/PDB и RVA. Формат внешнего TCP-конверта, набор допустимых opcode и содержимое отдельных сообщений здесь не определяются: они принадлежат конкретным направлениям `nets/net*`.

Отметки в таблице относятся к исходному формату по EXE/PDB. Правила работы с такими свидетельствами заданы [отдельно](../reconstruction/evidence-and-contracts.md).

## Layout

Смещения считаются от начала **внутреннего сообщения**, передаваемого в `CBaseMessage`. Все слова занимают четыре байта и хранятся в порядке little-endian x86. В коде layout выражен `#[repr(C)]` и `zerocopy::little_endian::U32`; Windows `long` исходного процесса имел именно 32 бита.

| Смещение | Размер | Тип и значение | Статус |
| --- | ---: | --- | --- |
| `+0x00` | 4 | Полная длина этого внутреннего сообщения в байтах, **включая** все 16 байт заголовка. При создании пустого сообщения — `16`; после добавления данных обновляется до фактической длины буфера. Исходная запись использовала Windows `long`, Rust сохраняет те же 32 бита в `U32`. | `VERIFIED` для обычных достижимых размеров; поведение буфера при переполнении 32-битной длины — `UNKNOWN` |
| `+0x04` | 4 | Полный 32-битный `MsgType`. Конструктор конкретного `CMessage` записывает сюда переданный тип; базовый конструктор оставляет ноль. Чтение/запись Rust трактует слово как `i32` без изменения остальных байтов. | `VERIFIED` |
| `+0x08` | 4 | Непрозрачное слово. Новый буфер содержит ноль; при приёме слово копируется как есть. Значение ненулевого слова и его назначение не установлены. | Нулевое начальное значение и буквальное копирование — `VERIFIED`; семантика — `UNKNOWN` |
| `+0x0C` | 4 | Второе непрозрачное слово с тем же подтверждённым начальным поведением. | Начальное значение и копирование — `VERIFIED`; семантика — `UNKNOWN` |
| `+0x10` | переменный | Начало данных конкретного сообщения. Общая структура payload этим заголовком не задаётся. | Граница — `VERIFIED`; единая схема payload — `UNKNOWN` |

Заголовок в целом имеет статус `PARTIAL`: размеры, порядок байтов, длина, `MsgType` и сохранение двух последних слов подтверждены, но смысл `+0x08` и `+0x0C` неизвестен. Нельзя переименовывать эти слова в «socket», «CRC», «flags» или «timestamp» на основании догадки. Runtime-поля конкретных `CMessage` живут отдельно от данного wire-layout.

## Построение и чтение буфера

`CBaseMessage::new` создаёт ровно 16 нулевых байт, записывает длину `0x00000010` в `+0x00` и ставит курсор чтения на `0x10`. `from_header_and_payload` копирует четыре слова входного заголовка, нормализует длину под фактический размер добавленных данных и также ставит курсор на `0x10`. Остальные три слова не толкуются и не обнуляются повторно. `set_message_type` меняет только слово `+0x04`; `Update` и добавление данных обновляют только длину. Эти операции видны в [`CBaseMessage`](../../server/rust/src/nets/basemessage.rs) и шести конкретных владельцах: [`netauth`](../../server/rust/realm/src/app/auth_message.rs) (Realm app; `nets/netauth/message.rs` — переходный реэкспорт), [`netbilling`](../../server/rust/realm/src/app/billing_message.rs) (Realm app; `nets/netbilling/message.rs` — переходный реэкспорт), [`netlogin`](../../server/rust/src/nets/netlogin/message.rs), [`netmisc`](../../server/rust/realm/src/app/misc_message.rs) (Realm app; `nets/netmisc/message.rs` — переходный реэкспорт), [`netserver`](../../server/rust/src/nets/netserver/message.rs), [`networld`](../../server/rust/realm/src/app/world_message.rs) (Realm app; `nets/networld/message.rs` — переходный реэкспорт).

Курсор — offset **внутри всего буфера**, а не относительно payload. Успешный числовой `Get` перемещает его на размер значения; при нехватке данных исходный числовой метод возвращал ноль, не сдвигая курсор. Rust возвращает `Option` и тем самым отличает ноль от нехватки. Сырой `Get` копирует требуемое число байт и сдвигает курсор только при полном успехе, иначе возвращает `false`. `unread_bytes` отдаёт остаток с текущего курсора без его изменения. Двух- и многобайтовые числа записываются и читаются little-endian: `char`/`unsigned char` — 1 байт, `short`/`unsigned short` — 2, Windows `long`/`unsigned long` и `float` — 4, `__int64` — 8. Это `VERIFIED` для описанных методов, а не универсальная схема полей каждого сообщения.

Общий writer добавляет сырые байты без длины; `AddEx` добавляет сначала четырёхбайтовую длину, затем данные. C-строка при наличии значения добавляется с завершающим NUL, а отсутствие значения не добавляет ничего. У Auth-варианта `GetStr` отсутствие NUL до конца сообщения даёт пустой результат и оставляет курсор в конце. Ограниченный `GetStr` расходует прочитанные байты вместе с NUL; достижение предела без NUL даёт пустой результат **без отката уже сдвинутого курсора**. Если вход кончился раньше предела, исходный `GetChar` возвращает ноль; уже собранный префикс может сохраниться. GUID writer добавляет один байт `0` для `GUID_INVALID` либо маркер `0x10` и следующие 16 байт GUID; reader воспринимает любой ненулевой маркер как наличие 16 байт. При нехватке данных после маркера курсор назад не перемещается. Эти правила подтверждены для базового буфера; они не назначают конкретное поле или значение opcode какому-либо пакету.

Граница `PARTIAL`: парный writer `AddEx` реализован, но `GetEx` не имеет Rust API. Исходные Login RVA `0x00065D60` и Game RVA `0x00012DA0` делали недостаточную проверку границ после чтения четырёхбайтовой длины; наблюдаемая реакция процесса на специально укороченный payload остаётся `UNKNOWN`. Реакция на повреждённый RLE-поток с последним marker без следующего байта также `UNKNOWN`; корректный RLE описан и реализован в owner-файле, но он не меняет значения четырёх слов заголовка.

## Как пользоваться общим буфером

Для нового сообщения существующего направления создайте соответствующий `nets/net*/CMessage`, запишите payload через его `base_mut()` и вызовите send-метод направления. Общие числа, строки, GUID и RLE уже реализованы в `CBaseMessage`; повторять их в обработчике не требуется. Внешний TCP-префикс строит send-метод, поэтому его не добавляют в payload вручную.

`set_message_type` сохраняет payload **и курсор**. При пересылке переиспользованного сообщения send берёт `as_wire_bytes()`, включая уже прочитанные поля. Если требуется переслать только непрочитанный остаток, существующий механизм — новое сообщение и `add(unread_bytes())`. Эти варианты передают разные байты; выбор задаёт конкретный протокол. Пример переиспользования — `AsMessageHandlers::on_gma_message` в [Login](../../server/rust/src/loginserver/applogin/message/asmessage.rs).

Чтение не транзакционно: если первые поля считаны, а следующее отсутствует, общий буфер не откатывает курсор. `get_long()` позволяет обнаружить нехватку, но `unwrap_or(0)` в вызывающем коде снова объединяет её с нулём. В текущих службах оба подхода используются; это различие контрактов handlers, а не общее правило «все повреждённые пакеты отклоняются». Нулевой маркер GUID и неполные 16 байт после ненулевого маркера оба дают `None`, но расходуют разное число байт. При изменении декодирования проверяйте и возвращённое значение, и курсор.

Ещё одна локальная граница: текущий `get_str_bytes(0)` пытается прочитать один байт и возвращает пустую строку. Ненулевой байт в исходной нулевой границе мог оставлять строку без терминатора; наблюдаемая реакция caller остаётся `UNKNOWN`. Это не образец для новых строковых полей: их ограничение должно следовать формату сообщения.

## Свидетельства

Верхний комментарий [`basemessage.rs`](../../server/rust/src/nets/basemessage.rs) указывает точные пары исходных бинарников и отладочных символов, SHA-256 и пути исходного owner-а. Для создания базового буфера зафиксированы следующие RVA:

| Вариант EXE/PDB | RVA конструктора `CBaseMessage` |
| --- | ---: |
| `AuthServer/authserver.exe` + `authserver.pdb` | `0x00012FB0` |
| `BillingServer/billingserver.exe` + `billingserver.pdb` | `0x0000D530` |
| `LoginServer/loginserver.exe` + `LoginServer.pdb` | `0x00066360` |
| `MiscServer/miscserver.exe` + `miscserver.pdb` | `0x00011100` |
| `GameServer/gameserver.exe` + `GameServer.pdb` | `0x00013520` |
| `WorldServer/Nworldserver.exe` + `WorldServer.pdb` | `0x00023EE0` |

Числовые чтения подтверждены, в частности, Auth RVA `0x000129B0..0x00012A10`, Login `0x00065C10..0x00065C70` и World `0x000236F0..0x000237C0`; inline `Update` — Game `0x00005060` и World `0x0001A990`. Полные списки RVA, включая сырые чтения и GUID, сохранены в исходном комментарии.
