# Порядок серверных циклов

Сеть и фоновые работники публикуют события асинхронно. Владелец службы применяет входящие события в определённых местах цикла; некоторые DB-работники, например Billing, сами ставят ответы в сетевую очередь. Поэтому порядок нужно прослеживать через конкретного производителя и потребителя, а не предполагать единый цикл всех событий. Разделение сетевого снимка и доменной обработки объяснено в [сетевом runtime](network-runtime.md).

## Очереди и время

Снимок ограничивает объём очереди в текущей стадии. Это не единый снимок всего процесса: очередь, до которой цикл ещё не дошёл, может принять новую запись и обработать её в том же такте. Замена на «читать до пустоты» меняет границу между стадиями и может задержать таймеры.

| Потребитель | Как задаётся текущая порция | Что происходит при ошибке |
| --- | --- | --- |
| `CServer::process_command_snapshot` | Атомарный `CSocketCommands::take_all`. | Локальная ошибка добавляется в отчёт; остальные команды снятого списка обрабатываются. |
| Auth `process_message`, `process_database_results` | Отдельно снимается размер сетевой FIFO и затем DB results; выполняется не более этого числа pop. | Ошибка через `?` заканчивает проход; текущий объект уже извлечён, оставшиеся находятся в общей очереди. `game_thread_func` переходит к освобождению. |
| Login `process_message` | Размер World, обработка World; затем размер Client, обработка Client; затем размер Auth events. | Ошибка handler прекращает проход; извлечённое событие не возвращается. Reconnect-событие может заменить объект клиента в своей позиции FIFO. |
| Billing `process_message` | Размер FIFO Game снимается один раз. | `Unsupported` и прочие outcomes сохраняются в отчёт; общего `Result` для прекращения этого прохода нет. |
| World `process_message` | Сначала число событий принятого server-направления, затем число сообщений исходящего Login-направления. | Результат отдельного сообщения представлен `ProcessedWorldEvent`; более поздние блокирующие стадии основного цикла имеют собственные результаты. |
| Game `process_messages` | Последовательные `take_all_messages` World, Billing, затем `take_all_events` принятого server-направления. | Сообщение передаётся в `run_incoming_message`; снятый снимок не является очередью автоматических повторов. |
| Misc `process_message` | `take_all_messages` текущего клиента атомарно забирает всю FIFO. | Результаты handlers собираются поэлементно; reconnect внутри handler ожидается до следующего элемента. Замена клиента не отменяет уже снятый список. |

Источники: [общая очередь](../../server/rust/src/nets/msgqueue.rs), [сетевой снимок](../../server/rust/src/nets/servers.rs) и методы процессов из таблицы ниже. При ошибке различайте данные, оставшиеся в общей очереди, и уже снятый владеющий список: уничтожение локального списка может потерять его необработанный хвост. Конкретный пример — [работник покупки Billing](auth-login-and-services.md).

Для рассматриваемых интервалов используются 32-битные wrapping-миллисекунды от `CLOCK_BOOTTIME`; это отдельная шкала от календарного времени ban и других дат. В текущем коде есть как сравнение разности с интервалом, так и сравнение `last.wrapping_add(interval)` с `now`. При переполнении они не эквивалентны. Существующие выражения сохраняются как часть конкретного контракта, а не служат рекомендацией копировать любой найденный таймер.

## Один ход

| Процесс | Последовательность | Существенная деталь |
| --- | --- | --- |
| [Auth](../../server/rust/src/authserver/src/cgame.rs), `run_main_loop_turn` | Сетевой проход с обработкой сообщений → DB results → server-info → notices → пауза 1 ms. | Due-таймер записи server-info обновляется даже при отказе переполненной DB-очереди. |
| [Login](../../server/rust/src/loginserver/loginserver/game.rs), `main_loop_turn` | Refresh → проверка выхода → применение GAS events → account-log notices → World → Client → Auth → login queue → ping World → server-info → пауза 1 ms. | Перед этим внешний цикл выполняет `run_network_turn`. GAS events включают прикладные эффекты и подтверждение работнику, а не только диагностику. |
| [Billing](../../server/rust/src/billingserver/billingserver/game.rs), `run_runtime_turn` / `main_loop` | Сетевой проход → refresh → проверка выхода → FIFO сообщений → ping-флаг → пауза 1 ms. | `PingStarted` — событие отчёта; этот участок не строит пакет ping. Флаг `in_ping` здесь не сбрасывается. |
| [World](../../server/rust/src/worldserver/worldserver/game.rs) | Save gate → World AI → сообщения → session factory → player-data queue → timer/войны → DB misc → сетевые сессии → ping и периодические стадии. | Поздний блок сохраняет выполненный префикс. Полнота хвостовых ветвей — `PARTIAL`. |
| [Game](../../server/rust/src/gameserver/gameserver/game.rs) | Проверка выхода → scripts → AI → World → Billing → Game-клиенты → team/session maintenance → net sessions → auction → ожидание. | Интервал 80 ms; опоздание более 1000 ms перенастраивает deadline. Профилирование сохраняет порядок. |
| [Misc](../../server/rust/src/miscserver/miscserver/game.rs), `run_game_thread_turn` | Начало sync-такта → refresh → один неблокирующий сетевой опрос → AI комнаты → снимок FIFO → при оставшемся `client_close` reconnect и попытка confirm; внешний цикл ждёт 50 ms. | Reconnect возможен уже внутри FIFO. Успешный внутренний reconnect снимает флаг и пропускает хвостовой reconnect/confirm. |

В Game AI предшествует сообщениям. Следствие для команды, поставленной обработчиком **в очередь AI**: её исполнение относится к последующему AI-проходу. Это не распространяется на все эффекты handler: некоторые действия меняют состояние и отправляют ответы сразу. Сам порядок scripts → AI → сообщения одинаков при включённом и выключенном профилировании.

## Сетевые проходы World и Game

У World `WorldProcessNetworkRuntime::run_turn` при наличии принятого server-компонента запускает отдельную Tokio-задачу с `WorldServerNetworkRuntime`. Её ход: собрать завершения accept/I/O → начать очередной accept → применить сетевой снимок → запустить I/O-действия → вывести отчёт → ждать сигнал остановки либо 10 мс. Это пауза между проходами, а не гарантия такта ровно каждые 10 мс. Исходящий World→Login остаётся в `WorldProcessNetworkRuntime::run_turn` с одним неблокирующим опросом. Код — [World runtime](../../server/rust/src/worldserver/worldserver/runtime.rs); общие объекты и границы блокировок — в [сетевом runtime](network-runtime.md#кто-владеет-соединением).

У Game сетевой ход после обслуживания принятых соединений выбирает готовые операции сначала World, затем Billing: не более **128 I/O-шагов World** и **16 I/O-шагов Billing**. Каждый `poll_once` прекращает ожидание при `Pending`; `Closed` или `Err` включаются в отчёт и заканчивают выборку этого направления. Бюджет считает I/O-шаги, включая записи и чтения неполного кадра; он не ограничивает число сообщений или длительность одного шага. Это позволяет за проход принять больше уже готовых данных, сохраняя конечную границу перед следующим направлением и доменным тактом. Код — [GameProcessNetworkRuntime::run_turn](../../server/rust/src/gameserver/gameserver/runtime.rs).

Этот ограниченный drain не выполняет dispatch: сообщения остаются в прежних клиентских FIFO, а `CGame::process_messages` обрабатывает World → Billing → Game-клиентов на прежней стадии после AI. У World сетевые callbacks также только пополняют FIFO; число событий для доменного прохода по-прежнему снимает `CGame::process_message`. Причина разделения планирования — [ADR-0002](../decisions/0002-semantic-boundary.md).

## Таймеры, которые нельзя унифицировать механически

| Механизм | Условие и следствие в текущем коде |
| --- | --- |
| Первый receive принятого сокета | `CServer::expire_new_accepts`: `now.wrapping_sub(accepted_at) >= timeout`, default 8000 ms. Снимается при первом TCP-фрагменте, до проверки полного кадра и авторизации. Timeout ставит `QUIT` в следующий сетевой снимок. |
| Timeout AuthManager | `timeout < now.wrapping_sub(start)`, default 1000 ms; публикация локального ответа без удаления pending. Повторяется до обработки ответа. |
| Два таймера Auth server-info | `last.wrapping_add(interval) < now`. Таймер записи обновляется даже при отказе `push_db_quest`; обычного retry до следующего срока нет. |
| Ping World в Login | Запрос начинается при строгом превышении интервала и очищает прежний список ответов. В активном ping завершение по числу ответов и timeout проверяются независимо: один проход может записать оба события. |
| Server-info Login | При ненулевом интервале используется `interval <= now.wrapping_sub(last)`. Неблокирующий захват telemetry-lock может не добавить новые записи, но уже накопленные остаются доступны работнику. |
| Game pacing | Целевой шаг 80 ms; после ожидания deadline увеличивается на шаг. Если знаковое отставание от обновлённого deadline больше 1000 ms, он заменяется новым tick. Это не гарантия выполнения каждого такта за 80 ms. |

Методы для проверки: `CServer::acknowledge_first_receive` / `expire_new_accepts`, [AuthManager::run](../../server/rust/src/loginserver/loginserver/authmanager.rs), Auth `update_server_info`, Login `main_loop_turn`, Game `finish_main_loop_pacing`. Исходные свидетельства этих ветвей указаны в комментариях к ним; равенство поведения планировщика Windows и Tokio остаётся `UNKNOWN`.

## Инициализация и завершение

Auth, Login, Billing и World могут частично создать ресурсы, затем встретить ошибку. Освобождение должно учитывать реально созданных владельцев; действующие методы не выражают универсальное правило «сначала остановить всех производителей, затем всю сеть». World и Game описаны в [их жизненном цикле](world-and-game.md), а общая передача сигнала — в [модели процессов](process-model.md).

| Процесс | Значимый порядок освобождения |
| --- | --- |
| World | Остановить производителей событий → закрыть сеть → провести save barrier → дождаться DB-работников → освободить нужные им игровые данные. Для принятой сети `release_server` посылает stop и ждёт сетевую задачу: та останавливает accept, ставит `QUITALL`, проводит снимки до пустой карты и завершает I/O-задачи. Если задача не запускалась, этот путь выполняется напрямую. |
| Auth | `release_auth_runtime`: завершить DB-работников, затем сеть. `release_auth_network`: остановить accept → `QUITALL` → обрабатывать сетевые снимки до пустой карты клиентов → завершить I/O-задачи. |
| Login | `release`: сеть World → сеть Client → остановка reconnect и удаление Auth-клиента → очистка account-log и остановка account-log/GAS → освобождение DB/очередей и ожидание оставшихся DB-работников в их собственных позициях. |
| Billing | Присоединить DB-работников до сетевого `QUITALL`. |
| Misc | Выдержать 2005 ms → сформировать `MiscGameThreadRelease { exit_notice: true, ... }` → очистить комнату → уничтожить `CGame`. Сетевого notice в этом хвосте нет. |

Таблица описывает исполняемые методы освобождения, а не обещает доставку всех накопленных ответов. Пустая карта соединений и завершённые I/O-задачи сами по себе не означают, что все прикладные задания исполнены. World-сохранение дополнительно описано в [savedb](../../server/rust/src/worldserver/worldserver/savedb.rs). `SIGINT/SIGTERM` передаются через [process/mod.rs](../../server/rust/src/process/mod.rs); доменное завершение выбирает служба.

## Что может изменить поведение

Изменение позиции pop относительно callback или SQL влияет на возможность повтора. Поздняя ошибка не возвращает автоматически удалённую запись и не откатывает уже отправленные пакеты. Правила конкретных SQL-фаз находятся в [БД](../architecture/database.md).

FIFO сохраняет фактический порядок публикации в конкретную очередь. Между независимыми соединениями порядок определяется конкурирующими I/O-задачами, а между направлениями — местом снятия их очередей в цикле. Общего гарантированного порядка по времени сетевого прихода здесь нет. Исходное поведение при приостановке ОС остаётся `PARTIAL`.

На повреждённом пакете Rust может возвращать типизированную ошибку вместо неопределённого чтения старого кода. Исходная реакция в таких местах указывается в [протоколе](../protocol/README.md), а не выводится из безопасного поведения нового декодера.
