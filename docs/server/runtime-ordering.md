# Порядок серверных циклов и завершение процесса

Эта страница фиксирует порядок событий, который влияет на наблюдаемую семантику. Источники — конкретные owner-файлы с указанием точной пары EXE/PDB в их верхних комментариях. Статус `VERIFIED` здесь означает статически подтверждённую последовательность оригинального owner-а, **не** успешный запуск текущего Nebokrai.

## Общий принцип хода

Сеть и DB workers могут публиковать события асинхронно, но доменный владелец потребляет их в установленном месте основного цикла. В большинстве Auth/Login/Billing/World/Game проходов очередь снимается на текущий размер один раз; callback, добавивший сообщение во время обработки, не продолжает текущий snapshot. Поэтому замена циклов на «читать до пустоты» меняет relative ordering и потенциально таймеры. `MiscServer` отличается: его message FIFO снимается целиком и reconnect выполняется до следующего элемента. Это `VERIFIED` по [`Auth CGame`](../../server/rust/src/authserver/src/cgame.rs), [`Login CGame`](../../server/rust/src/loginserver/loginserver/game.rs), [`Billing CGame`](../../server/rust/src/billingserver/billingserver/game.rs), [`World CGame`](../../server/rust/src/worldserver/worldserver/game.rs), [`Game CGame`](../../server/rust/src/gameserver/gameserver/game.rs), [`Misc CGame`](../../server/rust/src/miscserver/miscserver/game.rs).

Все названные cadence в исходных владельцах используют 32-битные wrapping миллисекунды; проверка часто строго `interval < now.wrapping_sub(last)`, а не `<=`. Разница в один миллисекунд и поведение на переходе `u32` являются частью достигнутого порядка. `CLOCK_BOOTTIME` и управляемые задачи Rust заменяют платформенный счётчик и detached Win32 threads, но не разрешают менять размещение таймера относительно сообщений. Статус `VERIFIED` для указанной арифметики; идентичность при системной приостановке во всех вариантах Windows `PARTIAL`.

| Процесс | Значимый порядок одного хода | Особая граница |
| --- | --- | --- |
| Auth | Снимок очереди сообщений → снимок DB results → server-info по двум независимым wrapping таймерам. | Due-таймер server-info обновляется даже при отказе переполненной DB-очереди. [`cgame.rs`](../../server/rust/src/authserver/src/cgame.rs), `VERIFIED`. |
| Login | GAS notices → account-log notices → сообщения **World → Client → Auth** → login queue → ping World → server-info. | Перед ping очищаются прежние ответы; запрос идёт один раз до завершения или timeout. Ошибка обработчика не откатывает префикс. [`game.rs`](../../server/rust/src/loginserver/loginserver/game.rs), [`message/mod.rs`](../../server/rust/src/loginserver/applogin/message/mod.rs), `VERIFIED` для указанных стадий. |
| Billing | Снимок message FIFO, refresh до exit-check, раздельные cadence информации и ping. | Ping-флаг выставляется однократно, процесс выдерживает паузу 1 ms. [`game.rs`](../../server/rust/src/billingserver/billingserver/game.rs), `VERIFIED`. |
| World | Предварительный save gate → World AI → сообщения → session factory → player-data queue → timer/войны → DB misc → сетевые сессии → ping и последующие периодические стадии. | Поздний блок останавливает текущий ход после уже выполненного префикса; полного rollback нет. [`game.rs`](../../server/rust/src/worldserver/worldserver/game.rs), `VERIFIED` для достигнутого исходного порядка, полнота всех хвостовых ветвей `PARTIAL`. |
| Game | Проверка exit → scripts → AI → сообщения **World → Billing → Game** → team/session maintenance → net sessions → auction → pacing. | При включённом профилировании сохраняется тот же порядок, лишь замеряется время. Интервал хода 80 ms; опоздание более 1000 ms перенастраивает deadline. [`game.rs`](../../server/rust/src/gameserver/gameserver/game.rs), `VERIFIED` для порядка и констант. |
| Misc | AI → message FIFO → reconnect → confirm, затем пауза 50 ms. | Первое соединение добавляет sync; reconnect регистрируется иначе, и после отказа client отсутствует. Shutdown tail: 2005 ms → notice → очистка auction room. [`game.rs`](../../server/rust/src/miscserver/miscserver/game.rs), `VERIFIED`. |

У Game и World периодические операции привязаны не к абстрактной частоте кадров, а к местам основного прохода. Например Game сначала запускает scripts и AI, потом доставляет сообщения. Команда, появившаяся из сообщения, не исполняет предыдущий AI в том же ходе. Это прямое следствие найденного порядка (`INFERRED` как поведенческое объяснение, исходная последовательность `VERIFIED`).

## Инициализация и остановка

- `Init` может частично создать listener, worker или DB owner и затем ошибиться. Auth, Login, Billing и World в достигнутых владельцах всё равно проводят `Release` над уже созданным состоянием; повторный `Release` не повторяет завершённые сетевые стадии. Источники: указанные `CGame` owner-ы, статус `VERIFIED` для этих процессов. Обобщать это на всякий ещё не восстановленный process нельзя (`UNKNOWN`).
- World останавливает производителей событий, закрывает сеть, проводит **save barrier**, дожидается DB/workers и только затем уничтожает игровые владельцы, чьи snapshots могли быть нужны worker-у. Преждевременное освобождение изменило бы не только безопасность памяти, но и то, какие данные успевают сохраниться. Источник: [`worldserver/game.rs`](../../server/rust/src/worldserver/worldserver/game.rs), [`savedb.rs`](../../server/rust/src/worldserver/worldserver/savedb.rs), [`runtime.rs`](../../server/rust/src/worldserver/worldserver/runtime.rs); статус `VERIFIED` для найденного lifecycle.
- Auth останавливает accept, публикует `QUITALL`, ожидает опустевшую карту клиентов и потом завершает I/O. Billing присоединяет DB workers до сетевого `QUITALL`. Эти разные порядки не надо искусственно унифицировать. Источники: [`authserver/cgame.rs`](../../server/rust/src/authserver/src/cgame.rs), [`billingserver/game.rs`](../../server/rust/src/billingserver/billingserver/game.rs); статус `VERIFIED`.
- `SIGINT`/`SIGTERM` в [`process/mod.rs`](../../server/rust/src/process/mod.rs) — техническая Linux-замена способа запросить остановку; она не переносит доменные эффекты из owner-а в signal handler. Статус текущей реализации `VERIFIED` по коду, эквивалентность всем сценариям завершения оригинального Windows UI `PARTIAL`.

## Ошибки и неизвестное

Типизированный Rust-отказ на усечённом сообщении или отсутствующем owner-е безопаснее прежнего неопределённого чтения/указателя, но это сознательная граница технической замены: наблюдаемое поведение оригинала для malformed входа часто `UNKNOWN`. Ошибка после частично выполненного хода не подразумевает откат. Время доставки между **разными** TCP-соединениями и линейный глобальный порядок всех сообщений `UNKNOWN`; FIFO и стадийность доказаны для конкретного владельца, а не для распределённой системы в целом. Проверка реального cadence при нагрузке и исходным клиентом ещё не проводилась.
