# Auth, Login, Billing и Misc

Эти службы обслуживают вход, операции со счётом и аукцион. Общая схема запуска описана в [модели процессов](process-model.md); здесь показаны рабочие маршруты и места изменения кода.

## Login выбирает маршрут входа

Login сохраняет связь account с ожидающим клиентом и выбранным World, управляет очередью входа и дополнительными проверками. Auth — один из возможных исполнителей проверки пароля. После разбора [клиентского запроса](../protocol/login-auth.md) `CLoginQueue::on_quest_cdkey` выбирает путь в следующем порядке:

| Условие | Что происходит |
| --- | --- |
| В запросе непустой `world_server` | Создаётся `TagPwdChecked` с `has_matrix = false`; вызываются `prepare_enter` и, если нужно, `enter_game`. Эта ветвь предшествует выбору режима и проверке пароля ниже. |
| World не указан, `inside_use == 0` | Запрос помещается в GAS-очередь. |
| World не указан, `inside_use` отличен от `0` и `1` | Возвращается `InsideModeIgnored`, дальнейшей проверки нет. |
| World не указан, `inside_use == 1` | Сначала локальные проверки account, ban, IP и matrix; затем при подключённом Auth создаётся Auth-запрос, иначе вызывается локальная проверка пароля. |

Это фактический выбор ветвей в [loginqueue.rs](../../server/rust/src/loginserver/loginserver/loginqueue.rs), а не рекомендация обходить проверку учётной записи. При изменении входа нельзя делать Auth обязательным этапом для всех путей без пересмотра этого контракта. Обычный и расширенный клиентские запросы также различаются порядком чтения и нормализацией account; общий смысл «войти» не делает их взаимозаменяемыми.

Успешная проверка ещё не завершает вход. `TagPwdChecked` передаётся в `handle_pwd_checked`, где учитываются ошибочные valid-code, при необходимости выдаётся картинка, выполняется matrix-проверка и продолжается `prepare_enter`/`enter_game`. Ответ Auth с кодом `0` создаёт эту запись с **пустым** World и `has_matrix = false`; локальный пароль использует свой полученный matrix-флаг. Реализация продолжения — [AuthHandler::on_response](../../server/rust/src/loginserver/loginserver/authhandler.rs) и `CLoginQueue::complete_checked_entry`.

## Асинхронная проверка через Auth

Login хранит ожидающий запрос в `AuthManager`, а Auth владеет отдельной очередью DB-заданий и очередью результатов. Так ответ можно вернуть через прежнее Login-соединение, не передавая DB-потоку клиентский сокет или весь `CGame`.

1. `AuthManager::add_quest` отбрасывает точный дубликат account. Новую запись добавляет в хвост **до** постановки сообщения `0xCF501`, затем вызывает `on_quest`. Ошибка построения отправки не откатывает запись.
2. Auth разбирает запрос в `AuthMessageHandlers` и ставит `DbQuest`. В задании раздельно хранятся `return_socket_id` соединения Login→Auth и переданные Login данные конечного клиента. Работники возвращают `DbResult`; основной Auth-проход строит ответ в `process_database_results`.
3. Login получает `0xCF601` через Auth-очередь. `AuthManager::on_response_auth` ищет pending **по account**, удаляет запись и только затем вызывает listener. IP и socket конечного клиента берутся из ответа; отдельной сверки этой пары с удалённой записью здесь нет. Повтор после удаления получает `InvalidResponse`.
4. Listener переводит успех в `TagPwdChecked`, а отказ — в клиентский код. Только default-код ошибки пароля дополнительно меняет счётчик ошибок; остальные отказы нельзя приравнивать к неверному паролю.

Точки изменения — [AuthManager](../../server/rust/src/loginserver/loginserver/authmanager.rs), [AsMessageHandlers](../../server/rust/src/loginserver/applogin/message/asmessage.rs), [AuthMessageHandlers](../../server/rust/src/authserver/appauth/message/message_func.rs), [Auth CGame](../../server/rust/src/authserver/src/cgame.rs). Wire-поля этой пары приведены в [протоколе входа](../protocol/login-auth.md).

Timeout AuthManager публикует в ту же очередь локальный `0xCF601` с результатом `4`. Он не удаляет pending и не обновляет время старта, поэтому может публиковаться повторно до обработки первого ответа. Поздний реальный ответ конкурирует с ним за ту же запись account. Следствие для расширения: нельзя обещать корреляцию по уникальному request ID или автоматический повтор операции — таких механизмов здесь нет.

Auth ограничивает очередь заданий настройкой `max_auth_queue_size`. При отказе `AuthDbContext::push_quest` сам публикует отрицательный результат: для проверки account — код `6`, для блокировки — `false`; для `WriteServerInfo` ответ не создаётся. Это прикладная реакция перегрузки, отдельная от сетевых лимитов. SQL-контракты находятся в [описании БД](../architecture/database.md).

## Очередь входа и дополнительные проверки

`CLoginQueue` хранит несколько стадий ожидания. Обычная CD-key FIFO пропускает одну запись при наступлении своего срока; очереди списка и данных персонажа разделены по World. Есть отдельные очереди обхода ожидания, очередь проверенных паролей, valid-code и matrix. Благодаря такому разделению Login может дозировать обращения к World, сохраняя ожидающего клиента после проверки пароля. Это вывод из структуры и порядка `CLoginQueue::run`, а не установленный исторический мотив.

Правила удаления различаются. Повторный `TagPwdChecked` вызывает `kick_out` под lock, затем заменяется новой записью в хвосте. `handle_pwd_checked` разбирает очередь под тем же lock, включая callbacks; добавляя callback, нельзя повторно входить в этот mutex. Valid-code удаляется при успехе или несовпадении endpoint, но сохраняется при неправильном коде. Matrix-запись расходуется после любой проверки. `on_client_lost` удаляет только предусмотренные первые совпадения обычных очередей; это не полная очистка всех стадий account.

В `run` сохранена локальная странность: проход по снимку GAS вызывает `on_quest_cdkey`, после чего очищает **no-queue CD-key FIFO**, а не GAS. В режиме `inside_use == 0` вызов снова добавляет GAS-запрос. Работник GAS также потребляет эту очередь, поэтому результат зависит от того, какие записи достались каждому проходу; сводить их к одной очереди с однократной обработкой нельзя. Источник исходного правила — Login EXE/PDB в `loginqueue.rs` (`VERIFIED` для указанной ветви); исходная гонка производителей и потребителей остаётся `UNKNOWN`.

## Внешняя проверка GAS

[CGasThread](../../server/rust/src/loginserver/applogin/gasthread.rs) выполняет HTTP-проверки через [CMyWinInet](../../server/rust/src/loginserver/applogin/mywininet.rs) в отдельном blocking-потоке. После проверки работник публикует владеющий `GasWorkerEvent` и ждёт подтверждения: основной Login-проход выполняет `apply_worker_event`, применяет DB/сетевые эффекты и подтверждает завершение до следующего запроса. Это существенно сильнее простого «HTTP работает в фоне»: медленный основной цикл задерживает следующий GAS-запрос, зато один работник не обгоняет собственный предыдущий результат. Пауза пустой очереди — 10 ms.

Конкретные открытые вопросы:

- Исходный default `verification_sign_upper` не установлен (`UNKNOWN`). При отсутствии значения GAS возвращает `SignatureUppercaseMissing`.
- Для высокобитных ANSI-символов учётной записи не установлена исходная карта регистра (`UNKNOWN`); соответствующая ветвь очереди отклоняется явно.
- Исходная схема `userinfo` отсутствует в найденных backup. [Локальная проекция](../architecture/database.md) описана как допущение стенда.

CD-key, IP, локальный пароль и matrix-card используют [rscdkey](../../server/rust/src/dbaccess/logindb/rscdkey.rs).

## Billing: запрос, рабочая очередь, ответ Game

Billing принимает от Game запросы баланса, покупки и обмена. Основной цикл разбирает пакет и передаёт владеющую запись в `CBillingPlayerManager`; DB-работник снимает сначала запросы баланса, затем сделки и строит ответы через `ServerCommandHandle`. Ответ не возвращается для отправки в основной доменный цикл Billing: он сразу становится командой сетевого слоя. Реализация — [BillingMessageHandler](../../server/rust/src/billingserver/appbilling/billingmessage.rs) и [CBillingPlayerManager::run](../../server/rust/src/billingserver/appbilling/billingplayermanager.rs).

`game_server_id` в рабочей записи здесь хранит **socket ID принятого соединения**, полученный из метаданных сообщения. Это адрес ответа, а не переданный в payload номер Game. Поле `session_id` имеет смысл конкретного запроса: в Increment Shop это ID скидочного товара, в обмене — связь с сеансом/участником. При отключении Game очередь не превращается автоматически в журнал доставки для нового соединения: поздняя адресная send-команда может не найти прежний socket. Таблица запросов и ответов — в [каталоге opcode](../protocol/opcode-catalog.md).

DB-ветвь сделки выбирается по пустоте `seller_identity`, а не только по `trade_type`. Наличие обработчика ответа также не подтверждает подключение всех отправителей. Полный путь применения оплаты, короткий отказ `0xFF003`, неподключённые ветви лавки/комиссии и повторы разобраны в [аукционе и платежах](../gameplay/auction-and-payments.md).

У балансов и сделок разные FIFO, поэтому они не сохраняют общий порядок TCP-запросов после передачи работнику. Например, баланс, поставленный позже сделки, может попасть в балансовый снимок раньше обработки сделки. При изменении порядка следует прослеживать очередь, момент её снятия и отправку ответа вместе.

У покупки есть важная граница ошибки: `goods_number > 1000` проверяется **после** вызова DB-операции и постановки полученного increment-log. Затем работник записывает диагностику и возвращает `false`, не формируя ответ этой покупки. Необработанный хвост уже снятого локального списка сделок уничтожается. Это не отказ валидации до побочных эффектов; перемещение проверки меняет контракт. Правила самих DB-операций описаны [отдельно](../architecture/database.md).

Отдельный [rsplayerfillmgr](../../server/rust/src/dbaccess/dbbilling/rsplayerfillmgr.rs) обрабатывает ожидающие пополнения. Выборка максимум 50 записей `TBL_NeedUpdate` по ID и удаление обработанного набора описаны в [БД](../architecture/database.md). Основное подключение и cash-log настраиваются отдельно; служба читает `Setup.ini` и `GSInfoSetup.ini`.

При изменении покупки прослеживайте и DB-результат, и ответ Game. Игровые расчёты магазина и обмена описаны в [торговле](../gameplay/trade.md).

## Misc: комната аукциона и связь с World

Misc хранит комнату аукциона и обслуживает её AI перед входящими сообщениями. Команды World изменяют её состояние и формируют ответы; окончательные операции хранения остаются за World. Живой контейнер — [CAuctionRoom](../../server/rust/src/public/auctionroom/aucitionroom.rs), подключённый как модуль `public::aucitionroom`; диспетчер — [Misc CGame::process_message](../../server/rust/src/miscserver/miscserver/game.rs), команды — [on_msg_w2m_auction](../../server/rust/src/miscserver/miscserver/miscservermessage.rs).

Первое подключение ставит регистрацию `0x5FA01` с `byte(0)`, `long(listen_port)` и C-строкой локального IP, затем пустой sync-запрос `0x15EB05`. `reconnect` создаёт нового сетевого клиента, регистрируется с портом `0x092F` и не посылает initial sync. Адрес подключения по-прежнему берётся из настроек World: `0x092F` — поле регистрации, а не замена TCP-порта назначения. Это `VERIFIED` для исходной Misc-ветви по EXE/PDB в `game.rs`; причина выбора регистрационного порта остаётся `UNKNOWN`.

EOF публикует локальное `0x16EA01`. Его обработчик ставит `client_close` и дожидается одной попытки reconnect **до следующего элемента уже снятой FIFO**. Если она не удалась, `net_client` отсутствует, флаг остаётся установленным. Тогда хвост того же такта делает ещё одну попытку и пытается поставить `0x10EF00`; при отсутствии клиента `send` возвращает `Ok(0)`. Успешное первое восстановление сбрасывает флаг и не заходит в этот хвост. Поэтому формула «любой reconnect затем confirm» неверна. Реализация — [on_msg_m2m_function](../../server/rust/src/miscserver/miscserver/onbillserver.rs), `run_game_thread_turn` и `connect_world`.

Reconnect заменяет объект с его сетевыми очередями, но не пересоздаёт `CAuctionRoom`. Команда очистки комнаты тоже отдельна: `0x16EA02` сначала вызывает `clear`, затем пытается ответить `0x15EB05`; отказ отправки не возвращает содержимое комнаты. Неполные goods-пакеты останавливаются на десериализации, сохраняя уже выполненные изменения и счётчики. Порядок AI → команда → ответ важен и при исправлении аукциона, и при восстановлении соединения.

## Очереди и завершение

Очереди сетевых команд, сообщений и прикладных заданий имеют разных потребителей. Их модель и порядок добавления нового сообщения описаны в [сетевом runtime](network-runtime.md); точные границы снимков, таймеры и освобождение ресурсов — в [серверных циклах](runtime-ordering.md). Для изменения служебной операции прослеживайте не только handler, но и удаление задания из очереди, адрес ответа и реакцию на отключение.
