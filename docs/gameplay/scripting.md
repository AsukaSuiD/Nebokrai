# Сценарии: исполнение, ожидание и сохранение

Сценарии связывают игровые проверки и действия: диалог NPC, использование предмета, выдачу задания, награду, реакцию на вход или смерть игрока. World загружает тексты и рассылает их Game; Game исполняет команды над живым состоянием. В подключённом World-модуле `appworld/script` есть хранилище общих переменных, но нет отдельного исполнителя сценариев. Запрос World «запустить сценарий игрока» маршрутизируется в Game. Это применение принятой [границы World/Game](../decisions/0005-world-game-boundary.md).

Общий путь состоит из ресурсов и реестра команд в [Zone content](../../server/rust/zone/src/content/), активных экземпляров в [Game `CGame`](../../server/rust/src/gameserver/gameserver/game.rs), [интерпретатора](../../server/rust/src/gameserver/appserver/script/script.rs) и [диспетчера игровых функций](../../server/rust/src/gameserver/appserver/script/function.rs). Им пользуются разные игровые события: отдельный исполнитель для каждого вида задания или предмета не нужен. Ниже описаны действующий механизм и его ограничения; ограничения сами по себе не являются рекомендуемыми архитектурными решениями. Правила заданий находятся [на отдельной странице](quests.md).

## От файла до ресурса Game

При инициализации World профиль `ScriptFile` вызывает `CGame::load_script_file_data`, который передаёт загрузку в [Realm content/scripts.rs](../../server/rust/realm/src/content/scripts.rs). `ScriptResources` владеет текстами функций, переменных и картой сценариев; выбирает источник списка, порядок чтения и замены. Это обязанность Realm content: подготовить содержимое для передачи Zone. Исполнитель, очередь и состояние персонажа сюда не входят. Shared предоставляет индекс, пакеты и чтение ресурсов. Переходный `WorldScriptLoadContext` связывает Realm с установленным ресурсным контекстом и уведомлениями. Старый World сохраняет запуск загрузки и рассылку, но больше не владеет тремя отдельными полями с этими данными.

Параметры каталога сценариев и `general_variable_data.ini` прежнего метода не используются: Realm обращается к фиксированному `scripts`. Общие переменные World загружаются отдельно из `data/general_variable.ini`, затем из БД. Перечень стартовых профилей — в [World game.rs](../../server/rust/src/worldserver/worldserver/game.rs).

Загрузчик сначала очищает прежние ресурсы. Отсутствие файла функций или переменных прекращает загрузку с уже выполненными изменениями; отказ переменных оставляет загруженный файл функций. `load_one` заменяет существующий сценарий только после успешного чтения, убирает один начальный обратный слеш и заменяет остальные на `/`, без приведения регистра. `get` ищет исходный путь до первого NUL без такой нормализации. Сами тексты хранятся целиком; C-string-представление для сообщения выбирает отправитель.

Если установленный индекс содержит `\scripts`, Realm получает `.script` через `ResourceCatalog::find_file_list`. Даже пустой индексный список завершает выбор источника: добавлять к нему дисковые файлы нельзя. При отсутствии индексного корня используется дисковый обход `scripts/*.*`. Наличие записи в индексе не доказывает доступность пакета: каждый путь затем читается обычным resource-механизмом, и ошибка отдельного сценария не останавливает остальные. Это исправляет прежнее расхождение Rust, где загрузка всегда выбирала диск и пропускала сценарии, существовавшие только в пакетах.

`ScriptLoadReport` содержит источник списка (`Index`/`Disk`) и число успешных/неудачных чтений. Это диагностика Rust: прежний общий bool остаётся успешным после загрузки двух обязательных файлов, даже при отказах отдельных сценариев. World пишет предупреждение о частичной загрузке. Отказ обязательного файла возвращается отдельно, с сохранением уведомления оператору и частичного состояния. Очистка принадлежит `ScriptResources`; при `Release` адаптер использует возвращённые признаки освобождения для прежнего журнала событий.

Дисковый поиск выделен в [Realm content/scriptfiles.rs](../../server/rust/realm/src/content/scriptfiles.rs), публичный интерфейс — `nebokrai_realm::content::find_script_files`. Это подготовка содержимого Realm: компонент собирает файлы для загрузки и передачи, но не владеет исполняемыми сценариями или очередью Game. Переходный адаптер `WorldReloadContext::script_files` передаёт корень установленного `DefaultClientResourceOwner`, включая контекст с недоступным индексом. Без установленного контекста используется `.` — как при прямом дисковом чтении. Поиск больше не выбирает отдельный cwd при уже установленном другом корне.

Обход использует `walkdir` с прежним `follow_links(false)`. Корень на диске разрешается через общий `resolve_resource_path` по [ADR-0012](../decisions/0012-resource-path-case.md): например, буквальный запрос `scripts` может найти `Scripts`; неоднозначность или отказ доступа возвращаются как ошибки. Расширение сравнивается без учёта ASCII-регистра. Из найденного физического пути убирается добавленный корень, после чего собирается логический путь исходного шаблона, приводится к ASCII lowercase и `/`. Для шаблона `scripts/*.*` ключ остаётся `scripts/npc/...`, без host-префикса вроде `/runtime/World/`. Список сортируется, как и прежде; исходные байты имён на Unix сохраняются до ASCII-преобразования.

Результат `ScriptFileScan` содержит найденные пути и ошибки разрешения корня/обхода. Ошибка части дерева не отменяет найденные файлы; вызывающий владелец пишет причины и сводку неполного поиска. Этот отчёт относится только к дисковой ветви и не вводит нового барьера запуска. Сводка `ScriptLoadReport` считает чтения полученного списка, а не полноту дискового обхода; ошибки обхода журналируются отдельно.

### Основание загрузки и границы проверки

Проверена сборка `Nworldserver.exe`: SHA-256 `f3ac454daf83e7e9c8f844c725be2c5a24efa946c27d75319cfcb68a2f466ef1`, ImageBase `0x00400000`. `WorldServer.pdb`: SHA-256 `04e2cc4ce1187a3aab455566ddc39e72ed7568cab0edbd731b4f84629f6ef1e4`; GUID `289f1fb3-96a0-4ff4-8b5d-1fd17b50b751`, age `1` совпадают с CodeView EXE. Соседние `worldserver.exe` и `worldserver (2).exe` имеют другой GUID; эти адреса к ним не относятся. Основание — инструкции и данные EXE; пропуски в границах функций Ghidra после `operator delete/free` дополнительно прочитаны непосредственно из PE.

Дисковый поиск остаётся `PARTIAL` по отношению к Win32: `FindScriptFile` (`0x004106e0`) рекурсивно ищет сценарии и вызывает `_strlwr`, но сразу после `FindFirstFileA` вызывает `FindNextFileA` без обработки первой записи (`0x00410726–0x0041074c`). Rust продолжает обрабатывать все найденные файлы, сортирует их и использует ASCII-регистр; тождество порядка Win32, поведения первой записи и не-ASCII имён не установлено. Эти свойства прежней Rust-ветви не объявляются подтверждённым поведением оригинала. Явный корень, разрешение регистра каталогов и отчёт ошибок — инфраструктура Rust. Формат сообщений и поведение горячей перезагрузки этим исследованием заново не подтверждались.

### Передача Game

World передаёт ресурсы сообщениями `0x7F801`:

| Селектор, в порядке начальной передачи | Применение в Game |
| --- | --- |
| `0x0A`, текст `FunctionList` | Построить соответствие точного имени команды числовому ID. |
| `0x0B`, текст `VariableList` | Сохранить объявления для последующей загрузки переменных. |
| `0x0C`, общие переменные World | Загрузить объявления Game и наложить значения снимка. |
| `0x0D`, путь и байты сценария | Вставить или заменить один ресурс. |

Отправитель — `continue_game_server_*_configuration` в [World `servermessage.rs`](../../server/rust/src/worldserver/appworld/message/servermessage.rs), получатель — `decode_script_startup` в [Game `servermessage.rs`](../../server/rust/src/gameserver/appserver/message/servermessage.rs). При загрузке текст не компилируется. Game сравнивает пути побайтно до первой NUL, без изменения регистра и разделителей; World передаёт текст сценария до первой NUL. Поэтому путь из каталога задания и ключ ресурса должны совпадать, даже если файловая система допускает другие написания.

Перезагрузка имеет текущие ограничения. `reload_one_script` меняет ресурс для будущих запусков: существующий `ActiveScript` уже хранит копию текста. Полный `send_script_reload_data` не удаляет из Game исчезнувшие пути. Кроме того, `reload_one_script` после нормализации ключа ищет ресурс по исходному пути и может вернуть `WorldReloadOneScriptBlock`. Эти ограничения не означают запрета заменять списки функций и переменных: прежний ранний выход `RepeatedOwnerFreed` был ошибкой Rust-реконструкции и удалён.

### Установка ресурсов в Zone

[Zone content/scripts.rs](../../server/rust/zone/src/content/scripts.rs) содержит `ScriptResources`: полученные тексты функций и переменных, карту сценариев, операции установки, чтения и очистки. Это отдельный от Realm владелец: Realm получает файлы из ресурсного каталога, а Zone применяет уже доставленные данные. Повторять в Zone загрузку с диска или пакетов не требуется. Старый Game `CGame` вызывает библиотеку и предоставляет данные игрокам, обработчику снимка общих переменных и будущим запускам сценариев; самостоятельные поля с этими буферами удалены.

`set_functions` освобождает старый буфер, устанавливает новый и каждый раз вызывает перестроение реестра по тексту до первой NUL. [ScriptFunctionRegistry](../../server/rust/zone/src/content/functions.rs) также находится в Zone content; формат читает [Shared scripting/functionlist.rs](../../server/rust/shared/src/scripting/functionlist.rs). Game связывает два владельца и журналирует результат; интерпретатор остаётся в прежнем пакете. `set_variables` также всегда устанавливает новый буфер; переинициализация значений уже загруженных персонажей этой операцией не выполняется. Потребители новых объявлений читают один буфер Zone, включая декодирование персонажа и его регистрацию.

`set_script` вставляет или заменяет текст под исходным ключом до первой NUL. Регистр и разделители ключа не меняются; `script` ищет его по тому же правилу. Переданный буфер пути теперь используется во владении без прежнего дополнительного копирования. `clear` освобождает только ресурсы; Game отдельно вызывает очистку реестра Zone и освобождение активных экземпляров и общих переменных. `Published`/`Replaced` и признаки освобождения — диагностика Rust, а не исходные ответы протокола.

Основание: `gameserver.exe`, SHA-256 `4f5c98e0fdf6147d8aecf55f7937aaf6e2cf5e4f5a2c44491a6359228762c80e`, ImageBase `0x00400000`; `GameServer.pdb`, SHA-256 `b17bb9b7d69a9cc43e314c0e35c517830bb42caa89416e173380ab17d2d66016`. CodeView EXE и PDB совпадают: GUID `5bee6dd1-bf90-49b8-8be9-eb25c4038d53`, age `2`. Инструкции сопоставлены с байтами EXE; продолжения после `operator delete` прочитаны непосредственно из PE.

| Установленный факт | Прямое основание, VA этой сборки | Статус |
| --- | --- | --- |
| Повторный FunctionList заменяет старый буфер и снова вызывает LoadFunction | SetFunctionFileData `0x00402310–0x0040233d`; после delete `0x00402320–0x00402334` нет раннего возврата | VERIFIED |
| Повторный VariableList устанавливается после освобождения старого буфера | SetVariableFileData `0x00402340–0x0040236d`; запись нового указателя `0x00402350–0x0040235e` | VERIFIED |
| LoadFunction очищает прежний реестр и строит новый | CScript::LoadFunction `0x0042915a–0x004291f6`, включая продолжение после освобождения прежней map | VERIFIED |
| SetScriptFileData заменяет значение существующего ключа или вставляет новый; Set/Get используют исходный C-string без преобразования пути | `0x0040b4b0–0x0040b745`, `0x00428c00–0x00428d1d` | VERIFIED |

Эта таблица относится к владению буферами и вызову обновления реестра. Правила самого FunctionList установлены ниже; wire-decoder и поведение активного интерпретатора при reload этим исследованием заново не подтверждены.

### Разбор FunctionList и реестр команд

Shared `FunctionListRecords` читает определения без доступа к игровому состоянию. Zone `ScriptFunctionRegistry` очищает прежнюю карту, добавляет прочитанные имена и предоставляет поиск по исходным байтам до NUL. Последнее объявление одинакового имени заменяет прежний ID. `FunctionRegistryLoadReport` возвращает числа прочитанных записей, замен и итоговых имён, а также первую ошибку. Формат и хранение разделены, поэтому игровой интерпретатор не нужен для загрузки реестра.

Применяются следующие правила memory-ветви CIni из указанной выше сборки Game:

- Текст ограничен первой NUL. Секция начинается с `[` в нулевой позиции или сразу после LF. Имя секции сравнивается побайтно; начальные пробелы и заголовок без `[` не принимаются. Используется первое совпадение. Имя заголовка читается тем же способом, что и значение: до `;`, LF, CR, табуляции или `]`.
- Записи начинаются после LF заголовка. Блок заканчивается перед строкой, первый байт которой — CR, LF, пробел, табуляция, `/`, `0xff` или `0xfd`. Начало следующей секции само по себе в оригинале не является таким терминатором: разделять секции нужно разрешённой границей блока.
- Подпись ID читается до CR, `=` или `;`. Поиск значения идёт до `=` либо CR; LF сам по себе этот поиск не останавливает. Значение после `=` заканчивается на `;`, LF, CR, табуляции или `]`. Пробелы вокруг имени не удаляются. Например, `6=Wait;comment` задаёт имя `Wait`, а `6= Wait ` — имя с пробелами.
- ID читает начальный десятичный префикс со знаком; отсутствие цифр даёт ноль. Накопление и смена знака оборачиваются в 32 битах: `4294967295` даёт `-1`, а не `i32::MAX`. Пропуск пробельных символов воспроизведён для ASCII; зависимость CRT от иной локали не установлена.

Rust прежде использовал `section_records` из переменных: принимал дополнительные варианты заголовка, обрезал имена и иначе завершал блок. Общий проход CIni теперь находится в [Shared scripting/ini.rs](../../server/rust/shared/src/scripting/ini.rs); FunctionList и VariableList используют его с отдельными правилами преобразования записей. Реестр не добавляет скрытых имён: прежняя безусловная запись `AddJingJieBuff = 11131` удалена, поскольку LoadFunction исследованной сборки только читает файл и не выполняет такую регистрацию. Она также могла перезаписать явное объявление с другим ID. Утверждение прежнего комментария о регистрации в «позднем GameServer» не подтверждено идентифицированным артефактом; обработчик ID 11131 остаётся, но имя должно прийти из данных.

| Установленное правило | Прямое основание, VA той же сборки Game | Статус |
| --- | --- | --- |
| Memory-источник до NUL, позиции секций и побайтный выбор первой | CIni::Open `0x004c4fa5–0x004c4fd8`, InitIndex `0x004c4d50–0x004c4e14`, FindIndex `0x004c50c0–0x004c5159` | VERIFIED |
| Терминаторы блока и чтение подписи/значения без trim | GetContinueDataNum `0x004c5340–0x004c53c7`, ReadCaption `0x004c52c0`, ReadDataName `0x004c4e20`, ReadText `0x004c5160` и `0x004c4e90` | VERIFIED |
| Накопление ID и смена знака с 32-битным переполнением | Вызов atoi `0x00429215`; переход `0x0061bb53 → 0x0061bacb`, арифметика `0x0061bb3d–0x0061bb50` | VERIFIED |
| Повтор имени перезаписывается; после чтения нет дополнительной регистрации | LoadFunction `0x00429266–0x00429307` | VERIFIED |

Безопасные границы Rust отделены от этих правил. Отсутствующая секция, заголовок без последующих данных, подпись длиной 64 байта и более или отсутствие `=` до CR/конца возвращают `FunctionListError` со смещением. В оригинале соответствующие ветви могут обращаться за границы памяти или освобождать статическую пустую строку; их итог не определяется как совместимый успешный результат. Новый буфер уже опубликован, реестр очищен и содержит только прочитанный префикс; отката в Rust нет. Это явная политика отказа, не подтверждение исходного поведения повреждённых данных. Game возвращает ошибку загрузки и не пишет `FunctionList...OK!`. Прерывание всего запуска процесса этим изменением не вводится.

## Контекст события и очередь исполнения

Вызывающий код передаёт путь и `ScriptExecutionContext`: ID игрока, NPC и региона, GUID использованного предмета, индекс погибшего монстра и точку выпадения предметов. Ненужные поля пусты. Контекст хранит идентификаторы, а не заимствования объектов на всё время ожидания: планировщик заново проверяет игрока, игровые функции разрешают остальные нужные им объекты.

Реальные входы показывают, как пользоваться этим механизмом:

- Диалог NPC в `dispatch_player_message` после проверки игрока, NPC, региона и расстояния передаёт `player_id/npc_id/region_id`. Сценарий предмета там же получает `used_item_id`. См. [обработчик игрока](../../server/rust/src/gameserver/appserver/message/playermessage.rs).
- [Обработчик навыков](../../server/rust/src/gameserver/appserver/message/skillmessage.rs) строит путь в `scripts/skills/` и передаёт игрока и регион.
- `complete_world_player_login`, повышение уровня и смерть игрока в [Game](../../server/rust/src/gameserver/gameserver/game.rs) берут общие пути из `CQuestSystem`. Обработка смерти монстра ставит его сценарий и `scripts/monster/monster_all.script` с контекстом получателя награды и места смерти.
- World-пересылка `0x6013D → 0x7FE3A` в парных `organsysmessage` приводит к тому же `queue_player_script` в Game.

`run_script_file` только ставит экземпляр в `active_scripts`; `Option<i32>` сообщает результат постановки, не исполнения. `queue_player_script` дополняет контекст текущим регионом. Общий `queue_script_file` требует `player_id`, отказывает при уже стоящей в карте паре «игрок, точный путь», удаляет ожидающие диалоги этого игрока (`2307/2309/2324`), затем ищет текст и выделяет ID через `wrapping_add`. Даже отсутствующий новый файл поэтому может закрыть прежний диалог. Проверка дубликата относится к карте: текущий исполняемый экземпляр временно вынут из неё.

`ActiveScript` хранит текст, байтовую позицию, контекст, локальные словари, ожидаемую функцию и таймер. Временный `CScript` получает эти данные на один шаг и возвращает изменённую позицию и переменные. Практический смысл этой организации — сохранить исполнение между проходами, не создавая поток на каждый сценарий и не удерживая ссылку на игрока через ожидание.

В `CGame::main_loop` стадия `run_script_loop` идёт перед AI и сообщениями; полный порядок — в [серверном цикле](../server/runtime-ordering.md). Планировщик берёт снимок ID из `BTreeMap` в порядке ключей и исполняет каждый экземпляр до завершения или ожидания. При отсутствии игрока экземпляр отбрасывается. Запуск из обработчика сообщения обычно начнётся на следующем проходе. Дочерние запуски от `call` и истёкшего `RunTime` специально добавляются в текущий список обхода.

`call` создаёт отдельный экземпляр с тем же контекстом и пустыми локальными словарями. Родитель продолжает после `call` на следующем проходе, даже если дочерний сценарий ещё ждёт. Стек вызовов, ожидание завершения дочернего файла и передача его `return` родителю здесь не реализованы. Непосредственный `run_script_line`, используемый обработчиком GM-команды, создаёт временный экземпляр с ID `0`, выполняет шаг и отбрасывает его вместе с возможным ожиданием. Для операции, которой нужно продолжение, этот вход не заменяет очередь файлов.

## Разбор и вычисление команд

[Parser на `nom`](../../server/rust/src/gameserver/appserver/script/parser.rs) работает с байтами: продвигает позицию, разбирает комментарии, границы команд, метки и внешнюю форму вызова. Аргументы остаются срезами текста и вычисляются позже. Предварительного AST или байткода нет. Такое разделение позволяет вычислять только параметры, нужные выбранной функции, в определённом для неё порядке; это свойство текущего кода, а не утверждение об историческом мотиве.

В `CScript::run_step` подключены `if/else`, `goto`, `call`, `return`, присваивания и зарегистрированные функции. `<begin>`, `<end>` и метки пропускаются. Это подмножество, а не полная спецификация языка оригинала:

- Разделители команд — `;`, табуляция и перевод строки вне двойных кавычек. Для переходов через блоки `{` и `}` должны читаться отдельными командами. Сканер пропускает `//` и `/*…*/` при поиске начала команды; универсальной обработки комментариев внутри выражения нет.
- Пропуск ветви `if/else` требует блока со скобками; `goto` ищет метку повторным проходом от начала файла. Управляющие слова нечувствительны к ASCII-регистру, метки и зарегистрированные имена сравниваются точно.
- Целочисленный вычислитель поддерживает `i32`, чтение переменных/массивов, вызовы, арифметические, сравнительные, логические и некоторые побитовые операции. `&&` и `||` вычисляют обе стороны. Арифметика через `checked_*` возвращает ошибку при переполнении или делении на ноль; арифметика конкретной игровой функции может иметь другие правила.
- Строки остаются байтами. Подключены конкатенация, строковые переменные и отдельный диспетчер результатов `GetName/GetStringByID/GetTeamerName`; числовой результат можно преобразовать в десятичную строку. Полная система escape-последовательностей не реализована.

Неизвестная команда, невычислимое присваивание или условие прекращают экземпляр; ошибка разбора тоже завершает его. Предыдущие игровые эффекты не откатываются. Ошибку аргумента диспетчер часто получает как `None` или `0x09FFFFF9`, и конкретная функция выбирает свой исход. `Handled` не является универсальным подтверждением игрового действия. В шаге нет квоты команд: цикл `goto` без выхода или ожидания может удерживать игровой цикл.

## Ожидание и продолжение

Ожидание хранится в `ActiveScript`, не в отдельной Tokio-задаче:

| Причина остановки | Продолжение |
| --- | --- |
| Функция вернула `Yielded` | Запоминается ID функции. Ответ должен найти тот же script ID и игрока; некоторые обработчики дополнительно сверяют ожидаемую функцию. |
| `wait`, ID `6` | Аргумент — миллисекунды, отрицательное значение заменяется нулём. Срок — `now.wrapping_add(delay)`. Ожидание снимается при строгом `deadline < now`; следующая команда читается ещё на следующем проходе. |
| `RunTime`, ID `22` | Такой же срок, плюс путь сценария. Примерно раз в секунду отправляется `0xBF80E` с оставшимися целыми секундами. По истечении запускается дочерний файл, затем продолжает родитель. |

Таймеры используют `u32` миллисекунды и прямое сравнение срока с текущим временем: сроки через переполнение счётчика нельзя считать корректно поддержанными. Сохраняемый таймер задания в секундах — [другой механизм](quests.md).

Диалоговые `TalkBox/Help/TalkBoxSmall` (`2307/2309/2324`) отправляют текст со script ID и возвращают `Yielded`. [Game `othermessage.rs`](../../server/rust/src/gameserver/appserver/message/othermessage.rs) принимает `0x8FB02`: режим `0` передаёт число, `1` преобразует строковый ввод через `atoi`, `-1` удаляет экземпляр. `continue_player_script` проверяет игрока и наличие ожидания, но сам по себе не ограничен диалоговыми функциями. Ответ только снимает ожидание, а код продолжает исполняться на сценарной стадии.

`ActiveScript::continue_with` записывает результат в локальную `$m_TalkRet`. Если асинхронная функция остановила условие или присваивание, позиция возвращена к началу команды (`replay_command`). При повторном проходе результат ожидаемой функции один раз потребляется из `resumed_function`. Остальные вычисления строки могут повториться: это повторное вычисление команды, не сохранение всего стека выражения и не откат прежних эффектов.

К World обращаются с ожиданием, например, `GetPlayer`, `IsPlayerOnline`, `GetRegionID`, `GetOnlinePlayers`; ответы принимает [GM-диспетчер](../../server/rust/src/gameserver/appserver/message/gmmessage.rs). `GetCopyNumber` (`9314`) продолжает `0x7FA15` через `continue_player_script_function`; список заблокированных игроков (`5106`) тоже проверяет ожидаемую функцию. В `ActiveScript` таймаут 10 секунд задан только для `9314/5106`: снимает ожидание и пишет `0/-1` в `$m_TalkRet`. При таймауте `resumed_function` не устанавливается, поэтому выражение на сохранённой позиции может снова отправить запрос. Общего таймаута всех функций и универсального продолжения вложенных аргументов здесь нет.

## Переменные и сохранение

### Объявления VariableList

[Shared scripting/variablelist.rs](../../server/rust/shared/src/scripting/variablelist.rs) разбирает объявления Game без доступа к игроку, World или БД. `VariableListRecords` последовательно возвращает имя, смещение и начальное значение: число, заимствованную байтовую строку или размер массива с числом для заполнения. Shared не выделяет массив значений и не хранит живое состояние. Переходный [Game CVariableList](../../server/rust/src/gameserver/appserver/script/variablelist.rs) очищает собственный список, материализует объявления и затем применяет сохранённые значения. Именно этот путь используют персональные переменные при декодировании GameSave и копия общих переменных при startup. Реестр ресурсов в Zone content по-прежнему владеет исходным текстом.

Границы секции, подписи и текста значения задаёт общий [разбор CIni](#разбор-functionlist-и-реестр-команд) с именем `VariableList`. Дополнительные правила:

- Каждая строка создаёт отдельное объявление в порядке файла, включая повтор имени. Загрузчик объявлений не обновляет предыдущую запись. Пробелы в имени сохраняются.
- При неположительном размере тип определяется первым байтом значения: `"` выбирает строку, всё остальное — `atoi`. Префикс `#` в имени не задаёт тип объявления. Пробел перед кавычкой поэтому не создаёт строку. Строковая ветвь удаляет первый и последний байт значения, не проверяя последнюю кавычку; это не parser строк с экранированием.
- Размер массива берётся из первой пары `[...]`. При положительном результате имя обрезается на последней `[`, массив целиком заполняется одним числом через `CIni::ReadInt`. Неположительный размер оставляет полное имя и выбирает обычную ветвь числа/строки: `$a[0]` не превращается в `$a`, и отрицательное выражение также не объявляется ошибкой массива. Если `ReadInt` не находит `=` до CR/конца, его установленный результат — `-99_999_999`; для массива это начальное значение каждого элемента.
- Начальное число и поддержанный числовой размер используют 32-битное оборачивание CRT, как [ID функций](#разбор-functionlist-и-реестр-команд). Прежние Rust trim, насыщение числа, объединение повторов и выбор строки по `#` удалены.

**Граница выражений — PARTIAL.** `GetArrayNum` передаёт содержимое первых скобок в `CScript::RunLine`, дописав `;`. Shared теперь вычисляет десятичные неотрицательные литералы и бинарную арифметику `+`, `-`, `*`, `/`, `%` с группировкой скобками; например, `[2+3]` задаёт массив из пяти элементов. Переполнение сложения, вычитания и умножения следует 32-битным операциям оригинала. Деление на ноль и `i32::MIN / -1` возвращают безопасный отказ. Переменные, унарные знаки, вызовы функций, сравнения, логические, битовые и присваивающие операции здесь не вычисляются: оригинал запускает полный `CScript`, а этот перенос не воспроизводит его остальную обработку выражений. Их поведение этим переносом не объявляется неподдержанным оригиналом.

Основание — идентифицированная выше пара Game EXE/PDB (GUID `5bee6dd1-bf90-49b8-8be9-eb25c4038d53`, age `2`); соответствие CodeView/PDB и байты инструкций проверены повторно. Продолжения после delete прочитаны непосредственно из PE.

| Установленный факт | Прямое основание, VA Game | Статус |
| --- | --- | --- |

Безопасная политика Rust: синтаксический отказ, недостающая `]`, неподдержанное подмножество выражения, ошибка деления, переполнение размера выделения или значение из единственной кавычки возвращают ошибку со смещением. Неположительный результат размера сохраняет ветвление оригинала и разбирается как scalar/string с полным именем. Отказ выделения массива также возвращается вызывающему. Уже материализованный префикс остаётся; оригинальные неинициализированные записи и выходы за границы памяти не воспроизводятся. Декодирование снимка прекращается до чтения его полей при отказе объявлений; регистрационный fallback журналирует отказ и сохраняет прежнюю политику регистрации с имеющимися данными. Отсутствующий ресурс `None` пока оставляет пустые объявления, как до переноса. World `GeneralVariableList`, обновление живых значений и wire-кодек этим шагом не перенесены.

### Владельцы и сохранение значений

Срок жизни переменной определяется хранилищем:

| Хранилище | Модель | Срок жизни |
| --- | --- | --- |
| Словари `ActiveScript` | Локальные целые и строки, имена в ASCII lowercase. | Только экземпляр, включая ожидания. |
| `CPlayer::variable_list` в Game | Объявления `VariableList` и значения персонажа: `i32`, байтовая строка, массив `i32`. | GameSave и сохранение персонажа. |
| `CGame::general_variables` в Game | Копия общих переменных. | Сценарное присваивание меняет копию и ставит обновление World; входящий echo меняет только копию. |
| `CVariableList` World | Объявления `GeneralVariableList`, пары `current/saved`. | Мировое сохранение через `CRsGenVar`. |

`evaluate_integer/evaluate_string` ищут **локальные → игрок → общие Game**. В [Game `CVariableList`](../../server/rust/src/gameserver/appserver/script/variablelist.rs) lookup нечувствителен к ASCII-регистру, но загрузка/замена записей снимка ищут точное имя. Массив читается с вычисленным индексом; локальное целое имеет приоритет только для индекса `0`.

Сейчас локальные словари создаются пустыми. Интерпретатор явно добавляет `$m_TalkRet` при продолжении и таймауте; обычное присваивание нового имени локальную переменную не создаёт. `run_assignment` меняет существующее локальное имя, затем пробует переменную игрока, затем общую. Неизвестное имя может остаться без изменения и без ошибки сценария. Несовпадение типа у игрока прекращает поиск как обработанное присваивание. Слева индекс массива не разбирается: `$a[2] = …` ищется как буквальное имя с индексом `0`. Это неполнота текущего присваивания, а не правило, которое следует повторять в новых механизмах.

Персональные переменные проходят `CPlayer::encode_game_save/decode_game_save` в [Game](../../server/rust/src/gameserver/appserver/player.rs). [World `CPlayer`](../../server/rust/src/worldserver/appworld/player.rs) хранит число записей и непрозрачный payload. `save_script_flag/load_script_flag` в [rsplayer](../../server/rust/src/dbaccess/worlddb/rsplayer.rs) записывают/читают `CSL_PLAYER_ABILITY.VariableList`. В GameSave есть count и длина payload; DB-поле содержит count и payload без отдельной длины. Порядок записей и теги типов заданы общим кодеком `CVariableList`. Позиция исполнения, контекст, ожидание, локальные словари и script ID туда не входят: продолжение открытого диалога при повторном входе не восстанавливается.

У общих переменных отдельный маршрут. `run_assignment` вызывает `set_script_general_variable_integer/string` в [Game](../../server/rust/src/gameserver/gameserver/game.rs): сначала выполняется локальный setter, затем для найденного имени ставится `0x5FA05` через общий World-клиент. Поля — `i32 tag` (`1` для числа, `3` для строки), имя с NUL, затем `i32` либо строка с NUL. Неизвестное имя не отправляется; совпавшее имя с несовместимым типом не приравнивается к отсутствующему. Основание порядка — `CScript::DispatchCommand` RVA `0x00025200`, `UpdateToWorldServer` RVA `0x000250E0/0x00025170` точного GameServer; тела сохранены в `script.rs`.

World принимает `0x5FA05`, меняет объявленную переменную и при успехе рассылает `0x7F805`. Обработчик ответа вызывает только `set_general_variable_integer/string`, поэтому echo не создаёт новую отправку. Это два входа в общий механизм: сценарное изменение с публикацией и применение входящего значения. Для нового сценарного входа используйте первый, для приёма обновления — второй.

Локальное изменение предшествует отправке. Отсутствие World, потеря соединения или отказ World не откатывают его; подтверждения долговременного сохранения и автоматического повтора здесь нет. Нельзя трактовать завершение присваивания как синхронное изменение всех Game. Результаты проверок — в [состоянии проекта](../status/audit.md).

[World `CVariableList`](../../server/rust/src/worldserver/appworld/script/variablelist.rs) сохраняется через `savedb::save_general_variables` и [Tiberius `CRsGenVar`](../../server/rust/src/dbaccess/worlddb/rsgenvar.rs): INSERT пишет `VarName/SValue/CValue`, UPDATE — только `CValue`; ошибка UPDATE регистрируется, но может оставить общий результат успешным. Массивы передаются World→Game, однако `save_row` выдаёт для них пустые значения, а `load_one_var` превращает DB-значение в scalar или строку: сохранение массива в `CSL_GENVAR` не обратимо. World также блокирует смену числового/массивного типа на строковый через setter, тогда как Game её допускает. Для постоянного общего состояния эти расхождения требуют отдельного решения. Общие транзакционные фазы — в [описании БД](../architecture/database.md).

## Как расширять, используя существующий путь

По [ADR-0007](../decisions/0007-reuse-existing-mechanisms.md), при одинаковых требованиях новый вход следует связывать с общей очередью и диспетчером, а новое сохраняемое поле — с существующим маршрутом Game → World → DB. Иной механизм требует причины; текущие дефекты не оправдывают параллельную реализацию. Соседние средства собраны в [каталоге общих механизмов](../architecture/shared-mechanisms.md). Границы игровых эффектов и инфраструктуры закреплены в [ADR-0002](../decisions/0002-semantic-boundary.md), владение сохранением — в [ADR-0005](../decisions/0005-world-game-boundary.md).

Для команды должны сойтись имя в данных, вычисление аргументов, числовой обработчик и вызов из сценария. Объявления устанавливает [реестр Zone](#разбор-functionlist-и-реестр-команд), который использует формат Shared. Наличие имени ещё не доказывает наличие обработчика ID; добавлять имя в обход данных ради прохождения загрузки нельзя.

Определение ID, `script_function_parameter_kind` и подключение к `dispatch_script_function` либо строковому диспетчеру находятся в [function.rs](../../server/rust/src/gameserver/appserver/script/function.rs). Есть 32 позиции аргументов; неиспользуемые не вычисляются. Особый порядок и ранние проверки — в `CScript::run_function`: `MonsterTalk` вычисляет текст перед именем, дополнительные параметры `AddTimeGoods` — при создании каждого подходящего предмета. Их нельзя заменять общим предварительным вычислением без проверки эффектов. Семейство JJC сначала проходит через [dispatch_jjc_script_function](../../server/rust/src/gameserver/appserver/script/jjcfunc.rs).

Игровая команда должна вызывать существующие операции игрока, региона, предмета или сессии, сохраняя их проверки и публикации. Для ожидания нужны согласованные `Yielded`, корреляция ответа, продолжение/удаление экземпляра и таймаут; простого добавления ID недостаточно. Синтаксис меняется согласованно в `parser`, `run_step` и вычислителях; порядок исполнения — в `CGame::run_script_loop`. Диагностика уже содержит `script_id`, `command_point`, `function_id`, причину остановки и таймаут.

Исторические `CScript::Check`, `Count`, `ComputeVar`, `SetVariableList`, `UpdateVariableList`, `RunStep` и `ScriptLoop` в карточках исследования `script.rs` не исполняются. Подключённая замена — описанные `parser`, `CScript`, `ActiveScript` и методы `CGame`. `UNKNOWN`: соответствие всего языка и всех исходных ресурсов этому подмножеству. Полноценные локальные объявления и общий стек продолжений выражений не становятся доступными от наличия их исследовательских метаданных.
