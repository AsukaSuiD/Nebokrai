# Мировые регионы, страны и организации

WorldServer хранит **глобальные свойства** региона, государство, фракцию и союз. GameServer исполняет локальную симуляцию региона и получает нужную ему проекцию сообщением. Такое разделение важно для налогов, владения городом, принадлежности игрока и сохранения: физический регион на Game не должен стать вторым независимым владельцем мирового результата. **Статус общей модели:** `PARTIAL` — кодовые пути и указание EXE/PDB в заголовках owner-ов найдены; полная парная трасса всех изменений World ↔ Game ещё не проверена.

## Регион и его долговременное состояние

`CWorldRegion` содержит базовый регион, страну, тип войны, параметры налогов и владельцев, настройки возврата, NPC/monster/weather ресурсы. Но DB-снимок строится **только из параметров региона**: девять полей `RegionSaveSnapshot` включают ID, налоги, вышестоящий регион и ID владеющих фракции/союза; имя, NPC и текущая погода в него не входят. Фактический SQL owner-а пишет в `CSL_Region` только `RegionID`, `OwnedFactionID`, `OwnedUnionID`, `CurTaxRate`, `TodayTotalTax`, `TotalTax`: наличие остальных трёх полей в snapshot само по себе не доказывает их сохранение. Ресурсы читаются при загрузке, меняемые мировые параметры сохраняются отдельно. Источник: [`CWorldRegion::generate_save_data`](../../server/rust/src/worldserver/appworld/worldregion.rs), [`RegionSaveSnapshot` и SQL](../../server/rust/src/dbaccess/worlddb/rsregion.rs). **Статус:** `VERIFIED (reconstructed source)`; заголовок owner-а указывает EXE/PDB, но независимая проверка формата БД в этом документе `PARTIAL`.

Ресурсы региона читаются последовательно через один опубликованный resource-owner: базовый ресурс, monster, NPC, weather, `.rs` setup и `.Tax` при успешной базовой загрузке. Пустой или неполный setup не заменяется удобными значениями: неинициализированные поля остаются `None`, а попытка сериализовать обязательное поле даёт типизированный блок. Это сохраняет различие между «в оригинале поле прочитано» и «мы угадали default». Источник: [`load_region_resource`](../../server/rust/src/worldserver/appworld/worldregion.rs). **Статус:** `PARTIAL (EXE/PDB provenance + source)`; реакция всех исходных клиентов на недостающий ресурс `UNKNOWN`.

DB-загрузка ограничивает `current_tax_rate` сверху `max_tax_rate`, а total/today tax переносит в `u32` как 32-битное представление. Обновление от Game меняет только текущий налог и две суммы. Proxy snapshot включает базовый объект, country, war type и параметры; selective decode потребляет ровно `0x24` байта параметров, но меняет только current tax, total/today tax и owner faction ID. Остальные поля, включая owner union ID, не должны перезаписываться просто потому, что присутствуют в wire. Источник: [`set_param_from_db`, `set_param_from_gs`, `add_to_byte_array_for_proxy`, `decord_region_param_from_byte_array`](../../server/rust/src/worldserver/appworld/worldregion.rs). **Статус:** `PARTIAL`; точные вызывающие opcode стоит связать с отдельной protocol-страницей.

После загрузки региона `init_owner_relation` проверяет, существует ли фракция-владелец, затем союз; отсутствующие связи очищаются последовательно, а существующее владение публикуется в организационный owner. Это не «проверка для красоты»: сохранённый DB ID может ссылаться на удалённую организацию и не должен оставаться живым мировым владельцем. При переводе игрока после деревенской войны `set_enter_pos_xy` сначала решает, действует ли окно очистки; точку возврата берёт из setup региона либо параметров страны. Если указанного региона возврата нет, координаты остаются `-1`, но ID региона игроку всё равно назначается. Источник: [`init_owner_relation`, `get_return_point`, `set_enter_pos_xy`](../../server/rust/src/worldserver/appworld/worldregion.rs). **Статус:** `PARTIAL`.

## Государства

`CCountryHandler` владеет картой стран по `u8` ID. При инициализации он загружает БД, и лишь если загрузка успешна, вызывает обновление локального дня. `Run` сначала убирает истёкшие top-info по отдельным 32-битным wrapping ticks, затем вызывает AI только у стран с назначенным королём. День проходит в порядке country key, и сохранение формирует отдельный snapshot каждой существующей страны. Источник: [`CCountryHandler`](../../server/rust/src/worldserver/appworld/country/countryhandler.rs), [`CCountry`](../../server/rust/src/worldserver/appworld/country/country.rs), [`DbCountry`](../../server/rust/src/dbaccess/worlddb/dbcountry.rs). **Статус:** `PARTIAL (EXE/PDB owner note + source)`.

Nullable slot страны возможен в технической структуре. Нормальный сериализатор пишет count и ordered country records, но при пустом slot прекращает операцию типизированной ошибкой вместо разыменования null; это **безопасная техническая замена** внутреннего UB, а не новый игровой исход. `CCountryHandler` вместо process-global указателя хранится в жизненном цикле World. В обоих случаях должны сохраниться порядок и bytes нормального пути; для повреждённого slot исходное поведение не принимается как контракт. Источник: [`countryhandler.rs`](../../server/rust/src/worldserver/appworld/country/countryhandler.rs). **Статус решения:** `INFERRED` о допустимости замены UB; byte parity нормального пути ещё требует парной проверки.

## Фракции, союзы и игрок

`COrganizingCtrl` — владелец registries фракций и союзов, заявок, отношений, управления городами и ежедневных callbacks. При инициализации он очищает список резервирования **до** DB-вызова, загружает и публикует союзы, затем загружает и публикует фракции, после чего регистрирует календарное событие и строит рейтинг фракций. Отказ загрузки фракций не откатывает уже опубликованные союзы; только отдельный blocked constructor/lifetime путь прерывает продолжение. Причина сохранить порядок — фракции при linking могут ссылаться на уже опубликованный союз. Источник: [`initialize_from_database_owners`](../../server/rust/src/worldserver/appworld/organizingsystem/organizingctrl.rs), [`RsUnion`](../../server/rust/src/dbaccess/worlddb/rsunion.rs), [`RsFaction`](../../server/rust/src/dbaccess/worlddb/rsfaction.rs). **Статус:** `PARTIAL`; source-owner заявляет `worldserver.exe`/PDB, полного runtime-теста нет.

При входе online-члена `on_player_enter_game` сначала разрешает его фракцию, затем вызывает callback фракции и только после успешной/допустимой ветви отправляет top-info клиенту. При выходе вызывается faction-exit callback; новая широковещательная рассылка не выводится автоматически из самого изменения online-списка. Источник: [`on_player_enter_game`, `on_player_exit_game`](../../server/rust/src/worldserver/appworld/organizingsystem/organizingctrl.rs) и [переходы игрока](player-lifecycle.md). **Статус:** `PARTIAL`.

Снимок организации проходит фракции перед союзами; изменённый owner копируется в save queue и только после удачной копии сбрасывает dirty mask. Затем IDs удалённых фракций и союзов переносятся в delete queue, и исходные списки очистятся. Поздний отказ не является общей транзакцией. Порядок SQL-фаз удаления и записи определяет [`DoSaveData`](../architecture/database.md); перенос флага/списка до DB-успеха делает стратегию повтора при сбое важным ещё открытым вопросом. Источник: [`COrganizingCtrl::generate_save_data`](../../server/rust/src/worldserver/appworld/organizingsystem/organizingctrl.rs). **Статус:** `VERIFIED (reconstructed source)`, гарантия отсутствия потерь при DB-отказе `UNKNOWN`.

**Неизвестное:** полная таблица связей country ↔ faction ↔ union ↔ region для всех subtype сообщений; семантика повторного сохранения после частичного SQL-отказа; права каждого организационного действия; доказанная byte parity всех proxy snapshot. Не выводите эти правила из одного владельца или соседней игры.
