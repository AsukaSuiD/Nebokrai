# Мировые регионы, страны и организации

World связывает территорию, государство и объединения игроков. Регион хранит владение и налоги, страна — казну и должности, фракция — участников и принадлежащие ей города, союз — объединение фракций. Game получает проекции этих данных для локального исполнения. Изменение владельца города поэтому затрагивает несколько объектов и сообщений; одной записи ID в регионе недостаточно.

## Регион: ресурс, маршрут и меняемые параметры

В `CGame` назначение региона связывает его с GameServer и конкретным типом `WorldRegionOwner`: `Base`, `Village`, `City`, `Country`. Все варианты предоставляют общий `CWorldRegion`, а военные варианты добавляют свои данные. AI этих World-регионов в текущем `WorldRegionOwner::ai` пуст; локальную симуляцию исполняет Game, а глобальные фазы обслуживают отдельные [системы войн](world-wars.md).

У региона есть три разных представления:

| Представление | Для чего служит |
| --- | --- |
| Ресурсы и setup | Базовый регион, monster/NPC/weather, `.rs`, `.Tax`, точки возврата и правила. Это вход загрузки. |
| Мировые параметры | Налоги, суммы, вышестоящий регион, владельцы. Это изменяемая модель World. |
| Межсерверный snapshot | Проекция для конкретного сообщения Game. Наличие поля здесь не определяет его запись в SQL или право перезаписи при обратном сообщении. |

`load_from_context` в [worldregion.rs](../../server/rust/src/worldserver/appworld/worldregion.rs) читает ресурсы последовательно: базовый, monster, NPC, weather, затем `.rs`; только чтение `.Tax` дополнительно требует успешной базовой загрузки. Обязательные непрочитанные setup-поля остаются `None`; сериализация такого поля останавливается типизированным результатом. Конкретный неизвестный параметр нельзя заменять удобным default ради получения snapshot.

[CRsRegion](../../server/rust/src/dbaccess/worlddb/rsregion.rs) загружает `CSL_Region` по `RegionID` в уже созданные регионы. Для отсутствующего региона строка пропускается. При ошибке поздней строки ранее применённые значения остаются. `set_param_from_db` ограничивает текущую ставку сверху `max_tax_rate`, но не вводит нижнюю границу; суммы переносит из `i32` в `u32` как битовое представление. `set_param_from_gs` меняет ставку и две суммы без этого ограничения сверху.

`RegionSaveSnapshot` содержит девять полей: `region_id`, `max_tax_rate`, `current_tax_rate`, `total_tax`, `today_total_tax`, `superior_region_id`, `turn_in_tax_rate`, `owned_faction_id`, `owned_union_id`. SQL пишет только `RegionID`, `OwnedFactionID`, `OwnedUnionID`, `CurTaxRate`, `TodayTotalTax`, `TotalTax`. Остальные параметры снимка, имя, NPC и погода этим запросом не сохраняются. Это важная граница при добавлении свойства региона.

Обратный `decord_region_param_from_byte_array` потребляет `0x24` байта, но применяет лишь current tax, total/today tax и owner faction ID. Union ID из этого payload не заменяет текущего владельца союза. Для изменения сообщения нужны вызывающий opcode и парный Game-кодек; общий `decord_from_byte_array` World-региона, напротив, является no-op.

## Почему владение приходится связывать отдельно

Текущие ID владеющих организаций хранятся в `owned_city_organizing`. `effective_param` подставляет их в параметры для сохранения; `generate_save_data` использует именно эту эффективную проекцию. Запись только в старую копию параметров не должна рассматриваться как завершённое изменение владельца.

При загрузке `init_owner_relation` начинает работу только при положительном ID фракции. Если фракция отсутствует, очищает оба ID; затем проверяет союз. Для существующей фракции добавляет город в её список через `add_owned_city_to_faction` и устанавливает стране региона принадлежность фракции. При поздней ошибке уже сделанные изменения остаются. Это связывание восстанавливает двусторонние отношения после независимой загрузки БД, а не просто проверяет корректность чисел.

В ходе войны право владения меняют обработчики результата в `COrganizingCtrl`, а последующая DB-сборка сохраняет регион и организацию раздельно. Их запись не атомарна на уровне всего мира. Путь завершения войны описан в [мировых войнах](world-wars.md), судьба снимков при отказе SQL — в [сохранении](../architecture/persistence.md).

Точка возврата также зависит от мировой модели. `set_enter_pos_xy` проверяет окно очистки деревенской войны, выбирает возврат из setup региона либо параметров страны. Если целевой регион отсутствует, координаты остаются `-1`, но ID региона всё равно назначается. Правила находятся рядом с `get_return_point` в `worldregion.rs`; нельзя превращать эту ветвь в успешное размещение по произвольной точке.

## Страна: должности, ресурсы и смена дня

[CCountryHandler](../../server/rust/src/worldserver/appworld/country/countryhandler.rs) хранит страны по `u8` ID и общий поток сообщений top-info. Его `run` сначала удаляет истёкшие сообщения по wrapping ticks, затем вызывает AI стран с королём. При инициализации обновление локального дня следует только за успешной загрузкой БД. [CCountryParam](../../server/rust/src/worldserver/appworld/country/countryparam.rs) задаёт лимиты, должностные требования, технологию и точки возврата; [CCountry](../../server/rust/src/worldserver/appworld/country/country.rs) хранит текущие значения.

В `set_new_day` сначала обнуляются счётчики silence/PK. При первом дне лишь запоминается дата. В дальнейшие дни при наличии короля начисляется доход деревень, затем `new_term` сбрасывает признаки назначения и получения жалованья короля/министров, обрабатывается должность 7 и меняется день. Ошибка начисления может оставить ранние обнуления без завершения остальных стадий.

Название `add_village_tax_to_treasury` не означает суммирование `TodayTotalTax` регионов. За каждую деревню из возвращённого контекстом списка начисляется фиксированный `_daily_country_treasury`. Для каждого шага применяется формула `min(max(wrapping_add(treasury, daily_treasury), 0), maximum_treasury)` со знаковым 32-битным сложением, затем пишется king-log. Вывод из кода: изменение дохода деревни нужно согласовывать с этим начислением, а не только с региональным счётчиком налога.

`clone_save_data` сохраняет казну, силу, технологические опыт/уровень, короля, исход войны и шесть слотов министров с типами `2..7`. Очки control/material/war короля ограничиваются сверху переданными лимитами. Берутся первые шесть записей карты министров, затем раскладываются по типу должности; отсутствующие слоты записываются в SQL нулями и пустым именем. Списки изгнания, top-info и весь setup страны не являются частью этого DB-снимка.

[TiberiusDbCountry::save](../../server/rust/src/dbaccess/worlddb/dbcountry.rs) обновляет существующую строку `CSL_Countrys`. При отсутствии строки возвращает `true` без INSERT. Значит создание объекта страны в памяти и его успешный save ещё не создают страну в БД. Новый тип должности потребует изменения модели, ограничения шести слотов, SQL и клиентской проекции; одного дополнения карты недостаточно.

## Фракция, союз и права участника

[COrganizingCtrl](../../server/rust/src/worldserver/appworld/organizingsystem/organizingctrl.rs) хранит фракции, союзы, заявки и ожидающие удаления. Союз содержит фракции; фракция содержит игроков. Организационная принадлежность в `CPlayer` — проекция этих отношений. При изменении членства нужно обслужить карты, сведения игрока и уведомления, а при входе/выходе — соответствующий callback фракции.

Инициализация очищает список резервирования, публикует загруженные союзы, затем загружает фракции, после чего выполняет календарное завершение и подготовку рейтинга. Это даёт фракции возможность связаться с уже опубликованным союзом. Неуспех загрузки фракций не откатывает союзы; временный префикс неуспешной загрузки фракций не превращается автоматически в живые объекты.

Права не сводятся к одному признаку «лидер». В [CFaction](../../server/rust/src/worldserver/appworld/organizingsystem/faction.rs) `check_operator_validate` требует членство и конкретное право `EPurview`. Вариант `check_operator_validate_target` дополнительно запрещает действие на себя или мастера, требует членства обоих и не позволяет обычному участнику действовать на обладателя того же права. Соответствующий игровой обработчик выбирает проверку и только затем меняет состояние. Полная матрица прав всех subtype остаётся не сведённой; соседний разрешённый handler не доказывает право другого действия.

## Что делает маска изменений

Для изменения существующей организации с теми же требованиями используйте её мутации, `generate_save_data` и профильный DB-модуль, а для территории — общий `CWorldRegion` и организационный контекст владения. Это применение [ADR-0007](../decisions/0007-reuse-existing-mechanisms.md), а не требование переносить любую новую мировую сущность на маску фракции. Регион, страна и союз уже имеют другие правила копирования; перед повторным использованием сравниваются состав, время передачи и обработка отказа.

Фракция сохраняется по частям. `set_change_data(0)` сбрасывает всю маску; обычные вызовы с одним битом добавляют нужную часть. DB-метод читает маску один раз перед обходом:

| Бит фракции | Содержимое копии и ветка записи |
| --- | --- |
| `1` | Основные свойства: `save_faction_property`. |
| `2` | Участники и их данные: `save_faction_members`. |
| `4` | Сообщения организации: `save_leave_words`. |
| `8` | Ability-часть, в том числе принадлежащие города и заявки: `save_ability`. |

`CFaction::clone_save_data` копирует выбранные части, а при нулевой маске возвращает `None`. `COrganizingCtrl::generate_save_data` помещает копию в пакет и **сразу** снимает маску живой фракции. Так изменение после копирования может пометить новую порцию данных. Это объяснение следует из структуры кода; гарантией успешной записи уже отделённой копии оно не является.

У [CUnion](../../server/rust/src/worldserver/appworld/organizingsystem/union.rs) маска служит признаком необходимости копии, но `clone_save_data` копирует основные данные и всех участников. [TiberiusRsUnion::save_confederation](../../server/rust/src/dbaccess/worlddb/rsunion.rs) не повторяет четыре выборочные ветки фракции: сохраняет базу, затем состав союза. Нельзя распространять таблицу битов фракции на SQL союза.

[TiberiusRsFaction::save_faction](../../server/rust/src/dbaccess/worlddb/rsfaction.rs) продолжает выбранные ветки после обычных внутренних SQL-неуспехов и может вернуть `ReturnedTrue`; типизированные блокировки обрабатываются отдельно. Общая фаза затем расходует копию по правилам [сохранения](../architecture/persistence.md#что-означает-результат). Для нового поля нужны одновременно мутация, нужный бит, выборочная копия, DB-проекция, чтение и запись. Для нового отношения дополнительно проверьте обе стороны, игрока и сообщения Game.
