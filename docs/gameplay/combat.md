# Базовая атака и защита

Боевая операция строит упорядоченные компоненты атаки, пропускает их через защиту цели и только затем меняет её ресурсы. Эта страница описывает текущую ветвь базовой атаки и общие приёмники урона. Порядок компонентов, RNG и преобразований чисел влияет на результат, поэтому их нельзя свести к одному вычитанию HP.

После смертельного урона остаются синхронная фиксация смерти и отложенное событие AI. Продолжение — выбор получателя награды, опыт, рост уровня, восстановление и возрождение — описано в [смерти и развитии персонажа](death-and-progression.md).

## Владелец и границы

Zone владеет живыми игроками, монстрами, зарегистрированными навыками и применением урона. Большая часть исполнения пока находится в переходном Game. `CPlayerAI` выбирает ожидающую команду; зарегистрированный экземпляр навыка хранит lifecycle и reuse; конкретный навык строит `AttackInformation`; защита цели преобразует компоненты урона; приёмник цели применяет конечные HP/MP и последствия попадания. Realm не рассчитывает контакт атаки. Связь с выбором команды описана в [навыках](skills.md), происхождение действующих характеристик — в [атрибутах](attributes-and-states.md).

`AttackInformation` хранит тип и ID атакующего, ID/уровень навыка, признаки критического и усиленного удара, поправку к попаданию, множитель и добавку урона, а также **упорядоченный** список физических, стихийных, духовных и ядовитых составляющих. Порядок существенен: защита и окончательное применение проходят этот список последовательно, а каждый physical/element-компонент может потребить собственный вызов RNG. [Структура и конечная арифметика](../../server/rust/zone/src/combat/attackpower.rs) принадлежат Zone; прежний Game лишь экспортирует эти типы. `MasterInfo` находится рядом как данные источника. Заполнение полей зависит от атакующего навыка. В частности, `CBaseAttack` не записывает ID/уровень в атаку и оставляет конструкторские `UNKNOWN` и `1`. Подстановка ID `1` по названию навыка изменила бы данные, которые получают защита и callbacks.

## Путь базовой атаки игрока

1. Запрос проходит [декодер навыка](../../server/rust/src/gameserver/appserver/message/skillmessage.rs), допуск игрока и очередь AI. Начало зарегистрированного исполнения, проверка цели/дальности и ожидание времени каста описаны в [модели навыка](skills.md). Допуск запроса сам по себе не означает попадания.
2. При расчёте [`CBaseAttack`](../../server/rust/src/gameserver/appserver/skills/baseattackruntime.rs) получает текущий уровень базовой атаки и свойства. Вычисляет `damage_factor` как `GetWeaponModifier(target_level)`: `delta = max(weapon_damage_level - target_level, 0)`, `factor = float(delta) / divisor`, затем верхнее ограничение `1.0`, затем нижнее `minimum`. При нулевом divisor отдельной защиты в реконструкции нет: `0/0` может оставить NaN. Это важная особенность порядка сравнений, а не повод автоматически заменить формулу на обычный `clamp`.
3. `hit_modifier` берётся из usage-поля навыка. Физическая составляющая: `span = max(max_attack.wrapping_sub(min_attack), 0)`, затем `max(min_attack.wrapping_add(random(span)), 0)`, с трактовкой исходных attack-полей как `i32`; верхняя граница генератора исключена. После неё добавляются `max(add_element_attack as i32, 0)` и `add_soul_attack`. Далее **один** бросок проверяет `random(100) < cch`; при успехе каждая уже построенная составляющая умножается на `critical_rate` через `truncate_original(f64::from(damage) * f64::from(rate))`, без промежуточной записи результата в `f32`.
4. Перед контактом отсеиваются сам атакующий, object type `500` и недопустимая текущая цель. Собираются PK-разрешения. Общий контакт вызывает защиту цели и её side effects. Затем caller вызывает увеличение RP игрока **даже если внутренний контакт отказал**. Этот порядок зафиксирован в [исполнителе базовой атаки](../../server/rust/src/gameserver/appserver/skills/baseattackruntime.rs); не переносить начисление RP внутрь успешного попадания без нового свидетельства.

## Защита, попадание и арифметика

Числа `attack`, `defense`, сопротивлений и `avoid` берутся из свойств конкретного атакующего и цели; глобальные границы, `critical_rate`, PvP-множитель и коэффициенты оружия — из [GlobeSetup](../../server/rust/shared/src/resources/globesetup.rs). Урон и защита — целочисленные величины, множители сохраняются как `f32`. Для ветвей, воспроизводящих x87, адаптер вычисляет произведение в `f64` после преобразования сохранённых `f32`-констант и **один раз** усекает к нулю. Результат за пределами signed `i32`, NaN или бесконечность дают `i32::MIN`, а не насыщение. Реализация — [`truncate_original`](../../server/rust/zone/src/combat/rounding.rs) и [функции защиты](../../server/rust/zone/src/combat/fightdefense.rs).

| Стадия | Подтверждённый порядок текущей реализации |
| --- | --- |
| Попадание по монстру | `hit = clamp(max_hit + (target_level - attacker_level - 3) * 15 + hit_modifier, min_hit, max_hit)`; если `hit <= random(100)`, physical/element/soul и `damage_modifier` становятся нулём, `full_miss = 2`. Poison остаётся. |
| Попадание по игроку | `hit = clamp(max_hit + hit_modifier, min_hit, max_hit)`. При ненулевом `target.full_miss` до hit-броска возможен отдельный RNG: если есть положительный element, порог `full_miss * attacker.full_miss_scale` сравнивается как x87-произведение без промежуточного усечения; иначе с целым `full_miss`. На промахе `full_miss = 1` для этого уклонения, `2` для hit-проверки. Poison не обнуляется. |
| `PreDefense` | Для игрока защитные состояния/щиты проходят **в порядке регистрации** для каждой составляющей до обычной защиты. [`DefenseShieldState::apply_pre_defense`](../../server/rust/zone/src/effects/defenseshield.rs) пропускает ID `530..=545`, кроме `544`, для всех своих вариантов — `VERIFIED` по диспетчеру VA `0x005B0A50–0x005B0A72` совпадающей Game EXE/PDB (`jl 0x212`, `jg 0x221`, `jne 0x220` на выход). Для monster/build стихией может управлять `Promotion` с тем же исключением. |
| Physical и Element | Проверяется отдельный blast-бросок. При blast сначала множитель attack, затем защита/сопротивление с blast-масштабом; иначе вычитается половина беззнаковой защиты (логическое деление на 2). Critical меняет защитное вычитание через `critical_rate`. Затем `avoid`: если `1 <= 100 - avoid < 100`, результат умножается на `(100 - avoid) * 0.01_f32` с конечным усечением. Для атаки игрока по игроку/монстру нижняя граница результата здесь `1`; для атаки монстра по игроку/монстру — `0`. |
| Soul и Poison | Soul вычитает отдельное `soul_resistance`, при части ветвей critical масштабирует вычитание; нижняя граница `0`. Poison обычной physical/element/soul-защитой не меняется. Нельзя сводить все четыре категории к единой формуле. |
| `PostDefense` и множители | `PillarState` для атаки по игроку применяется после обычной защиты и до `damage_factor`, кроме `skill_id 0x212..=0x224`. Положительный результат умножается на `damage_factor` и ограничивается снизу `1`; только в ветви игрок → игрок затем применяется `pvp_damage_factor`, без повторного ограничения снизу. |
| Конечное применение | `AttackInformation::final_damage_values` последовательно вычитает из HP/MP каждый компонент как DWORD, ограничивает максимумом владельца, после компонентов применяет `damage_modifier` к HP. `hp_record/mp_record` — только положительная знаковая разница старого и нового; отсутствие записи не доказывает отсутствие изменения состояния. |

Сводка составлена по [ветвям `CFightDefense`](../../server/rust/zone/src/combat/fightdefense.rs) и [`AttackInformation`](../../server/rust/zone/src/combat/attackpower.rs). **Она не является одной общей формулой для всех навыков:** разные concrete owners создают компоненты, проверяют расход/цель и вызывают защиту в разных точках. В частности, разные ограничения попадания и PvP-множитель делают перенос формулы player → player на monster → player ошибкой.

## Как защита использует живые состояния

Общий контакт `apply_owned_skill_contact` находится в [`game/rush.rs`](../../server/rust/src/gameserver/gameserver/game/rush.rs), а приёмники — в [`game/periodicattack.rs`](../../server/rust/src/gameserver/gameserver/game/periodicattack.rs), несмотря на узкие имена файлов. Контакт выбирает путь цели; `receive_player_skill_attack`, `receive_monster_skill_attack` и `receive_stationary_build_skill_attack` реализуют её проверки, защиту, применение ресурсов и последствия. Для нового эффекта с теми же требованиями это существующая граница применения атаки. Прямой `set_health` в новом навыке обошёл бы её проверки и callbacks. Сам `apply_owned_skill_contact` не вызывает общий `IsAttackAble`: необходимые предварительные проверки атакующего остаются у caller.

Защита игрока начинается с прохода **зарегистрированных** Defense-навыков: `begin_received_base_defense` берёт очередной экземпляр базовой защиты и вызывает его общий Begin. Поэтому отсутствие или повторение этой регистрации влияет на число проходов. После расчёта вызывается зарегистрированный End(0). Нельзя незаметно заменить это одной безусловной функцией защиты для каждой цели.

Наложенные Life/Mana/Machine/Promotion-щиты при этом остаются состояниями фигуры. Приёмник временно извлекает их payload через `take_defense_shields` в [`StateBatch`](../../server/rust/src/gameserver/appserver/moveshape/state_storage.rs), рассчитывает PreDefense в порядке состояний и возвращает изменённые значения тем же ключам через `restore_defense_shields`. Возврат заполняет только ещё существующие пустые ячейки. Это способ выполнить расчёт без копии щитов и без удержания изменяемого заимствования игрока; он подходит для участка без вложенных игровых callbacks. Во время изъятия payload недоступен обычному state-поиску.

Для машинного щита [`Zone effects`](../../server/rust/zone/src/effects/machineshield.rs) исполняет числовой `PreDefense`, а Game передаёт текущий MP игрока и компонент атаки. По Game EXE/PDB `VERIFIED` для ветви `CFightDefense::PreDefense` VA `0x005B0CD8–0x005B0E5F`: входной HP-урон сначала умножается на `damage_factor` и усекается через `__ftol2` до младшего DWORD. Если прочность, MP и этот урон положительны, WORD-факторы умножаются на float-константу `0.01`; MP-коэффициент дополнительно сохраняется как `f32` перед вычислением. Сначала сравнивается прочность с поглощаемым HP, затем младший WORD MP с рассчитанным MP-уроном. В соответствующей ветви обнуляется прочность и возвращается непоглощённая часть HP; иначе прочность уменьшается, HP-урон становится нулём. Во всех случаях итоговый HP-урон делится на исходный `damage_factor` и усекается. Рассчитанный MP-урон остаётся в компоненте атаки для позднего применения, а не списывается из игрока здесь. Это не доказывает совпадение каждого x87-пограничного значения в Rust `f64`-модели.

Мана-щит использует [тот же числовой хвост](../../server/rust/zone/src/effects/shieldabsorption.rs) после собственной защиты. По ветви `CFightDefense::PreDefense` VA `0x005B0ABC–0x005B0C72` `VERIFIED`: после начального масштабирования HP-урона физический компонент (`kind=1`) теряет половину физической защиты, стихийный (`kind=3`) — половину стихийной; остальные виды не теряют её. Деление знакового DWORD на два усекает к нулю, вычитание переполняется по DWORD, затем отрицательный результат обнуляется. После этого совпадают проверки прочности/MP, порядок двух сравнений и завершающее деление на `damage_factor` машинного щита. [Модель мана-щита](../../server/rust/zone/src/effects/manashield.rs) передаёт защиты общему расчёту; Game выбирает текущего игрока и порядок состояний.

Щит жизни имеет [собственную числовую ветвь Zone](../../server/rust/zone/src/effects/lifeshield.rs), поскольку его ресурсы и ранний выход отличаются. По `CFightDefense::PreDefense` VA `0x005B0E64–0x005B1030` `VERIFIED` для арифметики: первоначальное умножение HP-урона на `damage_factor` усекается через `FISTP DWORD` ещё до поиска предмета боевого духа. Если предмет отсутствует, обратного деления нет. При его наличии положительные прочность, MP предмета и урон допускают поглощение с теми же WORD-факторами, сравнением прочности и младшего WORD MP, затем остаток HP делится на исходный `damage_factor`; рассчитанный MP-урон записывается в компонент атаки. `PARTIAL` для живых чтений: оригинал запрашивает MP предмета дважды в этой ветви, а переходный Game передаёт один снимок. Между запросами в исходном коде нет изменения предмета, но весь путь обращения к нему и конкурентные изменения отдельно не проверены.

Исчерпание ресурса и снятие щита — отдельные стадии. Конкретные AI/End находятся в [`shieldstate`](../../server/rust/src/gameserver/appserver/skills/shieldstate.rs): например, Life End может создать Cure, а Machine/Mana имеют свой завершающий visual. Следовательно, вычеркнуть исчерпавшийся щит из локального списка защиты недостаточно: так потеряются его последствия и связь с сохранением. Общее различие End, уничтожения и пересчёта описано в [состояниях](attributes-and-states.md#обход-состояний-и-завершение).

Для изменения боевого эффекта проследите заполнение `AttackInformation`, приёмник нужного типа цели, действующие свойства/щиты и конечное применение. Повторное использование общего приёмника уместно при совпадении этих требований; специальные WarSoul-ветви имеют иной путь и не являются образцом для обычного удара.

## Открытые границы

`UNKNOWN`: полный набор производных PreDefense/PostDefense и порядок последствий для ещё не реализованных форм навыков и типов цели. В текущем коде перечисленные щиты, `Promotion`, `PillarState` и WarSoul имеют конкретные ветви; их наличие не обобщает одну формулу на все атаки.

Для восстановления оригинальной арифметики исходные свидетельства сохранены в комментариях `baseattackruntime`, `fightdefense` и `attackpower`: пара `gameserver.exe/GameServer.pdb`, функции и адреса. Соответствие всей ветви оригиналу остаётся `PARTIAL`; формулы выше описывают текущий Rust. При одинаковых требованиях используйте существующие компоненты атаки и [числовые преобразования Zone](../../server/rust/zone/src/combat/rounding.rs), сохраняя порядок RNG, signed/unsigned-преобразования и момент усечения.
