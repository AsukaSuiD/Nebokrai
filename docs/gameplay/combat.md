# Базовая атака и защита

Эта спецификация описывает **достигнутую ветвь** базовой атаки GameServer. Формулы ниже точно описывают текущий Rust-код; соответствие оригиналу оценивается отдельно. Исходное свидетельство для ветви — `gameserver.exe` SHA-256 `4F5C98E0FDF6147D8AECF55F7937AAF6E2CF5E4F5A2C44491A6359228762C80E` и `GameServer.pdb` SHA-256 `B17BB9B7D69A9CC43E314C0E35C517830BB42CAA89416E173380AB17D2D66016`, указанные у owners [baseattackruntime](../../server/rust/src/gameserver/appserver/skills/baseattackruntime.rs), [fightdefense](../../server/rust/src/gameserver/appserver/skills/fightdefense.rs) и [attackpower](../../server/rust/src/gameserver/appserver/states/attackpower.rs). Сами EXE/PDB при составлении этой страницы повторно не разбирались; поэтому совпадение каждой операции с ними — `PARTIAL`, а не результат нового независимого сравнения.

## Владелец и границы

GameServer владеет живыми игроками, монстрами, зарегистрированными навыками и применением урона. `CPlayerAI` выбирает ожидающую команду; зарегистрированный экземпляр навыка хранит lifecycle и reuse; конкретный навык строит `AttackInformation`; защита цели преобразует компоненты урона; владелец цели применяет конечные HP/MP и последствия попадания. WorldServer не рассчитывает контакт атаки. Источник последнего разделения: [связанный путь исполнения](simulation.md) и [архитектура World/Game](../server/world-and-game.md); исходная межпроцессная семантика в целом — `PARTIAL`.

`AttackInformation` хранит тип и ID атакующего, ID/уровень навыка, признаки критического и усиленного удара, поправку к попаданию, множитель и добавку урона, а также **упорядоченный** список физических, стихийных, духовных и ядовитых составляющих. Порядок существенен: защита и окончательное применение проходят этот список последовательно, а каждый physical/element-компонент может потребить собственный вызов RNG. Это не одна скалярная величина damage. [Структура и применение](../../server/rust/src/gameserver/appserver/states/attackpower.rs) — `VERIFIED` для текущей реализации, `PARTIAL` для соответствия исходному `tagAttackInformation`/`CMoveShape::ApplyFinalDamage` (EXE/PDB в owner-комментарии).

## Путь базовой атаки игрока

1. Запрос проходит [декодер навыка](../../server/rust/src/gameserver/appserver/message/skillmessage.rs), допуск игрока и очередь AI. Начало зарегистрированного исполнения, проверка цели/дальности и ожидание времени каста описаны в [модели навыка](skills.md). Допуск запроса сам по себе не означает попадания.
2. При расчёте [`CBaseAttack`](../../server/rust/src/gameserver/appserver/skills/baseattackruntime.rs) получает текущий уровень базовой атаки и свойства. Вычисляет `damage_factor` как `GetWeaponModifier(target_level)`: `delta = max(weapon_damage_level - target_level, 0)`, `factor = float(delta) / divisor`, затем верхнее ограничение `1.0`, затем нижнее `minimum`. При нулевом divisor отдельной защиты в реконструкции нет: `0/0` может оставить NaN. Это важная особенность порядка сравнений, а не повод автоматически заменить формулу на обычный `clamp`.
3. `hit_modifier` берётся из usage-поля навыка. Физическая составляющая: `min_attack + random(max(max_attack - min_attack, 0))`, затем `max(…, 0)`; верхняя граница генератора исключена. После неё добавляются `max(add_element_attack, 0)` и `add_soul_attack`. Далее **один** бросок `random(100)` проверяет `critical <`; при успехе каждая уже построенная составляющая умножается на `critical_rate` и усекается к `i32`. Формулы и порядок RNG — `VERIFIED` для Rust, `PARTIAL` относительно сохранённого owner-контракта EXE/PDB.
4. Перед контактом отсеиваются сам атакующий, object type `500` и недопустимая текущая цель. Собираются PK-разрешения. Общий контакт вызывает защиту цели и её side effects. Затем caller вызывает увеличение RP игрока **даже если внутренний контакт отказал**. Этот порядок зафиксирован в [исполнителе базовой атаки](../../server/rust/src/gameserver/appserver/skills/baseattackruntime.rs); не переносить начисление RP внутрь успешного попадания без нового свидетельства.

## Защита, попадание и арифметика

Числа `attack`, `defense`, сопротивлений и `avoid` берутся из свойств конкретного атакующего и цели; глобальные границы, `critical_rate`, PvP-множитель и коэффициенты оружия — из [GlobeSetup](../../server/rust/src/setup/globesetup.rs). Единицы времени здесь не участвуют; урон и защита — целочисленные величины, множители — `f32`. Для операций исходного x87 Rust-адаптер вычисляет произведение в `f64` после точного преобразования сохранённых `f32`-констант и **один раз** усекает к нулю. Результат за пределами signed `i32`, NaN или бесконечность дают `i32::MIN` (исходное indefinite), а не насыщение. [Адаптер и отдельные ветви](../../server/rust/src/gameserver/appserver/skills/fightdefense.rs) — `VERIFIED` для Rust; происхождение x87-порядка заявлено owner-ом с EXE/PDB, статус исходной арифметики `PARTIAL` до независимого дифференциального сравнения.

| Стадия | Подтверждённый порядок текущей реализации |
| --- | --- |
| Попадание по монстру | `hit = clamp(max_hit + (target_level - attacker_level - 3) * 15 + hit_modifier, min_hit, max_hit)`; если `hit <= random(100)`, physical/element/soul и `damage_modifier` становятся нулём, `full_miss = 2`. Poison остаётся. |
| Попадание по игроку | `hit = clamp(max_hit + hit_modifier, min_hit, max_hit)`. При ненулевом `target.full_miss` до hit-броска возможен отдельный RNG: если есть положительный element, порог `full_miss * attacker.full_miss_scale` сравнивается как x87-произведение без промежуточного усечения; иначе с целым `full_miss`. На промахе `full_miss = 1` для этого уклонения, `2` для hit-проверки. Poison не обнуляется. |
| `PreDefense` | Для игрока защитные состояния/щиты проходят **в порядке регистрации** для каждой составляющей до обычной защиты. Для monster/build стихией может управлять `Promotion`; диапазон ID `530..=545`, кроме `544`, исключён из его применения. |
| Physical и Element | Проверяется отдельный blast-бросок. При blast сначала множитель attack, затем защита/сопротивление с blast-масштабом; иначе вычитается половина беззнаковой защиты (логическое деление на 2). Critical меняет защитное вычитание через `critical_rate`. Затем `avoid`: если `1 <= 100 - avoid < 100`, результат умножается на `(100 - avoid) * 0.01_f32` с конечным усечением. Для атаки игрока по игроку/монстру нижняя граница результата здесь `1`; для атаки монстра по игроку/монстру — `0`. |
| Soul и Poison | Soul вычитает отдельное `soul_resistance`, при части ветвей critical масштабирует вычитание; нижняя граница `0`. Poison обычной physical/element/soul-защитой не меняется. Нельзя сводить все четыре категории к единой формуле. |
| `PostDefense` и множители | `PillarState` для атаки по игроку применяется после обычной защиты и до `damage_factor`, кроме `skill_id 0x212..=0x224`. Положительный результат умножается на `damage_factor` и ограничивается снизу `1`; только в ветви игрок → игрок затем применяется `pvp_damage_factor`, без повторного ограничения снизу. |
| Конечное применение | `AttackInformation::final_damage_values` последовательно вычитает из HP/MP каждый компонент как DWORD, ограничивает максимумом владельца, после компонентов применяет `damage_modifier` к HP. `hp_record/mp_record` — только положительная знаковая разница старого и нового; отсутствие записи не доказывает отсутствие изменения состояния. |

Сводка составлена по [ветвям `CFightDefense`](../../server/rust/src/gameserver/appserver/skills/fightdefense.rs) и [`AttackInformation`](../../server/rust/src/gameserver/appserver/states/attackpower.rs). **Она не является одной общей формулой для всех навыков:** разные concrete owners создают компоненты, проверяют расход/цель и вызывают защиту в разных точках. В частности, разные ограничения попадания и PvP-множитель делают перенос формулы player → player на monster → player ошибкой.

## Ошибки и открытые границы

`UNKNOWN`: полный порядок callback-ов контакта, смерти, добычи и исходящих пакетов для всех типов цели и всех concrete навыков; совпадение каждого перехода с оригинальным клиентом; поведение на необычных NaN/переполнениях в живом runtime. `PARTIAL`: щиты, `Promotion`, `PillarState`, WarSoul и остальные состояния — некоторые типизированы и подключены, но не все исходные `PreDefense`/`PostDefense` производные ветви материализованы. Следовательно, эта страница описывает конкретный достигнутый боевой маршрут, а не полный паритет GameServer.

Современная замена исходных указателей и x87-инструкций типизированными `Vec<AttackPower>` и явным адаптером допустима **только пока сохраняет** порядок составляющих, число/порядок RNG, signed/unsigned-преобразования и момент усечения. Это инженерный критерий совместимости, а не уже пройденная runtime-проверка. Сборка и клиентские сценарии для этой страницы не запускались.
