# Мировые сессии, рейтинги и периодические обновления

World поддерживает взаимодействия, которые переживают смену региона: команду игроков, общие рейтинги и подбор арены. Эти механизмы используют мировые маршруты игроков, но имеют разные модели жизни. Команда существует в памяти и синхронизируется сообщениями; рейтинг может строиться по БД или по событиям; недельный сброс отдельно меняет Game и БД. Их нельзя считать одной разновидностью TCP-сессии или общей очередью сохранения.

## Команда как сессия с участниками

`CSessionFactory` хранит два реестра: сессии по factory session ID и участников (`plug`) по factory plug ID. В командной сессии есть также игровой `team_id`; `CGame` связывает его с session ID. Участник хранит identity владельца `(owner_type, owner_id)`, для игрока это тип `400` и ID персонажа. Эти идентификаторы различны: player ID не заменяет plug ID.

Действующая фабрика различает объявленный тип и возможность создать его:

| Тип | Поведение `create_session` / `create_plug` |
| --- | --- |
| Session `Normal = 0` | Создаёт базовую `CSession`. |
| Session `Team = 1` | Создаёт `CTeam`. |
| Plug `Teamate = 5` | Создаёт `CTeamate`. |
| Plug `Normal = 0`, `Trader = 1`, `PersonalShopSeller = 2`, `PersonalShopBuyer = 3`, `EquipmentUpgrade = 4` | Значения распознаются enum, но фабрика возвращает `0`, объект не создаётся. |
| Неизвестный тип | Возвращается `0`. |

Это поведение тела методов в [csessionfactory.rs](../../server/rust/src/worldserver/appworld/session/csessionfactory.rs). Его вводный комментарий о создании шести plug-типов шире реализации. Поэтому наличие названия `Trader` здесь не доказывает действующую мировую торговую сессию.

[Базовая CSession](../../server/rust/realm/src/sessions/csession.rs) хранит упорядоченных участников, минимум/максимум, lifetime в миллисекундах и signed-флаги. `start` ставит время и `started = 1`; вставка разрешена при ненулевом started, нулевых ended/aborted и числе участников меньше максимума. AI требует именно `started == 1`; при ненулевом lifetime завершает сессию, когда `wrapping_add(start, lifetime) <= tick`. Проверка доступности отдельно сравнивает число участников с минимумом.

Фабрика в AI сначала удаляет null-запись; недоступную сессию прерывает через `abort`, завершённую обслуживает через `end`, иначе исполняет её AI и обход участников. Эффекты доставляются между этими стадиями, перед удалением объектов. Реестр сохраняет порядок bucket-ов на основе `key ^ 0xDEADBEEF` и signed-ключей через `LegacyMsvcHashRegistry`. Это текущая реализация совместимого обхода; из неё не следует правило применять такую карту для любого нового реестра.

## Как команда пересекает границу Game

Game передаёт начальное состояние команды через `0x60001`. Фабрика декодирует сессию и участников; `CTeam` начинает сессию ещё до чтения числа plug-ов. `TeamStarted` публикует маршрут `team_id → session_id`. Следующие сообщения в [on_team_message](../../server/rust/src/worldserver/appworld/message/teammessage.rs) используют этот маршрут для добавления/выхода участника, смены региона и лидера, исключения и обновления распределения добычи.

При смене региона `CTeamate::set_owner_region_id` сначала меняет поле и создаёт state `6`; фабрика отправляет соответствующую проекцию другим Game, где находятся участники. `send_to_team_game_servers` исключает сервер источника и повторные назначения одному Game. Запрос `0x60008` возвращает сериализованную команду в `0x7FD08`. Так другой Game может получить общее состояние команды без собственной независимой мировой копии.

`WorldSessionEffect` и `WorldPlugSessionEffect` — существующий способ выполнить побочные действия после освобождения заимствования объекта. `drain_session_effects` обрабатывает их сразу в порядке появления. `TeamEnded` сначала рассылает `0x7FD02`, затем удаляет team route; `KickPlayer` адресует `0x7FD06` Game конкретного игрока. Это не долговечная очередь: она не даёт повторов после SQL или доставки и не входит в `DoSaveData`.

[CTeam](../../server/rust/realm/src/sessions/cteam.rs) даёт новой команде отсрочку проверки минимального состава в 125 AI-проходов, не миллисекунд. Затем примерно раз в минуту проверяет наличие лидера среди plug-ов и при его отсутствии выбирает первого участника. [CTeamate](../../server/rust/realm/src/sessions/cteamate.rs) отдельно проверяет существование игрока: после минутного gate посылает `0x7FD09` и сбрасывает признак подтверждения; следующий gate при неподтверждённом существовании делает участника недоступным. Ответ `0x60009` устанавливает признак только при ненулевом `existed`. Отсутствие маршрута при отправке не равнозначно немедленному удалению участника.

Есть локальные особенности, которые не следует превращать в образец нового API: `set_allocation_scheme` передаёт ID игрока-лидера туда, где ожидается plug ID, а handler разрешает любое изменившееся значение `< 2`, включая отрицательное. При изменении команды используйте фабрику, route и существующую доставку effects; исправление этих особенностей требует отдельного решения о наблюдаемом поведении.

## Два разных рейтинга

[CPlayerRanks](../../server/rust/src/worldserver/worldserver/playerranks.rs) — упорядоченный результат DB-статистики: ID, имя, профессия, уровень и имя фракции. Ежедневное событие ставится на локальное время из настроек; при равенстве с текущим временем не переносится, перенос на завтра выполняется только при `< now`. После расчёта регистрируется следующая дата.

`CGame::stat_player_ranks` сначала очищает список, пишет start-log, затем вызывает `RsPlayerOwner::stat_ranks`. DB может оставить прочитанный префикс и вернуть обычный неуспех; caller всё равно заканчивает журнал и публикует полученный список. Типизированный блок прерывает путь. Рассылка идёт через `0x7F801`, subtype `0x17`, с signed count и порядком вставки. Это текущая политика обновления: она не является общей рекомендацией очищать прежний кэш перед любым неуспешным чтением.

[CHonorRanks](../../server/rust/src/worldserver/worldserver/honorranks.rs) накапливает результаты игровых событий в памяти. Для четырёх стран отдельно хранятся `history` и `current`, каждый с day/week/month/total. `push_to_ranks` меняет существующую запись без замены имени; у новой требует видимую длину имени меньше 20 байт. Stable-сортировка идёт по eliminations убыванию, затем по уровню убыванию, после чего остаётся десять записей. `killed_one_player` переводит страну игрока `1..4` в индекс `0..3`; остальные страны пропускает.

При смене дня маска равна `0x09` (day + total), первого числа добавляется `0x04` (month), в понедельник — `0x02` (week). Сначала выбранный current копируется в history; day/week/month очищаются, total сохраняется. Затем локальная очередь World получает `0x5FD0C` для сброса счётчиков персонажей, Game получает `0x7F801` subtype `0x27..0x2A`; total дополнительно несёт mask. Сброс касается и ожидающих результатов загрузки через `CPlayerDataQueue::reset_honor_eliminate_info`, чтобы позже опубликованный персонаж не вернул прежние значения.

`generate_save_data` отделяет DB-копию history/current с локальным timestamp; `take_save_owner` передаёт её save-потоку. Живые списки продолжают меняться. Механизм передачи и результат SQL описаны в [сохранении](../architecture/persistence.md), а не задаются фактом отправки рейтинга Game.

## Арена JJC: очередь и занятые регионы

[CJJcSystem](../../server/rust/src/worldserver/appworld/jjcsystem.rs) соединяет очередь игроков, пары боёв по региону, свободные/занятые регионы и таблицу диапазонов уровней. Это отдельная мировая система, которая не создаёт `CSession` на каждый бой.

`apply_player` проверяет допустимость участия и маршрут, резервирует минимальный свободный region ID, затем добавляет игрока в очередь и ищет соперника. Подходят игроки одной положительной группы уровней; из них выбирается минимальная дистанция JJC level с исходной 32-битной арифметикой. При равной дистанции `<=` позволяет более позднему кандидату заменить предыдущего в обходе по ID. Если соперника нет, регион возвращается в пул, а игрок остаётся ждать. Если пара найдена, World заполняет взаимные ссылки, регион и одинаковое время начала, регистрирует бой и отправляет сообщения Game.

`end_pk` сверяет взаимного соперника, timestamp начала и регион перед удалением пары и возвратом региона. Это существующая корреляция результата; одного ID игрока недостаточно. Текущие особенности — проверка лимита занятых регионов через точное `==`, пропуск следующей записи после некоторых удалений и отсутствие поиска другого региона при непригодности выбранного — не являются универсальными правилами для нового matchmaking.

Обновление JJC ranks запускается по strict условию `rank_interval_seconds < wrapping_sub(now, last_refresh)` и меняет timestamp до DB-вызова. **В действующей реализации [RsJjcSysOwner::load_jjc_rank](../../server/rust/src/dbaccess/worlddb/rsjjcsys.rs) возвращает `true`, не меняя vector и не выполняя SQL.** `WorldJjcProcessContext` использует этот метод. Следовательно, лог успешной загрузки здесь не доказывает заполненный рейтинг. Его отличие от DB-статистики `CPlayerRanks` существенно; исходное назначение этой no-op ветви не следует достраивать по имени.

## Сбросы периода: уведомление отдельно от DB-результата

Недельный JJC-сброс сравнивает день недели, час и минуту; настроенные секунды не участвуют в gate. Сначала выставляется флаг выполнения, Game получает `0x80509`, затем запускается DB-worker. Его успешный запуск означает только создание потока: [WorldJjcWeekClearWorker](../../server/rust/src/worldserver/worldserver/jjcmaintenanceworker.rs) позднее выполняет `sp_JJcWeek_BAKE`, затем `sp_JJcWeekClear` и публикует событие результата.

`reset_jjc` обновляет `passed_weeks`, `last_clear_time` и INI даже при неуспешном запуске weekly worker-а. При `passed_weeks > 8 && passed_weeks % 8 == 1` следует сезонный сброс с `0x8050A`; его helper ожидается синхронно. Флаг недельного обновления сбрасывается во все дни, кроме воскресенья, независимо от настроенного дня. Это конкретная особенность текущей реализации: при другом дне gate может открываться повторно в той же минуте.

[CLeiTing::run](../../server/rust/src/worldserver/appworld/leiting.rs) использует другой механизм смены дня: сравнивает `year_day`, вычисляет `update_kind = 1 + (month_changed)`, обновляет всех игроков карты World и посылает по каждому `0x7FA17`. Затем запускает отдельный [DB-reset worker](../../server/rust/src/worldserver/worldserver/leitingresetworker.rs), пишет окончание и запоминает дату. Поздний DB-результат не возвращает прежние значения живых игроков и не откатывает дату.

Для новой функции с теми же требованиями следует использовать существующий подходящий механизм: командную фабрику и эффекты для команды, общий календарь для календарного события, пакет сохранения для долговременных мировых данных. Раздельные реализации JJC и LeiTing показывают текущие различия порядка и ожидания, а не принятое правило создавать отдельный worker для каждой новой таблицы. Границы повторного использования собраны в [общих механизмах](../architecture/shared-mechanisms.md). Полная реакция клиентских экранов и все сочетания разрыва связи с этими переходами остаются открытыми вопросами.
