# Навыки GameServer

Навык связывает команду игрока или ИИ с проверками, расходом ресурсов и игровым эффектом. Запрос только выбирает действие и цель. Зарегистрированный экземпляр хранит время повторного применения, участников и ход каста; конкретная реализация решает, когда списывать ресурс, наносить удар или создавать состояние.

Эта страница описывает текущий исполняемый Rust-путь. [Форматы команд](../protocol/game-actions.md) остаются в протоколе, [хранение экземпляров](objects-and-lifetimes.md) — на странице объектов, [наложенные эффекты](attributes-and-states.md) — на странице атрибутов и состояний. Здесь нет общего обещания исполнения всех ID из фабрики.

## Конфигурация, регистрация и команда

Есть три разных условия готовности навыка:

1. **Доступны свойства нужного уровня.** World передаёт кэш, который принимает Game `CSkillFactory::rebuild`. `CSkillBaseProperties` содержит usage/value, имя, тип и прочие параметры. Подключение кэша находится в [servermessage](../../server/rust/src/gameserver/appserver/message/servermessage.rs).
2. **У фигуры есть экземпляр.** `CMoveShape` хранит `MoveShapeSkill` с ID, уровнем, конкретным `SkillOwner`, lifecycle, данными исполнения, visual и `last_used_ms`. Метаданные читаются из текущей фабрики; выбранный ID сам по себе не создаёт экземпляр.
3. **Поддержана форма исполнения.** `CGame::execute_player_skill_owner` выбирает конкретный путь для `SelfTarget`, `Point` либо `Object`. Наличие ID в фабрике не доказывает поддержку всех трёх форм или исполнения через любого AI.

[`CSkillFactory`](../../server/rust/src/gameserver/appserver/skills/skillfactory.rs) содержит и изменяемый кэш свойств, и статическое соответствие ID классу/политикам. Это разные данные. Изменяемый кэш (`CSkillBaseProperties`, composite key `id << 16 | level & 0xffff`, двоичный кодекс и `rebuild`) находится в [`Zone content`](../../server/rust/zone/src/content/skills.rs) — по правилу «Realm готовит определения, Zone устанавливает полученный набор»; статический реестр владельцев и политик находится в [Zone `skills`](../../server/rust/zone/src/skills/skillfactory.rs); файл старого пакета остаётся тонким glob-реэкспортом. `rebuild` очищает прежний кэш до чтения и публикует записи по мере разбора: поздняя ошибка оставляет разобранный префикс. Точный цикл и malformed-record skip подтверждены дизассемблировкой RVA `0x0006CE10` совпадающей пары Game EXE/PDB; сериализатор WorldServer — парная сторона wire-контракта. Это текущая особенность загрузки, которую необходимо учитывать при диагностике; она не устанавливает общее правило для новых загрузчиков.

Регистрации разделены на Attack, Defense, Summon и State. Дубликаты ID и порядок имеют значение; поиск через актуальные метаданные может отличаться от прямого обхода категории. Подробности и область действия `RegisteredSkill`/`SkillSlot` — в [модели хранения](objects-and-lifetimes.md#зачем-нужны-порядок-и-поколенческий-ключ-одновременно).

## От запроса до первого Begin

[`PlayerSkillRequest` и `BattleFairySkillRequest`](../../server/rust/zone/src/skills/dispatch.rs) хранят прочитанные поля команды в Zone. `skill_id()` очищает старший бит исходного DWORD; обычная, предметная и боевая ветви чтения оригинального Game делают это сразу после первого поля (совпадающая Game EXE/PDB, VA `0x00488BAD–0x00488BE4`, `0x00488E73–0x00488EAE` и `0x004892DF–0x00489320`, `VERIFIED`). `CGame` отдельно вычисляет признаки доступности цели по текущему игроку и региону и передаёт их как `PlayerSkillRequestFacts` либо `BattleFairySkillRequestFacts`. Эти признаки — внутренняя модель Rust, не поля пакета.

[`CPlayer::request_player_skill_core`](../../server/rust/src/gameserver/appserver/player.rs) очищает эмоцию и проверяет уровень зарегистрированного либо предметного навыка. Свойство self-target подставляет самого игрока. Затем общий [`SkillTarget::form`](../../server/rust/zone/src/skills/dispatch.rs) в Zone выбирает форму цели и для обычного, и для навыка боевого духа: если type или ID цели равен нулю, нулевой X **или** Y выбирает `SelfTarget`, иначе получается `Point`; при ненулевых type/ID получается `Object`. Проверка существования региона и объекта остаётся у `CPlayer` после этой классификации. Поэтому координатная цель с одной нулевой координатой не эквивалентна обычной point-команде. Условия выбора и перегрузки вызова сверены по совпадающей Game EXE/PDB: обычный запрос VA `0x00488D20–0x00488E20`, предметный запрос `0x00488FE6–0x00489109`, запрос боевого духа `0x0048949D–0x00489547` (`VERIFIED` для этой развилки; enum и `CGuid::GUID_INVALID` остаются представлением Rust).

У запроса боевого духа уровень определяет [`battle_fairy_skill_level`](../../server/rust/zone/src/skills/battlefairy.rs). При `property_offset == 0` результат `1` без чтения свойства; иначе берётся ID из ключа `GAP_BF_MAN + offset` с DWORD-переполнением. Если он совпал с запрошенным ID, уровень читается из того же ключа. При несовпадении последовательно проверяются свойства `224` на ID `0x222` и `225` на ID `0x223`; любое совпадение даёт уровень `1` независимо от запрошенного ID. Нулевой результат отклоняет запрос. Это странное разрешение сохраняет поведение оригинала, а не исправляется предположением. Порядок, индексы свойств `2`/`1`, условия и значения `VERIFIED` по `CPlayer` VA `0x0042E7A0–0x0042E81C` и вызову VA `0x00489413–0x00489423` совпадающей Game EXE/PDB. Game по-прежнему читает свойства живого предмета через прежний getter.

Девять навыков оснащённого боевого духа проходят свойства `178, 179, 180, 181, 182, 183, 184, 224, 225` в этом порядке. При снятии [`battle_fairy_skill_id`](../../server/rust/zone/src/skills/battlefairy.rs) запрашивает только ID (индекс `2`). При установке `battle_fairy_skill_entry` для первых семи читает уровень (индекс `1`) **перед** ID, а для последних двух читает только ID и подставляет уровень `1`. Каждый слот теперь читается перед изменением соответствующего навыка, без предварительного снимка всех девяти свойств. Порядок getter → изменение навыка → вызов клиентского уведомления `VERIFIED` по совпадающей Game EXE/PDB VA `0x00430610–0x00430756` и `0x00430760–0x00430921`. Game по-прежнему владеет предметом, getter-ом и изменением списка навыков. Некоторые Rust-пути накапливают уведомления в журнале до отправки, поэтому время их доставки относительно следующего слота ещё не подтверждено как поведение оригинала.

При сбросе навыка [`select_battle_fairy_reset_skill`](../../server/rust/zone/src/skills/battlefairy.rs) в Zone использует несовместимые пары ID `530↔534` … `533↔537`. Для одного из трёх стихийных слотов каждая попытка вызывает переданный игровой RNG с аргументом `13` и прибавляет `530` в арифметике DWORD; ненулевой кандидат отвергается при совпадении с любым из трёх текущих ID или если его парный ID находится в двух других слотах. Для общего слота аргумент RNG равен `3`, прибавка — `543`, и отвергается лишь прежний ID. Ноль после сложения обе ветви принимают до сравнений. Каждая повторная попытка расходует ещё один результат того же RNG; код не вводит собственного генератора или предельного числа попыток. Пары `VERIFIED` по конструктору Game EXE/PDB VA `0x00504052–0x00504149`, последовательность вызовов и условия — по ветвям `ResetSkill` VA `0x00501815–0x00501A8D` той же сборки. Потребление предмета сброса, снятие/установка навыков и публикация сообщений остаются у операции игрока в Game; полный живой сценарий не проверен.

Перед расходом предмета [`battle_fairy_reset_preflight`](../../server/rust/zone/src/skills/battlefairy.rs) проверяет флаг функции, затем наличие головного предмета в колонке `10` и значение его свойства `172` с индексом `1`. Только значение `1` допускает продолжение. При выключенном флаге Game отправляет строку `ZHGS0008` красным цветом; отсутствие предмета и неподходящее свойство дают ранний выход без этого сообщения. Порядок ветвей и сравнение `VERIFIED` по совпадающим Game EXE/PDB VA `0x00501599–0x00501645`; строка читается по адресу `0x00653C5C`. Чтение предмета и отправка остаются в Game.

Когда вызывающий требует расход предмета, [`battle_fairy_reset_item`](../../server/rust/zone/src/skills/battlefairy.rs) запрашивает в рюкзаке `ZHJNS01`, затем `ZHJNS02` и лишь после обоих запросов выбирает набор по позиции: `3–5` — первый, `6` — второй. Отсутствие предмета в выбранном наборе останавливает сброс с уведомлением; при неверной позиции предмет не расходуется. Game сохраняет поиск живого предмета по фабричному ID. Оригинальный `CVolumeLimitGoodsContainer::TraversingContainer` проходит предметы через listener: тот сравнивает их ID с результатом поиска имени и собирает подходящие GUID. Неизвестное имя даёт ID `0` (lookup VA `0x00464EA5–0x00464EAF`), который тоже участвует в сравнении; поэтому Rust не должен отбрасывать его заранее. Порядок двух запросов и выбор `VERIFIED` по Game EXE/PDB VA `0x00501663–0x0050178A`, механизм обхода и сравнения — по конструктору контейнера VA `0x004DE0A0–0x004DE0CD`, вызову виртуального слота `+0x28` и listener VA `0x004E2220–0x004E2284`. Дублирование имён в фабрике и порядок кандидатов при нескольких совпадениях требуют отдельной сверки.

После нахождения предмета [`battle_fairy_reset_item_change`](../../server/rust/zone/src/skills/battlefairy.rs) определяет операцию по количеству: `>1` уменьшить на один, `0` или `1` попытаться удалить экземпляр. Нулевое количество не пропускает вызов удаления. Unsigned-сравнение с единицей и удаляющая ветвь `VERIFIED` по функции игрока Game EXE/PDB VA `0x004315E9–0x00431702`. Результат расхода при ошибке контейнера остаётся неустановленным.

После необязательного расхода предмета [`battle_fairy_reset_slot`](../../server/rust/zone/src/skills/battlefairy.rs) последовательно читает ID (индекс `2`) из свойств `181–184`, даже если позиция окажется неверной. Только затем позиция `3–6` определяет заменяемое свойство и прежний ID. В Game остаются getter живого головного предмета и перевод свойства в числовой ключ. Порядок чтений и таблица переходов `VERIFIED` по совпадающим Game EXE/PDB VA `0x005017B4–0x00501806`.

После выбора нового ID [`write_battle_fairy_reset_skill`](../../server/rust/zone/src/skills/battlefairy.rs) задаёт четыре вызова записи выбранного свойства головного предмета: `(индекс 1, 0)`, `(2, 0)`, `(1, 1)`, `(2, новый ID как DWORD)`. Game выполняет их на живом предмете; отказ отдельного setter-а не прерывает последовательность. Для ключей `181–184` порядок `VERIFIED` по совпадающим `gameserver.exe`/`GameServer.pdb`, `CBattleFairyContainer::ResetSkill` VA `0x00501892–0x00501AC7`: три первые ветви переходят к общему четвёртому вызову. Дальнейшее присоединение навыков и клиентский сценарий этим наблюдением не подтверждены.

Если новый ID после присоединения навыков не находится у игрока, `ResetSkill` заканчивается без выбранного уведомления `0xBF71D` и обновления предмета `0xBF918`; предыдущие изменения уже сделаны. Это следует из проверки нулевого указателя после `GetSkill` в Game EXE/PDB VA `0x00501AD4–0x00501AE2` (`VERIFIED` для этой ветви). Для найденного навыка [`battle_fairy_reset_notice_cost`](../../server/rust/zone/src/skills/battlefairy.rs) трактует DWORD стоимости MP как знаковый перед умножением на double `0.0001` и усечением до младшего WORD сообщения. Основание — `fild dword`, константа и вызов преобразования в VA `0x00501B6B–0x00501B8D` той же сборки (`VERIFIED` для числового пути); остальные уведомления о навыках используют свои прежние правила.

Результат — `GameEffectJournal` с `QueuePlayerSkill` и предшествующими уведомлениями. [`CGame::apply_skill_effect_journal`](../../server/rust/src/gameserver/gameserver/game.rs) применяет его и передаёт команду каноническому `CPlayerAI`. Здесь ещё нет универсальной оплаты или попадания.

[`PlayerSkillDispatch` и `BattleFairySkillDispatch`](../../server/rust/zone/src/skills/dispatch.rs) в Zone хранят форму команды (`SelfTarget`, `Point`, `Object`) и объектную цель как [Zone identity](../../server/rust/zone/src/regions/identity.rs). Ожидающий запрос сравнивается по ID навыка и выбранной форме: point — по X/Y, object и self — по type/ID цели; уровень боевого духа и GUID в этот ключ не входят. Полный `Eq` самого dispatch остаётся отдельным сравнением данных исполнения. `has_target` проверяет положительные type/ID объектной формы либо ненулевые X и Y точки. По совпадающей Game EXE/PDB `VERIFIED` для `CBaseAI::HasTarget` VA `0x004C7DD0–0x004C7DF6` при существующем owner (+`0x68`) и сравнений `CPlayerAI` VA `0x0050A13A–0x0050A15C`, `0x0050A349–0x0050A367`; enum, его варианты и полный `Eq` — модель Rust, а не native layout. Живая постановка и отмена команды этим переносом не проверялись.

В `schedule_player_skill` Game проверяет состояние основных очередей AI и жизнь игрока, выбирает pending-команду, назначает текущий ID и проверяет разрешение боя. Верховая езда имеет отдельный отказ. Если выбранный ID не разрешается в реестре, планировщик пробует default-навык и заново разрешает его. Уже исполняемый экземпляр не получает новый Begin этого прохода.

Для выбранного действия `begin_player_skill_schedule` из [playerskillschedule](../../server/rust/src/gameserver/gameserver/game/playerskillschedule.rs) и `execute_player_skill_owner` согласуют общую базу Begin с конкретным исполнителем. У семейств, использующих [playercast](../../server/rust/src/gameserver/appserver/skills/playercast.rs), базовый Begin принадлежит самому адаптеру. После `Begun` AI ставит активное действие боя; последующие `execute_active_player_skill` продолжают тот же экземпляр. Фоновый проход использует те же зарегистрированные экземпляры, но отдельную очередь AI.

## Общая база и конкретные стадии

[`SkillLifecycle`](../../server/rust/zone/src/skills/lifecycle.rs) в Zone хранит `user`, `sufferer`, координатную цель, время старта, `ended`, `available`, `prepared` и причину завершения. `SkillExecutionKernel` добавляет dispatch и стадию. Идентичность фигуры принадлежит [Zone regions](../../server/rust/zone/src/regions/identity.rs): прежний `shape.rs` только переэкспортирует её. При установке конкретного payload база переносится внутрь его kernel; источник, цель и часы не создаются второй раз. Каталог конкретных исполнений и End-hooks пока находится в [адаптере Game](../../server/rust/src/gameserver/appserver/skills/kernel.rs).

`SkillStage` содержит Idle, Begin, Check, Calculate, Attack, Apply. Это общий словарь стадий и проверяемых переходов, а не планировщик: конкретный навык сам вызывает `advance` и может пройти несколько стадий за один AI-вызов. `Pending` означает продолжение ожидания, а не автоматический повтор Begin. `ended` нельзя выводить только из наличия payload: после End данные исполнения могут ещё существовать до отдельного освобождения.

Объектный `SkillLifecycle::begin_objects` при отсутствующей стороне сохраняет её прежнее значение; часы читаются при наличии источника. `finish_begin(false)` сам не очищает контекст и не удаляет конкретные данные. Это текущая семантика общей базы. Путь отказа должен исполнять предусмотренное завершение, а не полагаться на возврат `false`.

Для подходящих player-семейств общий `execute_registered_player_cast_impl` выполняет следующий каркас:

- Проверяет конкретную регистрацию и совпадение dispatch. Если её исполнение уже начато, вызывает конкретный AI и обрабатывает результат.
- Для нового каста выполняет общий Begin, создаёт visual при необходимости, устанавливает конкретный payload в Idle, вызывает переданную проверку и только после успеха переводит стадию в Begin.
- `finish_outcome` переводит терминальный результат в зарегистрированный End. `Released` превращает результат обратно в `Pending`.

Повторно использовать здесь следует этот каркас с собственными `check`, `materialize` и `run_ai`, **если совпадают требования к порядку Begin, visual, проверки и End**. Базовая атака и некоторые другие пути имеют отдельное исполнение; само наличие похожей функции ещё не доказывает, что её порядок подходит новому семейству.

## Как завершается применение

`MoveShapeSkill` хранит [visual-ресурс навыка](../../server/rust/zone/src/skills/visualeffect.rs). `SkillVisualEffectKind` выбирает Rust-обработчик публикации в переходном Game; это не идентификатор оригинального протокола. Общий [CVisualEffect](../../server/rust/zone/src/effects/visualeffect.rs) используется также наложенными состояниями. В исследованном `gameserver.exe` его `BeginVisualEffect` сбрасывает `ended` и записывает знаковый `loop`, а обе перегрузки базового `UpdateVisualEffect` вызывают виртуальный End только при нулевом `loop`. Поэтому замена visual и базовый хвост обновления не должны сами отправлять клиентский пакет: публикация и возможный ранний выход остаются у конкретного обработчика навыка. Это разделяет владение ресурсом и его публикацию без второго реестра visual.

Общая точка — [`CGame::end_registered_instance_with_clock`](../../server/rust/src/gameserver/appserver/states/skill.rs). Она адресует выбранный экземпляр, а не новый поиск по одному ID. Порядок следующий:

1. Конкретный `prepare_derived_end` и политика `SkillOwner::end_policy` очищают фазу/пути, возвращают движение, меняют доступность и выполняют завершающий эффект в предусмотренном порядке. Если получен `Released`, общий хвост пока не исполняется.
2. При ненулевом аргументе и категории, отличной от Defense, выполняется `run_registered_after_use`. Конкретный набор последствий задаёт `SkillOwner::after_use`; его нельзя восстановить только по названию категории.
3. Очищаются участники, координаты, время начала и `prepared`. При тех же условиях отдельно читается время и обновляется `last_used_ms`.
4. Удаляется принадлежащий экземпляру visual, затем база получает `ended = true` и `SkillTermination`.

`End(0)` пропускает AfterUse и новую отметку reuse; для него есть `end_registered_instance_without_after_use`. Это не возврат потраченных ресурсов: общий End не содержит универсального отката. `SkillTermination::{Completed,Rejected,Cancelled}` описывает результат, а числовой аргумент End отдельно управляет игровыми последствиями.

Освобождение payload и команды AI выполняется отдельно. `finish_registered_player_execution` завершает базу и удаляет payload, сохраняя ту же базу в регистрации; сам он не заменяет конкретный cleanup и AfterUse. `finish_registered_player_command` согласует очистку команды с её dispatch. `StopAllSkills` вызывает End(0) в порядке Attack → Defense → Summon → State и не очищает AI target/FIFO/background. Для полного прекращения поведения нужно проследить вызывающий сценарий, а не заменить его одним `clear_skills`.

Повторное применение конкретные навыки проверяют через [`skill_is_restored`](../../server/rust/zone/src/skills/lifecycle.rs): `last_used.wrapping_add(delay) <= now`; delay обычно читается из usage `10005`. Это локальные часы экземпляра. Замена регистрации создаёт новое время `0`, а таймер попытки AI у монстра остаётся отдельным механизмом. По совпадающей Game EXE/PDB `VERIFIED` для `CSkill::IsRestored` VA `0x004D8220–0x004D825F`: при доступной таблице свойств запрос `10005` предшествует чтению `timeGetTime`, а сравнение unsigned и сложение DWORD допускают переполнение. Отсутствующая таблица в оригинале даёт успех до чтения часов; переходные вызовы Rust разрешают таблицу заранее и эту ветвь не моделируют внутри функции Zone.

Текст недостатка MP боевого духа использует [правило Zone](../../server/rust/zone/src/skills/battlefairy.rs): unsigned стоимость умножается на double `0.0001`, усекается через QWORD и передаётся как младший DWORD. По той же Game EXE/PDB `VERIFIED` для ветви ошибки `CWangsheng::AI` VA `0x0051E097–0x0051E0E7`; остальные конкретные навыки продолжают вызывать тот же Rust-хелпер в своих точках отказа. Это правило текста, а не размер фактического списания MP.

## Сценарий: базовая атака

[`execute_player_base_attack`](../../server/rust/zone/src/skills/baseattackruntime.rs) начинает исполнение, затем проверяет цель и дальность, поворачивает атакующего, публикует начало и ждёт задержку. В момент удара цель разрешается снова. Расчёт компонентов, защита и изменение HP описаны в [бое](combat.md).

Эта ветвь показывает, зачем нужны разные моменты допуска и контакта: существование цели при постановке команды не гарантирует её жизнь или допустимость при ударе. Отдельный вызов `with_published_player_ai` позволяет вложенным обработчикам контакта видеть и менять тот же AI.

## Сценарий: Flash и поздний отказ

[`execute_player_flash`](../../server/rust/zone/src/skills/flash.rs) использует общий playercast. Его `check_cast` проверяет reuse, оружие, достаточность MP/RP, отсутствие Pillar и запрещает движение. На этом этапе MP/RP ещё не списаны.

В `run_ai` сначала строится и проверяется путь, повторно проверяется оружие и наличие подготовки RageBreak. Затем подготовка снимается через `end_and_destroy_state_at`; только после этого повторно проверяются и списываются MP, затем RP. Если MP уже не хватает, подготовка всё равно израсходована. Если отказал поздний RP-check, уже списанный MP не возвращается. После успешной оплаты происходят перемещение и контакты вдоль пути; типизированные данные каста хранят путь и список уже затронутых фигур.

Это пример частичных эффектов конкретного порядка исполнения. Общая проверка «достаточно ресурсов» в декодере не заменяет повторные проверки и не делает применение транзакцией. При изменении навыка следует сохранить либо явно обосновать изменение этих точек расхода; копировать такой порядок в другой навык без совпадающих требований не нужно.

## Сценарий: постоянный эффект переживает каст

Автозапуск пассивных навыков направляет State-регистрации в фоновую очередь. `begin_player_back_stage_skills` создаёт self-исполнение и проверяет конкретный immediate-state cast. Затем навык может установить отдельный экземпляр состояния у фигуры и завершить собственное применение. После этого числовую прибавку поддерживает уже property-callback состояния, а не активная команда AI. Пример увеличения HP и его замены разобран в [атрибутах](attributes-and-states.md#сценарий-постоянное-увеличение-максимумов-hp-и-mp).

Удаление регистрации навыка не равнозначно удалению фонового ID или наложенного состояния. Очередной проход фонового AI отдельно обнаруживает отсутствующую регистрацию. Изменяя пассивный навык, нужно проследить обе жизни: регистрацию умения и созданный эффект.

## Путь изменения и границы общих механизмов

Для изменения навыка сначала определите поддержанный dispatch в `execute_player_skill_owner`, затем найдите его общие адаптеры и конкретные callbacks. Если изменяется только эффект при сохранённом порядке каста, используйте существующие playercast, зарегистрированный End и общий механизм состояний. Новый порядок исполнения требует причины в различии требований, а не только нового ID; общий принцип изложен в [повторном использовании механизмов](../architecture/shared-mechanisms.md).

Согласуйте usage/value с источником кэша World, а сохраняемое состояние — с его кодеком и restart. Для изменений движения или снятия запрета проверьте `SkillOwner::end_policy` и все исходы: успех, отказ проверки, потерю цели, клиентское завершение и переход региона. Менять только «счастливую» стадию Apply недостаточно.

Текущие расхождения с единым каркасом: не каждый concrete caller использует зарегистрированный End; низкоуровневые удаления из экипировки и очистка реестра ещё не всегда вызывают его. Часть исполнителей адресует данные через ID, а общая граница допускает `RegisteredSkill`; при вложенной замене это различие существенно. Они не задают предпочтительный способ для нового кода.

Конкретные неизвестные остаются у неподдержанных ID/форм Begin/AI/End. `execute_player_skill_owner` явно отклоняет невыбранную ветвь. Подтверждённый исходный no-op `0x90006` теперь входит в typed dispatcher и завершается без игрового эффекта, поэтому не попадает в общий warning неизвестного сообщения. Соответствие недостигнутых перегрузок оригиналу — `UNKNOWN`; точные EXE/PDB-свидетельства для реализованных семейств приведены в исходных файлах.

Масштаб элемента использует исходную `0.01f` и усечение `FISTP DWORD`. Для этих ветвей и порядка запросов `VERIFIED` по инструкциям `CChaosSphere::Summon` VA `0x005A82E8–0x005A84F3` той же пары Game EXE/PDB. Размещение формы и отправка пакета этим не проверялись.

По совпадающим Game EXE SHA-256 `4F5C98E0FDF6147D8AECF55F7937AAF6E2CF5E4F5A2C44491A6359228762C80E` и PDB SHA-256 `B17BB9B7D69A9CC43E314C0E35C517830BB42CAA89416E173380AB17D2D66016` `VERIFIED` для конструктора VA `0x005FEE80`, writer VA `0x005FECB0` и AI VA `0x005FF270`: срок, скорость и частота проверяются строгим unsigned `>`; первый `ForceMove` получает последнюю точку и длительность `длина пути × скорость`, после вызова записываются часы и флаг; последующие тики двигают индекс не дальше последней клетки. Удар читает текущую клетку пути и обходит квадрат `3×3` от координат минус один. Снимок пишет ID/уровень навыка, тип/ID владельца, остаток времени и затем базовый `CShape`; путь и часы периодов в пакет не входят. Пустой путь прекращает AI до перемещения и удара. Сверка здесь относится к этому циклу и формату; фактические попадания и отправка пакета клиенту не запускались.

## Область SoulMirror

[Правило Zone](../../server/rust/zone/src/skills/soulmirror.rs) выбирает размер и клетку маски, ведёт столбец и строку области и задаёт порядок повторных чтений живых уровня и направления. Для пустой проходимой клетки оно читает срок, направление владельца и ID изображения призываемого существа; общий скелет каста зеркала с диспетчером вызова — в [hub Zone](../../server/rust/zone/src/skills/zonalcast.rs) (порция T5; входные снимки порождённых существ — wire-конверт summonshape). [Адаптер Game](../../server/rust/src/gameserver/appserver/skills/soulmirror.rs) предоставляет живые значения и после каждой выданной клетки разрешает цели, применяет удар или размещает существо в регионе. Список уже атакованных целей пополняется после вызова Attack; занятость клетки устанавливается по любой разрешённой живой фигуре, даже если она не подходит для атаки.

Для той же пары Game EXE/PDB `VERIFIED`: `CSoulMirror::GetScope` VA `0x005A40D0` выбирает байтовые таблицы `0x006A33D0`, `0x006A3420`, `0x006A34F0` по уровням 1–3 и направлениям 0–7; `GetLength/GetHeight` VA `0x005A4120/0x005A4150` возвращают 3, 5, 7. Формула Zone сопоставлена со всеми 664 клетками таблиц без расхождений. В `CSoulMirror::AI` VA `0x005A5342–0x005A5373` для свободной клетки после данных владельца запрашивается LIFETIME `30001`, затем живое направление, затем изображение `30003`. Это статическая сверка указанной части обхода; призыв, попадание и клиентский результат не запускались.

Обход по AI VA `0x005A4F80–0x005A513F` и `0x005A539F–0x005A53D0` отдельно сверен по инструкциям: исходная точка фиксируется один раз, размер проверяется перед каждым столбцом и каждой строкой, затем читаются текущие уровень и направление для маски; после обработки клетки увеличивается строка, после окончания столбца — столбец. `SoulMirrorArea::next_cell` возвращает только очередную включённую клетку, поэтому callbacks Game завершаются до следующих чтений. Это `VERIFIED` для порядка обхода, а не подтверждение фактической атаки.

## Прямые элементальные попадания

[Расчёт Zone](../../server/rust/zone/src/skills/directelement.rs) задаёт варианты Lightning, ChainLightning, Infernol, Seal, SoulMirror и трёх пошаговых снарядов. [Адаптер Game](../../server/rust/src/gameserver/appserver/skills/directelementattack.rs) разрешает владельца, цель, таблицу и живые свойства, исполняет общий RNG, критический хвост и применяет рассчитанную атаку. До таблицы он сохраняет раннее чтение модификатора элемента; у EnergyBolt/SnakeBolt оружейный множитель игрока также читается до неё. Начальная стадия Zone записывает ID, уровень и допустимый для варианта `damage_modifier` до остальных живых чтений. Затем Zone задаёт порядок `HIT 20001 → масштаб 20015 → MAX 20009 → MIN 20008 → RNG → повторный MIN → живой элемент`, добавляет элементальный урон и только для трёх снарядов усиливает его через число душ. Seal и SoulMirror заканчивают расчёт без критического шанса и второго броска.

Снимок душ для трёх снарядов снимается до расчёта урона; формат состояния и порядок его завершения описаны в [накоплении душ](attributes-and-states.md#накопление-душ).

По совпадающим Game EXE/PDB `VERIFIED` для последовательности свойств, двух чтений MIN и одного RNG в `CalculateAttackPower` VA `0x005ACBA0`, `0x00576770`, `0x005A6EC0`, `0x005AA480`, `0x005A4A30`, `0x0053C2A0`, `0x00534390`, `0x00537B50`. Инструкции `FILD unsigned → 0.01f → FIMUL → FISTP DWORD` устанавливают масштаб элемента; `abs(MAX−MIN)+1` вычисляется с 32-битным переполнением. У Lightning, ChainLightning и Infernol присутствует критический хвост со вторым RNG, у Seal, SoulMirror и трёх снарядов его нет; последние используют `(souls × 0.7f + 1)` с исходным усечением низкого DWORD результата. Это сверка расчёта, не подтверждение попадания или клиентского результата.

## Граница серверного снимка FireBall / FireBolt

Карточка серверного `DecordFromByteArray` FireBall (pub `1:001fafa0`, RVA `0x1FBFA0`, исходный `appserver/skills/fireballphalanx.cpp`) перенесена в шапку [модуля projectile Zone](../../server/rust/zone/src/skills/projectile.rs): чтение последовательности 32-битных полей, восстановление уровня навыка, перезапуск отсчёта по живым часам и передача дальнейшего чтения базовой фигуре сверены машинно (`VERIFIED_DISASSEMBLY`) и покрыты общим `BaseProjectileFlight::decode_server_snapshot`; достижимого caller-а у оригинала нет. Клиентский encoder не заменяет отсутствующий caller серверного декодирования. Полный исходный фрагмент сохранён в локальном корпусе.
