# Навыки GameServer

Навык связывает команду игрока или ИИ с проверками, расходом ресурсов и игровым эффектом. Запрос только выбирает действие и цель. Зарегистрированный экземпляр хранит время повторного применения, участников и ход каста; конкретная реализация решает, когда списывать ресурс, наносить удар или создавать состояние.

Эта страница описывает текущий исполняемый Rust-путь. [Форматы команд](../protocol/game-actions.md) остаются в протоколе, [хранение экземпляров](objects-and-lifetimes.md) — на странице объектов, [наложенные эффекты](attributes-and-states.md) — на странице атрибутов и состояний. Здесь нет общего обещания исполнения всех ID из фабрики.

## Конфигурация, регистрация и команда

Есть три разных условия готовности навыка:

1. **Доступны свойства нужного уровня.** World передаёт кэш, который принимает Game `CSkillFactory::rebuild`. `CSkillBaseProperties` содержит usage/value, имя, тип и прочие параметры. Подключение кэша находится в [servermessage](../../server/rust/src/gameserver/appserver/message/servermessage.rs).
2. **У фигуры есть экземпляр.** `CMoveShape` хранит `MoveShapeSkill` с ID, уровнем, конкретным `SkillOwner`, lifecycle, данными исполнения, visual и `last_used_ms`. Метаданные читаются из текущей фабрики; выбранный ID сам по себе не создаёт экземпляр.
3. **Поддержана форма исполнения.** `CGame::execute_player_skill_owner` выбирает конкретный путь для `SelfTarget`, `Point` либо `Object`. Наличие ID в фабрике не доказывает поддержку всех трёх форм или исполнения через любого AI.

[`CSkillFactory`](../../server/rust/src/gameserver/appserver/skills/skillfactory.rs) содержит и изменяемый кэш свойств, и статическое соответствие ID классу/политикам. Это разные данные. `rebuild` очищает прежний кэш до чтения и публикует записи по мере разбора: поздняя ошибка оставляет разобранный префикс. Это текущая особенность загрузки, которую необходимо учитывать при диагностике; она не устанавливает общее правило для новых загрузчиков.

Регистрации разделены на Attack, Defense, Summon и State. Дубликаты ID и порядок имеют значение; поиск через актуальные метаданные может отличаться от прямого обхода категории. Подробности и область действия `RegisteredSkill`/`SkillSlot` — в [модели хранения](objects-and-lifetimes.md#зачем-нужны-порядок-и-поколенческий-ключ-одновременно).

## От запроса до первого Begin

[`CPlayer::request_player_skill_core`](../../server/rust/src/gameserver/appserver/player.rs) очищает эмоцию, проверяет уровень зарегистрированного либо предметного навыка и выбирает форму цели. Свойство self-target подставляет самого игрока. Если type или ID цели равен нулю, нулевой X **или** Y выбирает `SelfTarget`, иначе получается `Point`; при ненулевых type/ID получается `Object`, требующий доступной цели в регионе. Поэтому координатная цель с одной нулевой координатой не эквивалентна обычной point-команде.

Результат — `GameEffectJournal` с `QueuePlayerSkill` и предшествующими уведомлениями. [`CGame::apply_skill_effect_journal`](../../server/rust/src/gameserver/gameserver/game.rs) применяет его и передаёт команду каноническому `CPlayerAI`. Здесь ещё нет универсальной оплаты или попадания.

В `schedule_player_skill` Game проверяет состояние основных очередей AI и жизнь игрока, выбирает pending-команду, назначает текущий ID и проверяет разрешение боя. Верховая езда имеет отдельный отказ. Если выбранный ID не разрешается в реестре, планировщик пробует default-навык и заново разрешает его. Уже исполняемый экземпляр не получает новый Begin этого прохода.

Для выбранного действия `begin_player_skill_schedule` из [playerskillschedule](../../server/rust/src/gameserver/gameserver/game/playerskillschedule.rs) и `execute_player_skill_owner` согласуют общую базу Begin с конкретным исполнителем. У семейств, использующих [playercast](../../server/rust/src/gameserver/appserver/skills/playercast.rs), базовый Begin принадлежит самому адаптеру. После `Begun` AI ставит активное действие боя; последующие `execute_active_player_skill` продолжают тот же экземпляр. Фоновый проход использует те же зарегистрированные экземпляры, но отдельную очередь AI.

## Общая база и конкретные стадии

[`SkillLifecycle`](../../server/rust/src/gameserver/appserver/skills/kernel.rs) хранит `user`, `sufferer`, координатную цель, время старта, `ended`, `available`, `prepared` и причину завершения. `SkillExecutionKernel` добавляет dispatch и стадию. При установке конкретного payload база переносится внутрь его kernel; источник, цель и часы не создаются второй раз.

`SkillStage` содержит Idle, Begin, Check, Calculate, Attack, Apply. Это общий словарь стадий и проверяемых переходов, а не планировщик: конкретный навык сам вызывает `advance` и может пройти несколько стадий за один AI-вызов. `Pending` означает продолжение ожидания, а не автоматический повтор Begin. `ended` нельзя выводить только из наличия payload: после End данные исполнения могут ещё существовать до отдельного освобождения.

Объектный `SkillLifecycle::begin_objects` при отсутствующей стороне сохраняет её прежнее значение; часы читаются при наличии источника. `finish_begin(false)` сам не очищает контекст и не удаляет конкретные данные. Это текущая семантика общей базы. Путь отказа должен исполнять предусмотренное завершение, а не полагаться на возврат `false`.

Для подходящих player-семейств общий `execute_registered_player_cast_impl` выполняет следующий каркас:

- Проверяет конкретную регистрацию и совпадение dispatch. Если её исполнение уже начато, вызывает конкретный AI и обрабатывает результат.
- Для нового каста выполняет общий Begin, создаёт visual при необходимости, устанавливает конкретный payload в Idle, вызывает переданную проверку и только после успеха переводит стадию в Begin.
- `finish_outcome` переводит терминальный результат в зарегистрированный End. `Released` превращает результат обратно в `Pending`.

Повторно использовать здесь следует этот каркас с собственными `check`, `materialize` и `run_ai`, **если совпадают требования к порядку Begin, visual, проверки и End**. Базовая атака и некоторые другие пути имеют отдельное исполнение; само наличие похожей функции ещё не доказывает, что её порядок подходит новому семейству.

## Как завершается применение

`MoveShapeSkill` хранит [visual-ресурс навыка](../../server/rust/zone/src/skills/visualeffect.rs). `SkillVisualEffectKind` выбирает Rust-обработчик публикации в переходном Game; это не идентификатор оригинального протокола. Общий [CVisualEffect](../../server/rust/zone/src/effects/visualeffect.rs) используется также наложенными состояниями. В исследованном `gameserver.exe` его `BeginVisualEffect` сбрасывает `ended` и записывает знаковый `loop`, а обе перегрузки базового `UpdateVisualEffect` вызывают виртуальный End только при нулевом `loop`. Поэтому замена visual и базовый хвост обновления не должны сами отправлять клиентский пакет: публикация и возможный ранний выход остаются у конкретного обработчика навыка. Это разделяет владение ресурсом и его публикацию без второго реестра visual.

Общая точка — [`CGame::end_registered_instance_with_clock`](../../server/rust/src/gameserver/appserver/states/skill.rs). Она адресует выбранный экземпляр, а не новый поиск по одному ID. Порядок следующий:

1. Конкретный `prepare_derived_end` и политика `SkillOwner::end_policy` очищают фазу/пути, возвращают движение, меняют доступность и выполняют завершающий эффект в предусмотренном порядке. Если получен `Released`, общий хвост пока не исполняется.
2. При ненулевом аргументе и категории, отличной от Defense, выполняется `run_registered_after_use`. Конкретный набор последствий задаёт `SkillOwner::after_use`; его нельзя восстановить только по названию категории.
3. Очищаются участники, координаты, время начала и `prepared`. При тех же условиях отдельно читается время и обновляется `last_used_ms`.
4. Удаляется принадлежащий экземпляру visual, затем база получает `ended = true` и `SkillTermination`.

`End(0)` пропускает AfterUse и новую отметку reuse; для него есть `end_registered_instance_without_after_use`. Это не возврат потраченных ресурсов: общий End не содержит универсального отката. `SkillTermination::{Completed,Rejected,Cancelled}` описывает результат, а числовой аргумент End отдельно управляет игровыми последствиями.

Освобождение payload и команды AI выполняется отдельно. `finish_registered_player_execution` завершает базу и удаляет payload, сохраняя ту же базу в регистрации; сам он не заменяет конкретный cleanup и AfterUse. `finish_registered_player_command` согласует очистку команды с её dispatch. `StopAllSkills` вызывает End(0) в порядке Attack → Defense → Summon → State и не очищает AI target/FIFO/background. Для полного прекращения поведения нужно проследить вызывающий сценарий, а не заменить его одним `clear_skills`.

Повторное применение конкретные навыки проверяют через `skill_is_restored(last_used, delay, now)`: `last_used.wrapping_add(delay) <= now`; delay обычно читается из usage `10005`. Это локальные часы экземпляра. Замена регистрации создаёт новое время `0`, а таймер попытки AI у монстра остаётся отдельным механизмом.

## Сценарий: базовая атака

[`execute_player_base_attack`](../../server/rust/src/gameserver/appserver/skills/baseattackruntime.rs) начинает исполнение, затем проверяет цель и дальность, поворачивает атакующего, публикует начало и ждёт задержку. В момент удара цель разрешается снова. Расчёт компонентов, защита и изменение HP описаны в [бое](combat.md).

Эта ветвь показывает, зачем нужны разные моменты допуска и контакта: существование цели при постановке команды не гарантирует её жизнь или допустимость при ударе. Отдельный вызов `with_published_player_ai` позволяет вложенным обработчикам контакта видеть и менять тот же AI.

## Сценарий: Flash и поздний отказ

[`execute_player_flash`](../../server/rust/src/gameserver/appserver/skills/flash.rs) использует общий playercast. Его `check_cast` проверяет reuse, оружие, достаточность MP/RP, отсутствие Pillar и запрещает движение. На этом этапе MP/RP ещё не списаны.

В `run_ai` сначала строится и проверяется путь, повторно проверяется оружие и наличие подготовки RageBreak. Затем подготовка снимается через `end_and_destroy_state_at`; только после этого повторно проверяются и списываются MP, затем RP. Если MP уже не хватает, подготовка всё равно израсходована. Если отказал поздний RP-check, уже списанный MP не возвращается. После успешной оплаты происходят перемещение и контакты вдоль пути; типизированные данные каста хранят путь и список уже затронутых фигур.

Это пример частичных эффектов конкретного порядка исполнения. Общая проверка «достаточно ресурсов» в декодере не заменяет повторные проверки и не делает применение транзакцией. При изменении навыка следует сохранить либо явно обосновать изменение этих точек расхода; копировать такой порядок в другой навык без совпадающих требований не нужно.

## Сценарий: постоянный эффект переживает каст

Автозапуск пассивных навыков направляет State-регистрации в фоновую очередь. `begin_player_back_stage_skills` создаёт self-исполнение и проверяет конкретный immediate-state cast. Затем навык может установить отдельный экземпляр состояния у фигуры и завершить собственное применение. После этого числовую прибавку поддерживает уже property-callback состояния, а не активная команда AI. Пример увеличения HP и его замены разобран в [атрибутах](attributes-and-states.md#сценарий-постоянное-увеличение-максимумов-hp-и-mp).

Удаление регистрации навыка не равнозначно удалению фонового ID или наложенного состояния. Очередной проход фонового AI отдельно обнаруживает отсутствующую регистрацию. Изменяя пассивный навык, нужно проследить обе жизни: регистрацию умения и созданный эффект.

## Путь изменения и границы общих механизмов

Для изменения навыка сначала определите поддержанный dispatch в `execute_player_skill_owner`, затем найдите его общие адаптеры и конкретные callbacks. Если изменяется только эффект при сохранённом порядке каста, используйте существующие playercast, зарегистрированный End и общий механизм состояний. Новый порядок исполнения требует причины в различии требований, а не только нового ID; общий принцип изложен в [повторном использовании механизмов](../architecture/shared-mechanisms.md).

Согласуйте usage/value с источником кэша World, а сохраняемое состояние — с его кодеком и restart. Для изменений движения или снятия запрета проверьте `SkillOwner::end_policy` и все исходы: успех, отказ проверки, потерю цели, клиентское завершение и переход региона. Менять только «счастливую» стадию Apply недостаточно.

Текущие расхождения с единым каркасом: не каждый concrete caller использует зарегистрированный End; низкоуровневые удаления из экипировки и очистка реестра ещё не всегда вызывают его. Часть исполнителей адресует данные через ID, а общая граница допускает `RegisteredSkill`; при вложенной замене это различие существенно. Они не задают предпочтительный способ для нового кода.

Конкретные неизвестные остаются у неподдержанных ID/форм Begin/AI/End. `execute_player_skill_owner` явно отклоняет невыбранную ветвь. Подтверждённый исходный no-op `0x90006` теперь входит в typed dispatcher и завершается без игрового эффекта, поэтому не попадает в общий warning неизвестного сообщения. Соответствие недостигнутых перегрузок оригиналу — `UNKNOWN`; точные EXE/PDB-свидетельства для реализованных семейств приведены в исходных файлах.

## Снятие конфликтов Fury

[`Zone skills`](../../server/rust/zone/src/skills/fury.rs) задаёт девять ID, с которыми несовместима Fury; [Game](../../server/rust/src/gameserver/appserver/skills/fury.rs) обходит живые слоты владельца и вызывает End с уничтожением оставшегося экземпляра. По совпадающей Game EXE/PDB `VERIFIED` для участка `CFury::AI` VA `0x00536C21–0x00536CCE`: проверяются `0x138`, `0xD2`, `0xC9`, `0x67`, `0x192`, `0x191`, `0x198`, `0x199`, `0x1A6`; пустой и другой слот пропускаются. После End код заново читает тот же слот, уничтожает текущий объект, обнуляет слот и увеличивает индекс. Только после обхода создаётся Cure. Этот список короче списка самого [Cure](#очищение-cure); объединять правила по сходству ID нельзя. Фактическое снятие эффектов и клиентский результат не запускались.

## Прибавки GodBless и GodBless2

[`Zone skills`](../../server/rust/zone/src/skills/godbless.rs) хранит правило расчёта трёх прибавок и подготовки состояния; [Game](../../server/rust/src/gameserver/appserver/skills/godbless.rs) выбирает живых участников, читает оружие и устанавливает эффект. После `visual1` текущий уровень урона оружия игрока или ноль передаётся в Zone. Свойства читаются в порядке `121 → 116 → 122 → 117 → 120 → 115`: для каждой прибавки коэффициент умножается на оружие по DWORD, результат масштабируется сохранённой `0.01f` и округляется до `f32`; константа складывается с ним и снова округляется до `f32`. После удаления прежнего состояния отдельно читается срок `10002`, затем элемент, максимум и минимум усекаются через `FISTP DWORD` и создаётся состояние. Его формат и применение описаны в [атрибутах](attributes-and-states.md#что-делает-экземпляр-состояния).

По совпадающим Game EXE/PDB `VERIFIED` для этого порядка и числовых преобразований в `CGodBless::AI` VA `0x005B0626–0x005B0703`, `0x005B0859–0x005B08D7` и `CGodBless2::AI` VA `0x00550BA8–0x00550C81`, `0x00550DAB–0x00550E29`. Реальное наложение и клиентский результат не проверялись.

## Создание стойки Pillar

[`Zone skills`](../../server/rust/zone/src/skills/pillar.rs) вычисляет параметры нового состояния, а [Game](../../server/rust/src/gameserver/appserver/skills/pillar.rs) переключает стойку у живого игрока. По совпадающей Game EXE/PDB `VERIFIED` для `CPillar::AI` VA `0x0057033C–0x0057039B`: только если прежний ID `0x74` не найден, запрашивается unsigned свойство `20003`; его значение умножается на сохранённую float-константу `0.001` в x87 и округляется до `f32`. После этого запрашивается срок `10002` и создаётся состояние. При повторном применении первый прежний экземпляр завершается без запросов этих двух свойств. Запись и срок состояния описаны в [атрибутах](attributes-and-states.md#что-делает-экземпляр-состояния). Игровой и клиентский сценарии стойки не запускались.

## Область Roar

[`Zone skills`](../../server/rust/zone/src/skills/roar.rs) рассчитывает границы обхода по текущим X/Y источника и размерам региона; [Game](../../server/rust/src/gameserver/appserver/skills/roar.rs) читает клетку и решает, можно ли наложить состояние на живую цель. По совпадающей Game EXE/PDB `VERIFIED` для `CRoar::AI` VA `0x0054B1CC–0x0054B23E`: минимум каждой координаты равен `max(source − 2, 0)`, максимум — `min(source + 2, размер региона)`; обе оси обходятся включительно, X снаружи, Y внутри. Переходный Game сохраняет чтение живой клетки на каждой итерации, без общего снимка или дедупликации. Сохраняемый эффект описан в [состояниях](attributes-and-states.md#что-делает-экземпляр-состояния). Фактический обход с клиентом не запускался.

## Очищение Cure

[`Zone skills`](../../server/rust/zone/src/skills/cure.rs) задаёт порог очищения и список ID; [Game](../../server/rust/src/gameserver/appserver/skills/cure.rs) читает свойства применённого навыка, текущий модификатор элемента пользователя, обходит живые состояния цели, тратит RNG и вызывает их End с уничтожением оставшегося экземпляра. По совпадающей паре Game EXE/PDB `VERIFIED` для `CCure::CastCure` VA `0x005ADB10–0x005ADC91`: unsigned коэффициент `20015` превращается в x87 число (при старшем бите с добавлением `2^32`), умножается на float-константу `0.01` и signed модификатор элемента пользователя, затем результат усекается в DWORD. Далее он умножается на константу `20010` и складывается с вероятностью `40001` по DWORD; итог сравнивается как signed с отдельным броском `random(100)` для каждого подходящего слота. Список ID: `0x138`, `0xD2`, `0xC9`, `0x67`, `0x192`, `0x191`, `0x198`, `0x199`, `0x1A6`, `0x73`, `0x7C`, `0x1F8`. Пустой или неподходящий слот не расходует RNG; после End оригинал заново читает ту же позицию перед уничтожением, затем переходит к следующей. ID `0x198` входит в проверку, хотя активный SpiderMist в нынешней модели не является записью `CMoveShape::m_vStates`; это не основание создавать ему второй state-owner. Сохраняемый эффект Cure описан в [состояниях](attributes-and-states.md#что-делает-экземпляр-состояния). Фактическое снятие эффектов и клиентский результат не запускались.

В обходе VA `0x00600840` начало Y вычисляется с `height / 2`, но внутренний предел цикла использует `length`; для нынешнего caller-а размеры равны `1×1`. AI VA `0x00600A70` выбирает истечение только при unsigned `now > start + lifetime` и делает обход до ветви удаления. За пределами фактически создаваемой области `1×1` поведение патологических размеров и переполнения координат остаётся `PARTIAL`.

`VERIFIED` для срока и начальной маски по той же паре Game EXE/PDB, что указана в разделе Weak: конструктор `CPoisonFogPhalanx` VA `0x005FBD90` записывает ID `0xC9`, параметры состояния и создаёт `CScope`. Этот End меняет состояние фигуры и формирует сообщение выхода. Полный порядок наложения на все типы целей и поведение иных значений уровня здесь не объявляются восстановленными.

## Область SpiderMist

Поведение неподтверждённых уровней и крайних переполнений координат остаётся `PARTIAL`; компиляция и клиентское действие — отдельные проверки.

## Область SnowStorm

При призыве [параметры Zone](../../server/rust/zone/src/skills/snowstorm.rs) задают ключи определения и порядок чтения: число целей `20010`, максимум атаки `20009`, минимум `20008`, частота `6001`, затем повторное чтение текущего уровня экземпляра и срок `30001`. `CGame` предоставляет снимок определения и живой уровень; такое разделение сохраняет порядок `CSnowStorm::Summon` VA `0x00584060` по совпадающей паре Game EXE/PDB. Конструктор области получает эти значения после выделения времени начала и ID.

[Модель Zone](../../server/rust/zone/src/skills/snowstorm.rs) владеет массивом заранее выбранных клеток, счётчиком окон, часами и снимком параметров атаки; она же собирает `AttackInformation` с элементальным уроном и пишет поля клиентского снимка области. [Адаптер Game](../../server/rust/src/gameserver/appserver/skills/snowstormphalanx.rs) получает центр из `CShape`, передаёт игровой RNG и часы, добавляет базовую форму к снимку, проверяет живую цель и применяет подготовленную атаку. Общий поток RNG сохраняется при заполнении клеток и при каждом попадании. Проверки нулевой частоты, количества целей больше 25 и недопустимого размера массива — защитные границы Rust: для соответствующих неверных параметров оригинальный путь не установлен как успешный.

`VERIFIED` для перечисленных ветвей по той же совпадающей паре Game EXE/PDB, что указана выше: конструктор VA `0x005F9040` задаёт ID `0x193`, vtable `0x00660DFC`, сохраняет частоту и параметры атаки; VA `0x005F91E1–0x005F9204` делит срок на частоту, умножает на ширину и высоту маски и выделяет по восемь байт на пару координат. Константы уровней 1–3 в `0x006A52C4–0x006A52D8` задают ширину и высоту 5. `Initialize` VA `0x005F8D70` обнуляет массив, для каждой выбранной клетки вызывает общий RNG `0x0041CBA0` сначала с шириной, затем с высотой, проверяет маску и пишет X/Y в окно; при полной маске этих уровней повторная клетка допустима. Виртуальный encoder VA `0x005F8ED0` пишет ID, уровень, тип/ID владельца, остаток времени, срок, частоту, число клеток `lifetime / frequency × 25` и сырые пары X/Y, затем передаёт запись базовой форме. Getter времени VA `0x005E9870` повторно читает часы только при положительном остатке. Слот AI `+0x3C` ведёт к VA `0x005F94B0`: unsigned `now > start + lifetime` завершает область, unsigned `now > last_attack + frequency` разрешает очередное окно; до обхода целей записывается новое `last_attack`, после обхода увеличивается индекс окна. `Attack` VA `0x005F93B0` создаёт сведения атакующего, сохраняя дополнительные поля только для типа 400, и после проверки цели вызывает `CalculateAttackPower` VA `0x005F92D0`: ID `0x193`, младший байт уровня, точность 100, множитель 1.0 и один элементальный компонент. Формула элемента VA `0x005F934B–0x005F9388` вычисляет `abs(max − min) + 1` в 32-битной арифметике, вызывает RNG один раз, прибавляет минимум и элементальный модификатор с переполнением и ограничивает отрицательный результат нулём. Обработка исчерпанного массива native, нестандартных масок и последующее применение урона остаются `PARTIAL`.

## Области GodThunder

[Модель Zone](../../server/rust/zone/src/skills/godthunder.rs) хранит ID, снимок элементальной атаки, часы и массив окон GodThunder `0x140`/GodThunder2 `0x143`. Первый вариант использует полный квадрат `3×3`, второй — округлую маску `7×7` и отдельный ранний проход боевых духов. Та же маска применяется прежним Thunder через единственное определение Zone. [Адаптер Game](../../server/rust/src/gameserver/appserver/skills/godthunderphalanx.rs) держит `CShape`, получает центр и игровой RNG, а [региональный обход](../../server/rust/src/gameserver/gameserver/game/godthunder.rs) разрешает живые цели и применяет общий [элементальный расчёт](#элементальные-удары-призванных-областей).

Параметры призыва теперь собирает та же модель Zone. `VERIFIED` для `CGodThunder::Summon` VA `0x00573840` и `CGodThunder2::Summon` VA `0x00553A80` по указанной паре Game EXE/PDB: после общего масштабирования элемента оба пути читают живой CCH как WORD, число целей `20010`, живую добавку элемента, максимум `20009`, минимум `20008`, частоту `6001`, текущий уровень экземпляра, затем срок `30001`. Только после этого берутся часы и создаётся область. Каждый исходный путь вызывает собственный конструктор с фиксированным ID `0x140` или `0x143`; общий Rust-адаптер теперь получает этот выбор от диспетчера и не заменяет его поздним повторным чтением ID. Game предоставляет живые значения через [общий тип чтений](../../server/rust/zone/src/skills/elementphalanx.rs); Zone задаёт порядок и ключи, чтобы поздний отказ не перемещал уже выполненные запросы.

По идентифицированной выше паре Game EXE/PDB `VERIFIED` для конструкторов VA `0x005F5B50`/`0x005EF190`: число окон равно unsigned `lifetime / frequency`, размер массива — число окон × полная площадь маски × восемь байт; исходный нулевой делитель не даёт успешного экземпляра. Данные маски второго варианта `0x006A4AF8–0x006A4B90` совпадают для уровней 1–3 и по байтам равны маске Thunder в `0x006A43AC`. `Initialize` VA `0x005F59C0`/`0x005EEF30` обнуляет массив, запрашивает X, затем Y из общего RNG, повторяет неактивные клетки и записывает координаты в окна с шагом полной площади; допустимы повторы клеток. Общий writer VA `0x005EF0C0` записывает ID, уровень, тип/ID владельца, остаток срока, срок, частоту и счётчик `(lifetime / frequency) × target_count`, затем непрерывный префикс массива указанной длины и базовую форму. AI VA `0x005F6150`/`0x005EF6B0` проверяет строгие unsigned границы срока и частоты на отдельных чтениях часов, записывает время удара перед обходом и увеличивает номер окна после него, даже если регион не найден. Защитное ограничение Rust отклоняет число целей больше площади и недопустимый размер массива; фактические попадания и клиентский снимок не запускались.

## Огненная стена FireWall

[Правило Zone](../../server/rust/zone/src/skills/firewall.rs) выбирает маску по уровню и собирает параметры призыва в порядке исходных чтений; [адаптер Game](../../server/rust/src/gameserver/appserver/skills/firewall.rs) предоставляет текущие свойства владельца, таблицу навыка и уровень, создаёт живую форму и согласует её с соседними стенами. По той же совпадающей паре Game EXE/PDB, что приведена выше, `VERIFIED` для `CFireWall::Summon` VA `0x005ABC70`: после масштабирования элемента запрос `20010`, 32-битное умножение с переполнением и прибавление 100, перевод беззнакового результата через исходную `0.01f` в отдельное `f32`, затем запрос `30001` и усечение произведения через `FISTP DWORD`. Далее инструкции VA `0x005ABE2D–0x005ABE83` читают CCH как WORD, прибавку элемента, свойства MAX `20009`, MIN `20008`, частоту `6001` и текущий уровень экземпляра именно в этом порядке до вызова конструктора. Конструктор `CFireWallPhalanx` VA `0x005FFF30` задаёт ID `0x134` и выбирает из данных `0x006A5624–0x006A5654` маску `1×1` для уровня 1, крест `3×3` для уровня 2, полный квадрат `3×3` иначе. Совместимость атаки по целям и клиентское поведение этим переносом не подтверждаются.

[Маска неподвижной области](../../server/rust/zone/src/skills/masked_area.rs) теперь хранится в Zone для FireWall и YinYang: адаптер передаёт центр старой формы и маску новой области, Zone снимает пересекающиеся активные клетки; обход атаки читает ту же маску. Прямые инструкции `ReplaceAffectRegion` FireWall VA `0x005FFCD0`, YinYang VA `0x005FE270` и YinYang2 VA `0x005F2190` подтверждают вызов пересечения, выбор маски нового уровня и переставленные координаты записи через `CScope::SetInScope` VA `0x005E9990`. Для обычного пересечения масок `VERIFIED` результат снятия клеток; крайние переполнения координат и иные нештатные размеры остаются `PARTIAL`.

Тот же объект Zone хранит срок и режим обхода. `VERIFIED` по AI FireWall VA `0x006003E0`: unsigned `now > start + lifetime` завершает стену; иначе новое чтение часов проверяет строгое `now > last_attack + frequency`, а третье записывает `last_attack` перед поиском региона и целей. AI YinYang VA `0x005FE9A0` и YinYang2 VA `0x005F28C0` ожидают строгое истечение срока и делают один обход с последующим завершением. Вызовы часов и работа с регионом остаются в [адаптере Game](../../server/rust/src/gameserver/gameserver/game/maskedelement.rs); компиляция не доказывает фактические удары или End.

## Элементальные удары призванных областей

Числовой снимок элементального удара FireWall, YinYang/YinYang2, GodThunder/GodThunder2 и ChaosSphere хранится в [Zone skills](../../server/rust/zone/src/skills/elementphalanx.rs). Это статическая сверка расчёта; применение урона и клиентский результат не запускались.

## Движущаяся область ChaosSphere

[Модель Zone](../../server/rust/zone/src/skills/chaossphere.rs) владеет путём, индексом клетки, часами движения и удара, первым перемещением и пятью полями клиентского снимка. [Адаптер Game](../../server/rust/src/gameserver/appserver/skills/chaosspherephalanx.rs) держит `CShape`; [цикл региона](../../server/rust/src/gameserver/gameserver/game/chaossphere.rs) читает живые часы, вызывает `ForceMove` и обходит цели. Отдельные [правила элементальной атаки](../../server/rust/zone/src/skills/elementphalanx.rs) применяются к попаданию.

[Правило призыва Zone](../../server/rust/zone/src/skills/chaossphere.rs) сначала запрашивает SPEED `30002` и только при ненулевом результате повторно читает SPEED, затем LIFETIME `30001` для длины пути. [Адаптер призыва Game](../../server/rust/src/gameserver/appserver/skills/chaossphere.rs) строит путь; исходно пустой путь прекращает призыв, а обрезанный по BLOCK2 до пустого всё ещё допускает создание формы. После этого Game получает владельца и живой модификатор элемента, а Zone последовательно читает коэффициент `20015`, CCH как WORD, SPEED `30002`, прибавку элемента, MAX `20009`, MIN `20008`, FREQUENCY `6001`, свежий уровень и LIFETIME `30001`. Масштаб элемента использует исходную `0.01f` и усечение `FISTP DWORD`. Для этих ветвей и порядка запросов `VERIFIED` по инструкциям `CChaosSphere::Summon` VA `0x005A82E8–0x005A84F3` той же пары Game EXE/PDB. Размещение формы и отправка пакета этим не проверялись.

По совпадающим Game EXE SHA-256 `4F5C98E0FDF6147D8AECF55F7937AAF6E2CF5E4F5A2C44491A6359228762C80E` и PDB SHA-256 `B17BB9B7D69A9CC43E314C0E35C517830BB42CAA89416E173380AB17D2D66016` `VERIFIED` для конструктора VA `0x005FEE80`, writer VA `0x005FECB0` и AI VA `0x005FF270`: срок, скорость и частота проверяются строгим unsigned `>`; первый `ForceMove` получает последнюю точку и длительность `длина пути × скорость`, после вызова записываются часы и флаг; последующие тики двигают индекс не дальше последней клетки. Удар читает текущую клетку пути и обходит квадрат `3×3` от координат минус один. Снимок пишет ID/уровень навыка, тип/ID владельца, остаток времени и затем базовый `CShape`; путь и часы периодов в пакет не входят. Пустой путь прекращает AI до перемещения и удара. Сверка здесь относится к этому циклу и формату; фактические попадания и отправка пакета клиенту не запускались.

## Область SoulMirror

[Правило Zone](../../server/rust/zone/src/skills/soulmirror.rs) выбирает размер и клетку маски, ведёт столбец и строку области и задаёт порядок повторных чтений живых уровня и направления. Для пустой проходимой клетки оно читает срок, направление владельца и ID изображения призываемого существа. [Адаптер Game](../../server/rust/src/gameserver/appserver/skills/soulmirror.rs) предоставляет живые значения и после каждой выданной клетки разрешает цели, применяет удар или размещает существо в регионе. Список уже атакованных целей пополняется после вызова Attack; занятость клетки устанавливается по любой разрешённой живой фигуре, даже если она не подходит для атаки.

Для той же пары Game EXE/PDB `VERIFIED`: `CSoulMirror::GetScope` VA `0x005A40D0` выбирает байтовые таблицы `0x006A33D0`, `0x006A3420`, `0x006A34F0` по уровням 1–3 и направлениям 0–7; `GetLength/GetHeight` VA `0x005A4120/0x005A4150` возвращают 3, 5, 7. Формула Zone сопоставлена со всеми 664 клетками таблиц без расхождений. В `CSoulMirror::AI` VA `0x005A5342–0x005A5373` для свободной клетки после данных владельца запрашивается LIFETIME `30001`, затем живое направление, затем изображение `30003`. Это статическая сверка указанной части обхода; призыв, попадание и клиентский результат не запускались.

Обход по AI VA `0x005A4F80–0x005A513F` и `0x005A539F–0x005A53D0` отдельно сверен по инструкциям: исходная точка фиксируется один раз, размер проверяется перед каждым столбцом и каждой строкой, затем читаются текущие уровень и направление для маски; после обработки клетки увеличивается строка, после окончания столбца — столбец. `SoulMirrorArea::next_cell` возвращает только очередную включённую клетку, поэтому callbacks Game завершаются до следующих чтений. Это `VERIFIED` для порядка обхода, а не подтверждение фактической атаки.

## Прямые элементальные попадания

[Расчёт Zone](../../server/rust/zone/src/skills/directelement.rs) задаёт варианты Lightning, ChainLightning, Infernol, Seal, SoulMirror и трёх пошаговых снарядов. [Адаптер Game](../../server/rust/src/gameserver/appserver/skills/directelementattack.rs) разрешает владельца, цель, таблицу и живые свойства, исполняет общий RNG, критический хвост и применяет рассчитанную атаку. До таблицы он сохраняет раннее чтение модификатора элемента; у EnergyBolt/SnakeBolt оружейный множитель игрока также читается до неё. Начальная стадия Zone записывает ID, уровень и допустимый для варианта `damage_modifier` до остальных живых чтений. Затем Zone задаёт порядок `HIT 20001 → масштаб 20015 → MAX 20009 → MIN 20008 → RNG → повторный MIN → живой элемент`, добавляет элементальный урон и только для трёх снарядов усиливает его через число душ. Seal и SoulMirror заканчивают расчёт без критического шанса и второго броска.

Снимок душ для трёх снарядов снимается до расчёта урона; формат состояния и порядок его завершения описаны в [накоплении душ](attributes-and-states.md#накопление-душ).

По совпадающим Game EXE/PDB `VERIFIED` для последовательности свойств, двух чтений MIN и одного RNG в `CalculateAttackPower` VA `0x005ACBA0`, `0x00576770`, `0x005A6EC0`, `0x005AA480`, `0x005A4A30`, `0x0053C2A0`, `0x00534390`, `0x00537B50`. Инструкции `FILD unsigned → 0.01f → FIMUL → FISTP DWORD` устанавливают масштаб элемента; `abs(MAX−MIN)+1` вычисляется с 32-битным переполнением. У Lightning, ChainLightning и Infernol присутствует критический хвост со вторым RNG, у Seal, SoulMirror и трёх снарядов его нет; последние используют `(souls × 0.7f + 1)` с исходным усечением низкого DWORD результата. Это сверка расчёта, не подтверждение попадания или клиентского результата.

## Граница серверного снимка FireBall / FireBolt

В [FireBallPhalanx](../../server/rust/src/gameserver/appserver/skills/fireballphalanx.rs) сохранена карточка `DecordFromByteArray`, RVA `0x001FBFA0`, исходный `appserver/skills/fireballphalanx.cpp:317`. Локальный разбор показывает чтение последовательности 32-битных полей, восстановление уровня навыка, установку начала отсчёта по текущему времени и передачу дальнейшего чтения базовой фигуре. Это `INFERRED` по исследовательскому псевдокоду; семантика пропускаемых полей и соответствие полноценного серверного decoder остаются `UNKNOWN` без дополнительного прямого основания. Клиентский encoder не заменяет отсутствующий caller серверного декодирования. Полный исходный фрагмент сохранён в локальном корпусе.
