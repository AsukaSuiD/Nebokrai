# Задания: каталог, состояние игрока и сценарии

Задание в восстановленном GameServer — связь каталога `CQuestSystem`, сохранённого состояния игрока и сценариев. Клиентский запрос о завершении **не** означает немедленную смену флага: он запускает сценарий при допустимом состоянии. Статус знания оригинала отделён от статической связности Rust согласно [правилам свидетельств](../reconstruction/evidence-and-contracts.md).

## Владельцы и модель данных

[`CQuestSystem`](../../server/rust/src/setup/questsystem.rs) владеет параметрами лимита заданий/разницы уровней, путями трёх общих сценариев (вход, повышение уровня, смерть) и каталогом по `u16 quest_id`. Запись включает тип, уровень, сложность, отслеживание, текстовые поля, пути сценариев отказа/завершения, регион и координаты, effect и признак отображения. [World init](../../server/rust/src/worldserver/worldserver/game.rs) загружает `Data/Quest.ini`, затем накладывает `Data/QuestEx.ini` по ID; [начальная конфигурация Game](../../server/rust/src/worldserver/appworld/message/servermessage.rs) передаёт сериализованный каталог селектором `0x16`. Отсутствие StringTable-ключа оставляет пустую строку, путь сценария нормализуется ASCII-lowercase. **`VERIFIED` для этих операций, EXE/PDB:** `worldserver.exe/worldserver.pdb` и `gameserver.exe/GameServer.pdb` названы в [owner-е каталога](../../server/rust/src/setup/questsystem.rs). `QuestEx.ini` нужен именно для переопределений, поэтому независимый список расширения не равнозначен итоговому каталогу. Неустановленные правила самих скриптов сюда не переносятся.

[`CPlayer`](../../server/rust/src/gameserver/appserver/player.rs) владеет `BTreeMap<u16,u8>` состояний. GameSave пишет число записей `i32`, затем каждую пару `u16 id` + `u8 state`; при чтении словарь сначала очищается. Неизвестный ID для `GetQuestState` возвращает **`2`**, существующий — сохранённый байт без дополнительной интерпретации. `0` используется как активное состояние, `1` — завершённое; значение `2` для отсутствия является результатом lookup, а не обязательной записью в словарь. **`VERIFIED`, EXE/PDB:** owner player отмечает `CPlayer::GetQuestState` и достигнутый GameSave codec. Другие возможные значения сохранённого `u8` и их смысл — `UNKNOWN`.

| Действие | Условие и порядок в достигнутом Rust-пути | Свидетельство/ограничение |
| --- | --- | --- |
| Добавить | Если игрок не локален — отправить World `0x6013B` (`i32 player_id`, `u16 quest_id`). Локально: запись должна быть в каталоге; только текущее `Some(0)` блокирует повтор; затем состояние становится `0`, после чего клиент получает `0xBFF2C` с описанием задания. | `PARTIAL`, EXE/PDB owner-контракты [CGame](../../server/rust/src/gameserver/gameserver/game.rs)/[CPlayer](../../server/rust/src/gameserver/appserver/player.rs). Как World доставляет отложенную команду обратно — отдельно не доказано. |
| Завершить | Локально требуется запись каталога и существующее состояние игрока; оно становится `1`, затем клиент получает `0xBFF2D` с ID и именем. Метод не проверяет, что предыдущее значение было именно `0`; повторный вызов для уже существующего `1` снова возвращает успех. | `VERIFIED` для данного owner-пути, EXE/PDB в комментариях; не означает автоматическое завершение после клиентского `0x90127`. |
| Удалить | Нелокальному игроку — World `0x6013C` с ID. Локально запись каталога и состояние должны существовать; запись удаляется до клиентского `0xBFF2E` с ID и именем. | `PARTIAL`, EXE/PDB owners. Доставка и постоянное сохранение через World здесь не прослежены. |
| Обновить место | `0xBFF2F` (`u16 id`, три `i32`: регион, X, Y) отправляется только игроку, у которого есть этот ID, без изменения самого каталога. | `VERIFIED` для достигнутого вызова [CGame](../../server/rust/src/gameserver/gameserver/game.rs). |

При формировании клиентского снимка [player owner](../../server/rust/src/gameserver/appserver/player.rs) сначала пишет `i32 max_quest_count`, `i32 count`, затем только **незавершённые** записи, которые удаётся разрешить в текущем каталоге; порядок — по `u16 ID` из `BTreeMap`. Следуют ID, пять `u32` (`old`, type, level, difficulty, track), три NUL-terminated строки (short description, name, description), `u8 display`, `i32 region/x/y/effect`. Завершённые записи при этом продолжают жить в GameSave. Это различие важно: невидимость в клиентском списке не означает отсутствие сохранённой истории. **`VERIFIED` для layout и фильтра, EXE/PDB owner-а `CPlayer::AddQuestDataByteArray_ForClient`;** исходный клиент с этим пакетом сейчас не проверен.

## Запрос, сценарий и межсерверная граница

[`organsysmessage`](../../server/rust/src/gameserver/appserver/message/organsysmessage.rs) принимает клиентские `0x90124..0x90128`. `0x90124` читает два `i32` и отправляет World `0x60130` с добавленным player ID. `0x90125/26` передают исходный payload в `0x60131/32`, дописывая player ID. У `0x90127` (завершить) и `0x90128` (отказаться) читается `u16 quest_id`; Game проверяет, что у локального игрока состояние **именно `0`**, выбирает соответственно `complete_script` или `abandon_script` из каталога и ставит его в очередь player-script. Только выполняемый сценарий затем может менять состояние и выдавать награду. Это отделяет доверенное состояние Game от клиентского желания завершить задание. **`PARTIAL`, EXE/PDB:** owner фиксирует коды и маршруты, но все исходы сценариев и их DB-side effects не доказаны.

Есть ещё ответ аукционного задания: [обработчик аукциона](../../server/rust/src/gameserver/appserver/message/onmsg_c2s_auction.rs) запрашивает тот же complete-script и, если он поставлен в очередь, публикует продолжение сценария `0x8FB02` с ответом. Граница `quest ↔ auction` поэтому не сводится к обычному `0x90127`.

Таймер задания принадлежит базовым свойствам игрока: `begin` сохраняет `now_seconds` и `time_limit`, `clear` обнуляет оба, остаток вычисляется в `i32` как `max(0, begin.wrapping_add(limit).wrapping_sub(now))`, но при нулевом begin или limit сразу возвращается `0`. Game отправляет `0xBF729` с лимитом и `0xBF72A` при очистке. Признак доступности заданий меняется отдельно через `0xBF728`. **`PARTIAL`, EXE/PDB:** арифметика и отправки видны в [player](../../server/rust/src/gameserver/appserver/player.rs) и [game](../../server/rust/src/gameserver/gameserver/game.rs); точный scheduler, который решает о просрочке, здесь не установлен.

## Передача каталога и технические замены

World→Game wire: `i32 max_count`, `u32 level_difference`, три C-строки сценариев, `i32 count`, далее упорядоченные записи. В каждой записи координаты `region/x/y` расположены **перед** `effect`, независимо от внутреннего C++ layout; map-key отдельно не сериализуется, он берётся из `u16 id`. Decoder сначала присваивает scalars и строки, затем очищает map и публикует только полностью прочитанные records; при дубликате побеждает последняя запись. Поэтому ошибка посередине потока может оставить частичный каталог — не следует молча превращать протокол в атомарную замену. **`VERIFIED`, EXE/PDB Game decoder RVA `0x000627A0`:** [codec](../../server/rust/src/setup/questsystem.rs). `BTreeMap` заменяет legacy map, а process singleton живёт внутри `CGame`; это не меняет lookup и wire, но требует сохранять упорядоченную сериализацию и момент обновления состояния.

`UNKNOWN`: полные правила наград, условий принятия, ветвей всех quest-скриптов, поведение World при relay, таблицы DB/stored procedures именно для заданий и живой клиентский сценарий. Наличие Rust-маршрута и owner-описания не заменяет сборку, запуск и проверку исходным клиентом.
