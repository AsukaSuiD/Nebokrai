# Аукцион и применение платежей

Billing меняет счёт, Game применяет результат к живому игроку, World хранит лоты и выдаёт аукционные возвраты, Misc ведёт активную комнату. Между этими этапами нет общей транзакции: успешное списание, постановка ответа в сеть и получение предмета — разные события. Здесь описана связка подключённого Rust-кода; правила местной [торговли](trade.md), [сеансов и контейнеров](items.md) остаются на своих страницах.

## Общий путь Billing

Game формирует запрос и передаёт его `CMessage::send_to_bs`; обычный `send` выбирает World, независимо от opcode. Billing разбирает запрос в `TagAccInfo` или `TagTradeNode` и добавляет его в FIFO менеджера. `push_trade_request` не проверяет дубликаты. DB-работник снимает сначала балансы, затем сделки; общего порядка этих двух очередей нет. Ответ сразу ставится в сетевую очередь через `ServerCommandHandle` на socket принятого Game-соединения, сохранённый в `game_server_id`. Это адрес доставки, не номер игрового сервера из payload. Источники — [CMessage](../../server/rust/src/nets/netserver/message.rs), [BillingMessageHandler](../../server/rust/realm/src/billing/billingmessage.rs) и [CBillingPlayerManager::run](../../server/rust/realm/src/billing/billingplayermanager.rs).

Выбор DB-операции в работнике зависит от пустоты `seller_identity`: пустое значение вызывает `buy_item_code`, непустое — `buy_player_item`. Поэтому `trade_type` сам по себе не определяет путь покупки. Для Increment Shop поле `session_id` переносит ID скидочного товара; в обмене игроков session/plug адресуют продолжение, а аукцион посылает в них нули и хранит ожидающий узел у покупателя. Увеличивающийся ID общего сеанса не заменяет идентификатор платежа. Источники — [менеджер Billing](../../server/rust/realm/src/billing/billingplayermanager.rs), [Increment Shop](../../server/rust/src/gameserver/appserver/message/incrementshopmessage.rs), [обмен](../../server/rust/src/gameserver/gameserver/game.rs) и [аукционный запрос](../../server/rust/src/gameserver/appserver/message/onmsg_w2s_auction.rs).

У Increment-покупки ограничение `goods_number > 1000` проверяется после DB-вызова и постановки increment-log. Нарушение прекращает проход без ответа этой покупки и уничтожает хвост уже снятого списка сделок. Это конкретный порядок с возможными частичными эффектами, не образец предварительной валидации. Устройство DB-вызовов описано в [БД](../architecture/database.md); граница очереди видна в [CBillingPlayerManager::run](../../server/rust/realm/src/billing/billingplayermanager.rs).

На стороне Game успешный ответ поступает в `dispatch_increment_shop_billing_message` из обычного диспетчера. Increment-покупка получает новую партию вещей; ответ сделки выбирает продолжение по `trade_type`: личная лавка, обмен или аукцион. В первых двух случаях баланс устанавливается **до** проверки пригодности сеанса; в аукционе сначала расходуется ожидающий узел и отправляется подтверждение World, затем устанавливаются балансы. Отсутствие сеанса не отменяет уже применённый баланс, а отсутствие ожидающего аукционного узла не мешает повторно установить баланс. Источники — [диспетчер CGame](../../server/rust/src/gameserver/gameserver/game.rs) и [unibillmessage](../../server/rust/src/gameserver/appserver/message/unibillmessage.rs).

Billing при ошибке сделки формирует `0xFF003` из трёх `i32`: buyer, seller, result. Game сначала читает этот общий 12-байтовый префикс. При ненулевом result он журналирует отказ и завершает обработку без изменения кошельков, сеансов или ожидающего аукционного узла; тип сделки в таком ответе отсутствует. Только успех требует ещё двух балансов и `trade_type`, то есть 24 байта перед выбором продолжения. Оборванный префикс возвращает `MissingField`, а дальнейший успешный хвост разбирается прежним обработчиком с его порядком эффектов. Источники — [построение ответа](../../server/rust/realm/src/billing/billingplayermanager.rs) и [read_billing_trade_response_prefix / диспетчер Game](../../server/rust/src/gameserver/appserver/message/unibillmessage.rs).

Текущие очереди и обработчики не используют transaction code как ключ дедупликации. После обрыва соединения нет общего журнала доставки в новый socket. Нельзя обещать ни повтор платежа, ни его компенсацию на основании сохранённого plug; особенности повторного применения каждой покупки разобраны в [торговле](trade.md) и ниже для аукциона.

## От лота к решению о покупке

У Game два разных аукционных состояния: реальные контейнеры предметов игрока и `CGameAuctionRoom`, в котором хранится проекция активных GUID/владельцев. Полные активные узлы принадлежат `CAuctionRoom` в Misc. Комната Game помогает отфильтровать запрос, но окончательное решение о живом лоте проходит через Misc. Оба типа подключены из [public/auctionroom/aucitionroom.rs](../../server/rust/src/public/auctionroom/aucitionroom.rs); это не два имени одного общего экземпляра.

При выставлении Game изымает предмет из ячейки и сохраняет сериализованный товар в `CGoodsNode`. При нулевом `auction_yuan_fee_minimum` узел передаётся World; Game очищает pending и отвечает клиенту, не ожидая результата DB-вставки. При ненулевом значении код рассчитывает комиссию и оставляет pending: отправка старого заказа `0xA1` через `g_BillMap` и его подтверждение в этот путь не подключены. Ожидание комиссии за выставление нельзя считать работающей покупкой через описанный выше Billing. Источник — [finish_current_auction_listing](../../server/rust/src/gameserver/appserver/message/onmsg_c2s_auction.rs).

Для полученного нового DB-лота World ставит `OT_IN_INSERT_NEW_ITEM` в `CDbMisc`; успешный выход этой очереди отправляет узел в Misc. Возврат уже существующего узла с `is_db == false` минует вставку и передаётся комнате после сброса buyer. World маршрутизирует Misc через запись сервера `5`, поэтому название `game_server` в этом участке не означает отдельный региональный Game. Источники — [обработчик World](../../server/rust/realm/src/app/auction.rs) и [CDbMisc::done_out_list](../../server/rust/realm/src/persistence/dbmisc.rs).

Покупка проходит следующий маршрут:

1. Game проверяет заявленный YuanBao, ограничение частоты и наличие GUID в своей проекции, затем посылает World пару player/GUID (`0x60805`). World передаёт её Misc (`0x14ED04`). Это ещё не резервирование платежа. Источники — [клиентский вход Game](../../server/rust/src/gameserver/appserver/message/onmsg_c2s_auction.rs) и [переадресация World](../../server/rust/realm/src/app/auction.rs).
2. Misc проверяет очередь по GUID, наличие активного узла и нулевого buyer. Принятая операция записывает покупателя и ставит GUID в `opt_list`; повтор до обработки не заменяет его. При этом `push_item_to_opt_list` **возвращает `false` и после успешной записи**. Обработчик поэтому отправляет отрицательный `0x15EB06`, который World рассылает как `0x80406(result=0, player)`; Game лишь фиксирует отказ в диагностике. **`VERIFIED` для этого необычного return:** Misc EXE/PDB, `CAuctionRoom::PushItemToOptList`, комментарий и перенос тела в [реализации комнаты](../../server/rust/src/public/auctionroom/aucitionroom.rs); вызов находится в [miscservermessage](../../server/rust/realm/src/app/miscservermessage.rs).
3. На следующем AI-проходе принятая операция переводит узел в `PRE_BUY`, убирает его из активных индексов и переносит в очередь `back`. За проход отправляется один минимальный GUID из этой очереди (`0x15EB02`); успех отправки не является условием удаления узла. World для `PRE_BUY` не пишет конечное состояние в БД: он ищет текущий Game покупателя и адресно посылает `0x80406(result=1, node)`. Если маршрута нет, продолжение не отправляется. Источники — [CAuctionRoom::ai/done_back_list](../../server/rust/src/public/auctionroom/aucitionroom.rs) и [on_msg_m2w_auction](../../server/rust/realm/src/app/onmsg_m2w_auction.rs).

Таким образом, немедленный `result=0` не доказывает, что лот остался свободным: тот же запрос уже мог поставить отложенное продолжение. По [ADR-0002](../decisions/0002-semantic-boundary.md) этот подтверждённый порядок сохраняется; превращать return в привычное «успешно поставлено» без согласованного изменения контракта нельзя.

## Применение в Game и возврат из World

Получив узел `PRE_BUY`, Game возвращает его на аукцион, если покупателя уже нет. Если у покупателя занят `current_auction_buy_node`, входящий узел тоже возвращается, **но затем обработка продолжается со старым ожидающим узлом**. Для оплаты YuanBao это может повторно отправить его запрос Billing. Один pending-слот поэтому ограничивает число хранимых узлов, но не обеспечивает однократную отправку. Источник — [ветвь WORLD_AUCTION_BUY_RESULT_MESSAGE](../../server/rust/src/gameserver/appserver/message/onmsg_w2s_auction.rs).

При Gold Game проверяет деньги, формирует журналы, списывает цену и отправляет подтверждение World. При YuanBao он посылает Billing сделку типа `3` и сохраняет узел до ответа. Успешный Billing-ответ расходует pending через `take_current_auction_buy_node`, формирует журналы и подтверждение World; затем обновляет баланс покупателя и местного продавца либо посылает World сообщение для продавца на другом Game. Повтор этого ответа уже не найдёт расходованный узел, но повторно применит балансы. При исчезнувшем покупателе обработчик выходит; автоматической компенсации он не создаёт. Источники — [ответ World](../../server/rust/src/gameserver/appserver/message/onmsg_w2s_auction.rs) и [dispatch_auction_billing_trade](../../server/rust/src/gameserver/appserver/message/unibillmessage.rs).

Подтверждение Game (`0x60806`) не кладёт предмет сразу в пакет покупателя. World ставит `OT_IN_MODIFY_STATE_A2S`; `CDbMisc::done_list_in` вызывает изменение состояния, затем `transfer_money`, и только при успехе обоих публикует выходной результат. Выход сообщает владельцу об изменении; Game запрашивает доступные возвраты с ограничениями по месту и деньгам. World загружает состояния BACK/UNDO/SUCESSED и деньги; очередной `done_out_list` посылает `0x80404` с товаром и ставит удаление DB-записи либо уменьшение возвращаемой суммы. Здесь удаление ставится **после команды отправки**, без подтверждения успешного размещения клиентским Game. Источники — [auction.rs](../../server/rust/realm/src/app/auction.rs), [CDbMisc](../../server/rust/realm/src/persistence/dbmisc.rs) и [обработка обновления Game](../../server/rust/src/gameserver/appserver/message/onmsg_w2s_auction.rs).

Game декодирует возврат: деньги применяет к аукционному кошельку, вещь — к `auction_goods` с extend `14`, после чего публикует контейнерные изменения и обновляет снимок. Получение в аукционный контейнер и последующий перенос в пакет — отдельные действия. В очереди World стадии идут в порядке выход → вход → загрузка: новый DB-результат не попадает задним числом в уже снятый выходной список. Источники — [возврат Game](../../server/rust/src/gameserver/appserver/message/onmsg_w2s_auction.rs), [CPlayer::return_auction_goods](../../server/rust/src/gameserver/appserver/player.rs) и [CGame::run_main_loop_db_misc_stage](../../server/rust/realm/src/app/world_game.rs).

## Как расширять этот путь

Для изменения выдачи проследите сериализованный `CGoodsNode` → очередь `CDbMisc` → сообщение возврата → `CPlayer` и снимок World. Для изменения оплаты сравните запрос Billing, успешный и отказной ответы, поиск продолжения и уже совершённые эффекты. Повторно используйте codec узла, рабочую очередь, контейнерные отчёты и `set_player_yuan_bao`; новый pending-словарь в каждом handler сам по себе не решит восстановление после потери ответа. Такое сопоставление принято в [ADR-0007](../decisions/0007-reuse-existing-mechanisms.md), граница живого состояния и сохранения — в [ADR-0005](../decisions/0005-world-game-boundary.md).

Статически установлены конкретные правила повторов, удаления из очередей и отсутствия автоматической компенсации в описанных обработчиках. `UNKNOWN`: восстановление всей сделки после разрыва Game/Billing/World и совпадение этих сценариев с оригинальным клиентом. Эта страница не является аудитом всех финансовых SQL-операций; подключение и reconnect служб описаны в [серверной странице](../server/auth-login-and-services.md), результаты запусков — в [состоянии проекта](../status/audit.md).
