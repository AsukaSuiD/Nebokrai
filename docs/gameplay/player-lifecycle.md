# Персонаж в WorldServer: загрузка, присутствие и сохранение

World ведёт долговременную проекцию персонажа и его маршрут между Login, Game и БД. Game владеет живой региональной симуляцией. Поэтому наличие `CPlayer` в World ещё не означает, что игрок вошёл в игру, а обновление мирового объекта ещё не означает запись на диск.

## Что означает присутствие игрока

World `CGame` хранит карту `players` по ID и отдельные списки `login`, `online`, `offline`. Карта отвечает на вопрос «какой объект известен World», списки — «на какой стадии находится присутствие». Это не одно поле enum: переход должен обслужить нужные списки и связанные callbacks.

`online_player_by_id` сначала проверяет online-список, затем карту. `append_map_player` сам по себе не делает игрока online; при повторном ID сохраняет прежний объект. В то же время путь публикации загруженного игрока явно удаляет прежнюю запись перед вставкой. Следовательно, правило замены зависит от операции, а не только от структуры карты. Опора для этих правил — [CGame](../../server/rust/src/worldserver/worldserver/game.rs), `append_map_player`, `publish_loaded_player`, `online_player_by_id`.

При добавлении ID в online сначала меняется список, затем вызывается `COrganizingCtrl::on_player_enter_game`. Это обновляет присутствие члена фракции. `remove_online_player` удаляет все вхождения ID и вызывает организационный exit-callback, даже если удалённых вхождений не было. Изменять только контейнер IDs недостаточно: сведения организации останутся несогласованными.

## Загрузка — работа двух очередей

Для новой операции загрузки с теми же требованиями используется существующая пара запрос/результат и `route_loaded_player`: они уже отделяют DB I/O от публикации в основном цикле. Это применение [ADR-0007](../decisions/0007-reuse-existing-mechanisms.md). Отмена выполняющегося запроса или объединение нескольких одновременных загрузок требуют дополнительных гарантий; приведённая ниже FIFO их не предоставляет.

Загрузка отделена от основного цикла, чтобы ожидание БД не удерживало владельца мира. Но worker не назначает маршрут и не публикует персонажа online.

1. `push_player_load_request` берёт account до NUL и требует длину меньше 20 байт: последний байт фиксированной записи остаётся терминатором. Запрос также содержит ID и IP клиента.
2. [CPlayerLoadQueue](../../server/rust/src/dbaccess/worlddb/playerloadqueue.rs) отсеивает повторный ID только среди ещё ожидающих записей. Worker атомарно забирает **всю** очередь через `pop_player_load_data_to_list`, затем обрабатывает свой пакет последовательно. После такого снятия проверка очереди уже не видит выполняющийся запрос; это не глобальная защита от двух одновременных загрузок одного ID. Отмена через `remove_player_load_data` тоже удаляет лишь ожидающую запись.
3. `WorldPlayerLoadWorkerSpec::process_batch` пропускает ID 0, создаёт отдельный `CPlayer`, назначает ID/account и вызывает загрузчик. При успехе применяет Largess. Результат, включая неуспешный с `player = None`, попадает в [CPlayerDataQueue](../../server/rust/src/dbaccess/worlddb/playerdataqueue.rs).
4. Основной цикл вызывает `process_player_data_queue`: один вызов обслуживает не более одной фактически извлечённой записи. Он передаёт результат в `route_loaded_player`, где уже принимается решение о Login/Game и публикации объекта.

В [playerloadworker.rs](../../server/rust/src/worldserver/worldserver/playerloadworker.rs) работники реализованы через `std::thread`, а асинхронная DB-работа исполняется через Tokio. Флаги выхода игрового потока и загрузчиков имеют отдельные роли; остановка и присоединение работников не заменяют обработку готовых записей.

## Из чего восстанавливается персонаж

`TiberiusRsPlayer::load_player` в [rsplayer.rs](../../server/rust/src/dbaccess/worlddb/rsplayer.rs) выполняет загрузку ability → заданий → предметов → JJC. Загрузчики применяют поля последовательно. Поздний отказ не откатывает уже заполненный объект, но worker не публикует его как успешного игрока.

После DB-загрузки [CPlayer::load_data](../../server/rust/src/worldserver/appworld/player.rs) достраивает производные характеристики: максимум RP из общих настроек, скорости восстановления по полу/профессии, базовые HP/MP и характеристики по профессии/уровню, затем `update_property`. Текущий RP ограничивается вычисленным максимумом. Graphics ID рассчитывается как `sex + 1 + occupation * 2`, скорость берётся из `GlobeSetupSnapshot`.

Сохраняемое исходное значение и вычисляемое свойство нельзя подменять друг другом. Если новое поле влияет на характеристики, следует решить, где оно хранится и на какой стадии участвует в пересчёте; запись только в вычисленный блок может исчезнуть при следующем `update_property`. Полная модель коэффициентов остаётся отдельной задачей: эта последовательность не устанавливает все игровые формулы.

## Как загруженный объект получает маршрут

`route_loaded_player` сначала обновляет организационную принадлежность, находит назначение региона, сбрасывает shape-state в 0 и проверяет подключённый GameServer и его порт. Отсутствие игрока, региона или доступного Game приводит к отказу Login. При пригодном маршруте World отправляет Login `0x1FF01` с subtype `0x1D`, адресом Game и краткими данными персонажа.

В обычном пути готовой очереди затем обновляются сведения друзей, игрок удаляется из online/offline, добавляется в login со временем входа и публикуется в карте. В прямом пути `WorldLoadedPlayerRouteOrder::Direct` публикация предшествует обновлению друзей; после него сбрасываются выбранные login-флаги. Результат отправки Login сохраняется в отчёте, но сам по себе не откатывает последующую публикацию. Порядок находится в `route_loaded_player` и `publish_loaded_player` в [game.rs](../../server/rust/src/worldserver/worldserver/game.rs).

Таким образом, успех загрузки БД означает только готовность объекта. Маршрут может быть отклонён позже, а стадия login ещё отличается от online. При разборе «персонаж загрузился, но не вошёл» нужно проверять эти границы последовательно.

## Возврат из Game и потеря сервера

Возврат персонажа и периодический сбор данных — разные обработчики. `decord_returned_player` обновляет существующего владельца либо создаёт нового, очищает transient pets и флаг получения данных фракции. В ветви нового владельца он дополнительно удаляет login/online и добавляет offline. Периодический `0x5FA03` использует `decord_server_snapshot_player`; его завершения запускают [сбор пакета сохранения](../architecture/persistence.md#когда-данные-передаются-worker-у). Нельзя переносить переходы присутствия из одного декодера в другой только из-за похожего payload.

При потере Game `on_game_server_lost` находит назначенные этому серверу регионы и выбирает уникальные ID сначала из online, затем из login. Для каждого обновляет online с callback-ом организации, список имён, первое login-вхождение и offline. Только после обработки всех игроков Login получает `0x1FE03` с signed count и именами в том же порядке. Ошибка отправки не отменяет уже выполненные переходы. Это перевод известных World объектов в offline; из него нельзя вывести получение последнего неотправленного состояния погибшего Game.

## Какие данные уходят в сохранение

World сначала создаёт отдельный `CPlayer` через encode/decode, а save-поток строит из него `PlayerDbProjection::save_snapshot`. Это view с четырьмя частями: base, abilities, quest и goods. `CPlayer::save_data` лишь делегирует вызов `RsPlayerOwner::save_player`; он не выбирает персонажа для очереди и не устанавливает универсальный dirty-флаг.

Сохраняются также составные данные: горячие клавиши, навыки, script flags, дополнительные состояния, друзья, ежедневные задания и показатели JJC. Для каждого состава используется своё преобразование, а не дамп памяти `CPlayer`. Перед изменением поля проследите оба кодека World/Game, клонирование World, DB-проекцию, создание строки, обновление и загрузку. Полный маршрут изменения и судьба неуспешных копий описаны в [сохранении](../architecture/persistence.md#повторное-использование-и-добавление-поля).

Не установлена исчерпывающая таблица переходов login/online/offline для всех opcode, в том числе сочетания повторного входа, разрыва Game и незавершённого сохранения. Указанные выше ограничения очереди и счётчика ответов известны из текущих ветвей; они не дают оснований объявлять все конкурентные сценарии проверенными.
