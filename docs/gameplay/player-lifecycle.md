# Персонаж в WorldServer: загрузка, присутствие и сохранение

**Область:** мировой `CPlayer` и его маршруты между Login, World, Game и БД. **Статус знания:** `PARTIAL`: порядок ниже установлен статически по реконструированным owner-файлам, чьи заголовки указывают `worldserver.exe`/`worldserver.pdb`; полного runtime-сценария с исходным клиентом и независимой сверки каждой ветви с EXE здесь нет. Сам факт существования метода в Rust не означает, что до него доходит каждый запрос.

## Владение и граница

World хранит `CPlayer` по ID и отдельно классифицирует присутствие игрока в списках ожидающих входа, online и offline. Игровой регион, клиентское соединение и активную симуляцию ведёт Game; World выбирает маршрут по назначенному региону, хранит мировую проекцию персонажа и владеет DB-переходами. Поэтому «игрок есть в карте World» и «игрок online» не одно и то же: `online_player_by_id` сначала проверяет online-список и лишь затем берёт owner из карты. Добавление в карту не заменяет переход в online-список; повторный ID сохраняет прежнего владельца. Источник: [`World CGame`](../../server/rust/src/worldserver/worldserver/game.rs), методы `append_map_player`, `online_player_by_id`, `append_online_player_id`. Статус этих правил в текущем коде `VERIFIED (reconstructed source)`; исходная семантика указана owner-комментариями как EXE/PDB, отдельно `PARTIAL`.

## Загрузка из БД

1. Запрос содержит account/CD-key, ID персонажа и IP клиента. World отбрасывает слишком длинный account для фиксированной записи очереди и не ставит второй запрос на тот же ID (`Duplicate`); нулевой ID worker пропускает. См. [`push_player_load_request`](../../server/rust/src/worldserver/worldserver/game.rs) и [очередь загрузки](../../server/rust/src/worldserver/worldserver/playerloadworker.rs).
2. Несколько работников конкурируют только за **атомарное снятие всего FIFO-пакета**. Получивший пакет работник обрабатывает записи последовательно: создаёт `CPlayer`, назначает ID/account, вызывает DB loader, затем при успехе применяет Largess и публикует результат в очередь готовых игроков. Неуспешная загрузка тоже публикует запись с отсутствующим player-owner-ом; она не превращается в пустого успешного персонажа. Источник: `WorldPlayerLoadWorkerSpec::process_batch` в [`game.rs`](../../server/rust/src/worldserver/worldserver/game.rs). Статус порядка `PARTIAL (EXE/PDB owner note + reconstructed source)`.
3. У `CPlayer::load_data` DB-загрузка предшествует производным характеристикам. Затем устанавливаются максимум RP, скорости восстановления, базовые характеристики по профессии/уровню, вычисляются свойства, текущий RP ограничивается максимумом, выбираются graphics ID и скорость из общих настроек. Поздний отказ не откатывает уже применённые поля. Источник: [`CPlayer::load_data`](../../server/rust/src/worldserver/appworld/player.rs). Конкретные коэффициенты и арифметика характеристик здесь **не обобщаются**; их следует документировать отдельно по каждой подтверждённой формуле (`UNKNOWN` для полной модели).

Worker-ы на остановке сначала видят флаг завершения игрового потока, затем отдельный флаг завершения загрузки. Текущий Rust запускает `std::thread` и использует Tokio только на Tiberius-границе; при закрытии ставит флаг и присоединяет slots в исходном порядке. Это техническая замена Win32 thread handle, а не изменение последовательности DB-действий. Источник: [`playerloadworker.rs`](../../server/rust/src/worldserver/worldserver/playerloadworker.rs). Проверка остановки под нагрузкой `UNKNOWN`.

## Переход World ↔ Game и потеря GameServer

Когда World помечает игрока online, он добавляет ID только один раз и **после этого** вызывает `COrganizingCtrl::on_player_enter_game`: членство в организации получает отдельный lifecycle callback. При удалении из online он удаляет все вхождения ID и вызывает `on_player_exit_game`. Декодирование вернувшегося от Game персонажа сохраняет различие существующего и вновь созданного owner-а: очищает transient pets и флаг полученных данных фракции, а ранний переход в offline с удалением из login/online выполняет только новая ветвь. Источник: [`game.rs`](../../server/rust/src/worldserver/worldserver/game.rs), `append_online_player_id`, `remove_online_player`, `decord_returned_player`; [`CPlayer`](../../server/rust/src/worldserver/appworld/player.rs). **Статус:** `PARTIAL`; порядок установлен по коду, но полный парный Game-path надо сверять отдельно.

При потере GameServer World сначала находит реально назначенные ему регионы, затем просматривает online-список и login-список в этом порядке, выбирая уникальные ID. Для каждого игрока он удаляет online-вхождения с callback-ом организации, обновляет список имён, снимает первое login-вхождение и однократно добавляет offline. После обработки всех игроков Login получает `0x1FE03` с signed count и C-строками имён в том же порядке. Эта последовательность важна: уведомление Login не должно опережать мировое изменение статуса, а дубликаты не должны давать двойное уведомление. Источник: [`CGame::on_game_server_lost`](../../server/rust/src/worldserver/worldserver/game.rs); в owner-комментарии указана исходная последовательность. Ошибка отправки уже выполненные изменения не откатывает. **Статус:** `PARTIAL`; испытание разрыва живого соединения `UNKNOWN`.

## Снимок и сохранение

World создаёт сохраняемый снимок **до** передачи DB-worker-у. `CPlayer::save_data` делегирует сохранение этого снимка `RsPlayerOwner`, вместе с JJC и goods DB owners; `CPlayer` не передаётся worker-у как живой изменяемый объект. По этой причине изменение игрока после снятия snapshot относится к следующему сохранению. Детальные фазы общего `DoSaveData`, включая сохранение регионов, стран и персонажей, перечислены в [контракте БД](../architecture/database.md). Источник: [`CPlayer::save_snapshot` и `save_data`](../../server/rust/src/worldserver/appworld/player.rs), [`savedb.rs`](../../server/rust/src/worldserver/worldserver/savedb.rs). **Статус:** `PARTIAL` для исходной семантики; нет проверки, что все живые изменения обязательно попадают в следующий цикл.

**Открытые вопросы:** исчерпывающая таблица состояний `login/online/offline` для всех opcode; гарантии при одновременном разрыве Game, повторном входе и save; соответствие каждого SQL-поля player snapshot конкретному полю клиентского wire; возможные потери обновлений при нескольких worker-ах. Ни один из этих пунктов нельзя выводить из одного успешного статического маршрута.
