# Архитектурные решения

Здесь записано, почему система устроена именно так. ADR нужен для существенного выбора: проблема → решение → причина → последствия. Подробные форматы и алгоритмы остаются на страницах подсистем.

| Решение | Основная причина |
| --- | --- |
| [0001. Документация для разработчика](0001-system-specification.md) | Устройство системы и причины решений должны быть понятны без повторного чтения всего кода и материалов анализа. |
| [0002. Современная инфраструктура](0002-semantic-boundary.md) | Tokio и библиотеки берут на себя общие механизмы, а проект сохраняет значимые игровые правила. |
| [0003. MSSQL и Tiberius](0003-database-contract.md) | Схема и процедуры уже участвуют в поведении игры; замена драйвера не требует одновременной миграции данных. |
| [0004. Оригинальные материалы отдельно от кода](0004-local-evidence.md) | Бинарники и ресурсы нужны для исследования конкретных вопросов и не входят в поставляемый код. |
| [0005. Разделение World и Game](0005-world-game-boundary.md) | Региональная симуляция и мировое сохранение имеют разных владельцев и жизненный цикл. |
| [0006. Гибридный локальный стенд](0006-hybrid-runtime.md) | Оригинальный GameServer позволяет работать над взаимодействием соседних служб. |
| [0007. Повторное использование общих механизмов](0007-reuse-existing-mechanisms.md) | Одинаковые требования должны опираться на одно подходящее решение; особенности текущего кода не назначают архитектуру автоматически. |
| [0008. Startup-регионы без war-tail](0008-region-startup-war-tail.md) | Оригинальные World и Game расходятся для типов 4/5; Rust сохраняет доказанный wire и не воспроизводит чтение неинициализированной capacity. |

| [0009. Граница распространяемого кода](0009-public-source-boundary.md) | Полный декомпилят и локальные параметры доступа отделены от реализации и спецификаций. |

Рутинное исправление не требует нового ADR. Если меняется выбранный подход, обновите решение и связанные страницы; историю прежних вариантов хранит Git.
