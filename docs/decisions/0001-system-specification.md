# ADR-0001: системная спецификация в docs

Статус решения: принято. Область: вся реконструкция.

## Контекст

Сведения о wire-полях, владельцах состояния и ошибочных ветвях накоплены в owner-комментариях, коде и первичных материалах. Одного локального комментария недостаточно, чтобы понять сквозной контракт между процессами; повторный вывод из большого дерева и EXE/PDB дорог и может создать противоречащие трактовки. Git хранит историю изменений, но не текущую модель игры.

## Решение

`docs/` описывает систему по темам: назначение, владелец, состояние и lifecycle, входные и выходные контракты, инварианты, порядок операций, пограничные случаи, замены инфраструктуры и причины их допустимости. Существенный установленный факт переносится сюда с точным свидетельством и статусом знания. Верхний комментарий owner-файла оставляет локальное происхождение, RVA/символ, вариант и особенности реализации; документ ссылается на него, но не заменяет.

Статус доказательства оригинала отделён от состояния Nebokrai: наличие кода, подключение к процессу, сборка и проверка с клиентом записываются отдельно. Неизвестное остаётся `UNKNOWN`, даже если будущая реализация требует решения. Для межкомпонентного поведения изменение кода и соответствующего документа выполняется в одном согласованном шаге.

## Последствия и проверка

Документация становится интерфейсом для нового разработчика и агента: сначала контракт и основания, затем код и точечный EXE/PDB для открытого вопроса. Риск устаревания снижается проверкой docs при изменении поведения, но полностью не исчезает; адреса ссылок, варианты EXE и текущий статус проверки нужно поддерживать. [Аудит](../status/audit.md) остаётся срезом доказанной готовности, а не дневником задач.

Основание решения — требование владельца проекта и существующие разрозненные owner-комментарии в [`server/rust/src`](../../server/rust/src/). Это решение о способе работы Nebokrai; оно не является свидетельством какой-либо игровой формулы.
