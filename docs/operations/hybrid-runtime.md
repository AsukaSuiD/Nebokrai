# Локальный гибридный стенд

Стенд нужен для работы над Rust-службами и их обменом с доступным оригинальным игровым процессом. Auth, Login, Billing, World и Misc запускаются из Rust-образа, Game — из локального Windows `gameserver.exe` через Wine. Этот состав принят в [ADR-0006](../decisions/0006-hybrid-runtime.md) и задан в [Compose](../../deploy/hybrid/compose.yaml). Сборка Rust GameServer описана [отдельно](build.md): в данном стенде он не исполняется.

## Источники данных и требования

Для запуска нужны Docker с Linux-контейнерами и Compose, PowerShell для подготовки данных, доступ к образам и пакетам из [Dockerfile](build.md), а также локальный `runtime/`. Он исключён из Git: обычный клон не содержит конфигов, игровых ресурсов, резервных копий БД и Windows GameServer. Скрипт подготовки не создаёт этот комплект и не копирует его из `original/`. Стенд нельзя воспроизвести только из отслеживаемых файлов. Источники — [prepare-runtime.ps1](../../deploy/hybrid/prepare-runtime.ps1) и [.gitignore](../../.gitignore).

Каждая служба получает свой `runtime/<служба>` как рабочий `/runtime`. Недостаточно положить рядом с EXE один `setup.ini`: подключённые загрузчики используют следующие входные файлы. Таблица не заменяет полный комплект игровых ресурсов.

| Каталог | Что читает процесс |
| --- | --- |
| `AuthServer` | `setup.ini`, список допуска `allowed_ls.ini` и, при включённом фильтре, `client_forbid_ip.ini`. Ошибка настройки может приводить к применению значений по умолчанию и продолжению запуска. [Auth CGame](../../server/rust/src/authserver/src/cgame.rs). |
| `LoginServer` | `setupex.ini` с первой числовой парой `area_id` ещё до создания CGame; затем `setup.ini`, `port.ini`, `WorldInfoSetup.ini`, `aslist.ini`. В `port.ini` сначала идёт клиентский порт, затем порт World. [Login CGame](../../server/rust/src/loginserver/loginserver/game.rs). |
| `BillingServer` | `Setup.ini` и список допуска `GSInfoSetup.ini`. Оба пути перед чтением разрешаются без учёта ASCII-регистра, поэтому нижний регистр, используемый подготовкой, допустим. [Billing CGame](../../server/rust/src/billingserver/billingserver/game.rs). |
| `WorldServer` | `setup.ini`, `serverSetup.ini` с маршрутами Game, языковые таблицы и прочие ресурсы; маршрутный файл также допускает различие ASCII-регистра. [World CGame](../../server/rust/src/worldserver/worldserver/game.rs), [загрузка ресурсов](../architecture/resources-and-configuration.md). |
| `MiscServer` | `setup.ini`; ещё до его чтения процесс создаёт или обнуляет `debug.txt`, поэтому каталог должен быть доступен для записи. [Misc CGame](../../server/rust/src/miscserver/miscserver/game.rs). |
| `GameServer` | `gameserver.exe`, конфигурация и соответствующие ему ресурсы Windows-комплекта. Образ Wine запускает этот файл из `/runtime` под пользователем `nebokrai` с UID 1000; права на смонтированные данные должны позволять ему работу. [Dockerfile.game](../../deploy/hybrid/Dockerfile.game). |

Login и World пробуют `setup.dat` только при ошибке чтения `setup.ini`, а не после неудачного разбора его содержимого. Подготовка стенда при этом требует именно редактируемых INI. Позиционные парсеры могут сохранить часть значений и вернуть отчёт об остановке чтения: открытый файл ещё не означает полную настройку. Подробности форматов и выбора источника — в [конфигурации и ресурсах](../architecture/resources-and-configuration.md).

В `runtime/Database` нужны `Account.bak`, `BillingDB.bak`, `GameDB05.bak`, `LogDB.bak` и `LoginDB.bak`. Файл `GameDB05.bak` восстанавливается в базу **GameDB**. Внутренние логические имена файлов backup тоже должны совпадать с аргументами `WITH MOVE`; переименование произвольного `.bak` в ожидаемое имя недостаточно. Имена и порядок заданы в [database-init.sh](../../deploy/hybrid/database-init.sh).

## Подготовка адресов и запуск

Следующие команды предназначены для отдельно разрешённого запуска. Из PowerShell в корне `C:\Nebokrai`, после получения runtime-комплекта:

```powershell
.\deploy\hybrid\prepare-runtime.ps1 -ClientAddress '<адрес Docker-хоста, доступный клиенту>'
```

Вместо текста в угловых скобках указывается адрес **сервера для клиента**, а не IP компьютера игрока. Он нужен для подключения к Game на `2347`; исходную точку входа клиента в Login на `2346` скрипт не настраивает. Настройки Windows firewall, NAT и маршрутизации он также не меняет. Сам runtime находится относительно каталога скрипта, независимо от текущего каталога PowerShell. Источник — [prepare-runtime.ps1](../../deploy/hybrid/prepare-runtime.ps1).

Подготовка переписывает выбранные адреса БД в `mssql`, межсерверные адреса — в имена `nebokrai_*`, а `LoginServer/aslist.ini` целиком заменяет одной записью Auth на `7100`. В Game она задаёт `BindPortForBS = 1993` и клиентский `LocalIP`. Большинство портов и остальные параметры остаются из полученного комплекта. Редактируемые INI читаются и записываются как Windows-1251. Это адаптация конкретного стенда, а не общий конвертер конфигурации. Источник — [prepare-runtime.ps1](../../deploy/hybrid/prepare-runtime.ps1).

У скрипта есть существенные ограничения, которые нужно учитывать до запуска:

- Отсутствующий ключ в `Update-Value` вызывает ошибку, но предыдущие файлы уже записаны; отката нет.
- Адрес в `WorldServer/serversetup.ini` заменяется только в строке `# 1 <адрес> 2347`, адрес допуска Billing — только в строках с портом `1993`. Отсутствие совпадения не вызывает ошибку. Существующий `BindClient 0` остаётся выключенным: `BindClient 1` добавляется лишь при отсутствии распознанной строки.
- `deploy/hybrid/.env` создаётся только при отсутствии файла. `MSSQL_SA_PASSWORD` генерируется, `NEBOKRAI_DB_PASSWORD` берётся из `DatabasePassword` Auth. Скрипт не согласует пароли в остальных INI и не обновляет существующий `.env`.

Следовательно, финальная строка «Runtime подготовлен» не подтверждает совпадение всех маршрутов, портов и учётных данных. Проверять эти значения следует локально, не публикуя содержимое `.env` и секретных INI. Точная область замен видна в [prepare-runtime.ps1](../../deploy/hybrid/prepare-runtime.ps1).

Все дальнейшие Compose-команды на этой странице и в [диагностике](diagnostics.md) выполняются из `deploy/hybrid`: рядом находятся `compose.yaml` и подготовленный `.env`.

```powershell
Set-Location deploy/hybrid
docker compose up -d --build
```

Команда собирает образы и запускает службы в фоне. Она не проверяет клиентский сценарий; состояние контейнеров и сообщения смотрят отдельно. Подстановка двух паролей передаёт их только MSSQL и `database_init`; Rust-службы продолжают читать учётные данные из собственных файлов. Проект по умолчанию называется `nebokrai-hybrid`, а относительные bind-mount пути ведут из каталога Compose в общий `runtime/`. Источник — [compose.yaml](../../deploy/hybrid/compose.yaml).

## Зависимости и порты

Сначала Compose ждёт SQL healthcheck MSSQL, затем успешное завершение `database_init`. После него допускаются Auth и Billing; Login также ждёт healthcheck Auth, World — Login, Misc — World, Game — World и Billing. Это условия запуска контейнеров, а не подтверждение игровых стадий. Точные ограничения проверок разобраны в [диагностике](diagnostics.md).

| Назначение | Адрес/порт, ожидаемый обвязкой | Публикация на хост |
| --- | --- | --- |
| Клиент → Login | Login на Docker-хосте; внутри сети — `nebokrai_login:2346` | `2346:2346` |
| World → Login | `nebokrai_login:2345` | Нет; именно `2345` используется healthcheck Login |
| Login → Auth | `nebokrai_auth:7100` | Нет |
| Game и Misc → World | `nebokrai_world:1747` | Нет |
| Game → Billing | `nebokrai_billing:8188`; подготовка задаёт `BindPortForBS = 1993` и допуск этого исходного порта в Billing | Нет |
| Клиент → Game | Адрес из `ClientAddress`, порт `2347` | `2347:2347` |

Порты в этой таблице — ожидания Compose и скриптов; фактические порты прослушивания Rust берёт из конфигурации. MSSQL на хост не опубликован. Клиентские публикации не ограничены адресом `127.0.0.1`; доступность с другой машины определяется также Docker-хостом и его сетью. Источники — [Compose](../../deploy/hybrid/compose.yaml), [подготовка](../../deploy/hybrid/prepare-runtime.ps1) и [entrypoint Game](../../deploy/hybrid/game-entrypoint.sh).

Например, перенос клиентского порта Login требует согласовать первую пару `LoginServer/port.ini`, правую сторону публикации контейнерного порта и адрес входа в клиенте. Межсерверный порт Login — вторая пара того же файла; при его изменении затрагиваются настройки World и healthcheck Login. Это два независимых направления. Для Game клиентский адрес нужно согласовать с `LocalIP`, маршрутом World и публикацией Docker; текущая подготовка жёстко ориентирована на `2347` и запись Game с ID 1. Загрузчики — [Login CGame](../../server/rust/src/loginserver/loginserver/game.rs), [World CGame](../../server/rust/src/worldserver/worldserver/game.rs); шаблон замен — [prepare-runtime.ps1](../../deploy/hybrid/prepare-runtime.ps1).

## Базы и постоянные данные

`database_init` — завершающийся процесс, а не постоянно работающая служба. Каждый запуск восстанавливает только отсутствующие базы, затем создаёт `LoginDB.dbo.userinfo`, если такого объекта нет, как представление над `BillingDB.dbo.TBL_Member_Data`. После этого скрипт создаёт **или меняет пароль** SQL login `Miracle`, связывает с ним пользователя в пяти БД и добавляет его в `db_owner`. Права описывают нынешний локальный стенд; они не являются новым общим требованием к развёртыванию. Источник — [database-init.sh](../../deploy/hybrid/database-init.sh).

Пять восстановлений и последующие операции не объединены в транзакцию. При позднем отказе ранние изменения остаются, а следующий запуск пропускает уже существующие базы. Новый `.bak` не обновляет старую БД; существующее представление также не пересоздаётся. Сообщение «пять баз восстановлены» выводится и тогда, когда восстановление было пропущено. Пересоздание контейнера MSSQL или редактирование `.env` не следует считать сбросом состояния или выполненной сменой пароля `sa`: это отдельное изменение существующего SQL Server. Источники — [database-init.sh](../../deploy/hybrid/database-init.sh) и [Compose](../../deploy/hybrid/compose.yaml).

| Место хранения | Что остаётся после пересоздания контейнеров |
| --- | --- |
| Именованный том `mssql-data`, `/var/opt/mssql` | Файлы БД и состояние SQL Server, включая учётные записи. По умолчанию полное имя тома — `nebokrai-hybrid_mssql-data`. |
| Именованный том `wine-prefix`, `/wine` | Настроенный 32-битный Wine prefix; по умолчанию том `nebokrai-hybrid_wine-prefix`. |
| Bind-mount `runtime/<служба>`, `/runtime` | Конфиги, ресурсы и записанные службой файлы. Это рабочие данные, а не только вход для образа. |
| `runtime/Database`, `/backup:ro` | Исходные backup; SQL не записывает туда текущие изменения БД. |

В частности, World пишет состояния городских регионов в `regions/<ID>.rgn` и обновляет `setup/JJcConfig.ini`, а файловые журналы служб попадают обратно в их host-каталоги. Поэтому сохранение одного SQL-тома не охватывает все локальные данные. Права на запись и исходная структура подкаталогов имеют значение. Источники — [Compose](../../deploy/hybrid/compose.yaml), [сохранение региона](../../server/rust/src/worldserver/appworld/region.rs), [World runtime](../../server/rust/src/worldserver/worldserver/runtime.rs).

## Остановка и повторное использование стенда

Из того же каталога `deploy/hybrid`:

```powershell
docker compose stop
```

Команда останавливает контейнеры, сохраняя их и данные. Rust-процессы получают `SIGTERM` и передают запрос в жизненный цикл службы; это запускает её путь завершения, но само по себе не доказывает сохранение всех изменений. В Compose нет собственного `stop_grace_period`; при исчерпании времени остановки процесс может быть завершён принудительно. Итог следует устанавливать по журналу и, для сохраняемых операций, повторной загрузке. Устройство сигнала — [process/mod.rs](../../server/rust/src/process/mod.rs), стадии освобождения — [серверные циклы](../server/runtime-ordering.md).

У Wine другая обвязка: shell запускает `wine` без `exec`, а обработчик `EXIT` убирает только Xvfb; пересылки `SIGTERM` в GameServer и ожидания игрового сохранения скрипт не реализует. Поэтому остановку контейнера Wine нельзя выдавать за подтверждённый штатный выход оригинального GameServer. При повторном запуске `wineboot --init` выполняется лишь при отсутствии `/wine/system.reg`. Источник — [game-entrypoint.sh](../../deploy/hybrid/game-entrypoint.sh).

`docker compose down` дополнительно удаляет контейнеры и сеть, но без удаления томов сохраняет обе именованные области данных и bind-mount каталоги. Удаление томов и восстановление поверх имеющихся данных требуют резервной копии и осознанного решения администратора. Для последующего запуска используется тот же `docker compose up -d --build`; замена файлов на диске не означает автоматического reload уже работающих процессов. Выбор и публикация ресурсов описаны в [конфигурации](../architecture/resources-and-configuration.md), наблюдаемый результат — в [состоянии проекта](../status/audit.md).
