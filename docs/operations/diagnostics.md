# Диагностика сервера

Начинайте с последнего завершённого этапа: создание процесса, конфигурация, соединение, сообщение, игровое действие или сохранение. Так можно найти пропущенный переход, а не принимать доступный порт за готовую игровую службу.

## Состояние гибридного стенда

Для уже разрешённого запуска из `deploy/hybrid`:

```powershell
docker compose ps -a
docker compose logs --tail 200 database_init nebokrai_world nebokrai_game
```

`ps -a` показывает и завершившийся `database_init`: успешный выход для него ожидаем, для долговременной службы — повод разбирать причину. В `logs` можно подставить нужные имена сервисов из Compose; команда показывает stdout/stderr контейнера, а не все файлы внутри `/runtime`. Состав и условия запуска задаёт [compose.yaml](../../deploy/hybrid/compose.yaml).

Проверки состояния слабее, чем утверждалось в прежнем описании:

- MSSQL выполняет `SELECT 1` от `sa`. Это проверка SQL-доступа с этими учётными данными, но не наличия пяти прикладных БД и не работоспособности login `Miracle`.
- Auth, Billing, Login и World выполняют `grep` по шестнадцатеричному порту в `/proc/net/tcp`. Команда не выбирает колонку локального адреса, не проверяет состояние `LISTEN` и не делает пробное подключение. Совпадение может относиться к другому состоянию или удалённому порту. У Login ищется межсерверный `2345`, а клиентский `2346` не проверяется.
- У Misc и Wine Game healthcheck нет. Состояние `running` означает наличие процесса контейнера; Game в этот момент может ещё ждать соседей. [Rust-дополнение](rust-runtime.md) проверяет `LISTEN` Game на 2347, но не вход игрока.

Проверки перечислены в [Compose](../../deploy/hybrid/compose.yaml); ожидаемые порты и их связь с INI — в [описании стенда](hybrid-runtime.md#зависимости-и-порты).

Скрипт запуска Game повторяет TCP-подключение к World на `1747`, затем к Billing на `8188`, пока каждый сосед не станет доступен; предела общего времени ожидания нет. Строка «ожидание …» печатается один раз перед каждым ожиданием. Даже строка «запуск gameserver.exe через Wine» появляется **до** запуска Xvfb и возможного `wineboot`, поэтому сама по себе не доказывает старт EXE. Вывод Xvfb находится в `/tmp/xvfb.log` контейнера; скрипт печатает его в stderr при обнаруженном отказе Xvfb до появления X-сокета. Для Wine образ устанавливает `WINEDEBUG=-all`. Последовательность видна в [game-entrypoint.sh](../../deploy/hybrid/game-entrypoint.sh) и [Dockerfile.game](../../deploy/hybrid/Dockerfile.game).

## Откуда берутся сообщения

Адаптеры `process` выводят в stderr каталог запуска, сетевые/DB-события и итог работы. При этом сообщения о настройке Auth, Billing, Login и Misc из `report_*_result` появляются только **после возврата `game_thread_func`**, вместе с итогом завершения. Их отсутствие у продолжающего работать процесса не доказывает, что Init ещё не начался. Login может завершиться раньше строки «запуск»: предварительное чтение `area_id` происходит до неё, и ошибка попадёт в общий текст «точка запуска не создана». Это следует из тел [process/loginserver.rs](../../server/rust/src/process/loginserver.rs) и соседних [адаптеров](../../server/rust/src/process/).

World дополнительно печатает сообщения загрузки ресурсов, сохранения и фоновых операций непосредственно из runtime. Его метод с именем `put_debug_string` выводит в stderr; искать для такого вызова файл общей одноимённой функции было бы ошибкой. Установленный через `install_crash_reporter` обработчик panic ограничивается строкой в stderr; автоматической записи дампа он не реализует. Источник — [World runtime](../../server/rust/src/worldserver/worldserver/runtime.rs).

Общая функция `run_process` в [process/mod.rs](../../server/rust/src/process/mod.rs) устанавливает один глобальный subscriber перед созданием Tokio runtime для каждого Rust-процесса. Готовый `tracing-subscriber` с возможностями `fmt` и `env-filter` форматирует события `tracing` и разбирает фильтр; отдельного собственного логгера нет. Вывод идёт в stderr без ANSI, поэтому доступен в журнале Docker. Ошибка установки subscriber завершает запуск через обычный результат `run_process`, до создания runtime. `public/logging.rs` по-прежнему содержит RAW-псевдокод и не подключён в `public/mod.rs`.

Фильтр читается из `RUST_LOG` один раз при запуске. Если переменная отсутствует или пуста, действует `warn`: видны `warn` и `error`. Некорректный фильтр, включая значение вне Unicode, целиком заменяется на `warn` с явным предупреждением в stderr; значение переменной и подробности ошибки разбора в сообщение не включаются. Синтаксис задаёт [EnvFilter](https://docs.rs/tracing-subscriber/0.3.23/tracing_subscriber/filter/struct.EnvFilter.html).

Для адресной диагностики передайте переменную в окружение нужного Rust-процесса; в Docker она должна попасть внутрь контейнера. Например:

```text
RUST_LOG=warn,nebokrai_server::gameserver=debug,nebokrai_server::worldserver=debug
RUST_LOG=warn,nebokrai_server::gameserver::gameserver::game=trace
```

Префикс crate в target — `nebokrai_server`, с подчёркиванием. Первая строка включает `debug` для Game и World, вторая — `trace` только для модуля Game `game.rs`. Явное `warn,` сохраняет предупреждения остальных модулей и зависимостей: непустой корректный `RUST_LOG` заменяет фильтр по умолчанию. Фильтр управляет только событиями `tracing`; прямые вызовы `eprintln!` и файловые журналы от него не зависят. Subscriber выводит переданные событием поля, поэтому в диагностические события нельзя добавлять секреты и полные конфиги.

Отдельные игровые пути вызывают файловые функции. Их пути разрешаются от текущего каталога процесса; в Compose это `runtime/<служба>` на хосте.

| Вызов | Где искать результат |
| --- | --- |
| `put_string_to_file(name, ...)` | `log/<name>_YYYY-MM-DD.txt`. |
| `add_game_log_text` / `add_game_error_log_text` | Общий дневной `log/YYYY-MM-DD.txt`. |
| `public::tools::put_debug_string` | `log/debug<год>_<месяц>_<день>[HH_MM_SS].txt`; имя фиксируется первым вызовом в процессе. |

Функции пытаются создать `log`, а ошибки открытия и записи игнорируют. Поэтому отсутствие строки может означать и отсутствие вызова, и отказ файловой системы. Имя и дата используют локальное время процесса; Compose не задаёт часовой пояс, соответствующий Windows-хосту. Отдельный `MiscServer/debug.txt` обнуляется при инициализации: его нужно отличать от этих журналов и учитывать при повторном запуске. Источники — [public/tools.rs](../../server/rust/src/public/tools.rs), [Misc CGame](../../server/rust/src/miscserver/miscserver/game.rs), [Compose](../../deploy/hybrid/compose.yaml).

Для событий `tracing` все Rust-службы используют общий subscriber из `run_process`; существующие прямой и файловый вывод сохраняются. Например, чтобы сделать видимой новую причину отказа Billing, сначала проследите результат обработчика через `BillingRuntimeStep` до `report_billing_step` и используйте этот путь наблюдения. Новый `tracing::warn!` также виден при фильтре по умолчанию, но не заменяет передачу результата операции. Такой поиск готового механизма соответствует [ADR-0007](../decisions/0007-reuse-existing-mechanisms.md); действующий потребитель результата — [process/billingserver.rs](../../server/rust/src/process/billingserver.rs).

## Как выбрать направление поиска

| Симптом | Что проверить | Где продолжить |
| --- | --- | --- |
| Процесс прекращается до основного цикла | Рабочий каталог, обязательные файлы, права и точную фазу из результата запуска. Подготовка runtime не создаёт недостающий комплект. | [Входные данные стенда](hybrid-runtime.md#источники-данных-и-требования), [процессы](../server/process-model.md) |
| Есть сообщение об успешной загрузке, но нет ресурса | Отчёт чтения индекса/пакета и дальнейший parser. `Load package file OK!` в World выводится безусловно. | [Конфигурация и ресурсы](../architecture/resources-and-configuration.md) |
| Порт доступен, но вход не проходит | Клиентскую публикацию Login, стадию Login → Auth/GAS → World и соответствие ответа ожидающему запросу. | [Службы входа](../server/auth-login-and-services.md), [пакеты входа](../protocol/login-auth.md) |
| Персонаж выбран, но Game недоступен | Адрес Game, объявленный World, `LocalIP` Game и публикацию `2347`. Успех подготовки не гарантирует замену маршрутной строки. | [Подготовка адресов](hybrid-runtime.md#подготовка-адресов-и-запуск) |
| Game не допускается Billing | Флаг и записи `GSInfoSetup.ini`, разрешение имени `nebokrai_game` и фактический исходный порт `1993`. Allow-list сравнивает также порт, если он не нулевой. | [AllowedAddress::matches](../../server/rust/src/nets/servers.rs), [Billing init_server](../../server/rust/src/billingserver/billingserver/game.rs) |
| Соединение закрывается после пакета | Направление, внешний префикс, CRC/RLE и затем тип/поля сообщения. | [Протокол](../protocol/README.md) |
| Клиент вошёл, команда не исполняется | Маршрут к игроку, обработчик, очередь AI, допуск и конкретный исполнитель. | [Симуляция](../gameplay/simulation.md) |
| Изменение пропало после повторного входа | Снимок Game/World, очередь сохранения, выполненные SQL-фазы и обратную загрузку. | [БД](../architecture/database.md), [персонаж](../gameplay/player-lifecycle.md) |
| После смены backup осталась прежняя БД или возник отказ DB-login | Состояние SQL-тома и результат `database_init`; пароли в INI и `.env` не синхронизируются автоматически. | [Базы и постоянные данные](hybrid-runtime.md#базы-и-постоянные-данные) |

## Отказ после выбора персонажа

Список персонажей и полная загрузка используют разные DB-проекции. Поэтому успешный вход в список ещё не подтверждает чтение abilities, заданий, предметов и JJC. Порядок и преобразования описаны в [БД](../architecture/database.md).

При выборе World пишет `log/TemptLoadDataLog_YYYY-MM-DD.txt` с ID и началом/концом загрузки. `Read DB End` означает завершение попытки, включая неуспешную. В этом случае `log/debug-DB_YYYY-MM-DD.txt` содержит `Read Player DB Error. (ID:...)`. Подробности теперь также идут в журнал Docker: DB-адаптер указывает этап, при ошибке scalar-поля — имя и категорию (`column-or-type`, `null`, `numeric-range`), при ошибке бинарного поля — его вид и причину разбора. Значения полей и учётные данные не выводятся. Адаптер World отдельно различает отказ БД и ошибку последующего расчёта характеристик. При `debug` для `worldserver::worldserver::game` успешная загрузка отмечается с ID и регионом.

Следующий рубеж — ответ выбора персонажа: отказ `0xAF503 / 0x1C` не содержит назначения Game; успех `0xAF503 / 0x1D` содержит account, текстовый IP, порт `u32 little-endian`, имя и уровень. World формирует его в [route_loaded_player](../../server/rust/src/worldserver/worldserver/game.rs), Login пересылает payload в [on_world_login_result](../../server/rust/src/loginserver/applogin/message/logmessage.rs). Только после успешного ответа проверяйте TCP к Game и его клиентский запрос `0x8F702`. Повторный слишком частый выбор также может получить `0x1C` от очереди Login, поэтому для расследования нужны ID и время конкретной попытки.

Если Game уже принял игрока, а клиент закрылся, текст последнего окна — только симптом. Сопоставьте Windows Application Error/дамп с **фактически отправленным** пакетом: восстановите TCP-поток по sequence number, снимите обрамление и RLE, затем сравнивайте курсор получателя с полями отправителя. Разбор только по Rust-сериализатору подтверждает его собственную последовательность, но может пропустить несовпадение с клиентом. Пример найденной таким способом причины — [сдвиг пакета входа](../status/audit.md#сдвиг-пакета-входа-перед-заданиями).

Перед повтором со стороны игрока проверьте, что захват сохраняет оба направления TCP. В локальном Linux-контейнере сокет `AF_PACKET` с `ETH_P_IP` пропускал исходящие кадры; захват `ETH_P_ALL` с последующим фильтром IPv4/TCP по Game-порту сохранил запросы и ответы. Ограничивайте время и размер записи, сохраняйте pcap вне Git: игровые пакеты могут содержать данные учётной записи. Наличие пустого соединения в pcap не подтверждает наличие ответного игрового payload.

## Завершение и запись результата

Строка «штатно завершён» и нулевой код выхода описывают итог, который проверил конкретный process-адаптер. Это не общий аудит SQL и сохранности файлов: например, ошибки сохранения городского региона World выводятся отдельно, а путь Release может продолжиться. Принудительная остановка контейнера способна оборвать и сам вывод итога; для Wine действуют дополнительные ограничения обвязки. Источники — [process/worldserver.rs](../../server/rust/src/process/worldserver.rs), [WorldProcessReleaseContext](../../server/rust/src/worldserver/worldserver/runtime.rs), [остановка стенда](hybrid-runtime.md#остановка-и-повторное-использование-стенда).

Для воспроизводимого наблюдения достаточно указать commit, службу и состав стенда, версию клиента и комплекта ресурсов, одно действие, последнюю успешную стадию и результат следующей. Для сетевого отказа полезны направление, opcode и причина; для сохраняемой операции — результат повторной загрузки. Учётные данные и содержимое секретных конфигов в отчёт не включаются; перед переносом фрагмента журнала проверяют и его содержимое.

Результат запуска фиксируется в [состоянии проекта](../status/audit.md), установленная причина — на основной странице подсистемы. Статическое чтение так и обозначается; наблюдения Windows GameServer под Wine относятся к нему, а не к Rust GameServer.
