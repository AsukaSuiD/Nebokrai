## Zone quests: прогресс живого игрока 24 сентября 2026

Карта `u16 ID → u8 state` и операции принятия, завершения, удаления и отбора для клиента перенесены из Game `CPlayer` в `Zone/quests/progress.rs`. Экземпляр остаётся вложенным в живого игрока; Game читает и пишет GameSave, связывает прогресс с каталогом и отправляет сообщения. Алгоритмы переходов Rust не менялись. Совпадение Game EXE/PDB подтверждено по SHA-256 и RSDS GUID/age. Инструкции `AddQuestDataByteArray` вместе с целями writer-ов подтверждают упорядоченные пары `u16 + u8` после `i32 count`; вход `AddQuestDataByteArray_ForClient` подтверждает пропуск состояния `1` и ID без записи каталога. Адреса и пределы проверки находятся в [правилах заданий](../gameplay/quests.md#клиентский-список-и-постоянное-сохранение). Исходные ветви принятия, завершения и удаления повторно не сверялись, поэтому полный контракт прогресса остаётся `PARTIAL`.

Linux `cargo check --locked --workspace --lib --bins` через `deploy/check-rust.ps1` прошёл за 36,99 секунды. Сервер и клиент не запускались; GameSave и клиентский список в работающем процессе после переноса не проверены.

## Realm content: загрузка каталога заданий 24 сентября 2026

World теперь хранит `QuestCatalog` из Realm: тот выбирает `Quest.ini`/`QuestEx.ini` и вызывает общий загрузчик Shared при старте и повторной загрузке профиля `QuestData`. World оставляет у себя StringTable, журнал и отправку сериализованного каталога Game. Второй файл теперь открывается только после разбора основного; при отсутствии основного ресурса к нему вообще нет обращения. Это соответствует раннему выходу оригинального `CQuestSystem::Load`. Прежнее безусловное сообщение `Load QuestData...OK!` сохранено, но Rust дополнительно предупреждает о неполной загрузке и сообщает причину/число применённых записей. Основание по совпадающей World EXE/PDB и адресам находится в [каталоге заданий](../gameplay/quests.md#каталог-и-состояние-персонажа).

Локальные `runtime/WorldServer/data/quest.ini` и `questex.ini` существуют; это не доказывает, что запущенный World выбрал их, разобрал полностью и передал рабочий каталог Game. Linux `cargo check --locked --workspace --lib --bins` через `deploy/check-rust.ps1` прошёл за 38,03 секунды. Сервер и клиент не запускались; причина недоступности заданий и навыков в наблюдавшейся сессии остаётся неизвестной.

## Как читать матрицу

- **Исходный факт** — конкретный EXE/PDB, owner или данные, на которые опирается реконструкция. Верхний комментарий указанного файла содержит детали; уровень знания определяется по [правилам свидетельств](../reconstruction/evidence-and-contracts.md).

Затем отправка закрывала сокет: `167293902 + 1054318 > 167772160` байт. `VERIFIED` по диагностике [CServer](../../server/rust/src/nets/servers.rs) и [World](../../server/rust/src/worldserver/worldserver/game.rs). Сетевой worker теперь обслуживает очередь независимо; лимит не увеличен. Общая запись TCP дописывает частичный Linux write, а Game вычитывает несколько готовых шагов за такт. Устройство и причина — [сетевой runtime](../server/network-runtime.md) и [ADR-0002](../decisions/0002-semantic-boundary.md).

`PARTIAL`: запуск выявил незакрытые участки, которые доступный порт не подтверждает:

- Для восьми начальных регионов типов `4/5` найдено исходное расхождение World/Game. `VERIFIED` статически: World создаёт их как обычный `CWorldRegion` и не сериализует три war-counter, а Game создаёт производный `CServerWarRegion` и inherited decoder читает эти 12 байт за logical end `CMessage`. Receive-copy не переносит туда CRC или следующий frame; свободная capacity `std::vector` не является wire-контрактом. Rust startup теперь читает для subtype `4/5` только доказанный `CServerRegion` prefix и не меняет World wire. Решение и адреса — [ADR-0008](../decisions/0008-region-startup-war-tail.md). Повторный совместный запуск после исправления ещё не выполнялся, поэтому runtime-статус остаётся `PARTIAL`.
- Ложные runtime-warning для `0x7F80D` в Game и `0x80403`/`0x7F80D`/`0x7F801` в Misc сняты прямым сопоставлением с оригиналами. `VERIFIED`: jump-table Game `OnServerMessage @ 0x0049D300` направляет `0x7F80C/0x7F80D` в общий no-op return `0x0049EFD0`; Misc `OnOtherMsg @ 0x00403CC0` обрабатывает только `0x7F809/0x7F80B`, а остальные типы безусловно игнорирует. Оригинальный World при этом действительно строит `0x7F80D`: `CGame::SendGlobeVariableToGS @ 0x004017E0` добавляет 16 байт и отправляет пакет. Rust теперь отличает эти исходные no-op от реально неподдержанных ветвей.
- SQL 208 для `AuctionLog`/`Auctionlog` снят как кодовый блокер: поставочный `LogDB.bak` не содержит auction-таблиц, а сохранённый запуск оригинального World показывает ту же ошибку и затем успешный старт listener-а и цикл сохранения. Точный DDL остаётся `UNKNOWN`, поэтому локальный стенд не создаёт фиктивную схему; граница описана в [документации БД](../architecture/database.md#схема-и-локальный-стенд). Обработчик внешних пополнений Billing отключён через `PlayerFillCheckSrvSwitch 0`, поскольку нет `TBL_NeedUpdate`; объяснение — [локальный режим Billing](../operations/rust-runtime.md#внешние-пополнения-billing).
- После загрузки регионов ранняя dev-сборка сообщала задержки порядка 1,4–1,7 секунды при целевом интервале 80 ms. Встроенное временное профилирование локализовало основную стоимость в `CGame::ai`: monster-проход обходил все зарегистрированные фигуры, включая sleeping monsters, а resolver очистки повторно сканировал регион даже без staged cleanup. Сопоставление с `CArea::GetActivedShapes`/`WakeUpMonsters` показало, что sleeping storage в этот AI-проход не входит. После перехода на active/pet/carriage monster storage и условного построения resolver release-профиль дал около 63 AI-вызовов за 5,04 s и `ai_ms` около 4,13–4,18 s, то есть примерно 65–66 ms на AI-вызов. Затем profiler удалён, release пересобран из чистого дерева; свежий Game дошёл до `server_id=1`, `regions=549`, healthcheck `healthy`, а за наблюдаемое steady-state окно warning об отставании цикла более чем на секунду не появился. Это серверная проверка темпа; качество движения клиента на этой сборке ещё не проверено.
- В World раннее steady-state отставание имело отдельную причину: `main_loop_resource_snapshot` трижды за один проход глубоко копировал реестр из 14 630 goods и индекс исходных имён. Временное dev-профилирование давало примерно 35–55 ms на один такой snapshot при целевом шаге World 40 ms. Горячие snapshot-ы переведены на `Arc`, а пути reload/release используют copy-on-write через `Arc::make_mut`, поэтому уже выданная версия остаётся неизменной для её потребителя. После чистой пересборки и перезапуска World 30-секундное steady-state окно прошло без `warning!!! 1 second not call AI()`; это runtime-подтверждение устранения именно наблюдавшегося hot-loop bottleneck, а не общей производительности всех подсистем.
- Natural save-cycle World после этого перезапуска также прошёл штатно: World видел `Connects = 1/1`, отправил `SaveNotify`, получил terminal save-data от `GameServer1`, запустил `SaveThread`, выполнил `Save Region Data` и завершил `Save Data end` / `SaveThread end`. Прежний SQL 8115 (`Arithmetic overflow ... int`) в этом цикле не повторился. Исправление сохраняет legacy DWORD-биты `today_total_tax`/`total_tax` при записи в SQL `int` через `u32 ↔ i32`; контракт описан в [регионах и организациях](../gameplay/regions-and-organizations.md). Этот цикл был без игроков (`player:0`), поэтому он подтверждает региональное сохранение и межсерверный save-handshake, но не полный player persistence/relogin.
- Ранний разрыв World до создания клиентского listener больше не считается доказанным пробелом реконструкции. `VERIFIED` по matching Game EXE/PDB: `CMyNetClient::HandleClose @ 0x0041A590` ставит `0x6F901` в собственную FIFO World-клиента, `CGame::ProcessMessage @ 0x00405830` обрабатывает её и без `s_pNetServer`, а reconnect-worker повторяет попытку каждые 8000 ms. При этом успешный `CGame::ReConnectWorldServer @ 0x0040B7B0` сам без null-check публикует `0x6F902` через `s_pNetServer->field_0xdc`. Следовательно, отдельного исходного pre-listener recovery-пути не найдено; Rust не материализует его догадкой. Наблюдённый в первом неудачном запуске последующий `NotConnected` остаётся фактом того запуска, а не основанием объявлять отсутствующей совместимую механику. Подробности — [жизненный цикл соединений](../protocol/connection-lifecycle.md#исходящие-соединения-между-серверами).

### Сдвиг пакета входа перед заданиями

Локальный клиент `Miracle game.exe`: SHA-256 `5b41ebfcea8c40ab8756e3fb676c8e03ec1f45fba527f33bc163b084cf520971`, размер 2068480 байт, база PE `0x00400000`. Повторный вылет 20 сентября в 23:06:13 местного времени записан Windows как `0xc0000005`, RVA `0x8F742` — тот же цикл чтения дополнительных свойств предмета, что и `0x8F703` в предыдущем дампе.

Захват обоих направлений TCP сохранил отправленный Rust Game пакет `0xBF401` длиной 2392 байта после RLE-декодирования. `VERIFIED` для этой записи: предмет экипировки `1010012` содержит 11 обычных свойств и нулевой счётчик дополнительных; этот участок согласован с клиентским чтением. Первое найденное расхождение перед заданиями — запись `city_war_died_state` четырьмя байтами вместо одного. [Контракт и адреса отправителя/получателя](../protocol/game-login.md#флаги-перед-заданиями) фиксируют исправленную ширину.

При чтении старой записи клиент берёт максимум заданий с offset `0x4E7` вместо `0x4EA` и получает 1677721600 вместо 100. Позднее он читает счётчик боевых фей с `0x4F9` вместо `0x4FC`: **39 вместо 0**. Эти 39 взяты из соседнего `loan_time_limit=10080`, а не из БД предметов. Дамп первого вылета содержит возврат `0x00451AEC`: именно вызов декодирования предмета этого контейнера; далее клиент читает чужие поля как запись предмета и выходит за границы пакета. Сообщение клиента о предметах поэтому не свидетельствует об их нехватке.

Исправлена ширина флага в Rust. Независимая сверка сообщений перед `0xBF401` также выявила неверный opcode результата CiQing, пару `(id, id)` вместо `(type, id)` и три расширенных поля в `0xBF721`; исправленные форматы и свидетельства собраны в [каталоге opcode](../protocol/opcode-catalog.md#уведомления-свойств-игрока). Сборка всех шести бинарников прошла за 59,89 секунды, кэш остался 1204 МиБ при лимите 2048 МиБ. ## Статическая реконструкция движения 21 сентября

`VERIFIED` по matching `gameserver.exe + GameServer.pdb`: `CBaseAI::MoveTo @ 0x004C7FF0` выполняет одноклеточный `Slip` по восьми направлениям `_slip_order` и проверяет весь `s_listMoveCheckCell[figure][direction]`. `CPlayerAI::MoveTo @ 0x00508F10` повторяет этот `Slip` один раз для ходьбы, два для бега и три при `RideState 0x186A4`; каждый повтор получает исходное желаемое направление. У игрока используемый virtual figure возвращает `0`. Rust-путь игрока приведён к тому же общему helper, который теперь разделяется с монстрами. Задержка вычисляется по направлению от исходной до окончательной клетки после обхода и не умножается на число Slip.

`VERIFIED` по машинному коду `CPlayerAI::OnSchedule @ 0x005098D0`: когда новая skill-команда отсутствует, очередь назначения движения проверяется раньше уже сохранённой текущей цели. Front назначения снимается только после возврата `MoveTo`, независимо от его успеха. Rust восстановил этот порядок и больше не удерживает queued movement только из-за прежнего `current_player_skill`.

`VERIFIED` по `CMoveShape::OnMove @ 0x004CD490`: направление меняется до `0xBF605`, пакет рассылается до virtual `SetTileXY`, а результат `SetTileXY` не проверяется; после возврата `CPlayerAI::MoveTo` ставит `ASA_MOVE`. Rust сохраняет этот частичный эффект и при собственной ошибке spatial-мутации после уже начатого `OnMove`. Обе формы `0xBF605` дополнительно сопоставлены с локальным reader `FUN_00546c80` исходного клиента. После изменений `cargo check --locked --lib --bins` через `deploy/check-rust.ps1` завершился успешно. На момент этой статической проверки runtime-вход с движением ещё не выполнялся; последующий клиентский проход описан ниже.

## Runtime-проверка Game AI 21/22 сентября

`PARTIAL`: после описанной выше реконструкции движения владелец исходным клиентом вошёл в игровой мир и смог перемещать персонажа. Первый проход имел заметные остановки: после короткого нормального участка персонаж бежал на месте, затем снова продолжал движение. Это подтвердило сам клиентский путь, но не корректную синхронизацию.

Отдельная серверная диагностика сначала обнаружила сильное отставание общего Game-loop: dev-профиль тратил на `CGame::ai` примерно 1,5–1,6 s за проход. После исправления active monster traversal и отказа от лишнего полного resolver-scan release-профиль держал AI примерно на 65–66 ms при базовом интервале 80 ms; предупреждения об отставании больше секунды в проверенном steady-state окне не возникали.

Повторный клиентский проход на release показал отдельную причину оставшихся остановок. `0x8F903` сначала приходил сериями, а затем примерно раз в три секунды, хотя сервер обрабатывал каждый принятый шаг за десятки миллисекунд: очередь назначения не росла, runtime speed был `2400`, spatial mutation возвращала `Ok`. В `run_player_ai_destination` игрок на время `move_step` извлекался из `CGame::players`, а around-runtime без detached-player snapshot не мог разрешить его как получателя; собственный длинный `0xBF605` тем самым пропускался. После передачи snapshot ID/team/shape через существующую границу `GameServerAroundRuntime::with_player` короткий повторный smoke дал последовательные клиентские шаги примерно каждые 0,4–0,5 s, а владелец подтвердил, что прежние остановки исчезли. Это подтверждает текущий обычный сценарий перемещения в проверенной области, но не длительную игровую сессию, все режимы движения или переходы между регионами.

## Пробелы, влияющие на путь к игре

1. **Сборка, совместный запуск, вход в мир и короткий обычный сценарий движения подтверждены, но полный lifecycle ещё нет.** [Rust-дополнение Compose](../../deploy/hybrid/compose.rust.yaml) запускает все шесть Rust-служб; [Rust Dockerfile](../../deploy/hybrid/Dockerfile.rust) успешно собрал release-бинарники. На текущем Game release клиент вошёл в мир и после исправления self-delivery `0xBF605` непрерывно перемещался в коротком smoke. Ещё не подтверждены длительная сессия, logout/save/relogin, региональный переход и устойчивость остальных gameplay-подсистем.
2. **Знание протокола не равно устойчивой работе с клиентом.** В отслеживаемом дереве нет проекта клиента или автоматического сквозного испытания. Наличие EXE/PDB, статических контрактов и даже одного достигнутого движения не подтверждает длительную игровую сессию, корректность всех вариантов движения или синхронизацию остальных подсистем.
3. **Модель БД зависит от локальных материалов.** `runtime/` целиком исключён из Git. [Локальный скрипт БД](../../deploy/hybrid/database-init.sh) создаёт проекцию `LoginDB.dbo.userinfo` поверх BillingDB, потому что в найденных backup исходной таблицы нет. Это поддерживает локальный сценарий, но не доказывает точную исходную схему и все её побочные эффекты.
4. **World и Game сохраняют явные границы реконструкции.** [`process/worldserver.rs`](../../server/rust/src/process/worldserver.rs) различает блокировку `Init`, цикла и `Release`; в GameServer dispatcher имеются сообщения без обработчика, а фабрика навыков знает больше ID, чем доказанно исполняемых реализаций. Эти факты ограничивают вывод о готовности к длительной игре даже после успешной компиляции.
5. **Сохранённый C++-проход не закрывает эти пробелы автоматически.** Из 716 `.cpp` файлов 535 пустые; [CMake](../../server/cpp/CMakeLists.txt) исключает пустые единицы трансляции и объявляет пять приложений без GameServer. Его код остаётся полезным источником, но не подтверждённой полностью работающей альтернативой.

## Что считать следующими доказательствами

Для каждого игрового сценария нужны: точная версия оригинального клиента, текущий commit сервера, необходимые локальные данные и конфигурация, проверка сборки всех нужных бинарников, наблюдённый вход/переход между процессами, результат действия игрока и, если оно сохраняется, проверка чтения после повторного входа. Результат записывается как проверенный сценарий с исходом и границами, а не как общий процент готовности. Текущий честный итог: **вход в мир и короткое непрерывное движение на текущем release подтверждены; стабильная длительная играбельность, сохранение состояния и переходы между регионами ещё не доказаны**.
