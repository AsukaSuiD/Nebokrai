# Аудит готовности серверной реконструкции

Состояние на 20 сентября 2026 года, ветка `main`. Это оценка **активного Rust-кода и отслеживаемого развёртывания**, а не доля перенесённых строк. Проверка `cargo check --locked --lib --bins` и сборка `cargo build --locked --bins` успешно пройдены на Linux x86_64 с Rust 1.97.1 через локальный [check-rust.ps1](../../deploy/check-rust.ps1). Получены и совместно запущены шесть Rust-бинарников в dev-профиле. Game открыл клиентский порт после получения конфигурации World; наблюдённые ошибки и границы проверки перечислены ниже. Владелец прошёл исходным клиентом до списка персонажей; после исправления чтения БД повторный выбор дошёл до загрузки персонажа и появления игрока в Game, подробнее ниже. «Не проверено» ниже означает отсутствие подтверждения, а не доказанный отказ.

Для общих переменных, переходов между регионами и торгового обмена Billing нет подтверждения работы через реальные соединения и исходный клиент.

## Как читать матрицу

- **Исходный факт** — конкретный EXE/PDB, owner или данные, на которые опирается реконструкция. Верхний комментарий указанного файла содержит детали; уровень знания определяется по [правилам свидетельств](../reconstruction/evidence-and-contracts.md).
- **Код** — есть ли исполняемая реализация, а не только имя файла или RAW-псевдокод.
- **Полнота** — покрыты ли заявленные ветви и варианты. «Частично» не означает оценку доли работ.
- **В процессе** — достигнут ли код из объявленного бинарного входа и игрового lifecycle. Это не эквивалент успешной работе.
- **Сборка / runtime / клиент** — отдельные уровни проверки текущего состояния кода. Колонка «Сборка» означает получение исполняемых серверов; успешный общий `cargo check`, указанный выше, её не заменяет.

## Совместный запуск 20 сентября 2026

`VERIFIED`: локальный Docker Desktop `desktop-linux`, Linux x86_64, Rust 1.97.1, dev без debug-информации и incremental; команды — [Rust-стенд](../operations/rust-runtime.md). Работают MSSQL и шесть процессов Rust. `database_init` завершён с кодом 0, пять прикладных БД находятся ONLINE. Существующие базы не восстанавливались поверх данных. NAS в этом запуске не использовался. Сборочный кэш после сборки — около 1203 МиБ в одном томе с порогом 2048 МиБ.

`VERIFIED` по журналам совместного запуска и состоянию сокетов: World зарегистрировал Game с ID 1 и Misc с ID 5; Game показал `server_id=1`, `regions=541` и открыл `2347` в состоянии `LISTEN`. Login слушает `2345` и клиентский `2346`, Auth — `7100`, Billing — `8188`, World — `1747`. Это подтверждает старт и начальный обмен конфигурацией, но не работу всех игровых подсистем из матрицы. Этот начальный запуск предшествовал клиентской попытке, описанной ниже.

При первом запуске Game не получал конфигурацию: World за 58 секунд ставил 6025 сообщений с 359566258 байтами payload, а сетевой цикл стоял вместе с доменным. Затем отправка закрывала сокет: `167293902 + 1054318 > 167772160` байт. `VERIFIED` по диагностике [CServer](../../server/rust/src/nets/servers.rs) и [World](../../server/rust/src/worldserver/worldserver/game.rs). Сетевой worker теперь обслуживает очередь независимо; лимит не увеличен. Общая запись TCP дописывает частичный Linux write, а Game вычитывает несколько готовых шагов за такт. Устройство и причина — [сетевой runtime](../server/network-runtime.md) и [ADR-0002](../decisions/0002-semantic-boundary.md).

`PARTIAL`: запуск выявил незакрытые участки, которые доступный порт не подтверждает:

- Для восьми начальных регионов типов `4/5` найдено исходное расхождение World/Game. `VERIFIED` статически: World создаёт их как обычный `CWorldRegion` и не сериализует три war-counter, а Game создаёт производный `CServerWarRegion` и inherited decoder читает эти 12 байт за logical end `CMessage`. Receive-copy не переносит туда CRC или следующий frame; свободная capacity `std::vector` не является wire-контрактом. Rust startup теперь читает для subtype `4/5` только доказанный `CServerRegion` prefix и не меняет World wire. Решение и адреса — [ADR-0008](../decisions/0008-region-startup-war-tail.md). Повторный совместный запуск после исправления ещё не выполнялся, поэтому runtime-статус остаётся `PARTIAL`.
- Ложные runtime-warning для `0x7F80D` в Game и `0x80403`/`0x7F80D`/`0x7F801` в Misc сняты прямым сопоставлением с оригиналами. `VERIFIED`: jump-table Game `OnServerMessage @ 0x0049D300` направляет `0x7F80C/0x7F80D` в общий no-op return `0x0049EFD0`; Misc `OnOtherMsg @ 0x00403CC0` обрабатывает только `0x7F809/0x7F80B`, а остальные типы безусловно игнорирует. Оригинальный World при этом действительно строит `0x7F80D`: `CGame::SendGlobeVariableToGS @ 0x004017E0` добавляет 16 байт и отправляет пакет. Rust теперь отличает эти исходные no-op от реально неподдержанных ветвей.
- SQL 208 для `AuctionLog`/`Auctionlog` снят как кодовый блокер: поставочный `LogDB.bak` не содержит auction-таблиц, а сохранённый запуск оригинального World показывает ту же ошибку и затем успешный старт listener-а и цикл сохранения. Точный DDL остаётся `UNKNOWN`, поэтому локальный стенд не создаёт фиктивную схему; граница описана в [документации БД](../architecture/database.md#схема-и-локальный-стенд). Обработчик внешних пополнений Billing отключён через `PlayerFillCheckSrvSwitch 0`, поскольку нет `TBL_NeedUpdate`; объяснение — [локальный режим Billing](../operations/rust-runtime.md#внешние-пополнения-billing).
- После загрузки регионов цикл Game в этой dev-сборке сообщает задержки порядка 1,4–1,6 секунды. Это наблюдение локального запуска; производительность release-сборки и причина затрат ещё не установлены.
- Ранний разрыв World до создания клиентского listener больше не считается доказанным пробелом реконструкции. `VERIFIED` по matching Game EXE/PDB: `CMyNetClient::HandleClose @ 0x0041A590` ставит `0x6F901` в собственную FIFO World-клиента, `CGame::ProcessMessage @ 0x00405830` обрабатывает её и без `s_pNetServer`, а reconnect-worker повторяет попытку каждые 8000 ms. При этом успешный `CGame::ReConnectWorldServer @ 0x0040B7B0` сам без null-check публикует `0x6F902` через `s_pNetServer->field_0xdc`. Следовательно, отдельного исходного pre-listener recovery-пути не найдено; Rust не материализует его догадкой. Наблюдённый в первом неудачном запуске последующий `NotConnected` остаётся фактом того запуска, а не основанием объявлять отсутствующей совместимую механику. Подробности — [жизненный цикл соединений](../protocol/connection-lifecycle.md#исходящие-соединения-между-серверами).

## Выбор персонажа в локальном клиенте

20 сентября владелец вошёл аккаунтом `admin` и увидел список персонажей; при выборе любого из трёх клиент сообщал, что не удалось подключиться к серверу. `VERIFIED` по World `log/debug-DB_2026-09-20.txt`: в 19:37:10, 19:37:19 и 19:37:24 UTC загрузка ID 16620, 16642 и 16622 завершилась `Read Player DB Error`. В `TemptLoadDataLog` есть соответствующие начала и завершения попыток. Это отказ до выдачи назначения Game, а не подтверждённая ошибка TCP к `2347`.

Сопоставление реальной локальной схемы с чтением Tiberius выявило расхождения регистра (`depotpassword`, `dwLt60Stamp`, `JJcLevel`/`JJcScore`) и типов: координаты — SQL `float(53)`, `goodsIndex` — `bigint`, `place`/`position` — `tinyint`. Загрузчики ожидали буквальное совпадение имён, `f32` и `i32` соответственно. Исправлены общие чтение имени/целого и явное преобразование координат; добавлена диагностика этапа отказа без содержимого DB-полей. Контракт — [чтение БД](../architecture/database.md#чтение-имён-и-чисел-через-tiberius), журналы — [диагностика выбора](../operations/diagnostics.md#отказ-после-выбора-персонажа).

`cargo build --locked --bins` после изменений прошёл; кэш — 1204 МиБ при лимите 2048 МиБ. На `b63c7f4e5` связанные службы перезапущены. В 19:56:33 UTC повторный выбор ID 16642 дошёл до `World завершил загрузку персонажа`, регион 13001; далее Game зарегистрировал `connections=1, players=1`. Это подтверждает загрузку и передачу игрока Game по реальному клиентскому соединению. По ответу владельца клиент завис, показал сообщение примерно о нехватке предметов поверх окна и затем закрылся; вход в управляемый мир не подтверждён. Автоматические тесты не создавались и не запускались.

На этой повторной попытке Billing в 19:56:41 UTC получил SQL 156 (`Incorrect syntax near CONVERT`) при `GetUserPoint`; Game в 19:56:44 записал `Receive MSG_B2S_BILLING_AUTHEN : (RES)-2`. Во всех четырёх вызовах процедур `rsplayeraccount` преобразования перенесены из аргументов EXEC в локальные переменные, как описано в [контракте БД](../architecture/database.md#параметры-вызовов-процедур-billing). Исправленная SQL-форма `GetUserPoint` вручную выполнена для того же account в локальной BillingDB: результат `0`, значение баланса получено. Эта процедура только читает баланс; покупки и cash-log для проверки не выполнялись. Сборка всех бинарников прошла, Billing перезапущен и Game подключился к нему заново. Ошибка `-2` в обработчике Game только журналируется, не отправляет клиенту отказ и не закрывает сокет: причинная связь с завершением клиента не установлена. Windows Application Error 1000 в 22:56:48 местного времени подтверждает аварийное завершение `D:\Miracle Game\Miracle game.exe` с `0xc0000005` по RVA `0x8F703`; разбор клиентского пакета остаётся открытым вопросом.

### Сдвиг пакета входа перед заданиями

Локальный клиент `D:\Miracle Game\Miracle game.exe`: SHA-256 `5b41ebfcea8c40ab8756e3fb676c8e03ec1f45fba527f33bc163b084cf520971`, размер 2068480 байт, база PE `0x00400000`. Клиент и его ресурсы при диагностике не изменялись. Повторный вылет 20 сентября в 23:06:13 местного времени записан Windows как `0xc0000005`, RVA `0x8F742` — тот же цикл чтения дополнительных свойств предмета, что и `0x8F703` в предыдущем дампе.

Захват обоих направлений TCP сохранил отправленный Rust Game пакет `0xBF401` длиной 2392 байта после RLE-декодирования. `VERIFIED` для этой записи: предмет экипировки `1010012` содержит 11 обычных свойств и нулевой счётчик дополнительных; этот участок согласован с клиентским чтением. Первое найденное расхождение перед заданиями — запись `city_war_died_state` четырьмя байтами вместо одного. [Контракт и адреса отправителя/получателя](../protocol/game-login.md#флаги-перед-заданиями) фиксируют исправленную ширину.

При чтении старой записи клиент берёт максимум заданий с offset `0x4E7` вместо `0x4EA` и получает 1677721600 вместо 100. Позднее он читает счётчик боевых фей с `0x4F9` вместо `0x4FC`: **39 вместо 0**. Эти 39 взяты из соседнего `loan_time_limit=10080`, а не из БД предметов. Дамп первого вылета содержит возврат `0x00451AEC`: именно вызов декодирования предмета этого контейнера; далее клиент читает чужие поля как запись предмета и выходит за границы пакета. Сообщение клиента о предметах поэтому не свидетельствует об их нехватке.

Исправлена ширина флага в Rust. Независимая сверка сообщений перед `0xBF401` также выявила неверный opcode результата CiQing, пару `(id, id)` вместо `(type, id)` и три расширенных поля в `0xBF721`; исправленные форматы и свидетельства собраны в [каталоге opcode](../protocol/opcode-catalog.md#уведомления-свойств-игрока). Сборка всех шести бинарников прошла за 59,89 секунды, кэш остался 1204 МиБ при лимите 2048 МиБ. Game перезапущен в 20:25 UTC; в 20:26 UTC снова открыл `2347`, зарегистрировал server ID 1 и 541 регион. Результат повторного входа описан ниже. Локальные pcap, декодированный пакет и дамп остаются вне Git; автоматические тесты для этого разбора не создавались.

## Проверка всей последовательности загрузки

После `ac5d48434` владелец повторил вход: прежнее сообщение о предметах сменилось окном `regions/512\config` на экране загрузки. В новой записи `0xBF401` занимает 2373 байта; Game также отправил исправленные `0xC010E` и 124-байтовый `0xBF721`, затем ответил на запрос конфигурации `0xC010D` (5400 байт). Это следующий достигнутый этап, а не подтверждённый вход в мир.

Сопоставление полного пути загрузки с клиентом и оригинальными EXE/PDB выявило дополнительные расхождения:

| Участок | Найденное расхождение и исправление |
| --- | --- |
| Ресурс региона в `0xBF401` | Вместо `resource_id=11001` передавалась ширина 512, вместо `exp_scale=1.0` — биты целой высоты 512. Имя дополнительно перекодировалось в UTF-8. Исправлена передача существующих полей региона и исходных байтов имени; [контракт](../protocol/game-login.md#поля-региона-после-player-snapshot). В `Pack2.pak` локального клиента действительно есть `regions/11001/config` и 22 записи ресурсов этого региона; пакеты клиента не изменялись. |
| Непустые контейнеры в снимке | Пропускался четырёхбайтовый префикс каждой записи; восстановлены признак экипировки, количество и позиция, общий порядок обхода и setup-флаг DaKong. Разделение обычных/DaKong-свойств снова проверяет наличие типа в каталоге, а не пустоту значений; [формат](../protocol/game-login.md#записи-контейнеров-и-предметов). В обеих записанных попытках эти контейнеры пусты, поэтому это отдельный найденный дефект. |
| Подтверждение загрузки карты `0x8F801` | Клиент передаёт `CString + i32`, Rust требовал ровно 4 байта. Добавлен явный разбор подтверждённого клиентского варианта с сохранением оригинального `i32`; `Some(Err)` теперь журналируется как ошибка, а не успех. Значение строки уточнено до `INFERRED: account`: клиент повторно использует тот же global `std::string` первым полем `0x2FD09`; прямое matching Login EXE-подтверждение этой семантики ещё не закрыто. [Парный контракт и предел знания строки](../protocol/opcode-catalog.md#подтверждение-входа-в-регион). |

| Локальная смена региона `0xBF505` | Перепутывались аргумент перехода и ID назначения; вместо имени передавался путь, а числовой хвост имел неверные поля и размер. Отправитель согласован с оригинальным Game и клиентским reader; [формат](../protocol/opcode-catalog.md#локальный-переход-в-регион-0xbf505). Обычный вход этот пакет не использует, но его может вызвать сценарий переноса. |

Статически прослежено завершение загрузки: `0x8F801` → размещение игрока → `0xBF501` → погода и окружающие фигуры. Клиент переключается из состояния загрузки 5 в игровое состояние 6 по `0xBF501`; отдельного завершающего пакета после соседей нет. Оболочки `0xBF502/0xBF507`, обычные NPC, монстры и короткие снимки игроков сопоставлены с клиентскими декодерами. Редкие постройки, ненулевые состояния, призванные фигуры и дополнительные ветви WarSoul не прошли фактический клиентский сценарий.

Сборка всех шести бинарников с полным набором исправлений прошла за 56,83 секунды; кэш — 1204 МиБ при лимите 2048 МиБ. В 20:52 UTC перезапущены Login, World, Misc и Game. Хеши исполняемых процессов World/Game совпадают с новыми артефактами сборки; в 20:53 UTC Game получил server ID 1, 541 регион и состояние healthcheck `healthy` по listener `2347`. Auth и Billing продолжают работать. Это подтверждает совместный запуск обновлённых служб; вход клиента в управляемый мир после этого набора пока не проверен.

## Пробелы, влияющие на путь к игре

1. **Сборка, совместный запуск и приём одного игрока в Game подтверждены; игровой сценарий ещё нет.** [Rust-дополнение Compose](../../deploy/hybrid/compose.rust.yaml) запускает все шесть Rust-служб. [Rust Dockerfile](../../deploy/hybrid/Dockerfile.rust) также копирует все шесть бинарников, но сборка этого release-образа в описанном запуске не выполнялась: использовались dev-бинарники из ограниченного кэша.
2. **Знание протокола не равно проверке с клиентом.** В отслеживаемом дереве нет проекта клиента или протокола сквозного испытания. Наличие EXE/PDB и статических контрактов подтверждает отдельные факты оригинала, но здесь не найдено подтверждения, что новый сервер провёл игрока от входа до устойчивой игры.
3. **Модель БД зависит от локальных материалов.** `runtime/` целиком исключён из Git. [Локальный скрипт БД](../../deploy/hybrid/database-init.sh) создаёт проекцию `LoginDB.dbo.userinfo` поверх BillingDB, потому что в найденных backup исходной таблицы нет. Это поддерживает локальный сценарий, но не доказывает точную исходную схему и все её побочные эффекты.
4. **World и Game сохраняют явные границы реконструкции.** [`process/worldserver.rs`](../../server/rust/src/process/worldserver.rs) различает блокировку `Init`, цикла и `Release`; в GameServer dispatcher имеются сообщения без обработчика, а фабрика навыков знает больше ID, чем доказанно исполняемых реализаций. Эти факты ограничивают вывод о готовности к длительной игре даже после успешной компиляции.
5. **Сохранённый C++-проход не закрывает эти пробелы автоматически.** Из 716 `.cpp` файлов 535 пустые; [CMake](../../server/cpp/CMakeLists.txt) исключает пустые единицы трансляции и объявляет пять приложений без GameServer. Его код остаётся полезным источником, но не подтверждённой полностью работающей альтернативой.

## Что считать следующими доказательствами

Для каждого игрового сценария нужны: точная версия оригинального клиента, текущий commit сервера, необходимые локальные данные и конфигурация, проверка сборки всех нужных бинарников, наблюдённый вход/переход между процессами, результат действия игрока и, если оно сохраняется, проверка чтения после повторного входа. Результат записывается как проверенный сценарий с исходом и границами, а не как общий процент готовности. Пока таких подтверждений нет, честный итог: **архитектура и значительный код восстановлены, но играбельность Nebokrai не доказана**.
