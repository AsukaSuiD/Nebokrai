# Аудит готовности серверной реконструкции

Состояние на 20 сентября 2026 года, ветка `main`. Это оценка **активного Rust-кода и отслеживаемого развёртывания**, а не доля перенесённых строк. Проверка `cargo check --locked --lib --bins` и сборка `cargo build --locked --bins` успешно пройдены на Linux x86_64 с Rust 1.97.1 через локальный [check-rust.ps1](../../deploy/check-rust.ps1). Получены и совместно запущены шесть Rust-бинарников в dev-профиле. Game открыл клиентский порт после получения конфигурации World; наблюдённые ошибки и границы проверки перечислены ниже. Владелец прошёл исходным клиентом до списка персонажей; выбор персонажа пока завершается отказом, подробнее ниже. «Не проверено» ниже означает отсутствие подтверждения, а не доказанный отказ.

Для общих переменных, переходов между регионами и торгового обмена Billing нет подтверждения работы через реальные соединения и исходный клиент.

## Как читать матрицу

- **Исходный факт** — конкретный EXE/PDB, owner или данные, на которые опирается реконструкция. Верхний комментарий указанного файла содержит детали; уровень знания определяется по [правилам свидетельств](../reconstruction/evidence-and-contracts.md).
- **Код** — есть ли исполняемая реализация, а не только имя файла или RAW-псевдокод.
- **Полнота** — покрыты ли заявленные ветви и варианты. «Частично» не означает оценку доли работ.
- **В процессе** — достигнут ли код из объявленного бинарного входа и игрового lifecycle. Это не эквивалент успешной работе.
- **Сборка / runtime / клиент** — отдельные уровни проверки текущего состояния кода. Колонка «Сборка» означает получение исполняемых серверов; успешный общий `cargo check`, указанный выше, её не заменяет.

## Совместный запуск 20 сентября 2026

`VERIFIED`: локальный Docker Desktop `desktop-linux`, Linux x86_64, Rust 1.97.1, dev без debug-информации и incremental; команды — [Rust-стенд](../operations/rust-runtime.md). Работают MSSQL и шесть процессов Rust. `database_init` завершён с кодом 0, пять прикладных БД находятся ONLINE. Существующие базы не восстанавливались поверх данных. NAS в этом запуске не использовался. Сборочный кэш после сборки — около 1203 МиБ в одном томе с порогом 2048 МиБ.

`VERIFIED` по журналам совместного запуска и состоянию сокетов: World зарегистрировал Game с ID 1 и Misc с ID 5; Game показал `server_id=1`, `regions=541` и открыл `2347` в состоянии `LISTEN`. Login слушает `2345` и клиентский `2346`, Auth — `7100`, Billing — `8188`, World — `1747`. Это подтверждает старт и начальный обмен конфигурацией, но не работу всех игровых подсистем из матрицы. Этот начальный запуск предшествовал клиентской попытке, описанной ниже.

При первом запуске Game не получал конфигурацию: World за 58 секунд ставил 6025 сообщений с 359566258 байтами payload, а сетевой цикл стоял вместе с доменным. Затем отправка закрывала сокет: `167293902 + 1054318 > 167772160` байт. `VERIFIED` по диагностике [CServer](../../server/rust/src/nets/servers.rs) и [World](../../server/rust/src/worldserver/worldserver/game.rs). Сетевой worker теперь обслуживает очередь независимо; лимит не увеличен. Общая запись TCP дописывает частичный Linux write, а Game вычитывает несколько готовых шагов за такт. Устройство и причина — [сетевой runtime](../server/network-runtime.md) и [ADR-0002](../decisions/0002-semantic-boundary.md).

`PARTIAL`: запуск выявил незакрытые участки, которые доступный порт не подтверждает:

- Восемь начальных сообщений военных регионов дошли до Game, но parser остановился на отсутствующем `m_lSymbolTotalNum`. Наблюдён `InitialRegionStartup(War(Input(UnexpectedEnd)))`; требуется сопоставить World-сериализацию и Game-десериализацию. Источник — [startup handler Game](../../server/rust/src/gameserver/appserver/message/servermessage.rs). Число 541 описывает созданные регионы, а не полноту всей карты.
- Game сообщает об отсутствии обработчика `0x7F80D`; Misc — о неподдержанных `0x80403`, `0x7F80D`, `0x7F801`. Регистрация Misc в World подтверждена, обработка аукционных операций — нет. Источники — [Game dispatch](../../server/rust/src/gameserver/gameserver/game.rs), [Misc process](../../server/rust/src/process/miscserver.rs).
- World получает SQL 208 для `AuctionLog`/`Auctionlog`; успешное открытие других соединений не закрывает этот участок БД. Обработчик внешних пополнений Billing отключён через `PlayerFillCheckSrvSwitch 0`, поскольку нет `TBL_NeedUpdate`; объяснение — [локальный режим Billing](../operations/rust-runtime.md#внешние-пополнения-billing).
- После загрузки регионов цикл Game в этой dev-сборке сообщает задержки порядка 1,4–1,6 секунды. Это наблюдение локального запуска; производительность release-сборки и причина затрат ещё не установлены.
- Ранний разрыв World до создания клиентского listener оставляет Game без reconnect: `schedule_world_reconnect_task` требует отсутствующий `net_server`. Это подтверждено чтением [CGame](../../server/rust/src/gameserver/gameserver/game.rs), а первый неудачный запуск показал последующий `NotConnected`. Восстановление после такого разрыва пока не исправлено.

## Выбор персонажа в локальном клиенте

20 сентября владелец вошёл аккаунтом `admin` и увидел список персонажей; при выборе любого из трёх клиент сообщал, что не удалось подключиться к серверу. `VERIFIED` по World `log/debug-DB_2026-09-20.txt`: в 19:37:10, 19:37:19 и 19:37:24 UTC загрузка ID 16620, 16642 и 16622 завершилась `Read Player DB Error`. В `TemptLoadDataLog` есть соответствующие начала и завершения попыток. Это отказ до выдачи назначения Game, а не подтверждённая ошибка TCP к `2347`.

Сопоставление реальной локальной схемы с чтением Tiberius выявило расхождения регистра (`depotpassword`, `dwLt60Stamp`, `JJcLevel`/`JJcScore`) и типов: координаты — SQL `float(53)`, `goodsIndex` — `bigint`, `place`/`position` — `tinyint`. Загрузчики ожидали буквальное совпадение имён, `f32` и `i32` соответственно. Исправлены общие чтение имени/целого и явное преобразование координат; добавлена диагностика этапа отказа без содержимого DB-полей. Контракт — [чтение БД](../architecture/database.md#чтение-имён-и-чисел-через-tiberius), журналы — [диагностика выбора](../operations/diagnostics.md#отказ-после-выбора-персонажа).

`cargo build --locked --bins` после изменений прошёл; кэш — 1204 МиБ при лимите 2048 МиБ. Сборка подтверждает компиляцию исправлений, успешный вход персонажем ещё требует повторной попытки исходным клиентом. Автоматические тесты не создавались и не запускались.

## Пробелы, влияющие на путь к игре

1. **Сборка и совместный запуск подтверждены, вход и игровой сценарий ещё нет.** [Rust-дополнение Compose](../../deploy/hybrid/compose.rust.yaml) запускает все шесть Rust-служб. [Rust Dockerfile](../../deploy/hybrid/Dockerfile.rust) также копирует все шесть бинарников, но сборка этого release-образа в описанном запуске не выполнялась: использовались dev-бинарники из ограниченного кэша.
2. **Знание протокола не равно проверке с клиентом.** В отслеживаемом дереве нет проекта клиента или протокола сквозного испытания. Наличие EXE/PDB и статических контрактов подтверждает отдельные факты оригинала, но здесь не найдено подтверждения, что новый сервер провёл игрока от входа до устойчивой игры.
3. **Модель БД зависит от локальных материалов.** `runtime/` целиком исключён из Git. [Локальный скрипт БД](../../deploy/hybrid/database-init.sh) создаёт проекцию `LoginDB.dbo.userinfo` поверх BillingDB, потому что в найденных backup исходной таблицы нет. Это поддерживает локальный сценарий, но не доказывает точную исходную схему и все её побочные эффекты.
4. **World и Game сохраняют явные границы реконструкции.** [`process/worldserver.rs`](../../server/rust/src/process/worldserver.rs) различает блокировку `Init`, цикла и `Release`; в GameServer dispatcher имеются сообщения без обработчика, а фабрика навыков знает больше ID, чем доказанно исполняемых реализаций. Эти факты ограничивают вывод о готовности к длительной игре даже после успешной компиляции.
5. **Сохранённый C++-проход не закрывает эти пробелы автоматически.** Из 716 `.cpp` файлов 535 пустые; [CMake](../../server/cpp/CMakeLists.txt) исключает пустые единицы трансляции и объявляет пять приложений без GameServer. Его код остаётся полезным источником, но не подтверждённой полностью работающей альтернативой.

## Что считать следующими доказательствами

Для каждого игрового сценария нужны: точная версия оригинального клиента, текущий commit сервера, необходимые локальные данные и конфигурация, проверка сборки всех нужных бинарников, наблюдённый вход/переход между процессами, результат действия игрока и, если оно сохраняется, проверка чтения после повторного входа. Результат записывается как проверенный сценарий с исходом и границами, а не как общий процент готовности. Пока таких подтверждений нет, честный итог: **архитектура и значительный код восстановлены, но играбельность Nebokrai не доказана**.
