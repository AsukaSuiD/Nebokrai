# Правила работы над Nebokrai

Это краткий bootstrap: обязательные рабочие правила и маршрутизация к canonical docs, а не их копия. Разделение хранения: код показывает implementation и ownership/API; architecture/gameplay docs — текущую модель и семантические контракты; `docs/reconstruction/` — происхождение и машинное evidence; этот файл — рабочие правила.

- Этот `AGENTS.md` — действующие правила владельца для работы над проектом. По решению владельца файл отслеживается в Git и доступен на GitHub; его изменение или вывод из отслеживания — только по явному указанию владельца.
- Перед изменениями прочитай [README.md](README.md), [руководство разработчика](docs/development.md) и страницу по своей задаче. Затем проследи конкретный код и относящиеся к нему свидетельства реконструкции; не подменяй исследование переносом существующих комментариев.
- После каждого завершённого шага выполняй предусмотренные для него проверки, затем коммит и push в `origin/main` без дополнительного согласования; сообщения коммитов пиши на русском. Публикацию помимо обычного push, изменение visibility, удаление удалённых веток и переписывание истории выполняй только по явному разрешению владельца. По решению владельца работаем в main; другую ветку создавай или выбирай только по прямой просьбе; публичный contribution workflow в CONTRIBUTING.md относится к внешним участникам.
- `server/rust/` — основная реализация, `server/cpp/` — отдельный C++-проход, `original/server/` — локальный оригинальный Windows-комплект. Содержимое `original/` и `related/` не изменяй и не добавляй в Git. EXE/PDB и код родственной игры не называй исходниками активного сервера.
- Единица работы — ответственность и её наблюдаемый контракт, а не legacy-файл: определи текущего и целевого owner → установи evidence → восстанови требуемое поведение → выбери форму в текущей архитектуре → интегрируй через API/контракты владельцев → обнови соответствующие docs/evidence. Старый Rust, C++ и EXE/PDB — источник поведения и доказательств, а не шаблон конечной структуры: при архитектурном основании допустимо разделить legacy-файл, объединить несколько legacy-частей, создать новый модуль/подмодуль, убрать ненужную прослойку, изменить внутреннее представление, хранилище или алгоритм — пока сохраняются наблюдаемые контракты. Не сохраняй структуру оригинала ради исторической похожести. Порядок применения карты — [realm-and-zone.md §9](docs/architecture/realm-and-zone.md#9-порядок-применения-карты).
- Realm и Zone — исполняемые роли с peer domain modules: модуль владеет своим state и API; `app` — composition/orchestration, не новый `CGame` и не domain owner; Shared — общий технический слой, а не владелец gameplay-состояния. Структура преимущественно плоская; новый модуль/подмодуль создаётся по отдельной responsibility и своей границе, а не по размеру файла. Новую реализацию компонента размещай сразу в целевом пакете по [принятым границам](docs/architecture/realm-and-zone.md), а не внутри старых `src/worldserver`/`src/gameserver`.
- `lib.rs` пакета и `mod.rs` компонента — компактные архитектурные карты и API-границы: основные части, public surface, internal boundary, короткая строка «что это за часть» у объявлений. Не превращай их в reconstruction-журнал или энциклопедию по каждому `.rs`. Visibility определяется архитектурным контрактом — ответственностью, intended API, существующими consumers и переходной совместимостью, — а не механическим отсутствием текущих callers.
- Комментарии production source краткие: назначение, responsibility, локальные invariants, достижимые quirks, наблюдаемые ordering/wire/RNG/persistence-ограничения, короткие ссылки на canonical страницы. Подробное происхождение — идентификаторы EXE/PDB, SHA/GUID, RVA/VA, vtables, disassembly-разбор, provenance и таблицы статусов — живёт в `docs/reconstruction/`; evidence не терять, но archaeology в source не возвращать. Политика — [комментарии и происхождение](docs/development.md#комментарии-и-происхождение-кода).
- Оригинальный клиент — фиксированная внешняя граница совместимости: всё видимое клиентом (opcode, framing, размеры/типы/порядок полей, кодировки, флаги, обязательные последовательности, ordering/timing, зависимые значения и переходы состояний, gameplay-семантика) сохраняется совместимым; внутренняя реализация сервера при этом свободна — ownership, модули, структуры, представления ресурсов, парсеры, хранилища, алгоритмы и архитектура Realm/Zone. Legacy межсерверный протокол — compatibility/reference там, где мы ещё связаны с оригинальным процессом, а не вечное ограничение своих компонентов. При будущем восстановлении клиента сначала — доказанный baseline на старом wire; изменение клиентского протокола — только отдельное согласованное изменение обеих сторон. Полная формулировка — [значения и совместимость](docs/architecture/values-and-compatibility.md#клиент-как-внешняя-граница-совместимости).
- Совместимые форматы, структуры, формулы и порядок действий восстанавливай только по прямому основанию по [правилам свидетельств](docs/reconstruction/evidence-and-contracts.md): `VERIFIED`/`точный`/`exact`/`byte-exact` — только при нём, иначе `PARTIAL`/`INFERRED`/`UNKNOWN` без достраивания догадкой. Псевдокод декомпилятора и PDB-имя основанием не являются. Сверка оригинала обязательна и при формально неизменном Rust-алгоритме; cargo check и diff до/после поведение оригинала не подтверждают. Проверяй, что EXE/PDB относятся к одной сборке; адреса, layout и поведение между сборками не переноси без отдельного основания; неоднозначные места проходи по [чек-листу](docs/reconstruction/evidence-and-contracts.md#обязательная-проверка-неоднозначных-мест). Незакрытый вопрос укажи явно; участок не объявляй полностью проверенным заранее.
- Странность сначала исследуй: отличай ошибку реконструкции или инфраструктуры Rust от значимой особенности оригинала. Установленное расхождение исправляй в том же участке, сохраняя клиентское/межсерверное поведение, значимые эффекты БД и игровые правила. Не «улучшай» совместимый контракт по своему предположению и не сохраняй дефект Rust только потому, что он уже был в коде. Неизвестное не закрывай заглушкой ради успешной сборки.
- Tokio, Tiberius и другие библиотеки могут заменять инфраструктуру оригинала при сохранении значимых форматов сообщений, порядка действий, времени, дубликатов, блокировок, частичных эффектов БД и игровых формул. Для одинаковых требований используй принятые решения и [общие механизмы](docs/architecture/shared-mechanisms.md); новый способ требует конкретной причины. Описание текущего кода и случайное дублирование не становятся архитектурным правилом автоматически; несоответствия отмечай отдельно, а изменение документации само по себе не разрешает переделывать код.
- Изменения протокола, сохраняемых структур и игровых формул согласовывай между затронутыми отправителем, получателем, БД и клиентом.
- Canonical docs обновляй в той же логической работе, когда меняются ownership, граница модуля, public API, cross-module контракт, gameplay-поведение, wire/persistence-контракт, статус evidence или архитектура процессов; внутренний рефактор без смены контракта docs не трогает. У каждого правила, формата и формулы — одно основное место в `docs/`; соседние страницы ссылаются вместо пересказа; docs организуются по смыслу знания, а не по source files и не по agent-волнам. Документацию пиши для разработчика: что делает система, где находится код и почему выбрана такая организация; существенное инженерное решение фиксируй в коротком ADR. Критерии новых документов и двусторонняя навигация — [правила документации](docs/development.md#правила-документации).
- Неизвестное указывай рядом с конкретным правилом. Общие результаты сборки, runtime и проверки клиентом храни в [состоянии проекта](docs/status/audit.md), не повторяй одну оговорку на каждой странице. В результате работы различай: что перенесено, что исправлено, какое поведение сверено с оригиналом и по какому основанию, что проверено компилятором или разрешённым запуском и что осталось неизвестным. Наличие кода, сверка машинного кода, сборка и работа с клиентом остаются разными фактами.
- Не запускай сборки, тесты, серверы и runtime-проверки, если текущий README этого не предусматривает или владелец явно не попросил. Статическое чтение не заменяет проверку работы.
- По решению владельца ни основной агент, ни субагенты не создают, не дописывают и не переписывают автоматические тесты; не предлагай и не включай их создание в план. Проверяй Rust через `cargo check`, а сборку и фактическую работу — разрешёнными запусками. Тест не задаёт требования к продукту и не является причиной сохранять отменённое поведение или добавлять обходы при согласованном изменении.
- Перед удалением данных, переписыванием истории или изменением внешних сервисов, кроме обычного push коммитов в `origin/main`, получи явное согласие владельца; уже данное согласие повторно не запрашивай. Документацию, комментарии и сообщения коммитов пиши на естественном русском языке.
