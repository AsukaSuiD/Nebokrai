# Участие в Nebokrai

Начните с [руководства разработчика](docs/development.md), [карты проекта](docs/architecture/workspace.md) и страницы нужной подсистемы. Основная реализация находится в `server/rust/`; исторические имена помогают сопоставлению, но не доказывают полноту реализации.

Лицензия проекта и условия внешнего вклада пока не выбраны. Обсуждать проблемы и предлагаемые решения можно уже сейчас; до принятия чужого кода владелец и автор должны явно согласовать права. Этот файл не является CLA, не передаёт авторские права и не разрешает перелицензирование. Открытые вопросы перечислены в сравнении лицензий (локальный материал владельца).

## Issue

Опишите наблюдаемую проблему, ожидаемый результат, commit, платформу и затронутую службу. Для клиентского сценария укажите вариант клиента по хешу, состав стенда и последний достигнутый этап. Отделяйте наблюдение от гипотезы. Прикладывайте только минимальные обезличенные выдержки, права на публикацию которых вам известны.

Не загружайте оригинальные EXE/DLL/PDB, клиентские ресурсы, backup БД, пользовательские данные, секретные конфиги, дампы и сетевые захваты. Уязвимости и случайные утечки обсуждаются по [правилам безопасности](SECURITY.md), без публичного раскрытия чувствительных деталей. Для архитектурного изменения сначала объясните проблему и границы предлагаемого решения в issue; отдельный issue для небольшой понятной правки не обязателен.

## Pull request

Один PR должен решать одну понятную задачу. В описании укажите проблему и результат изменения, затронутые процессы, способ проверки и оставшиеся неизвестные. Ссылайтесь на issue, если он существует. Не создавайте фиктивные проверки, релизы или задачи для увеличения активности.

Для совместимого контракта нужны основания по [правилам реконструкции](docs/reconstruction/evidence-and-contracts.md). Обновляйте основную страницу поведения; значимое инженерное решение объясняйте коротким ADR. Не превращайте реконструкцию в заявленную clean-room разработку без отдельного основания и не переносите чужой исходный код из локальных материалов.

Для внешнего участника обычный путь после согласования лицензии — ветка в своём fork и PR в `main`; прямой push не требуется. Документация и комментарии пишутся на русском, основной README — на английском. Старые русские сообщения коммитов сохраняются.

## Проверка и материалы

Автоматические тесты не создавайте, не дописывайте и не переписывайте. Для Rust используется `cargo check`; команды, зависимости и ограничения запусков находятся в [руководстве сборки](docs/operations/build.md). Документационные изменения проверяются статически.

В PR называйте фактически выполненную проверку. Успех компиляции не подтверждает вход клиента, сохранение персонажа или совместимость всей системы. Общие наблюдения runtime записываются в [состоянии проекта](docs/status/audit.md).

Перед отправкой просмотрите diff и список файлов. `.gitignore` не защищает уже отслеживаемые файлы или содержимое комментариев. Новое стороннее включение должно иметь источник, лицензию и необходимые уведомления; случайно найденный секрет не копируйте в issue или commit message. История, внешние сервисы и удаление данных меняются только с отдельным согласием владельца.
