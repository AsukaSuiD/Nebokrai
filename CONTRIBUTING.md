# Участие в Nebokrai / Contributing

**English summary.** Start with the [documentation portal](docs/README.md) and [developer guide](docs/development.md). Use a fork or branch, submit a focused pull request, and wait for review before merging into `main`. Russian is the normal working language, including commit messages; English questions and explanations are welcome. Contributions to Nebokrai's code and documentation are submitted under [AGPL-3.0-only](LICENSE); contributors retain their copyright. Original binaries, assets, decompiler output, credentials, and private captures are not accepted into Git.

## Где начать

[Руководство разработчика](docs/development.md) содержит таблицу «от задачи к коду». Для понимания системы прочитайте [архитектуру](docs/overview/architecture.md) и [путь игрока](docs/overview/player-journey.md); перед выбором задачи — [текущий статус](docs/overview/status.md). Для небольшого исправления документации отдельный issue не обязателен. Для изменения архитектуры сначала объясните проблему, границы и альтернативы.

## Рабочий процесс

Внешний участник работает в fork и отдельной ветке: **fork/branch → changes → pull request → review → main**. `main` — основная интеграционная ветка с рассмотренными изменениями; это не обещание production-готовности сервера.

Документация, комментарии и новые сообщения коммитов могут и дальше быть на русском. Старые сообщения не переписываются ради языка. Английский нужен для публичного входного слоя; массовый перевод и постоянно расходящиеся копии подробных страниц не нужны.

## Поведение и доказательства

Не достраивайте неизвестное поведение оригинала догадкой. Для совместимых форматов, структур, формул и порядка действий применяйте [правила свидетельств](docs/reconstruction/evidence-and-contracts.md). Различайте `VERIFIED`, `PARTIAL`, `INFERRED`, `UNKNOWN`; указывайте проверяемое происхождение и границы каждого нового утверждения. Псевдокод и имя в PDB сами по себе не подтверждают контракт.

Изменение протокола согласуется по затронутым отправителю, получателю, БД и клиенту. Для каждого правила должна быть одна основная страница; обновите её вместе с поведением. Существенное инженерное решение и последствия фиксируйте коротким [ADR](docs/decisions/README.md). Используйте подходящие [общие механизмы](docs/architecture/shared-mechanisms.md); отличие требует конкретной причины.

## Issue и pull request

Опишите проблему, ожидаемый и наблюдаемый результат, commit, платформу и службу. Для клиентского сценария укажите идентификатор сборки клиента, состав стенда и последний достигнутый этап. Отделяйте наблюдение от гипотезы; прикладывайте только минимальные обезличенные сведения, которые вправе распространять.

Один PR решает одну понятную задачу. В описании нужны результат изменения, затронутые границы, обновлённая документация, фактически выполненная проверка и оставшиеся неизвестные. Ссылайтесь на issue, если он существует. [Руководство сборки](docs/operations/build.md) содержит `cargo check` и команды сборки; [диагностика](docs/operations/diagnostics.md) помогает описать клиентское наблюдение. Наличие кода, проверка типов, сборка, запуск и подтверждённый клиентский сценарий — разные утверждения. Общие результаты фиксируются в [аудите](docs/status/audit.md).

## Материалы и права

В Git, issue и PR не принимаются оригинальные EXE/DLL/PDB, клиент, ресурсы игры, базы и backup, сторонние игровые исходники, полный декомпилят, credentials, пользовательские данные, raw pcap и дампы памяти. Их существование можно описать как локальный evidence source: сборка, SHA-256, matching EXE/PDB metadata, адрес/RVA и собственные выводы. Не выдавайте реконструкцию за clean-room разработку без основания.

Отправляя свой код или документацию для включения в Nebokrai, предоставляйте их на условиях [AGPL-3.0-only](LICENSE). Авторские права остаются у автора; отдельное CLA и передача copyright не требуются. Вносите только материалы, которые вправе предоставлять на этих условиях. Любое стороннее включение требует известного источника, совместимой лицензии и необходимых уведомлений. Вклад не предоставляет владельцу дополнительных прав на закрытое коммерческое перелицензирование.

Перед отправкой проверьте diff и список файлов: ignore-правила не очищают уже отслеживаемый материал. Об утечках и уязвимостях сообщайте по [SECURITY.md](SECURITY.md), не раскрывая чувствительные детали публично.
